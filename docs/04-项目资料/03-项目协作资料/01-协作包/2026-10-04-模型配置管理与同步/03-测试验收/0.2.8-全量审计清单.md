# 全量审计清单 · 9 个路由（软件 vs 原型）

生成时间：2026-10-24。**本文件只是清单与执行方案，尚未执行审计。**

用户要求：独立于 `0.2.8-差异审计清单.md`（那份只覆盖 6 条用户反馈），
做一份**覆盖全部 9 个路由的全量审计**；先出清单，确认后再按清单排查。

---

## 0. 为什么需要这份清单（自证不足）

现有 `parity-*.mjs` 五套「原型并排对照」断言的是**结构存在性**（如「两侧都有 Agent 自动填充」「两侧标题一致」），
不是逐元素比对。它们全绿**不能**推出「与原型一致」——2026-10-24 用户报的 5 条界面差异，这些脚本一条都没抓到。

所以本次审计改为：**逐屏、逐元素**，每条差异都要有「原型位置 + 软件现状 + 判定 + 严重度」。

## 2. 审计维度（每个界面都按这 7 项比对）

| 维度 | 具体比什么 | 判据来源 |
| --- | --- | --- |
| D1 存在性 | 元素在两边是否都存在 / 都不存在 | 原型 DOM vs 软件渲染 DOM |
| D2 文案 | 中文字面、标点、大小写、图标文案 | 原型字符串常量 |
| D3 顺序 | 元素先后、列表项次序、按钮排列 | 原型 DOM 顺序 / 数据排序规则 |
| D4 分组与层级 | 区块划分、标题层级、说明文字归属 | 原型 section/heading 结构 |
| D5 布局与尺寸 | 行/列结构、等高、对齐、宽度上限、是否换行 | 原型 CSS 关键规则 |
| D6 状态与交互 | 禁用/启用、悬停、长按、确认弹窗、错误提示 | 原型事件绑定与状态机 |
| D7 空态与边界 | 无数据、失败、超限、只读时的呈现 | 原型分支渲染 |

## 3. 执行顺序（建议）

按「用户反馈密度 + 改动风险」排序，而非按导航顺序：

| 批次 | 路由 | 理由 | 预估条目 |
| --- | --- | --- | --- |
| 1 | **models** | 已有 6 条已知差异；文件最大（1955 行）；用户主要工作区 | 40–60 |
| 2 | **sync** | 导出/导入刚被发现内外都不一致；含凭据与口令 | 25–35 |
| 3 | **settings** | 11 个分区，历史问题最多（曾说最优美） | 30–40 |
| 4 | **extensions** | 与 settings 的扩展分区可能重复，一起看 | 15–25 |
| 5 | **overview** | 状态展示与升级流程 | 15–20 |
| 6 | **panel** / **logs** / **tray** | 相对简单 | 10–15 各 |
| 7 | **conversations** | 软件无此路由，只记「未实现」结论 | 1 |

## 4. 每条差异的记录格式（强约束）

```
### <路由>-<序号> <一句话结论>
- 严重度：阻断 / 高 / 中 / 低
- 维度：D1..D7
- 原型：<文件:行号> + 关键代码片段（≤2 行）
- 软件：<文件:行号> + 现状描述
- 判定：不一致 / 缺失 / 多余 / 一致（仅登记已核对项）
- 修法建议：改原型 / 改软件 / 两者
```

**不接受**只写「看起来不一样」。没有原型行号的条目不进清单。

## 5. 产出物

1. 每个路由一节，逐条差异（格式见 §4）
2. 每节末尾一个小结表：一致 N 项 / 不一致 N 项 / 缺失 N 项 / 多余 N 项
3. 一张汇总表：按严重度排序的待修项，供后续排期
4. 截图证据目录：`docs/04-项目资料/01-项目支撑资料/06-问题记录/0.2.8-parity/<路由>/`

---

## 6. 明确不做的事

- **不**把「存在性断言通过」当作一致性证据（这正是上一轮漏掉 5 条差异的原因）
- **不**在没有原型行号的情况下写「不一致」
- **不**在同一批里既改原型又改软件（先定原型，再改软件，避免返工）
- **不**为了避免返工而缩小范围
