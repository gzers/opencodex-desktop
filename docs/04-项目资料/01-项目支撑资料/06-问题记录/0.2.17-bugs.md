# OpenCodeX Desktop 0.2.17 发布后问题记录

2026-10-28，Asia/Shanghai。本轮为用户反馈核对与记录；未修改软件、原型或用户配置，未启动新版本开发发布。沿用原[WP-89](0.2.16-bugs.md)，同根遗漏不另起重复开发组。

## WP-89跟进：安装路径可推进，但可读展示仍未收口

状态：显示遗漏已由截图和发布源码确认，待修；用户随后补充实际安装返回npm_failed/退出码1，失败原因尚待原始npm输出。用户反馈发生于0.2.17发布后，但截图没有关于页版本号，不把截图当作精确安装版本证明。

### 本次事实

- 安装向导第一步仍直接显示Windows扩展路径前缀，并混用Windows反斜杠和runtime/opencodex中的正斜杠。
- 截图中“下一步”呈可用样式，旧的红色路径校验错误没有出现。这支持“第一步词法阻断已改变”，不支持“用户机器完整安装已成功”或“点击下一步后仍失败”。
- 用户最初提出的是默认路径问题。上一轮已修合法路径被误判和后端安装身份，但漏了原清单要求的显示、默认预填、恢复默认一致；不能继续以“全部解决”概括。

### 发布源码原因

以v0.2.17/d7c7978f0核对：

1. apps/desktop/tauri/src/commands/runtime.rs:156～160将managed/default prefix直接to_string_lossy输出；数据根canonicalize保留Windows扩展路径形式。
2. apps/desktop/tauri/src/modules/runtime/mod.rs:32的相对路径常量为runtime/opencodex；与原生Windows根拼接后可在字符串层产生混用分隔符。
3. apps/desktop/ui/src/routes/SettingsRoute.vue:829～842的默认预填、恢复默认没有可读显示转换；目录选择同样直接使用原始返回值。
4. 后端runtime/paths.rs只在安装准入时规范存储路径，不会反向修正输入框。
5. test/smoke/windows-install-ui.mjs:14/18要求输入框等于原始DTO；只检查可推进，没有检查可读显示。这是验收遗漏，原绿灯不能覆盖该需求。

### 后续修复边界

- 默认预填、恢复默认、目录选择统一采用保持原目录身份的可读Windows路径展示，常规本地目录统一反斜杠；不能直接对任意设备命名空间删前缀。
- 保持实际保存/安装目标、历史自定义位置、长路径与UNC语义；不为显示修复搬移数据根或要求用户清空配置。
- 单独检查“显示正确”与“原生安装成功”，覆盖后端真实返回值、常规/扩展盘符及UNC、受保护/设备/点段拒绝。修正把原样显示作为正确条件的测试。
- 用户已补充实际安装失败提示；其具体根因仍需原始npm输出，不能将路径展示遗漏直接外推成npm失败原因。

## 用户补充：Windows标准路径与实际npm失败（2026-10-28）

用户明确给出的Windows路径格式：

~~~text
D:\Software\Develop\OpenCodeX Desktop
~~~

这是正常本地Windows路径表示。界面不应把内部扩展路径前缀与正反斜杠混用当作面向用户的默认显示；本次确认针对路径显示，不据此擅自将托管运行环境搬到Desktop安装根。沿当前数据目录规则时，托管子目录同样应显示为普通Windows反斜杠形式。

用户另报告实际失败，原文：

~~~text
managed runtime operation failed: npm_failed; npm 安装以退出码 1 结束
~~~

因此当前状态已从“截图不能判断后续安装”更新为“用户报告实际npm失败”；未取得该机器原始npm输出，实际根因未定位。

### WP95跟进：真实npm错误详情被最终提示丢弃

已从v0.2.17发布源码确认的错误信息缺陷：

1. runtime/install.rs的SystemNpmRunner对pack/install均收集脱敏后的末尾输出，并用npm_reason写入NpmFailed.detail。
2. InstallError::message匹配NpmFailed时忽略detail，仅返回退出码；转换为AppError再序列化后，原npm错误没有出现在最终失败提示中。
3. pack和install共用NpmFailed；最终一律叫“npm安装”，不能由该文案分辨下载打包还是安装阶段。
4. 界面又原样展示AppError中的内部英文分类串，既不可操作，也使用户无法根据摘要判断原因。执行中联网向导的输出区会显示进度行；补充截图与源码复核确认，失败后该区被隐藏，不能让用户继续从该区取得npm错误。内存仅保留最后400行，重新安装会清空前次输出。

此项并入WP95安装失败可诊断性，不声称已证明npm失败是路径、网络、权限或Node版本造成；退出码1仅说明npm命令失败。后续修复应保留脱敏原因、实际命令阶段及可追溯日志位置，沿现有错误/通知样式，不新增另一套界面。

待补证据：本次失败前的npm error/ERR错误段及所报npm日志路径；联网/离线与所选官方版本在原输出可见时一并核对。本次仅分析/记录，软件未修复、未发布下一版本。

### WP95补充：失败隐藏输出并误显示离线步骤（2026-10-28）

用户提供第4步失败截图：泛化npm_failed/退出码1、三项全未完成的“校验离线包／展开到私有前缀并链接bin／校验并切换运行来源”，没有npm输出区。“允许安装脚本并重试”置灰；此错误并非scripts_required，不能以授权脚本作为解决出口。

已核对真实源码并运行现有presentation模块：phaseShowsCommandLine在installing返回true，在failed返回false；offlineSteps(failed)返回三项pending。SettingsRoute.vue的showInstallCommandLine要求联网来源且处于downloading/installing，模板v-else无条件显示offlineStepList，导致联网失败也呈现离线列表。因此截图上的“离线包”不能证明用户选了离线安装，也不能据此断言是离线缓存缺失。

当前确认两处串联的信息缺陷：后端最终提示/历史丢弃NpmFailed.detail；前端失败阶段隐藏现存输出并切到错误来源步骤，且全pending丢失到达阶段。用户无法从该画面提供被要求的npm错误详情，上一轮“请从窗口取日志”的指导需纠正。

具体npm失败根因仍未取得原始stderr，不能断言是路径/网络/权限。命令创建SystemNpmRunner时明确设置缓存到当前数据根/cache/npm，原npm调试日志通常位于其_logs目录。按用户默认数据根对应D盘Software目录，可检查data/cache/npm/_logs的最新npm日志；不使用日常用户默认npm缓存位置猜测此次记录。

后续修复同归WP95：失败/完成时仍保留本次已脱敏输出或沿现有样式提供可访问的错误详情；步骤按真实安装来源和最后到达阶段展示，不能在联网失败时兜底成离线列表。需覆盖registry/offline × success/failure与关键阶段失败的UI回归。路径可读显示仍归WP89；本次只有分析记录，无软件开发或新发布。
