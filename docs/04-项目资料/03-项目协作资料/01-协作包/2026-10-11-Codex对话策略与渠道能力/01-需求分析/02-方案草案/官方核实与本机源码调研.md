## 官方定义核实结果

| 项目 | 已核实 | 不能据此宣称 |
|---|---|---|
| `features.async_compaction` | Schema 定义后台压缩，支持布尔开关或配置表；可配置阈值，默认占完整上下文窗口 65% | 指定 alpha 版本已经支持、Krill 全链路已经通过、任何情况下绝不等待 |
| `features.context_management` | Schema 接受布尔或配置表；普通参考页对相关实验设置仍有未开放说明 | `true` 一定能在所有渠道启用完整上下文管理 |
| `features.token_budget` | 包含 `enabled` 与 `use_history_notes_extension` 等字段 | 与后台压缩等同，或为其已证实的强制前置条件 |
| history/notes 与回退设置 | Schema 将 `use_history_notes_extension` 描述为内置历史与笔记扩展，并保留上下文轮转 / 自动压缩相关回退配置 | 普通 API 的 `context_management` 自动压缩等同于 Codex history/notes，或新模式绝无任何兜底压缩 |
| Fast / Ultrafast | 官方存在，Ultrafast 请求使用 `service_tier = "ultrafast"` | 模型面板出现入口即代表上游实际按此档执行 |
| 自定义服务地址 | `openai_base_url` 与 `chatgpt_base_url` 为真实配置项 | 复制 Krill 直连地址后仍经过现有本地代理 |
| 自定义 provider 的远端压缩 | 当前 Schema 可声明 `capabilities.remote_compaction = "v2"`，描述通过 Responses 发送 `compaction_trigger` | 旧引擎同样接受，或任意 Responses 渠道均支持该协议 |
| 模型目录 | 官方支持网关提供 Codex 原生模型目录 | 普通模型 ID 列表足以声明所有能力，新模型永远无需升级 |

尚未独立确认 Krill 教程中的 `0.163-alpha.11`、`0.159.0`、`0.160` 精确门槛。前序尝试取得指定 alpha 的公开源码未成功，因此不将其作为精确版本证据。

## OpenCodex 2.84.0 包内实现观察

包内源码根为 `src/`；包的仓库元数据指向 [lidge-jun/opencodex](https://github.com/lidge-jun/opencodex)。本轮依据为本机包文件，并非已经核对过的上游提交。

| 源码位置 | 观察结论 | 对本专题的影响 |
|---|---|---|
| `providers/openai-tiers-destination.ts` | 原生独立压缩入口判断限制在官方目的地；另有 `decodesNativeCompactionBlobs` 声明 | Krill 不能仅凭 Responses 适配器被推定为原生压缩渠道；“能读压缩状态”不等于“能产生压缩状态” |
| `adapters/openai-responses/passthrough.ts` | 非规范官方目的地的压缩请求会进入摘要转换，去掉触发项并附加摘要提示 | 请求使用 Krill 模型不等于调用 Krill 原生压缩能力 |
| `server/responses/compact.ts` | 存在原生独立压缩与路由摘要分支，并处理组合路由和上游身份 | 必须确认实际客户端走哪个入口，不能只补单个 URL |
| `providers/fastwire.ts` | 已识别 Ultrafast 意图；`fastMode = true` 可强制成 Fast，`false` 可删除档位；继承模式按能力决定传递 | 需要验证上游实际收到的档位，不仅检查配置值 |
| `types/config.ts`、`codex/catalog/operator-tiers.ts` | `ultraFastTier` 为可选机制，保留操作者明确提供的目录项，不自动为所有模型生成档位 | 模型目录与请求传递需要共同完成 |
| `config/schema/compaction-triggers.ts` | 当前覆盖 `manual`、`auto` | 需采集新版请求实际标记；尚不能仅凭此认定后台压缩失败，也不能提前发明新枚举 |
| `responses/compaction.ts` | 代理摘要使用 `ocx1:` 载体，真实原生压缩状态为不透明内容 | 可移植摘要与上游原生状态的续聊、切换行为需分别验证 |
| `codex/context-compat.ts` | 已识别 `alpha/history/v2/*`、`alpha/notes/v2/*` 的明确端点，并按用户配置启用；可调整受管本地地址前缀 | 已有上下文转发基础，但不能从开关存在推定 Krill 兼容 |
| `server/context-history.ts`、`providers/openai-sidecar.ts` | 上下文请求根据会话归属和凭据主体转发，目前候选限定为规范官方 ChatGPT 上游；笔记写入不做盲目重试 | Krill 需独立目的地、认证和会话归属适配，不能让模型请求走 Krill、history/notes 随机走另一上游 |
| `server/responses/response-effects.ts` | 成功模型请求后的 history/notes 归属登记受官方目的地判断限制 | 仅添加上下文端点转发 URL 仍不足，需要同步解决模型请求与上下文请求的归属关联 |

## 当前结论

用户随后重申外部管理层硬边界，本包不以修改上述内部实现解决差距。源码观察仅是原版能力范围证据，当前外层候选见[修订方案](代理保留与渠道能力接入方案.md)。

原版已有可复用基础，Ultrafast 优先评估公开入口复用；Krill 原生后台压缩与新版 history/notes 在当前观察中仍受内部目的地和状态归属限制，尚未证明无需修改上游即可完整接入。两种上下文策略先按渠道二选一说明设计候选配置，再验证优先级、实际请求与切换行为。所有“链路可用”“互斥已独立证明”“档位已授予”“同一会话跨渠道无损续聊”结论均待隔离联调。
