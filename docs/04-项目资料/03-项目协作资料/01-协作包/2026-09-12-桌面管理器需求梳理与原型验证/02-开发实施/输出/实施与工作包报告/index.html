02 · 开发实施协作包是干什么的

开发实施包不是把 docs/03-开发实施 复制一份，也不是再写一份技术契约。它是给你看的准备材料：把实施前置条件、工作包、测试口径和打包准备收拢成一份能读的东西。

它应该放什么

  • 实施前核对清单：确认 IMP、验收口径、开工授权
  • 工作包拆分草案：22 个 WP 的依赖、产出物、验收点
  • 实施核对记录：目录、状态、加密、扩展、同步、CLI 与 IMP 的对照
  • 测试基线：AC-01 ~ AC-13 的正常 / 失败 / 取消 / 恢复场景
  • 打包与签名准备：Tauri、macOS 签名、更新通道
  • 可读报告：HTML 单页，方便你不用翻一堆 Markdown

它不应该放什么

  • 不复制 IMP-OPENCODEX-DESKTOP-01 的全部字段，避免出现第二个契约源
  • 不写代码实现结论；没跑过的东西不能标「已通过」
  • 不把确认讨论当成正式事实；确认后要回写 docs/03-开发实施
  • 不放真实凭据、真实路径里的敏感内容

看权威事实

  • docs/02-项目核心：项目是什么、边界在哪
  • docs/03-开发实施/IMP-OPENCODEX-DESKTOP-01.md：技术怎么做、参数是什么
  • DMD-OPENCODEX-DESKTOP-MANAGER：需求与验收权威

看实施包

  • 一眼看清「现在能开工什么、还不能开工什么」
  • 把 WP-01 ~ WP-22 继续拆成带检查和证据的 TASK
  • 把 46 项冻结按工作包对上，确认没有漏项

04 · 契约已经锁住了什么

IMP 不只是方向，已经把字段、参数和阈值定死。这里只挑影响开工顺序最大的部分：

契约域 已冻结的关键点
数据根 七个物理目录：manager-state / opencodex-home / backups / logs / exports / cache / sync-state；结构版本 1
备份 每类最近 20 份、保留 30 天；备份清单含 SHA-256、字节数、文件数、可恢复标记

05 · 数据字段与对象关系

这一章回答两个问题：实现时数据长什么样；对象之间怎么连。字段是精简版，完整定义仍以 docs/02-项目核心/领域模型.md 为权威，不影响阅读。

先记住整体链路：EnvironmentGate 和 Installation 负责入口判断；AgentProcess / RuntimeFacts 看运行；DataRoot 是数据和备份的底座；SyncEndpoint / SyncRun / Conflict 处理同步；ExtensionConfig / Skill / McpServer / McpServerProjection / ClientTarget / WriteTransaction 处理扩展写入；UpdateTarget / Notification / IpcEndpoint 是外围通道。

为什么要落到字段级

防止不同人理解成不同版本。比如 DataRoot.sections 必须是七个 kebab-case 目录，McpServerProjection.client_id 必须落在六客户端枚举内，SyncEndpoint.tls_policy 固定 verify_required，这些都不能实现时临时改。

为什么对象关系要写

很多对象不靠外键强约束，但生命周期必须绑住：备份失败要阻断写入；冲突覆盖必须留 backup_ref；同步和凭据只传 ref_id，不复制真实值；统一 MCP 定义要派生多个客户端投影。

5.2 对象关系

读法：A → B 表示 A 引用或派生 B。同一连线写清 1 : N；关系用引用或投影绑定，不是全量复制。这里不再画一张大关系图，避免把长页报告变成第二张架构图。

源 目标 基数 绑定字段 / 方式 实现时要守住的规则
DataRoot BackupRecord 1 : N 备份落点必须在其 sections.backups 内 备份失败阻断导入、同步覆盖、扩展写入、数据根迁移等破坏性动作
DataRoot RuntimeFacts 1 : N（按时间事实） RuntimeFacts.data_root 展示生效数据根；管理器数据根与 OPENCODEX_HOME 分开处理
SyncEndpoint CredentialRef N : 1 SyncEndpoint.credential_ref → CredentialRef.ref_id 只保存引用；界面、日志、--json、导出和同步都不得带真实凭据
SyncEndpoint SyncRun 1 : N endpoint_id / 内存与文件锁 单端点单次同步；连接 15 秒、单件 10 分钟、总时限 30 分钟
SyncRun Conflict 1 : N scope=sync + 冲突目标 旧快照、清单缺失、载荷乱序或哈希不一致不能直接应用
Conflict BackupRecord N : 1 Conflict.backup_ref → BackupRecord.backup_id 被覆盖侧强制备份；无备份必须显式记录原因
ExtensionConfig Skill 1 : N skills 数组 统一配置是权威；反向导入只做合并，不覆盖其他客户端启用状态
ExtensionConfig McpServer 1 : N servers 数组 统一定义不携带单一客户端或单一启用开关
Skill ClientTarget N : N（按派生落点） Skill.targets + ExtensionConfig.enablement 未安装跳过且不落盘；目标哈希不同进冲突
McpServer McpServerProjection 1 : N McpServer.targets 统一定义派生逐客户端投影；同一定义可到多个客户端
McpServerProjection ClientTarget N : 1 target_ref → ClientTarget 投影只在客户端落点里表达启用、形态和最近结果
WriteTransaction BackupRecord N : 1 WriteTransaction.backup_ref → BackupRecord.backup_id 先备份再临时写入、原子替换、复验；备份失败阻断
WriteTransaction ClientTarget / 导入目标 N : 1 target / scope 只覆盖受控目标；不删除目标文件里的其他节点
UpdateTarget BackupRecord N : 1 backup_ref → BackupRecord.backup_id 本体升级和套壳自更新分开；签名失败即终止
Notification RuntimeFacts / SyncRun / Conflict / WriteTransaction / UpdateTarget 0 : N action_ref 只存跳转引用；通知正文不携带 S3 级数据
IpcEndpoint CLI / GUI 调用 1 : N socket_path + 请求 默认关闭；socket 0600；关闭时移除并确认不可连接
不是关系的地方：McpServer 不是“属于某个客户端”的记录；客户端归属在 McpServerProjection。Conflict 不是备份本身，它通过 backup_ref 找备份。Notification 不复制事件详情，只做通知与跳转引用。

06 · 代码规划结构

这一章是给实现者的阅读地图：先看分层，再看目录，最后看模块怎么接起来。目前只有规划，还没有代码；目录名是实现约定，不是本轮已创建的工程结构。

6.1 分层与调用规则

代码按四层组织，外层只能调用相邻内层。这样做的好处是：界面只管状态展示，后端才碰外部资源，公共能力不会被业务模块重复实现。

层 职责 禁止
UI / WebView 层 概览、面板、拓展、日志诊断、设置、托盘的界面状态与动作入口 不直接读写文件、网络、钥匙串
应用编排层 Tauri command、命令参数校验、状态序列化、路由到后端模块 不绕过后端模块直接执行业务
后端模块层 13 个实现模块；模块只收命令、返回领域状态 模块之间不做循环调用
公共基建层 数据根、锁、备份、写入引擎、日志脱敏、错误、通知、加密、同步客户端 只提供能力，不记录业务结论
一条硬边界：前端只发命令和渲染结果；文件、网络、钥匙串都由 Rust 后端访问。ocxd 也只连运行中实例的 IPC，不变成第二个写入者。

目录名按「先看模块归属，再看平台差异」拆开。前端不按功能拆成小仓库，后端按模块收拢，避免六客户端适配器散在各处。

6.3 后端模块与归属

模块不新增能力，只承接项目核心的 MOD-01 ~ MOD-13。公共逻辑沉到基建层，避免重复实现。

模块 代码目录 负责什么 不负责什么
MOD-01 发现 modules/discovery/ 环境门禁、安装发现、可执行校验 不安装 npm 包
MOD-02 进程托管 modules/process/ 启停、超时、取消、退出码 不管理 launchd / shim
MOD-03 状态 modules/status/ 官方输出映射、三维状态、刷新 不自己造运行状态
MOD-04 日志诊断 modules/diagnostics/ 日志读取、Doctor、通知数据 不做写入型修复
MOD-05 面板 modules/panel/ 官方面板承载与失败回退 不重绘或注入官方面板
MOD-06 数据根 modules/data_root/ 目录初始化、切换、检查 不直接搬动 OPENCODEX_HOME
MOD-07 迁移 modules/migration/ 加密导出、导入校验、回滚 不处理部分写入
MOD-08 同步 modules/sync/ WebDAV、manifest、冲突、备份 不把远端当可信数据
MOD-09 扩展管理 modules/extensions/ Skills、MCP、投影、冲突 不写核心运行配置
MOD-10 更新 modules/updates/ 本体升级引导、套壳自更新 不混用两条更新通道
MOD-11 通知 modules/notifications/ 通知生成、存储、清理 不复制业务事件详情
MOD-12 CLI / IPC modules/control_plane/ ocxd 命令、IPC、审计 不绕过实例写状态
MOD-13 托盘菜单 modules/tray_menu/ 托盘与原生菜单 不做业务逻辑入口
模块依赖原则：业务模块只调用基建层；需要另一个模块的数据时，先通过编排层组合，或沉淀成基建服务。特别要避免 extensions 直接依赖 sync，它们共用备份、锁和写入，但不共用业务状态。

6.4 前端工程选型

视觉不做组件库迁移。原型已经用原生 CSS 和 Design Token 完成整页风格，工程沿用这套资产，保证 macOS 与 Windows WebView 里的观感一致。

项 选择 原因
样式方案 原生 CSS + Design Token Token 直接来自原型，避免组件库默认样式和硬覆盖
基础能力 CSS Grid / Flex、:has()、color-mix()、backdrop-filter 都是标准 CSS，能覆盖玻璃质感、明暗主题和响应式布局
工程栈 TypeScript + Vite 类型化命令契约，开发与构建链路简单
状态管理 Pinia 只管理界面状态和 Tauri command 结果，不引入业务副作用
组件方式 自建小组件层 状态卡、动作条、表单、日志视图等数量有限，定制成本低于改框架
兼容策略 平台 WebView 冒烟 平台差异收敛到滚动条、字体回退与默认控件样式
选型边界：不引入 Element Plus、Ant Design 等 UI 组件库。Tauri 原生标题栏、托盘和系统菜单也不属于前端样式范围。

6.4 前端结构与状态流

前端按页面和状态切片组织，不按每个按钮拆文件。页面只渲染状态、触发命令，不解释业务细节。

目录 放什么
routes/overview/ 概览状态卡、动作区、运行详情折叠区
routes/panel/ 官方面板承载、失败回退
routes/extensions/ Skills 与 MCP 的统一视图、客户端开关
routes/diagnostics/ 日志、诊断、通知历史
routes/settings/ 数据目录、扩展写入开关、CLI / IPC
stores/runtime.ts runtime / connection / operation / gate
stores/notifications.ts 通知中心与通知历史共用数据
commands/ 类型化 command 封装与错误转换 
用户动作 → Tauri command → 后端编排 → 模块 / 基建
       ↑                                    ↓
界面状态 ← ActionState / 状态快照 ← 领域事实 / 操作结果
界面约束：动作按状态渲染；禁止无解释的灰按钮。状态显示最多两项，溢出聚合成「更多状态」。阶段编号 P0 / P1 / P2 不进界面。

6.6 错误、测试与依赖边界

AppError
  ├─ source        # 错误来源：ocx / fs / webdav / keychain / ipc / import / extension
  ├─ code          # AppErrorCode，对齐退出码 0 ~ 12
  ├─ message       # 用户可读摘要，最多 280 字符
  └─ hint          # 建议动作；可为空
规则 怎么做
统一错误出口 模块只返回 Result<T, AppError>；不散落 anyhow / unwrap
脱敏在出口 日志、错误摘要、--json、通知统一走脱敏器
测试分层 单元测模块内逻辑；集成测命令 + fixture；验收测 AC-01 ~ AC-13
不用真实数据 测试走临时路径与 mock；不碰家目录真实配置
依赖隔离 process_runner、http_client、keychain 抽成 trait，正式实现只放后端
还缺一步：本节是实施规划。正式工程结构应在 WP-01 授权后初始化；如果落地时发现某个目录不合理，先回写本报告和 TASK，再改代码。

6.7 平台目标矩阵

平台适配不是换一个编译目标就结束。这里先分清「能构建」「能验证」和「能承诺支持」：

目标 当前口径 验证与发布
aarch64-apple-darwin 正式支持 本机 / CI 全量验证；可承诺
x86_64-apple-darwin 计划支持 CI 构建或出 universal 包；Apple Silicon + Rosetta 只做基础冒烟，Intel 真机待补
x86_64-pc-windows-msvc 计划支持 Windows CI runner 做编译与自动化测试；GUI 完整冒烟待真实环境确认
aarch64-pc-windows-msvc 实验支持，本轮不生成 不进入验收目标，不进正式发布通道
平台结论：本轮只承诺 macOS arm64。macOS x86_64 和 Windows x64 先走 CI 构建与自动化验证；Windows ARM64 本轮不生成。平台差异必须隔离在基建层，不能散到业务模块。

Windows 适配至少要抽象这些能力：

能力 macOS Windows
凭据存储 Keychain Credential Manager / DPAPI
文件权限 Unix 0600 / 0700 ACL，等价于当前用户最小权限
IPC Unix domain socket + getpeereid Named pipe + 等价校验
文件锁 flock LockFileEx
进程控制 Unix 进程等待与信号 Job Object / 终止语义
打包签名 macOS 签名与公证 Authenticode + 安装器
执行规则：未完成对应平台验证前，报告、包名和发布页都不得写「官方支持」。实验包必须标 experimental，Windows ARM64 本轮不产出。

07 · 22 个工作包怎么用

工作包不是把工作量堆成一大张表，而是把需求、验收、依赖和安全控制拆到能建 TASK 的粒度。

先拆横切底座

WP-01 工程底座、WP-03 数据根与备份、WP-17 写入引擎、WP-21 测试基线、WP-22 打包签名。这些不做稳，后面的业务模块会反复返工。

P0 先打通主线

WP-02 发现 → WP-04 启停 → WP-05 状态 → WP-06 日志诊断通知 → WP-07 面板 → WP-08 风险恢复 → WP-09 升级引导 → WP-10 托盘 → WP-11 关于。

P1 处理写入与更新

WP-12 自更新、WP-13 / WP-14 加密导出导入、WP-15 Skills、WP-16 MCP、WP-17 写入引擎、WP-18 CLI / IPC。

P2 最后做同步

WP-19 WebDAV。它依赖加密、备份和写入引擎，不能提前抢跑。

先看懂 P0 / P1 / P2

P0 / P1 / P2 不是「重要 / 不重要」，而是交付顺序和前置依赖。原型里出现的所有功能都要实现，只是先做谁、后做谁不同。

分段 它解决什么 覆盖需求 为什么放这里
P0 · 运行管理主线 让 OpenCodex 在桌面壳里可用：发现安装、管理数据目录、启停进程、看状态日志、打开面板、识别风险、引导升级、托盘菜单和关于页 REQ-01 ~ REQ-12、REQ-16、REQ-19 ~ REQ-21 这是最低可用的日常入口；不先打通它，后面的安全能力和同步都没有稳定宿主
P1 · 写入、迁移与更新 开始碰真实文件和系统边界：加密导出导入、应用自更新、Skills / MCP 管理、受控写入、CLI / IPC REQ-13、REQ-14、REQ-17、REQ-18、REQ-22 ~ REQ-27 这些能力会写文件、碰凭据或开本地端口，需要复用 P0 的底座和备份机制
P2 · 跨机同步 WebDAV 加密同步与冲突处理 REQ-15 它同时依赖加密容器、备份、写入引擎和冲突模型，必须排在前面稳定之后

一句话：P0 是“桌面壳能日常用”；P1 是“敢写文件、能迁移、能自更新”；P2 是“敢跨机器同步”。
