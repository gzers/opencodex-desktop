## WP-89：Windows 的 OpenCodex 安装向导拒绝自身默认安装路径

### 用户现象与影响

设置 → 安装配置 → “安装 OpenCodex”的第一步中，默认安装位置带有 Windows 扩展路径前缀，例如下方形式；界面提示“安装位置必须是当前平台的完整绝对路径，且不能包含 . 或 ..”，“下一步”置灰。

~~~text
\\?\D:\Software\Develop\OpenCodeX Desktop\data\runtime\opencodex
~~~

完整[用户截图](../../../../.adg/evidence/0.2.16-issues/windows-default-install-path/user-screenshot.png)与[只读复现结果](../../../../.adg/evidence/0.2.16-issues/windows-default-install-path/analysis.json)已保留。截图是**软件内部的 OpenCodex 托管运行环境安装向导**，不能据此判定 Desktop 的 MSI/NSIS 安装目录本身错误。

影响为默认安装流程被第一步拦住；“恢复默认”仍取同一来源，可能再次产生同样的无效界面状态。首次安装、重装沿用历史前缀及离线安装都共用这一入口，均需回归。截图中的目录含空格不是本次词法拒绝的原因。

### 已确认原因

1. [SettingsRoute.vue](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/ui/src/routes/SettingsRoute.vue#L829) 将后端 managedPrefix 原样填入安装框；“恢复默认”取 defaultPrefix。第一步只要 installPrefixIssue 非空就禁用下一步，尚未调用安装命令。
2. [runtime source DTO](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/tauri/src/commands/runtime.rs#L134) 将已登记前缀或数据根下 runtime/opencodex 直接转成字符串。数据根启动链使用 Windows 原生 canonicalize，可能产生合法的扩展盘符或扩展 UNC 路径。
3. [installPath.ts](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/ui/src/features/runtime/installPath.ts#L6) 只识别普通盘符与普通 UNC；把扩展前缀中的问号视为不允许的 UNC 根，返回无效路径。同一解析器也让“数据根内/外”判断返回未知。
4. [既有测试](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/ui/tests/settings-install-path.test.ts#L69) 明确将扩展盘符路径放入“应禁用”用例，固化了错误口径。并非仅缺少一个界面提示。

实际加载发布源码中的路径函数，得到以下词法结果；没有调用安装、写用户配置或操作 Windows 文件系统：

| 输入形式 | 当前路径校验 | 当前能否进入下一步 |
| --- | --- | --- |
| 普通 D 盘绝对路径，包含空格 | 通过 | 是 |
| 同目录的扩展盘符形式 | 返回无效绝对路径 | 否 |
| 普通 UNC 共享目录 | 通过 | 是 |
| 同目录的扩展 UNC 形式 | 返回无效绝对路径 | 否 |

默认落点“数据根/runtime/opencodex”这一产品约定本身没有被证据推翻。已确认的是**自动返回的 Windows 路径表示与前端识别规则不一致**；移除前缀后词法通过，不等于证明真实安装、权限或 npm 命令均能成功。

### 修复建议与关联检查（待实施）

- [ ] 统一已知 Windows 盘符、UNC 及其扩展形式的路径身份；展示、默认预填、恢复默认、目录选择、输入校验和数据根包含关系使用一致规则。规范化后应指向原目录，不悄悄变更用户选择或已有安装登记位置。
- [ ] 显示采用可读的普通路径时，保留实际路径语义与长路径边界；不能对任意设备路径做字符串删前缀。设备命名空间、GLOBALROOT 等未支持形态继续明确拒绝。
- [ ] 后端使用实际文件系统校验绝对路径、权限、链接/重解析点及系统目录。现有 runtime/paths.rs 的 Windows 系统目录检查以字符串比较为主，扩展形式的身份等价也须同步复核；不能只放开前端而造成保护规则漏判。此项为源码风险与待验要求，未声称已在 Windows 上证明绕过。
- [ ] 首次默认安装仍落在当前数据根的 runtime/opencodex；重装沿最近有效安装记录，“恢复默认”取数据根默认值。不得以本次兼容修复把所有位置改为固定盘符或重新规划数据根。
- [ ] 纠正将合法扩展路径一律拒绝的旧测试；覆盖默认值和真实后端 DTO，而不只手工构造普通路径。保留相对路径、盘符/共享根、控制字符、遍历、跨共享及保护目录等原有拒绝要求。
- [ ] 保持原型安装向导的布局、按钮和四步流程，只修默认值及校验口径；不增加额外确认、核对状态或新的通知样式。

### 修复后必做验收

1. Windows 新安装在非系统盘、含空格/中文的数据根打开向导，自动默认值无需改字即可进入下一步；目录选择与恢复默认同样成立。
2. 使用实际 Windows 原生 canonicalize/DTO 返回的扩展盘符路径，并覆盖普通/扩展 UNC 的解析与身份等价；网络共享实际安装是否受支持按真实文件系统结果说明，不由词法通过推导。
3. 数据根内/外判断准确，兄弟目录、不同共享不误认；保护目录及其扩展等价形式不因规范化而放行，权限与链接检查保留。
4. 在隔离原生安装器环境完成一次真正的 OpenCodex 托管安装：核对最终落点、登记记录、可执行入口与版本读回；覆盖重装、恢复默认及离线共用入口。Desktop 安装/首屏通过不能替代本步骤。
5. 安装失败或权限不足保留用户选值并如实报错；macOS 的默认路径和保护规则保持原行为。没有 Windows 实测和真实安装回执前不标记修复完成。
