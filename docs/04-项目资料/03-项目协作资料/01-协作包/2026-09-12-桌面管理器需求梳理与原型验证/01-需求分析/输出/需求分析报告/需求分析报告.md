## 02 · 这是什么 {: #what }

一句话：把 OpenCodex 日常要敲的命令、要另开终端看的状态，收进一个 macOS 桌面应用，同时**不改变 OpenCodex 自己的行为和权威**。

<div class="card-grid">
<div class="card">
<h4>产品身份</h4>
<p>仓库标识 <code>opencodex-desktop</code>，界面展示名 <code>OpenCodeX-Desktop</code>。两者并存是既定约定，不要求统一。</p>
<p>它是独立产品，与 OpenCodex 官方项目及其权利人<strong>不存在隶属、授权或背书关系</strong>。</p>

<p>第一阶段以 <strong>macOS</strong> 优先；跨平台能力在实现层预留抽象，不作为首期验收范围。</p>
</div>
<div class="card">

## 03 · 解决什么问题 {: #problem }

麻烦的地方不在单条命令，而在于这些事散落在终端、配置文件和多个客户端之间。

<div class="pain-grid">
<div class="pain-card"><h4>启停要敲命令</h4><p>启动、停止、重启都要回到终端敲 <code>ocx start / stop / restart</code>，没有图形入口。</p></div>
<div class="pain-card"><h4>状态和日志分散</h4><p>健康状态、端口、进程、日志要另开终端看；出问题只能自己翻。</p></div>
<div class="pain-card"><h4>迁移和同步没有界面</h4><p>配置导出、跨机同步全靠手工，覆盖前有没有备份也说不清。</p></div>
<div class="pain-card"><h4>扩展配置分散在六处</h4><p>Skills 和 MCP 要手工改好几份客户端配置，格式还各不相同。</p></div>
</div>

<div class="ba-grid">
<div class="ba-box ba-before">
<h3>现在</h3>
<ul>
<li>启停要敲 <code>ocx start / stop / restart</code></li>
<li>状态和日志得另开一个终端看</li>
<li>配置导出、跨机同步没有图形入口</li>
<li>Skills 和 MCP 要手工改好几份客户端配置</li>
<li>出问题只能自己翻日志、翻环境</li>
</ul>
</div>
<div class="ba-box ba-after">
<h3>装了它之后</h3>
<ul>
<li>一个窗口里点启停，直接看到健康、端口、PID</li>
<li>日志和诊断中心并排看，敏感值自动打码</li>
<li>配置导成加密容器，走 WebDAV 同步，覆盖前先备份</li>
<li>Skills / MCP 统一管一次，再分发到六个客户端</li>
<li>出问题给原因和建议动作，不甩一个红点</li>
</ul>
</div>
</div>

## 04 · 做与不做 {: #scope }

先说清边界，后面才不会返工。范围原则只有一句：**原型里出现的功能都要实现**，P0 / P1 / P2 只表示先做后做和前置依赖，不表示可以不做。

<div class="card-grid">
<div class="card">
<h3 style="margin-top:0">做</h3>
<ul>
<li>发现并校验本机已有的 OpenCodex 安装（npm 形态）</li>
<li>托管官方 <code>ocx start / stop / restart</code> 子进程，展示健康、端口、进程标识、最近错误</li>
<li>日志只读脱敏、运行环境诊断、内嵌官方 Web 面板</li>
<li>加密的配置导出 / 导入，以及经 WebDAV 的加密同步</li>
<li>Skills 与 MCP 统一管理，并分发到多个客户端</li>
<li>两条独立更新通道：OpenCodex 本体升级引导、应用自身更新</li>
<li>托盘、macOS 原生菜单，以及默认关闭的可选 CLI 控制面</li>
</ul>
</div>
<div class="card">
<h3 style="margin-top:0">不做</h3>
<ul>
<li>不重写 OpenCodex 核心，不绕过官方 API</li>
<li>不管 npm（安装、卸载、依赖解析、全局前缀）</li>
<li>不替代官方 <code>ocx update</code> 的更新事务</li>
<li>不安装或管理 launchd，不接管 <code>codex-shim</code></li>
<li>不写入 provider、路由、模型映射等核心运行配置</li>
<li>不自动覆盖外部 provider 托管的配置，只检测、解释、引导官方 <code>restore</code></li>
<li>不明文迁移或同步凭据</li>
</ul>
</div>
</div>

<div class="callout callout-warn"><strong>唯一的例外：扩展配置可以写。</strong>具体是 Skills 目录同步和各客户端的 MCP 服务器节点。除此之外的一切 OpenCodex 配置仍然不可写，一律走官方 CLI。这也是安全评审里被反复盯住的边界。</div>

<div class="callout callout-info"><strong>先做后做的顺序：</strong>P0 是运行管理主线（发现、数据目录、启停、状态、日志诊断、面板、风险与 restore、官方升级引导、托盘菜单、关于页）；P1 是要先过安全评审的（配置迁移、扩展管理、CLI 控制面、应用自更新）；P2 是 WebDAV 同步，它依赖前面的加密容器和写入引擎。</div>

## 07 · 架构 {: #architecture }

三条主线：前端只管画、后端独占外部访问、模块划分和能力域一一对应。

| 项 | 取值 |
|---|---|
| **桌面壳** | Tauri v2 |
| **后端** | Rust |
| **前端** | Web 前端，渲染在 Tauri WebView 内 |
| **平台** | 第一阶段以 macOS 优先；跨平台能力在实现层预留抽象，不作为首期验收范围 |

### 13 个后端模块

模块按能力域切开，方便从能力追到实现。

| 模块 | 职责 |
|---|---|
| **发现模块** | 安装发现：路径、版本、可执行校验、前置条件门禁 |
| **进程托管模块** | 启停子进程的调用、超时、退出码与错误摘要 |
| **状态模块** | 官方状态命令的采集、映射与三维状态维护 |
| **日志与诊断模块** | 日志读取、脱敏、日志目录打开、Doctor 只读摘要 |
| **面板模块** | 官方 Web 面板快照的承载与失败回退 |
| **数据根模块** | 数据根的选择、检查、引用或迁移、备份 |
| **迁移模块** | 加密容器的导出、校验、导入与回滚 |
| **同步模块** | WebDAV 的加密、清单、冲突与覆盖前备份 |
| **扩展管理模块** | Skills 与 MCP 的读取、投影与受控写入 |
| **更新模块** | 官方升级引导与应用自更新（两条独立通道） |
| **通知模块** | 通知的产生、存储、聚合与清理 |
| **CLI / IPC 模块** | 命令解析、本机 IPC 委托、机读输出与访问控制 |
| **托盘与菜单模块** | 托盘菜单与 macOS 原生菜单入口 |

### 几条不能破的约束

- **单一真相源 + 投影：**管理器维护统一事实，各客户端配置是投影，不是权威。
- **只改目标节点：**结构化读改写，保留未知字段与注释，不整文件重建。
- **原子写：**同目录临时文件写好后原子替换，替换后保留原文件权限。
- **备份先行：**任何可能覆盖数据的写入，前面必须先有一份可恢复的备份；备份失败就阻断。
- **跨进程互斥：**和官方 CLI、编辑器共享同一批配置文件，写入要拿跨进程文件锁，并比对内容摘要。
- **凭据不出域：**凭据不进日志、不进命令行参数、不进错误信息、不进未加密文件。
- **后端独占外部访问：**前端不直接触碰文件系统与网络。

### 运行时与进程模型

- **管理器进程**：桌面应用本体，持有界面、后端逻辑和托管子进程。
- **托管子进程**：官方 `ocx start / stop / restart` 由它直接启动和持有，进程标识与退出码进入状态展示。
- **CLI 客户端**：`ocxd` 不独立执行能力，而是连接运行中实例的本机 IPC 端点委托执行；实例没跑的时候不得绕过它直接改状态。
- **重启语义**：应用自更新会重启应用本体，但不会停掉托管中的 OpenCodex 代理；重启后重新接管并恢复状态展示。
- **离线语义**：代理离线时，依赖实时能力的功能（比如实时日志）明确标注不可用，本地历史日志和日志目录仍然可用。

### 两条主要数据流

**状态采集**：托管子进程 / 官方状态命令 → 后端采集与字段映射 → 三维状态（运行 / 连接 / 操作）→ 前端按状态渲染动作与说明。

## 10 · 数据与安全 {: #data }

这个产品大半的复杂度都在这里：它要改别人机器上的配置文件，还要搬运凭据。原则是能不动就不动，非要动就先备份、可回滚、留证据。

### 数据根分区

用户可以选一个自定义数据根，管理器按用途划分产物。`OPENCODEX_HOME` 可以放在数据根里，也可以由用户指定成独立路径。

| 分区 | 放什么 | 约束 |
|---|---|---|
| `manager state` | 桌面壳设置、数据根元信息、界面偏好 | 不含真实凭据明文 |
| `opencodex home` | 可选承载 `OPENCODEX_HOME` | 引用或迁移，尊重既有数据 |
| `backups` | 升级、导入、同步覆盖前的备份 | 必须可定位、可校验、可恢复 |
| `logs` | 桌面壳操作日志与旋转后的日志 | 只读、脱敏、可轮转 |
| `exports` | 加密配置导出容器 | 口令保护，按凭据文件处理，权限 0600 |
| `cache` | 可丢弃缓存 | 可随时清空 |
| `sync state` | WebDAV 冲突记录、远端索引摘要、同步历史摘要 | 用于变更检测，不作权威 |

#### 切换语义：引用优先、迁移可选

选择目录 → 检查（可写 / 空间 / 已有数据）→ 引用 或 迁移 → 运行前备份 → 停止代理 → 执行迁移 → 校验 → 更新配置 → 恢复代理。

默认只「引用」已有位置，不搬动数据。迁移前强制备份，失败自动回滚并保留原数据目录。

### 数据分级

| 级别 | 数据 |
|---|---|
| <span class="tag tag-green">S0 公开</span> | 应用版本、官方项目信息 |
| <span class="tag tag-blue">S1 内部</span> | 安装路径、版本、运行状态、端口、进程标识、数据根路径 |
| <span class="tag tag-gold">S2 敏感</span> | 日志正文、备份内容、同步索引摘要、Skills 文件内容、MCP 配置结构 |
| <span class="tag tag-red">S3 凭据</span> | API key、token、Authorization、WebDAV 账号口令、加密口令、MCP 环境变量值 |

- S3 **不得**进入仓库、Markdown、日志、命令行参数或未加密文件。
- 敏感值范围**包含** `env`、`args`、`headers`，三者一律按潜在敏感值处理，默认掩码。
- 掩码在**取值之前**完成，不是「先明文取回来，再在界面上打码」；编辑场景按字段短暂显示。
- 涉及凭据的配置文件按凭据文件处理，Unix 权限 `0600`。
- MCP 的 `command` / `args` / `env` 具备执行本地程序的能力，必须展示执行边界并经用户显式确认，不得静默执行任意本地程序。

### 扩展配置落在哪

六家客户端的 MCP 节点位置、容器结构和文件格式都不一样，所以必须一家一个适配器，不能假设有统一 schema。这是实施阶段最容易低估的一块工作量。

| 客户端 | MCP 配置落点 | 格式 | MCP 键与形状 |
|---|---|---|---|
| **Codex** | `$CODEX_HOME/config.toml`（默认 ~/.codex/config.toml） | TOML | `[mcp_servers]` 表；`command` + `args` |
| **Claude Code** | `~/.claude.json`；项目级 `<project>/.mcp.json` | JSON | `mcpServers` 映射；另有 disabled / enabled 列表 |
| **Gemini CLI** | `~/.gemini/settings.json`；工作区同名文件 | JSON | 顶层 `mcpServers`（定义）+ `mcp`（全局规则） |
| **Grok CLI** | `~/.grok/user-settings.json`；项目级同名文件 | JSON | `mcp.servers`，是**数组** |
| **OpenCode** | `~/.config/opencode/opencode.json[c]`（XDG，可覆盖） | JSON / JSONC | `mcp.servers`；标签联合 local / remote，环境变量键为 `environment` |
| **Hermes Agent** | `<HERMES_HOME>/config.yaml`（默认 ~/.hermes/config.yaml） | YAML | `mcp_servers` 映射；`type` 归一化为 `transport` |

Skills 目录：Claude Code `~/.claude/skills/`、Codex `~/.codex/skills/`、Gemini CLI `~/.gemini/skills/`、OpenCode `~/.config/opencode/skills/`、Hermes Agent `~/.hermes/skills/`、Grok CLI 项目级 `.agents/skills/`。另有社区共享目录约定 `~/.agents/skills/`，可以作为 Skills 的源存储位置。

### 单一真相源 + 投影

管理器统一扩展配置（含每个能力项的启用矩阵）→ 逐客户端投影 → 各客户端 live 配置文件。

- 管理器维护统一事实；客户端配置是**投影**，不是权威。
- 每个能力项记录它在哪些客户端启用，启停以投影方式同步到对应文件。
- 导入方向相反：从客户端 live 配置读回并合并进统一结构，**不覆盖**其他客户端的启用状态。

<div class="ba-box ba-after">
<h3>允许写入</h3>
<ul>
<li>Skills 目录同步</li>
<li>各客户端的 MCP 服务器节点</li>
</ul>
</div>
<div class="ba-box ba-before">
<h3>禁止写入</h3>
<ul>
<li>provider、路由、模型映射</li>

</ul>
</div>

| 规则 | 要求 |
|---|---|
| **目标校验** | 目标必须是普通文件；符号链接、FIFO、设备文件或越出预期根目录的路径一律拒绝写入 |
| **前置备份** | 任何写入前生成可恢复备份；备份失败即阻断 |
| **原子替换** | 同目录临时文件写入后原子替换；替换后保留原文件权限 |
| **节点级写回** | 只改目标节点，保留未知字段与注释；解析失败即拒绝，不做部分写回 |
| **非目标文件** | 不改写同目录的凭据、认证等非目标文件 |
| **并发互斥** | 写入持有跨进程文件锁，并在写入前比对目标内容摘要 |
| **冲突处理** | 检测到外部改写或客户端间不一致时进入待处理，不静默覆盖 |
| **可恢复删除** | 卸载 Skills、删除 MCP 等删除类操作进入回收区，可恢复 |
| **串行化** | 扩展配置写入由单一状态锁串行化，避免并发动作互相覆盖 |

### 信任模型

| 对象 | 信任假设 | 结论 |
|---|---|---|
| **WebDAV 远端** | 不可信 | 上传前客户端加密；哈希只用于发现传输损坏与回放，真实性由认证加密覆盖，不能拿哈希当防恶意远端的措施 |
| **WebDAV 连接** | 需要证书校验 | 证书校验失败默认拒绝，且不提供「忽略证书」选项 |
| **外部客户端配置** | 可能被第三方改写 | 写入前比对内容摘要，冲突进入待处理 |
| **官方 CLI** | 权威写入者 | 不与其争夺 provider / 路由 / 模型映射的写入权 |

#### 加密导出容器

| 项 | 取值 |
|---|---|
| **内容范围** | 全量配置，包含敏感内容 |
| **保护方式** | 用户口令保护；推荐 Argon2id 派生 + AES-256-GCM 认证加密 |
| **完整性** | 认证加密自带完整性校验；解密或校验失败即拒绝，不部分导入 |
| **版本策略** | 容器头含格式版本与派生参数；不兼容即拒绝并说明支持范围 |
| **结构约束** | 只接受白名单字段与合法路径；拒绝未知字段与越界路径 |

<div class="callout callout-danger"><strong>几条「明确不做」也写在这里：</strong>不重写 OpenCodex 核心、不绕过官方 API；不管 npm；不替代官方 <code>ocx update</code>；不接管 <code>codex-shim</code>、不装 launchd；不写核心运行配置；不自动覆盖外部 provider 配置；不明文迁移或同步凭据。</div>

### 几条必须守住的界面口径

- **动作按状态渲染，不渲染没有解释的灰色禁用按钮。**用状态说明文字说清为什么现在不能点。比如 `starting_failed` 下，启动按钮的文案变成「重试启动」。
- **界面里不出现 P0 / P1 / P2。**设置分区、卡片标签、面板标题都只用功能名和「规划中 / 可用」，阶段编号只留在文档里。
- **两个版本对象分开。**概览「版本升级」卡和设置第一块是 OpenCodex 本体（官方 `ocx update` 引导）；设置第二块是桌面管理器自身（应用自更新）。按钮和文案必须让用户分清当前更新的是哪一个。
- **主题只有一份取值。**`ocx-theme`（light / dark / system）由外壳和内嵌官方面板共同派生，面板不保存自己的主题，切换时用 `postMessage` 实时同步。
- **WebDAV 卡按连接状态渲染。**未配置时不置灰，只把动作区换成一颗「配置 WebDAV」直达设置；其余状态各自的动作组合不同。
- **概览定稿为 B+ 合并版：**一行运行摘要 + 页内折叠的「运行详情」+ 压缩后的快捷动作卡。
- **敏感值永远掩码**，按钮用明确动词（启动、停止、重启、刷新状态、打开面板、查看日志），涉及 restore / 停止 / 重启 / 切换数据目录时必须解释后果。

<div class="callout callout-info"><strong>视觉来源：</strong>颜色体系从官方 GUI 构建产物的设计 token 提取，再向官方面板对齐，避免嵌入面板后割裂。截图只作为视觉 QA 证据，不用来反推样式。</div>

</div>

### P2 · WebDAV 加密同步

<div class="card">
<h4>WP-19 · WebDAV 加密同步 <span class="tag tag-gold">P2</span> <span class="tag tag-blue">AC-07</span> <span class="tag tag-purple">REQ-15</span></h4>
<p><strong>目标：</strong>跨机同步配置，但远端一律当不可信处理。</p>
<ul>

### 依赖与开工顺序

WP-01 工程底座 → WP-02 发现 → WP-04 进程托管 → WP-05 状态 → WP-06 / 07 / 08 / 10 / 11

WP-03 数据根与备份 → WP-09 升级引导 / WP-17 写入引擎 → WP-15 / 16 扩展管理 · WP-13 / 14 配置迁移 → WP-19 WebDAV

- **备份能力是公共底座。**WP-03 的备份与回滚会被 WP-09、WP-13、WP-14、WP-17、WP-19 一起用，所以要早做、做扎实。
- **写入引擎要先于扩展管理。**WP-17 是 Skills 和 MCP 的共同底座，先做引擎再做界面，避免两处各写一套。
- **WebDAV 排最后有原因。**它同时依赖加密容器（WP-13）和写入与备份（WP-17），前面不稳，同步就会丢数据。
- **安全阻塞项不排在最后。**WP-20 和 WP-15 ~ WP-19 并行推进，因为 6 条阻塞风险就长在这些能力里。
- **打包和签名要早准备。**WP-22 支撑应用自更新，签名链路通常比预想的慢。

<div class="callout callout-warn"><strong>最后提醒一句：</strong>这份清单是为了让你看清工作量，不是授权开工。正式开工前要走完「开工前必须先做完的三件事」；其中创建 IMP 和正式发布都属于需要单独确认的动作。</div>
