# 名称发布方案收口与开发前取舍

2026-11-10，Desktop0.2.24开发前工作，代码基线0.2.23。用户要求把开发前工作做好，本轮继续验证名称发布方式及隔离GUI条件；不修改apps、官方2.99源码/制品、日常配置或发布。

## 本轮新增实测

### 官方单目标组合映射

新建私有短路径HOME/OPENCODEX_HOME/CODEX_HOME，用原样官方2.99的validateConfigCandidate→真实loadConfig→refreshCodexModelCatalog→previewRouteModel验证单目标combo。公开alias与原路由fixture/gpt-6.1-sol相同，displayName分别设为英文改名、中文、空格和渠道内斜杠，目标仍是原fixture提供方及gpt-6.1-sol。

四例显示名均在真实官方刷新后保留，目录同slug只有一行，最终provider/modelId保持。但是逐字段比对发现：

- routeKind从explicit-provider变成combo，不能写成“仅display_name变化”。
- 描述及owned_by变成combo，原opencodex_capability_provenance消失。
- 此原样输入中，原模型low/medium/high/max/ultra变为low/medium/high，max/ultra不再被目录宣告。只比较名称和底层target会漏掉能力退化。
- 原生允许的82字符模型ID，其原路由作为combo alias被完整Schema拒绝；combo alias每个路由段长度有限，不能宣称覆盖所有原本合法模型ID。

因此该候选只证明另一条官方能力能显示名称，**不满足当前“名称适配不降能力、不改变已有路由语义和覆盖范围”的完整合同，本轮不采用。** 没有把能力差异当成已批准变化，没有改参数强补档位后再声称语义相同；若未来选择此方向，必须明确其新增配置/调度语义、失败/冷却/能力/长ID及客户端旧选择的影响并重新采用/验证。

### 短目录GUI假设

前轮实际com.openai.codex隔离实例因Chromium ProcessSingleton socket目录失败，不能确定是否由长Unix socket路径造成。本轮改用/private/tmp/ocxd24n-随机的短私有根，保持独立HOME/CODEX_HOME/Electron userData，外网/日常文件/Keychain读取拒绝及私有socket写集，仍在相同socket目录创建处exit21，未打开窗口。

此反例否定“只缩短路径即可解决当前隔离启动”的判断，不能继续重复同一尝试或标GUI通过。没有借此给日常应用目录/共享socket打开权限，未重启当前工作对话所在的日常客户端。应用存在且身份已确认，缺口是可用的隔离GUI桌面/通信环境，不能再记成不存在Codex App。

## 当前已验证路线的结论

| 路线 | 实测 | 对当前合同的判定 |
| --- | --- | --- |
| 官方modelDisplayNames写完整“渠道/模型” | 完整Schema拒绝ASCII斜杠。 | 不可直接用。 |
| provider.alias＋同名modelAliases | Schema可过的输入在真实load被清理。 | 不能用仅JSON校验通过代替可用。 |
| 合法ASCII渠道名作为provider实际键 | 真实文件加载/目录/原路由/客户端读回通过子集。 | 不覆盖中文/空格/斜杠渠道名，不能当全范围完成。 |
| Desktop独立display文件＋显式客户端启动覆盖 | 原路由/能力保持，真实读取及官方原目录刷新共存通过。 | 可用于受控启动子集，不证明手动默认GUI入口。 |
| 持久根model_catalog_json指向display文件 | 客户端无覆盖能读，但官方也选择同一文件，实际refresh把名称覆回原路由名。 | 不可作为默认GUI完整方案，禁止轮询相互覆盖当无竞争发布。 |
| 独立profile作为默认捷径 | 当前捆绑app-server拒绝--profile；未选profile不影响默认读取。 | 不能靠CLI profile假定手动GUI会选中。 |
| 官方单目标combo同公开alias＋displayName | 四类名称刷新保留，底层target相同；但routeKind/能力/来源改变且存在长ID限制。 | 本轮排除为透明显示修复，未经采用不能进入生产。 |

这些结果说明**目前测试过的可执行方案没有同时满足完整名称、手动默认入口、原包2.99完全不变、能力/路由保持和不竞争写入**。这不是证明所有未来方案数学上不可能；也不能把未证明的事件回调/二进制拦截/共享文件轮询写成已确认设计。官方publication-observer仅通知订阅者，源码明确订阅者不拥有发布成功，不能用通知回调失败吞掉的行为代替事务性显示发布。

## 需要的产品取舍与技术责任

当前采用决定仍为“直接官方2.99，由Desktop另行适配全部必要能力”，本轮没有自行覆盖它。要冻结名称生产方案，需要一个明确、经过验证的支持出口。建议优先评估**最小上游显示能力修正**：允许官方保存/发布所需的显示文本，仍由官方同一目录写者生成最终内容，真实slug、提供方、型号及其它能力不变。这样不引入单目标组合调度或双写目录。

该建议会触及此前“固定原样官方2.99、不制作新维护包”的边界；必须先由用户明确是否允许调整这个边界，然后才可设计/验证具体修正和制品身份。尚未授权时只记录建议，不改官方文件，不制作维护修订、不发上游公开PR或消息。最小修正也不能只删除一处检查就宣称全部解决，需完整Schema/load/保存/目录/原能力/实际客户端/刷新重启回退反例验证。

如果继续要求原样2.99且不允许新的显示支持出口，就应保留NAME-01为未闭合，不降级需求或将受控CLI的通过外推到手动GUI。其他已明确范围可以有独立实施计划，但不能把整版G0写为全部冻结。

## 2026-11-10后继纠正：固定键候选不等于普通改名链

本文件试验使用固定fixture键投影名称，未执行用户实际新增/改名保存，不能据此认定0.2.23合法英文改名不能生效。[后继真实保存链](20261110-新增与改名真实保存链复核.md)已取得10组实际保存→官方刷新/路由：合法英文新增/改名均正确；非ASCII/空格/斜杠等两操作都使用内部键，才落入尚未闭合的完整名称范围。既有name/键不一致的无新意图Save对齐测试也通过。

上文最小上游显示支持仅为剩余完整名称范围的待评估建议，不是普通英文改名的必要修法或已证明唯一解。明确渠道改名时同步实际键及引用是既有实现，不能把“所有slug永远不变”加成该动作的新约束。历史候选失败不重写，范围与当前结论以本节和同源矩阵为准。
