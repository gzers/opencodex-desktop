# Desktop用户配置目录结构设计

2026-11-06，Asia/Shanghai。**最新结构：.codex-desktop下先分desktop/与opencodex/，OpenCodex实例HOME为opencodex/home/，程序按新版本安装布局定位。** 用户本轮明确以此重新规划并分端说明，本稿替代此前根下平铺manager-state/opencodex-home的结构，以及Git提交74e8a6aa2中的.opencodex-desktop/data和更早AppData/Application Support建议。只设计/记录，已纳入0.2.23目录专题，尚未开发或执行数据迁移；不把新目标写成当前实现。

正式归属：范围/验收见[DMD-USER-DIRECTORY](../../../01-需求管理/需求/DMD-OPENCODEX-USER-DIRECTORY.md)，物理路径合同见[数据与状态 §1.4](../../../02-项目核心/数据与状态.md#14-用户目录新规则已确认待实现目标版本0223)，实施明细见[IMP-32](../../../03-开发实施/IMP-OPENCODEX-DESKTOP-32.md)，原型配套见[说明](../01-产品原型/用户目录与手动渠道恢复说明.md)。本稿保留双端树和人工参考，不另维护执行生命周期。

## 1. 拥有者与HOME边界

| 对象 | 拥有者与职责 |
| --- | --- |
| 用户.codex-desktop/desktop | 本项目Desktop的设置、绑定、布局、日志、备份和本机同步状态。 |
| 用户.codex-desktop/opencodex/home | 原版OpenCodex实例的OPENCODEX_HOME：配置、账号/认证、运行记录/锁、用量等；不是纯配置，不含程序安装包。 |
| 用户.opencodex/ocx-homes | 原版跨HOME实例登记，仅定位实际HOME，由原版维护，非渠道配置副本。 |
| 原有CODEX_HOME或用户.codex | Codex客户端配置、授权、会话、生成目录；不移入Desktop数据根。 |
| 现有Desktop/OpenCodex程序位置 | 可执行代码、依赖、资源及启动入口；按新版本安装布局定位，与用户配置目录分开，不继承旧版绑定。 |

系统HOME/USERPROFILE仍为当前OS用户主目录，不能设置成Desktop数据根。OPENCODEX_HOME才指向上述子目录。Desktop渠道界面继续读取/修改原版config.json，desktop/manager-state里的布局/采用关系不成为第二份渠道权威。

根名按用户最新拼写.codex-desktop，与原版已使用的.opencodex-desktop、.opencodex以及Codex的.codex分开，不因名称相似自动接管。根下仅按desktop/与opencodex/两类组织，再分别细分；不在根下平铺管理器文件、备份或日志。此前data避让层不再保留。新根已有未知/损坏/其它拥有者数据时明确停止，不能当空覆盖。

## 4. 定位、程序与端口合同

- 固定用户入口.codex-desktop/desktop/manager-location.json只定位活动数据根，默认.codex-desktop；活动根下desktop/manager-state/data-root.json负责结构/内部或外部HOME绑定。新Schema须消除重复active_data_root权威，旧HKCU或旧元数据不作为新默认的回退入口，不自动迁入旧配置，不能长存双写两套定位。未知/损坏不当空，不静默创建替代配置。
- 用户自定义活动数据根仍可通过同一定位选择，所选根同样先分desktop/与opencodex/，内部HOME默认为所选根/opencodex/home。固定用户入口的manager-location.json与manager-startup.lock不随活动根搬迁，活动根不生成第二份定位权威。现有明确外置OPENCODEX_HOME不自动复制；新结构默认使用内部HOME，如需继续使用外置HOME，由用户显式选择并校验，不静默继承旧绑定；不合并用户独立CLI原有.opencodex/config.json。
- **仅识别新版本路径，不兼容旧版**：程序、配置、启动、更新及卸载统一使用新版本规定的路径与新格式元信息。缺失时按新版本首次初始化/安装流程处理，损坏或无权限时明确报错；不扫描旧AppData、Application Support、安装旁data、旧注册表选择或旧运行包，不回退旧绑定、不提供专为旧程序建立的重新绑定逻辑。手动放入新HOME的JSON按当前支持格式读取，不开发旧格式转换。
- 程序与配置根显式解耦：desktop/manager-state/runtime.json仅记录新版本安装布局中的程序来源；启动/更新/卸载共用该来源，禁止依赖旧数据根/runtime。程序安装布局应由新版本安装合同明确，不能以旧版残留作为兜底。具体程序前缀在实施前按实际安装合同补齐，本方案不臆定跨平台绝对路径。
- 启动原版传本用户OPENCODEX_HOME，系统HOME/USERPROFILE和CODEX_HOME保持真实绑定；原版负责登记、监听、鉴权和运行事实。Desktop不手写ocx-homes代替身份验证，不新增一层HTTP代理。
- 同机TCP端口仍共享。复用原版config.port/公开启动能力与真实绑定结果，Desktop不另养第二份端口权威，也不能仅凭health200复用其它用户服务；需核对进程归属、令牌与各用户客户端指向。端口/PID/路径/本机凭据不作普通跨设备同步对象。

## 5. 旧版处理：不做自动迁移，手动备份与恢复渠道

### 5.1 最新范围决定

用户进一步明确“不用考虑迁移”，自行取出旧OpenCodex配置JSON，之后读取现有渠道恢复。本节替代此前自动迁移、全字段迁移验收、迁移事务和自动回退方案；本专题不开发旧版数据自动迁移。其它历史数据不要求保留。用户进一步明确全部识别按新版本路径进行、不考虑旧版兼容；旧位置仅作人工备份/清理参考，不能成为新版运行分支。当前只给位置与清理边界，不执行备份、删除或日常配置修改。

### 5.2 旧配置位置与恢复步骤

- 本机已只读确认实际配置：/Users/ezio/Library/Application Support/com.gzers.opencodex.desktop/opencodex-home/config.json。登记HOME与默认数据根指向一致；未读取或输出配置中的秘密。
- macOS默认：~/Library/Application Support/com.gzers.opencodex.desktop/opencodex-home/config.json。
- Windows候选：<Desktop.exe所在目录>/data/opencodex-home/config.json，或%APPDATA%/com.gzers.opencodex.desktop/opencodex-home/config.json。现有旧用户根、HKCU选择和合法自定义根可能改变位置，不能把候选路径当作该Windows机器已确认事实。
- 自定义/外置HOME以软件当前实际绑定为准：实际OPENCODEX_HOME/config.json。旧数据根manager-state/data-root.json包含active_data_root、opencodex_home_mode及可能的外置路径；原版.opencodex/ocx-homes登记仅供定位，不是渠道配置备份。

用户先退出相关配置写者，复制config.json到旧根之外的安全位置，不改原件。它包含渠道连接、模型和可能的Key，应按秘密文件保管。若某个渠道的认证/有效参数依赖外部文件、环境变量或未展开的引用，仅JSON不足，须保留相应依赖；不承诺所有历史格式都只靠JSON无损恢复。不关注的管理器布局/历史采用记录可放弃。

新结构实际实现并启用后，退出服务，将备份配置放入当前用户.codex-desktop/opencodex/home/config.json（目标已存在先另存，不能盲目覆盖）。重新打开软件，“读取现有渠道”读取当前绑定HOME的config.json，不是任意文件导入器。核对渠道、节点、Key状态与模型选择，按正常流程刷新运行配置并确认客户端可见，再清理旧资料。若JSON不符合当前支持格式或有无法解析引用，明确报错，由用户调整/重新配置；不开发旧格式兼容或转换，不假称已还原。目前新结构尚未实现，不能现在直接放入目标就认为生效。

### 5.3 可清理与必须保留的边界

以下均相对已确认的旧活动数据根；先退出Desktop及相关服务，避免在运行中删除。

| 路径 | 清理条件 |
| --- | --- |
| logs/、cache/ | 无需保留旧日志/缓存即可清理；先确认下载/更新任务已经结束。 |
| exports/、backups/ | 用户不需要旧导出/恢复材料时可清理；手动config.json备份必须已另存到这些目录之外。 |
| sync-state/ | 新结构切换成功且不再使用旧根后可清理；这是重置旧同步基线/范围状态，不在旧版继续同步时随意清理。 |
| manager-state/ | 新版本已按新路径独立启动、所需JSON已备份/恢复后可清理；新版不读取其中的定位、运行包来源或凭据。 |
| opencodex-home/ | 已备份所需JSON及必要依赖、新HOME恢复验证成功、原服务停止后才可清理；旧根未完成替换时保留。 |
| runtime/ | 旧版程序目录：旧版完全退出、新版本安装及程序入口验证独立可用后，可按旧版卸载范围清理；不能在新版仍未安装验证前直接删除。 |
| 原有.codex、.opencodex、.opencodex-desktop | 不整根清理；分别包含客户端数据、原版登记/独立配置及原版入口。失效登记由原版生命周期处理，不为清理旧配置删全根。 |

旧根整体清理须在手动备份完成、旧版及服务退出、新版本按新路径安装并恢复渠道成功后进行；新版不得依赖其中的runtime或manager-state。不能仅凭目录名判断拥有权，安装旁data仍按实际旧版所属范围清理。旧注册表选择不作为新版输入，无须为新版运行去人工修复旧指针。原生客户端/独立OpenCodex及其它用户数据不在清理范围内。
## 6. 当前状态与待验证

后续实施须完成以下三项检查，当前均为待实现/待验证，不代表已经解决：

- [ ] **新版本多用户端口与服务归属**：不同Windows账户允许同时打开管理器，启动锁/数据锁/IPC按用户隔离，同SID含多会话保留单实例；不同用户使用独立HOME及凭据；端口占用按新版本/原版正常规则处理，不能误连或停止其它用户服务。这属于当前版本正常运行要求，不扩展为旧版兼容专项。按实际涉及的Windows SID/进程/端口行为做必要原生补验。
