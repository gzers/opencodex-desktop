## WP-75：渠道编辑没有加载已有 Key，反复要求输入且不能点击眼睛查看

用户原话：

> 首先，每次都要输入密钥才能修改是不对的，应该密钥一直在编辑界面，可以在编辑界面点击眼睛明文查看。ccswitch就是这样。

### 已确认原因

- `ChannelEditor.vue:22` 把 `apiKey` 初始化为空；`:30` 离开页面清空；`:37` 获取清单成功后又清空。没有进入编辑器时加载当前渠道已有 Key 的流程。
- 同文件 `:97` 永远使用 `type="password"`，没有眼睛控件；是否“已配置”只看管理器的 `credentialRef`，不能代表官方配置是否已有 Key。
- 同文件 `:34` 的获取清单请求没有传 `providerId`；`commands/model_config.rs:338` 的 `model_channel_discover` 没有注入官方配置根。虽然测速命令已接入官方 Key 回落，这个编辑/获取清单入口仍未接入，已有官方 Key 的渠道也可能要求用户重填。
- `upstream.rs:209` 的公开快照会拒绝秘密字段，`provider_fields.rs:151` 将 `apiKey` 列为私有字段。当前“只传已配置状态、不回显保存的 Key”的实现与本轮编辑需求有差距。不能把公开快照当作编辑器已经加载 Key 的证据。

### 用户已明确的修复口径

1. 打开已有渠道编辑界面，应带出该渠道当前保存的 Key，默认掩码；点击眼睛可查看明文，再次点击恢复掩码。
2. 修改普通字段、获取模型清单和检测节点应复用已有凭据，不因管理器缺少 `credentialRef` 而要求再次输入。
3. Key 的加载、查看和修改属于当前渠道编辑流程；区分“保持原值 / 明确替换 / 明确清空”，不能把空输入自动解释为删除，也不能必须联网获取模型成功才允许保存 Key。
4. 沿用官方配置与真实凭据来源；若来源是环境变量、钥匙串引用或 Key 池，显示真实来源和可用状态，不能把“未读到明文”显示成“未配置”。具体引用显示方式留待实施核对。

验收：已有 Key 的渠道重复打开、编辑并保存不要求重填；眼睛切换正确；修改其它字段保留原 Key；新增和替换后再次打开能读取保存值。本条只登记 CC Switch 的用户参考，不声称已审计该产品实现。明文只供用户在当前编辑器查看，不写入问题记录、截图证据或操作日志。

## WP-76：保存结果占据页面底部，重启失败并残留客户端核对提示

用户原话：

> 你这个重启位置变成了底部的莫名其妙占位弹窗，样式bug。还有实际上无法重启codex，只能手动，但是面板的opencodex支持，分析源码看看。

### 已确认的界面与旧逻辑残留

- `ChannelsView.vue:325` 把 `SaveResultNotice` 直接放在渠道表格后面，位于页面正文。`SaveResultNotice.vue:54` 输出普通 section，`:82` 仅有卡片样式，没有进入全局通知宿主；因此列表底部出现一块占位卡，与截图一致。
- `App.vue:68` 已有统一 `.notif-layer`，里面是通知中心、Toast 与任务宿主。保存结果没有复用它，页面底部和右上角同时各有一份保存反馈。
- `commands/model_config.rs:254` 仍将 `committed` 保存结果投影为 `OperationPhase::Review`；`app/feedback/tasks.ts:30` 仍显示“已写入；客户端结果请在核对入口查看”。该入口已被删除，旧文案和旧阶段映射没有清理干净。
- `tasks.ts:21` 的终态仅包含 succeeded / failed / stopped，review 不受 8 秒自动收起控制；保存成功卡因此仍可能常驻，与“稍后即结束”的口径冲突。

### 重启结果判定缺陷

`cache_refresh.rs:84` 只以进程退出码判成功，`:88` 直接生成“Codex 已重启”，`:98` 使用 `restart_codex && success` 作为 `restarted`。这只能说明请求了重启且命令成功，不能说明实际执行过桌面端重启。即便缓存未变化或未触发重启动作，也可能被报告为“已重启”。非零退出时同样不能一概声称“缓存已重建”。

### 官方面板源码对比（OpenCodex 2.84.0）

| 动作 | 面板入口 | 实际行为 |
| --- | --- | --- |
| 同步模型 | `POST /api/sync`，无请求体 | `src/server/management/config-routes.ts:855` → `syncModelsToCodex(runtime?.port, config, null)`，同步目录/缓存并附带陈旧进程提示；这个路由本身不负责重启 |
| 重启 Codex | `POST /api/system/codex-restart`，无请求体 | `src/server/management/system-routes.ts:217` → `performCodexRestart()` → `runCodexRestart()` |
| 查询进程状态 | `GET /api/system/codex-app-server` | `readCodexAppServerState()`；为官方能力说明，不新增产品侧核对步骤 |

`src/codex/app-server-restart-service.ts:131` 先尝试同步，然后调用桌面重启；同步失败不会直接阻止桌面重启，也不要求缓存字节改变。`:38` 的桌面调用明确为 `restartCodexDesktopApp({allowHandoff:false})`，返回 attempted / stopped / surviving / relaunch / reason 等事实。macOS 最终由 `src/codex/desktop-app/darwin.ts:238` 执行退出并重新打开 Codex。

对比管理器所用 CLI：`src/cli/dispatch.ts:548` 只有 `completed && written` 才进入重启；缓存 unchanged、缺目录 missing_catalog、写锁 busy 等均可能正常返回 0（`:580`～`:613`）。即便进入重启，`handleRestartScopeAfterWrite()` 的重启结果也没有参与该命令退出码判定。

因此，用户点“立即重启”时，管理器可能因为缓存已一致而不重启，却显示成功。此前将“不重启属于幂等”写成此按钮的正常行为是不成立的：**“缓存刷新无需重写”不能替代“用户明确要求重启”**。官方面板的 HTTP 200 或顶层 success 也不能单独当成桌面已经重启，要读取实际 relaunch/reason。

### 分析版本与未验证边界

本机 `manager-state/runtime.json` 指向 managed 入口 `runtime/bin/ocx`，resolved_version 为 2.84.0；入口所指安装包 package.json 同为 2.84.0。上述关键官方源码与 `/tmp/ocx-official-2.84/` 分析副本的摘要一致。安装根 `.runtime-manifest.json` 仍写 2.78.0，记录为关联元数据差异；不能据此推断正在执行旧版本。

本轮未调用重启路由或 CLI，未采集反馈当时的命令返回、缓存变化和进程身份。已证实的是“按钮使用了条件性重启入口并错误报成功”；用户这一次命中缓存未变化、重启被跳过还是其它分支，仍待真实验收。

### 修复验收口径

保存结果复用既有通知样式与宿主，列表末尾不占位，详情与列表的保存使用同一出口；删除“客户端核对”文案和无效动作。保存成功给一次“已写入”及“立即重启 Codex / 稍后”；默认聚焦立即重启沿用此前裁决。点稍后即结束，不再要求事后确认状态。

重启优先参考或复用官方面板实际使用的能力，按真实返回结果说明是否重启；需要覆盖缓存改变和未改变两条路径。真实重启会影响当前 Codex，本轮未执行，后续验收应记录实际进程退出/重新启动及界面结果；这是实现验收，不新增产品中的客户端核对流程。

## WP-77：新增“N 个任务已收起·展开”入口，与既有铃铛重复

用户原话：

> 通知出现了另外定义的一个收起界面不应该，本身有铃铛的。

## WP-78：节点测速仍不可用，端点拼接和错误反馈未闭环

用户原话：

> 测速到现在还是用不了。

关联旧问题 WP-50、WP-72：本条为原问题在 0.2.13 的继续复现，不作为已修复后另起的无关问题；0.2.12/0.2.13 的单测和门禁通过不能等同用户节点已经可用。

### 已有观察与本轮分析边界

此前本轮只读 HTTP 探测观察到：用户 GZGG-NewApi 节点基址为根 URL，协议 anthropic；请求 `/models` 返回 HTTP 200 + text/html（站点首页），请求 `/v1/models` 返回 HTTP 200 + application/json 模型数组。探测没有写配置或调用生成接口；本文不记录 Key、认证头实值或完整模型响应。

不能据此把基址判为用户填错，应按官方协议路径规则处理根地址和带版本地址。更不能由 HTTP 200 单独断言“测速成功”。同样，这一条路径不足以证明所有失败渠道均为同一原因。

### 已确认的源码失败链

1. `tauri/src/modules/model_config/discovery.rs:188` 对 anthropic、OpenAI Chat 和 Responses 都直接追加 `/models`。根 URL 生成 `/models`，带 `/v1` 的基址才会生成 `/v1/models`，没有按这类根地址补齐路径的处理。官方 Anthropic 适配器 `src/adapters/anthropic.ts:396`～`:405` 已支持根地址、`/v1` 和 `/v1/messages` 的归一化，不能把管理器未适配根地址推给用户。
2. `discovery.rs:254` 先检查 HTTP 状态，`:278` 再执行 JSON 解析。返回 HTML 会被拒绝，不是误判为测速成功。此前“代码只检查 200”的说法不准确，应以本条为准。
3. HTML 触发的解析异常通过 `schema.rs:34` 变成 `invalid_document`；`measurements.rs:86` 只回传错误 code，丢掉原始原因分类信息。
4. `ui/src/features/models/useNodeMeasurements.ts:3`～`:4` 没有 `invalid_document` 映射，于是显示“检测未完成，请检查连接”。有效 JSON 缺少模型数组才是另一个 `discovery_shape` 错误。用户看到的泛化提示无法解释实际问题。

对本次节点，已有 HTTP 观察加上这条源码链支持“请求到首页、解析 HTML 失败”的判断；本轮没有重跑真实 IPC 检测。此前探测没有携带 `anthropic-version`，完整请求兼容性仍需实施验收，不能将那次 curl 当成完整软件链路通过。

### 认证与入口仍需一起收口

- 当前测速 hook 已传 `providerId`，命令层已注入 home。凭据优先级是本次输入 → 管理器 credentialRef → 官方配置 Key，不能再沿用旧结论“空输入/null ref 就必定匿名”。旧记录“25/26 必失败”不是本轮全量实测结论。
- `discovery_config.rs` 要求同源与协议一致后才取官方 Key；配置读取异常时可能回到无 Key 请求，credentialRef 失效时又会直接失败，均需提供清晰原因。
- 同一个详情页的“获取模型列表/确认连接与模型”仍缺 `providerId` 和 home 接线，见 WP-75。测速修一个分支不能算所有连接入口已经统一。
- `discovery.rs:182` 使用独立 no_proxy 客户端；需要代理的渠道尚未验证。DNS、TLS、代理、Key 池/引用、协议认证头差异也不能由本次单一节点的路径问题代替核验。

### 用户补充：自动判断并补全接口路径（2026-10-27）

> 我觉得测速要学会像ccswitch自动判断自动补链接路径，

纳入 WP-78 的明确要求：用户填写服务地址后，管理器根据协议、已有路径和实际响应自动找到模型清单端点，无需用户猜测或反复补写 `/v1`。CC Switch 是用户提出的行为参考，本轮未核验其源码，不把以下要求写成已经复用其实现。

| 输入情况 | 应有行为 |
| --- | --- |
| 根地址，如 `https://example.test` | 按所选协议补齐清单路径；OpenAI / Anthropic 兼容场景优先识别 `/v1/models` |
| 已带 `/v1` 或末尾斜杠 | 正确追加 `/models`，避免 `/v1/v1/models` 和重复斜杠 |
| 已填写完整模型清单地址 | 优先直接使用，不再次追加 `/models` |
| 带自定义代理前缀，如 `/proxy/v1` | 保留原有前缀，不擅自截回站点根路径 |
| 返回 HTML 首页或明确的路径不存在 | 自动尝试协议内的兼容候选路径，不能直接以笼统连接失败结束 |

自动补齐限于当前节点的同源地址，保留协议、域名和端口，不修改用户保存的服务基址。认证失败、DNS/TLS 错误和超时应按实际原因结束，避免靠无界重试路径掩盖问题。测速与获取模型列表共用路径处理；只有得到有效模型清单才报告成功，不能仅凭 HTTP 200。

验收新增：根地址、带版本地址、完整清单地址、自定义前缀和 HTML 首页回退都能自动处理；不重复追加、不破坏前缀、不改写原配置。至少复验本次 GZGG-NewApi 场景，记录最终请求路径、成功耗时和模型数量；不记录 Key。

### 修复验收口径

- 对官方支持的根地址和带版本基地址，生成正确清单路径，不要求用户反复改原配置来绕过管理器缺陷。
- 返回 HTML 首页、401/403、超时、DNS/TLS 失败、JSON 结构异常等，要显示可操作的具体原因；失败不能伪造毫秒数。
- 编辑页获取清单、详情节点检测、列表下拉检测的凭据和地址处理一致；不再出现某处可以、另一处要求重填或失败。
- 覆盖用户本次反馈渠道和多协议场景，验证成功耗时/数量；失败不改变原渠道、选择和当前节点。
