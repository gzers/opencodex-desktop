# Desktop用户配置目录结构设计

2026-11-06，Asia/Shanghai。用户提出用用户主目录下.opencodex-desktop替代com.gzers.opencodex.desktop目录名，并要求列出macOS/Windows完整结构。**本文件为最新目录设计稿，替代前序分析§7的“Windows LocalAppData、Mac保持Application Support”建议；未开发/迁移，未加入0.2.23六项范围。** 程序仍由Desktop托管并保留现有位置。下列路径中的产品目录实际统一拼写为.opencodex-desktop；不含空格。

## 1. 命名判断与所有权

两端统一使用用户主目录下的**.opencodex-desktop**作为易识别的用户入口，适合本项目面向开发工具的定位；这不代表“多数原生GUI软件都使用点目录”。Apple推荐用户Library/Application Support，Windows有AppData用户目录，VSCode用户设置也采用平台位置：[Apple规范](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/MacOSXDirectories/MacOSXDirectories.html)、[Windows已知目录](https://learn.microsoft.com/windows/win32/shell/knownfolderid)、[VSCode设置](https://code.visualstudio.com/docs/configure/settings)。因此选择点目录是本项目的跨平台路径体验决定，不伪称系统标准，也不要求更改应用bundle identifier/安装器标识。

还需避免已确认的命名重叠：原版OpenCodex Desktop已使用~/.opencodex-desktop/cli.json，并在macOS/Linux维护bin/ocx与path.sh。当前公开[cli_command.rs](https://github.com/lidge-jun/opencodex/blob/main/desktop/src-tauri/src/cli_command.rs)及[记录解析](https://github.com/lidge-jun/opencodex/blob/main/src/lib/desktop-cli-record.mjs)可核对，源摘要及边界见[查证记录](../../../../.adg/evidence/discussions/windows-multiuser-20261106/dot-home-layout-review.json)。

为保留用户建议的统一根名且不覆盖原版入口，本管理器**只拥有manager-location.json、manager-startup.lock和专属data子树**，不接管根目录全部文件。原版bin/cli.json/path.sh若存在就保持其拥有者，默认不创建/导入/删除它们。data已经存在且无法证明为本管理器结构时明确停止，不因同名目录自动纳管。程序不能以“配置根存在”判定它是另一产品已运行或已安装的充分证据，相关原版发现/卸载兼容需定向核对。

## 2. 两端根路径及程序位置

| 对象 | macOS | Windows |
| --- | --- | --- |
| 用户固定入口 | /Users/<用户>/.opencodex-desktop | C:\Users\<用户>\.opencodex-desktop（示例；实际由当前用户Profile解析） |
| 默认活动数据根 | ~/.opencodex-desktop/data | %USERPROFILE%\.opencodex-desktop\data |
| 默认OpenCodex实例HOME | ~/.opencodex-desktop/data/opencodex-home | %USERPROFILE%\.opencodex-desktop\data\opencodex-home |
| Desktop程序/资源 | 保留现有安装路径，常见/Applications/<实际应用名>.app | 保留实际安装路径，不固定盘符/Program Files/LocalPrograms |
| 托管OpenCodex运行包及入口 | 保留现有明确登记前缀/启动入口 | 保留现有明确登记前缀/启动入口 |
| 原版实例登记（原版拥有） | ~/.opencodex/ocx-homes/<hash>.json | %USERPROFILE%\.opencodex\ocx-homes\<hash>.json |
| Codex自身HOME（客户端拥有） | 原有CODEX_HOME或~/.codex | 原有CODEX_HOME或%USERPROFILE%\.codex |

符号~和%USERPROFILE%用于说明，实际实现通过当前OS用户目录API解析，不把字符串直接拼在工作目录，不从程序目录推断用户，也不更改系统HOME/USERPROFILE。macOS当前Application Support和Windows旧AppData/安装旁data作为已存在来源处理，不静默合并或丢弃。

## 3. macOS完整结构

~~~text
现有安装位置/
└── <实际Desktop应用>.app/          程序、资源及已有程序布局保持

现有明确托管位置/
└── <OpenCodex包体与启动入口>       如原runtime/opencodex、runtime/bin/ocx
                                   本次配置搬迁不移动、复制或重装程序

/Users/<用户>/
├── .opencodex-desktop/
│   ├── manager-location.json       本管理器启动定位：唯一活动数据根指针（新增设计）
│   ├── manager-startup.lock        固定入口协调锁（新增设计）
│   ├── data/                       默认活动数据根，本管理器私有
│   │   ├── manager-state/
│   │   │   ├── data-root.json      数据结构/HOME绑定元信息，迁移Schema后不养第二指针
│   │   │   ├── preferences.json    主题、缩放、显示等Desktop偏好
│   │   │   ├── runtime.json        原版程序来源、既有绝对前缀/入口及安装历史
│   │   │   ├── model-channel-layout.json  渠道布局/采用关系，非第二份渠道权威
│   │   │   ├── notifications.json  通知与任务记录
│   │   │   ├── sync-endpoints.json WebDAV连接及秘密引用
│   │   │   ├── transfer-choices.json 本机导入导出/同步范围偏好
│   │   │   ├── credentials/        已有本机秘密后端文件；私有权限，非备份明文公开区
│   │   │   ├── skills-store/       当前管理器已有受管Skill源
│   │   │   ├── config-uploads/     冻结上传计划，目录代次/端点绑定
│   │   │   ├── transfer-results/   原操作回执
│   │   │   ├── app.lock            当前活动根独占锁
│   │   │   └── …                  模版库、内容版本、事务等既有状态按原相对路径保留
│   │   ├── opencodex-home/         传给原版的OPENCODEX_HOME
│   │   │   ├── config.json         渠道、模型、路由与该实例port的唯一业务配置
│   │   │   ├── runtime-port.json   原版实际实例/PID/端口与身份材料，原版拥有
│   │   │   └── …                  原版账号、用量、运行日志/锁等依原版本定义
│   │   ├── backups/               保护备份与恢复材料
│   │   ├── logs/                  Desktop操作与诊断日志
│   │   ├── cache/                 可重建缓存/下载；不放唯一配置
│   │   ├── sync-state/            本机同步状态/索引（使用者沿当前实现）
│   │   └── exports/               默认导出；用户指定路径可外置
│   ├── cli.json                   若存在：原版Desktop拥有，禁止接管
│   ├── bin/ocx                    若存在：原版终端shim，不是本次搬入程序
│   └── path.sh                    若存在：原版PATH助手，禁止接管
├── .opencodex/
│   ├── ocx-homes/<hash>.json       原版登记：指向上述实际HOME，仅定位
│   └── config.json                若用户另用默认原版CLI，此文件独立，不自动合并
└── .codex/                        Codex客户端原有配置/授权/会话，不搬
~~~

这是目录职责全集和代表性已有文件，不是声称原版所有文件都列全。省略号中的状态按其真实写入者与清单保留，不为“结构漂亮”重命名全部文件。系统钥匙串/WebView/Cookie/OS偏好等按平台拥有者保留其用户目录；不能宣称所有系统文件也移入这个点目录。macOS敏感目录0700、文件0600，原系统安全存储保持；点目录不等于加密或安全边界。

## 4. Windows完整结构

~~~text
<实际Desktop安装位置>\
├── <Desktop.exe及资源>            程序位置不变
└── <已有OpenCodex程序前缀/入口>    若原来与安装布局相邻，继续保留原绑定
                                   不要求为所有用户复制程序包

<当前用户Profile>\
├── .opencodex-desktop\
│   ├── manager-location.json      本用户唯一活动数据根定位（新增设计）
│   ├── manager-startup.lock       本用户固定入口协调锁（新增设计）
│   ├── data\
│   │   ├── manager-state\
│   │   │   ├── data-root.json
│   │   │   ├── preferences.json
│   │   │   ├── runtime.json        仍指向既有程序位置；不是在data下新装另一份
│   │   │   ├── model-channel-layout.json
│   │   │   ├── notifications.json
│   │   │   ├── sync-endpoints.json
│   │   │   ├── transfer-choices.json
│   │   │   ├── credentials\       WebDAV等原后端的本用户DPAPI密文
│   │   │   ├── skills-store\
│   │   │   ├── config-uploads\
│   │   │   ├── transfer-results\
│   │   │   ├── app.lock
│   │   │   └── …
│   │   ├── opencodex-home\
│   │   │   ├── config.json         渠道/模型/路由/实例port，原版格式
│   │   │   ├── runtime-port.json   原版实例状态/身份材料
│   │   │   └── …
│   │   ├── backups\
│   │   ├── logs\
│   │   ├── cache\
│   │   ├── sync-state\
│   │   └── exports\
│   ├── cli.json                   若存在：原版Desktop记录，禁止接管
│   ├── bin\                      若存在：原版终端入口/发现路径，禁止接管
│   └── path.sh                    若存在：原版文件，不视为本管理器残留
├── .opencodex\
│   ├── ocx-homes\<hash>.json      原版登记上述实际HOME，不存全份渠道配置
~~~

Windows点开头名称不保证资源管理器隐藏，是否加隐藏属性是另一个显示决定，不把它当权限。用户根需适当NTFS ACL，DPAPI继续当前用户范围，不能复制另一SID密文来伪造支持。AppData中WebView2、系统更新/安装器、系统凭据等框架管理数据不强制移动；程序标识com.gzers.opencodex.desktop仍可用于Tauri/OS登记，与用户配置目录的可读名称无关。

## 5. 指针、程序及生命周期规则

1. **唯一启动定位。** 本用户固定入口manager-location.json只负责定位活动data根，记录本管理器拥有者/Schema与活动根，不存渠道/密钥。新增格式要正式定义版本/验证；未知/损坏不当空、不静默新建替代配置。manager-startup.lock协调该用户的选择/迁移，不锁住原版整个根。
2. **单一事实源。** 活动根manager-state/data-root.json继续承担结构和内部/外部HOME绑定；原active_data_root与新固定指针的Schema迁移需消除重复权威。旧HKCU StartupDataRootV1、旧数据根metadata仅作受控迁入来源；迁移后不双写两套定位。不实施前不能仅改一个文件假称迁好。
3. **程序不搬。** runtime.json中的程序前缀/入口显式保持原路径；启动、升级、卸载/恢复不再靠新data根推导另一份runtime。当前算法与此不符，需后续代码接线及版本化迁移，不在文档中假称已解耦。共享程序包更新需跨用户进程/权限协调，不能因为配置私有就放宽程序更新所有权。
4. **原版拥有实例。** 启动原版传OPENCODEX_HOME=<本用户活动data>/opencodex-home，系统HOME/USERPROFILE仍为当前用户；原版生成ocx-homes登记/实际端口与身份。用户明确外置HOME保持原位置，不另复制配置；不改写另一用户的原生Codex配置。
5. **端口独立核验。** 同机端口仍共享，复用原版config.port/公开启动能力及实际绑定。Desktop不能仅看到/healthz成功就复用，也不另养第二份端口权威。跨用户/原版及本管理器同时运行必须核对身份，不能误停其它实例；端口/PID/路径与本机秘密不作普通跨设备同步对象。
6. **自定义与测试。** 用户自定义活动根仍通过受控路径绑定，默认是固定根/data。不同用户明确选择同一活动根时应拒绝不可信共享或清楚说明不支持并发，不靠删除锁解决。开发/测试使用独立临时HOME/根/端口，不能扫描后接管日常点目录。
7. **卸载与清理。** 仅按本管理器拥有清单、用户意图及归属删除对应data内容/自己的定位文件；不得整删.opencodex-desktop根、原版bin/cli.json/path.sh、.opencodex登记区、.codex或其它用户数据。程序包卸载依真实来源单独处理，默认保留配置。目录重名不是拥有权证明。

## 6. 迁移设计与保护

新安装只在固定入口下创建自有定位/数据子树，先核对碰撞、真实用户、权限和既有原版文件。现有用户优先识别有效绑定：macOS Application Support、Windows用户AppData/安装旁data或已有自定义根。旧目录有内容时不能静默开一个空的新data让用户以为丢配置；只在用户采用迁移后复制属于该用户的配置/状态，校验摘要、权限和HOME/程序来源引用，提交定位并重启读回。旧目录保留，不自动删除；中断恢复清楚，失败保留原绑定。

程序/运行包保持原前缀，不把runtime包体跟配置复制；来源记录仍指向原前缀/入口。真正迁移的只是用户状态，不能复制已运行PID/端口/锁字节来伪造新服务；原版停机/重启再登记新HOME、维护生成文件和真实身份。新旧路径元数据/原版运行账本若引用旧HOME，需专项迁移或重建而不是全文件替换。Windows既有同SID的DPAPI材料可以在正确权限/验证下保留；不同SID不自动迁入。模型渠道/Key/账户是否归当前用户要先核实，不能把共享旧根无条件克隆到每位用户。

该专题一旦采用，会涉及Windows用户身份/路径/ACL/实例/程序来源解耦，属于[长期测试规范](../../../03-开发实施/测试与验收规范.md)的有条件原生补验范围。验证针对这些实际变化，不要求再做无关全量页面/玻璃专项。
