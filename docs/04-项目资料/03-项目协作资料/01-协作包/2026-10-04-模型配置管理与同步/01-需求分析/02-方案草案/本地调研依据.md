静态核对：此 UI 资源的 `D5r` 查询使用 `limit ?? 100`；模型选择相关调用未传更大 limit。请求为 `model/list`，`includeHidden:true`、`cursor:null`；选择处理只读取返回的 data，没有接着读取 nextCursor。另一个工具 guidance 查询会继续分页，不能将这条下拉行为推广成所有 Codex 调用的共同上限。

临时启动同版本 `codex app-server --listen stdio://`，只发送 initialize / initialized 与 model/list；没有 thread / turn 创建，没有目标模型生成或凭据输出，核对后结束进程。结果如下：

| 请求条件 | 返回条数 | hidden 数 | nextCursor |
|---|---:|---:|---|
| cursor=null，limit=100，includeHidden=true | 100 | 0 | `100` |
| cursor=100，limit=100，includeHidden=true | 8 | 0 | null |
| cursor=null，limit=1000，includeHidden=true | 108 | 0 | null |

因此 **当前本机下拉查询的有效读取上限是前 100 条，根因是只取第一页；model/list 与本地目录本身不是总共只能容纳 100 条**。本机 `opencodex-catalog.json` 与 `models_cache.json` 均有 108 项，visibility 均为 list，supported_in_api 均为 true；后 8 项完整存在于第二页，属于 GZGG-NewApi 下的 Kimi 与本地 Qwen / Gemma 模型。它可解释当前超过百项的缺失风险，不能重放用户此前每次“全选”的历史状态，也不能排除其他时点的可见性过滤。

本机 UI 还会按 hidden、登录 / 远端可用性及特例过滤，因此实际下拉可少于 100；“最多读 100”不意味着必然显示 100。计数以 catalog / model/list 的实际行数为准，不直接累加上游清单及 --fast 兼容行。前序观察 `/v1/models` 163 行含 55 个 --fast，而 catalog 108 项中以 Fast 元数据表达能力，不能把 163 当作本次分页输入。

OpenCodex 2.69.0 的另一层限制在 `src/providers/model-discovery-limits.ts`：共享保护值为响应体 4 MiB、最多解析 2,000 项、单模型 ID 最长 1,024；具体 adapter 可采用更小预算。`src/codex/catalog/provider-models.ts` 约 640～715 的失败分支使用旧缓存 / 配置回退；这是单次发现保护，不是全部渠道合计下拉上限。`model-visibility.ts` 约 262 还会排除 pending、disabled provider、disabledModels 及非空 selectedModels 白名单外项。subagent roster 的最多 5 项属于另一功能，不作为模型下拉数量依据。
