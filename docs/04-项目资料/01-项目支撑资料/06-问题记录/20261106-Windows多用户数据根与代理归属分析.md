# Windows多用户数据根与代理归属分析

2026-11-06，Asia/Shanghai。**分析及目录重新规划，未纳入0.2.23六项修复，尚未开发或迁移。** 本文末§7是用户补充“程序仍在Desktop”后的最新目录方案，前文记录原有实现事实。 用户先要求只讨论、不记录，随后明确允许“记录分析”；本文件承接该授权，不改0.2.23 DMD/IMP、长期默认目录策略或产品源码。这里的多用户指同一Windows机器不同登录账号/SID（含多RDP会话），不是应用内团队/多租户；不并入已有团队用量协作包。

## 1. 用户问题与结论

用户认为Desktop本来就是OpenCodex的桌面管理壳，若配置已在用户目录，是否继续沿用原版代理/端口策略即可；也询问目前OpenCodex配置是否已全部放进Desktop内部。

结论：**继续复用原版配置格式、监听/端口/鉴权/生命周期作为唯一代理执行者是合理方向；但当前壳层显式改变了OpenCodex HOME，且Windows数据根未保证默认按用户分开，不能仅因是套壳就宣称原版默认隔离自动成立。** 不需要因此再建一层模型HTTP代理、复制渠道配置或新增应用内账号系统。应先保证Desktop传给原版的实际HOME、端口配置、客户端目录和实例归属符合每用户边界，再验证原策略是否够用。

## 2. 代码核对：四种路径不能混为一谈

| 对象 | 实际规则与用途 |
| --- | --- |
| Desktop程序安装目录 | 软件可执行文件/资源所在位置；不是所有平台固定的配置根。Windows新默认数据根可能在旁边data，不等于软件包内固化配置。 |
| Desktop活动数据根 | lib.rs取平台app_data_dir后解析启动锚点/活动绑定；包含manager-state、日志、备份、同步状态和托管runtime等。 |

| OpenCodex可执行运行来源 | 显式可执行位置、托管安装或自动发现；托管默认活动根/runtime/opencodex及runtime/bin/ocx(.cmd)，可自定义。运行包位置与配置HOME独立。 |
| 当前用户HOME及Codex HOME | OS用户HOME仍按用户解析；与OPENCODEX_HOME不是同一变量。原版Codex通常用用户/.codex，也可有CODEX_HOME/用户实际绑定；不能说所有Codex配置和会话都已搬进Desktop。 |

ProcessRunner::spawn_environment使用原版start/stop/restart命令，显式env_clear后设置OPENCODEX_HOME=已解析内部/外部目录，再注入正确OS用户环境。原版getConfigDir优先OPENCODEX_HOME，只有未设置时才回用户/.opencodex。因此，Desktop运行原版时使用的是**同一原版配置文件，但路径被Desktop显式绑定**；渠道界面读写这份文件，不另立一份Desktop渠道权威。启动外部原版可执行也不会自动改用其默认HOME，除非Desktop的HOME绑定相应改变。

“OpenCodex全部在软件内部”需要更正为：默认托管运行包及内部配置HOME放在Desktop**活动数据目录**；不是嵌入安装包，也不是所有授权/Codex用户文件都移动了。用户明确外置HOME时，配置仍在外部。

## 3. 本机现状与Windows条件

本机macOS只读路径元数据确认：活动根为~/Library/Application Support/com.gzers.opencodex.desktop，模式inside，官方配置存在于其opencodex-home/config.json，托管入口为runtime/bin/ocx，用户Codex目录另为~/.codex。读取的绑定/runtime元数据前后字节一致，没有读取业务config.json原文或密钥；见[本机路径事实](../../../../.adg/evidence/discussions/windows-multiuser-20261106/local-path-facts.json)。这证明当前Mac路径关系，不证明Windows用户现场路径或版本。

Windows当前已采用的策略（核心数据与状态§1.2与代码bootstrap::default_anchor一致）：已有合法启动选择优先；没有选择时，已存在的旧用户AppData保留；否则尝试实际exe父目录/data。启动选择HKCU持久保存，启动选择信号量按SID隔离；但活动根/app.lock按实际数据根独占，并不因HKCU指针不同而把同一路径拆开。如果程序安装在各用户目录里，旁边data可能自然分开；若共用安装位置或明确选择同一个自定义根，不同SID仍会争用该根，具备权限时也可能顺序使用同一渠道内容。

截图文字同时用于启动选择信号量冲突和数据根文件锁冲突；只能确认发生独占准入冲突，不能确定是同用户重复启动、另一RDP会话、不同用户共用根或选择过程未结束。不能仅凭提示认定“全机器只能一个用户运行”。原图见[用户反馈](../../../../.adg/evidence/discussions/windows-multiuser-20261106/reported-data-root-lock.png)。

另外，WebDAV口令等Windows本地凭据采用当前用户DPAPI；把整个数据根共享并不能保证另一用户可解密。渠道配置、凭据引用、运行记录和安全后端应同属一个明确用户上下文，不能只移动一个偏好文件就宣称隔离完成。

## 4. 端口能否完全沿用原版

可以继续委托原版执行，但原版策略的前提必须由壳层正确提供：

- 独立OPENCODEX_HOME避免渠道、运行记录、账本/锁混用；各用户的实际客户端配置亦应独立。无需把配置强制搬回~/.opencodex，只要Desktop活动根是真正用户私有，内部HOME同样能成立。
- 同机TCP端口通常不按Windows账号或RDP会话隔离。原版默认requestedPort/config.port/10100；当前Desktop只传start子命令，没有自动按SID附加--port。配置目录分开后两个默认实例仍可能都请求10100。
- 核验已采用的2.97.0-post021.ownerquery.2归档：默认端口占用时会检查已有服务；已有OpenCodex或未知占用者会走拒绝/服务避让分支，不等于无条件自动换端口。独立实例须有独立HOME和合理配置端口。在线main策略已在前轮只读查看，与本批固定包分开标识。
- Desktop应呈现原版返回的实际端口/实例/就绪结果，端口已响应不是当前用户实例证明，不得误复用/误停其它用户代理。数据面鉴权、实例归属和启动服务身份需要一起验证，loopback地址不是用户安全边界。

可讨论的最小方向：Desktop负责用户级启动绑定和上下文，把端口选择结果落实到该用户的原版config/支持的启动参数；原版作为唯一监听/鉴权/代理/运行状态管理者。优先使用其公开配置/命令能力；若原版自动选择不足，再以真实两用户证据提出上游适配，不在壳中同时维护另一套代理或与原版不一致的运行端口权威。端口/PID/路径属于本机运行事实，不作为普通渠道配置跨设备复制。

## 7. 用户补充后的目录重新规划：程序留在Desktop，配置归当前用户

### 7.1 纠正ocx-homes含义

用户明确说的是“程序还是在Desktop”，并观察原版在用户.opencodex/ocx-homes下有文件，要求重新规划Desktop配置位置。本次核对固定维护归档的src/config/owner-registry.ts与在线原版实现：ocx-homes是跨HOME的运行实例登记目录，条目仅记录{home:实际路径,v:1}，不是完整渠道配置；真实权威仍为该home/config.json。登记条目也不是身份认证本身，还需相应受保护运行记录与服务核验。

本机只读看见1个小登记条目，它正指向Desktop现有内部opencodex-home，路径存在、读取前后字节不变。因此“用户目录中有ocx-homes条目”与“实际配置仍在Desktop数据根”可同时成立。不能据此把配置迁往ocx-homes，或用登记JSON充当渠道/认证配置。核对见[登记含义与本机布尔事实](../../../../.adg/evidence/discussions/windows-multiuser-20261106/owner-registry-clarification.json)。

### 7.2 目标边界与目录表（规划，未实施）

本次规划保持**Desktop程序/托管OpenCodex程序文件在现有已登记位置**，不因重新选配置根而自动移动、重装或复制程序。把“配置数据根”与“程序运行包来源/安装前缀”显式解耦。Windows默认配置由安装旁data改为当前用户LocalAppData是拟调整目标；macOS现有Application Support已是用户级，不需为了目录统一另搬一次。采用前不改核心当前事实。

| 内容 | Windows新默认规划 | macOS规划 | 说明 |
| --- | --- | --- | --- |
| Desktop程序/资源 | 现有安装位置 | 现有应用位置 | 不移动程序；多用户共用只读程序文件与私有用户状态分开。 |
| 托管OpenCodex运行包/启动入口 | 保留现有明确安装前缀与入口绑定 | 保留现有绑定 | 现有代码把默认runtime位置从活动根推导，必须改成显式来源关联；不能改配置根后自动寻找/初始化另一份runtime。若是共享可写运行包，升级所有权需另验。 |

| WebDAV等本机秘密 | 用户根内原安全后端/引用，Windows用户DPAPI；渠道授权依其当前后端 | 原安全后端 | 不共用其它SID密文/秘密，不把普通配置迁移变为可跨用户解密。 |

### 7.3 端口与身份继续交给原版，但上下文不能混用

Desktop启动原版时继续传入本用户实际OPENCODEX_HOME，OS HOME/USERPROFILE仍是当前用户，不能替换为Desktop数据根；这样原版登记落在本用户.opencodex/ocx-homes。config.port及实际运行记录仍由原版拥有，Desktop读取/展示并通过公开能力修改，不能另养第二份监听端口权威。若需用户实例的初次端口建议，先验证原版现有公开接口及占用策略，最终真实绑定结果为准。

不同Windows用户仍共享TCP监听空间，目录方案解决文件/锁/凭据归属，不单独解决10100冲突。需要两SID实测独立配置与明确端口、运行身份/令牌、各自Codex绑定、不能误停/复用其它用户服务。程序仍由Desktop托管与配置移到用户目录并不冲突；无需新增一层代理。

### 7.4 已有数据与程序绑定的接续要求

不通过直接改启动指针宣称完成：先识别当前锚点/活动根/外置HOME、运行前缀和OS所有者，保持读错/损坏/无权限不当空。用户明确选择后暂停相关写者，备份并按自有清单复制配置/状态，校验内容/权限及来源绑定，再提交本用户启动锚点并重启重绑定；旧数据保留。原版实例登记交原版生命周期更新，旧条目只作定位线索，不手删锁来绕过占用。

只迁移属于该用户的状态，不复制另一用户凭据、模型目录或进程记录来伪造隔离。若共享旧根没有可信归属，先明确选取导入内容，不能把整根自动分给每个新用户。程序前缀/入口保持原位置，迁移后来源记录仍指向它；程序更新/卸载不能误把另一用户状态当安装附属数据清理。安装旁data改为显式便携/兼容入口是否保留、默认新目录的具体迁移提示与自动化范围需后续采用，不在本次静默启用。
