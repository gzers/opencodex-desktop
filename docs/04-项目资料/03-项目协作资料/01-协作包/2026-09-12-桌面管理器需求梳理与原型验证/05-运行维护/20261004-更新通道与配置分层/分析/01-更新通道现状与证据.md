# 更新通道现状与证据

维护 ID：MNT-OPENCODEX-DESKTOP-20261004-02。登记日：2026-10-04。受影响可见版本 **0.1.1**；拟修复 **0.1.2**（未实施）。

本文件只回答“三条更新链路各自是否生效、为什么”，不复制源码正文，不预写执行结果。行号基于 2026-10-04 本机核对时的代码基线，后续修改可能位移。

## 1. 三条链路总览

| 链路 | 更新对象 | 当前是否生效 | 判定依据 |
|---|---|---|---|
| 官方 OpenCodex 版本卡片（桌面管理器内） | 只读展示 `ocx --version` | 不做远端查询 | 后端只执行受控 `ocx --version` |
| 桌面管理器自身自更新（Tauri Updater） | `OpenCodeX Desktop.app` | **不生效** | 端点、公钥、制品管线三处均为占位/缺失 |
| 官方面板内置更新器 | `@bitkyc08/opencodex` | 对标准全局安装生效，对托管/自定义前缀不安全 | 更新器按当前包路径推断安装方式，npm 分支不带 `--prefix` |

## 2. 官方 OpenCodex 版本卡片

- 前端 `loadOfficialProject()`（`apps/desktop/ui/src/stores/app.ts`）→ 后端命令 `official_project_facts`（`apps/desktop/tauri/src/commands/about.rs`）。
- 后端经受控来源 `OfficialCliVersionSource` 只执行 `ocx --version`（`apps/desktop/tauri/src/infrastructure/official_version_source.rs`），解析首行得出名称与版本。
- 结论：**不访问 npm registry、不比较远端版本**，“检查更新”实际语义是“重新读取本地版本”，“未发现 npm 全局安装”来自环境发现结果。属产品语义缺口（按钮文案与实际行为不一致），不是故障。

## 3. 桌面管理器自身自更新

**不生效**，三层原因叠加：

1. **端点占位**：`apps/desktop/tauri/tauri.conf.json` 中 `plugins.updater.endpoints` 仍为 `https://updates.example.invalid/opencodex-desktop/{stable,beta}.json`。`updater.check()` 连接失败，`commands/update.rs` 投影为“更新下载或连接失败；已保留当前版本”。
2. **公钥占位**：`pubkey` 值 Base64 解码为 `untrusted comment: signature from tauri-cli`，不是合法 minisign 公钥。即使端点可达且存在 `latest.json`，签名校验也不通过，`download_and_install` 不可达。
3. **无制品/签名管线**：`tauri.conf.json` 未启用 `bundle.createUpdaterArtifacts`；`.github/workflows/release.yml` 未注入 `TAURI_SIGNING_PRIVATE_KEY`。CI 不产出签名后的 `latest.json` / `.sig`，服务端没有可更新对象。

旁证：`IMP-OPENCODEX-DESKTOP-05` §469–474、`REL-OPENCODEX-DESKTOP-01` 第 146 行均记录“更新端点仍为占位”。`AC-09` 要求的 stable/beta 自更新在实现上尚未成立。

## 4. 官方面板内置更新器

面板“更新 opencodex”弹窗由官方代理后端驱动：

- 路由：`GET /api/update/check`、`GET /api/update/status`、`POST /api/update/run`（`src/server/management/route-registry.ts`、`config-routes.ts`）。
- `check`：`detectInstall()` 从当前运行包路径推断安装方式，再执行 `npm view @bitkyc08/opencodex@<tag> version`（`src/update/refresh-scheduler.ts` → `async-check.ts` → `registrySpawnTarget`）。
- `run`：`src/update/job.ts` 起 worker；npm 分支走事务式更新（stage → verify → swap → rollback，`src/update/transactional-install.mjs`）。
- `tag` 仅允许 `latest` / `preview`。本机实测 registry：`latest = 2.77.0`、`preview = 2.76.0-preview.20261003`，与弹窗“最新 2.77.0”一致。

## 5. 面板内更新对“托管 / 自定义前缀”的安全性

**不安全，语义错位**。官方更新器面向标准 npm / pnpm 全局安装：

- npm 分支：以**当前运行包的兄弟目录**为 scope。托管布局 `<数据根>/runtime/opencodex/node_modules/@bitkyc08/opencodex` 的包外侧直接是 `node_modules`、缺少 `lib/node_modules`，与其 staging / `sweepUpdateLeftovers` 的布局预期不符。
- npm 分支安装参数为 `install -g <pkg>@<tag>`，**不带 `--prefix`**，会落到它自己的全局前缀，而非托管前缀或管理里登记的 `custom` 前缀。
- pnpm 分支使用 pnpm 全局存储与 shim，自定义前缀基本失效。
- 不经过桌面管理器约束：不写 `.runtime-manifest.json`、不做离线包 / 代理 / `--ignore-scripts` 收敛，也不重启由桌面壳托管的代理。

桌面管理器的托管安装恰恰使用 `npm install --prefix <前缀>`（`apps/desktop/tauri/src/modules/runtime/install.rs`），前缀内直接是 `node_modules`；这与官方更新器假设的全局布局不同。因此**管理里登记的托管 / 自定义前缀，不能靠面板内更新器维护**。

## 6. 可核对路径

| 关注点 | 路径 |
|---|---|
| 更新端点 / 公钥 | `apps/desktop/tauri/tauri.conf.json` → `plugins.updater` |
| 更新命令层 | `apps/desktop/tauri/src/commands/update.rs` |
| 更新领域 / 端点死代码 | `apps/desktop/tauri/src/modules/update/mod.rs` |
| 官方版本来源 | `apps/desktop/tauri/src/infrastructure/official_version_source.rs` |
| 托管安装（`--prefix`） | `apps/desktop/tauri/src/modules/runtime/install.rs` |
| 官方更新器 | `@bitkyc08/opencodex/src/update/`、`src/server/management/config-routes.ts` |

## 7. 结论

三条链路彼此独立，不能合并。桌面自更新需补真实端点、真实公钥与签名制品管线；官方版本卡片需在“本地事实”与“远端查询”之间做产品选择；官方本体更新建议由桌面管理器复用自身受控安装能力完成，而不是代理官方更新器去改托管前缀。详见 [配置分层规划建议](02-配置分层规划建议.md) 与 [0.1.2-候选范围与待决策](03-0.1.2-候选范围与待决策.md)。
