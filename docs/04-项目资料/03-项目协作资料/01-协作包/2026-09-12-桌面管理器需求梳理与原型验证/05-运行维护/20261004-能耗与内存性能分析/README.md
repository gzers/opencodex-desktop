# 能耗与内存性能分析

- 维护记录：**MNT-OPENCODEX-DESKTOP-20261004-04**。
- 登记与观测日期：**2026-10-04**，Asia/Shanghai。
- 来源：用户反馈 macOS 将 OpenCodeX Desktop.app 列为“使用大量能耗”，要求分析能耗、内存与性能优化问题。
- 对象：本机安装的 **桌面管理器 0.1.3**、其托管的 **官方 OpenCodex 2.69.0**。
- 源码基线：桌面 `v0.1.3` 对应提交 **bd2b1b26cc7c2ade5cb243cd7c8f94560ebc9028**；官方部分以本机安装包源码与文件摘要核对。
- 状态：**历史原因分析完成；0.1.7 已实施并合入 main，回归、双平台构建和旧公钥验签通过，已公开并晋升稳定 Latest。** 原始观测保持 0.1.3 时点；新对照、限制与交付另见实施结果。不改变原协作包状态。

## 结论

当前应用存在明确的性能优化缺口，优先处理持续装饰动画和状态采集策略。

1. **概览页默认高档动画是本轮最有力的实测原因。** 两次高档采样中，桌面主进程、关联度高的 WebContent 与 GPU 辅助进程合计平均 CPU 为 **46.25% / 44.89%**；同一概览页切到中档静态后为 **0.27%**。结果与 SVG 动效和 WebGL 光场两套持续逐帧循环吻合。约 45% 相当于约 0.45 个 CPU 核的时间；不能解释为整机 45% 或耗电下降相同比例。
2. **隐藏到托盘后，后台降频判断存在实现缺陷。** 当前代码以“窗口集合为空”判断后台；关闭主窗口默认执行隐藏，窗口仍被注册，因而正常托盘驻留路径仍会按前台策略采集。
3. **状态监测调用了完整诊断链路。** 常态运行维度名义周期为 3 秒，每次全量采集启动 `ocx status --json`；官方命令包含运行环境、连接、健康、服务、shim、插件等诊断。连接维度的 15 秒周期没有把这些工作从 3 秒全量刷新中分离，其实际 CPU 占比还需单独剖析。
4. **本轮未证实内存泄漏。** 官方 Bun 服务 RSS 约 **1.24 GiB**，但 `vmmap` 的 physical footprint 为 **255.0M → 251.5M**（两次相隔约 28 分钟），峰值为 560.2M。计数器口径不同；255M 只代表该服务，不能当作整个应用的总内存。内嵌面板隐藏后保留 WebView，存在常驻内存取舍，需验证长期增长与回收。

原截图只提供系统能耗提示，未提供瓦数、CPU、内存数值或采样区间。本专题补充四组短时 CPU 对照和内存计数器；尚未测量真实功率、统一业务负载或长期 JS 堆趋势。

## 后续处理与运行边界

用户已明确：**前台概览的动画与视觉效果保持完整；离开概览或应用不在前台时停止装饰绘制，同时优化图形计算与渲染。** 不以默认中档、降低帧率、降低画质或缩短前台动画作为此次节能方案。概览路由已有卸载清理，实施时应保留并验证，补齐原生应用前后台状态的联动。

建议先处理 PERF-01～03：按页面与应用前台状态暂停绘制、减少不必要的图形计算与重复写入、降低后台检查频率并分离轻量状态与完整诊断；随后处理托盘桥接和面板驻留策略。用户要求**检查周期集中放入配置文件，暂不增加设置界面**；沿用现有 `runtime.defaults.json` 作为默认策略来源，具体技术与字段范围见 [优化方案](分析/03-优化建议与验证方案.md)。用户已同意面板闲置回收，明确要求**官方代理服务持续运行；回收对象仅为面板界面**。
