## 5. 依赖顺序与首批拆分

以下是**编码授权后的建议次序**，不是本轮执行项。字母后缀只是工作包内部子范围，不是新 WP 或 TASK ID。

### 5.1 避免底座之间互相等待

```text
IMP 确认 + 首批 TASK 授权
  → WP-01 公共接口/工程骨架
      ├→ WP-21 测试框架最小集
      ├→ WP-22 本地打包与 CI 最小集
      ├→ WP-18 单实例锁与命令边界基础（不开放 CLI）
      └→ WP-17A 锁/原子写原语
             → WP-03 备份与数据根
             → WP-17B 受控写入/回滚编排
```

WP-17A 不依赖备份服务；WP-17B 才依赖 WP-03。因此没有“先完成全部 WP-03 才能写 WP-17、又先完成全部 WP-17 才能写 WP-03”的循环。WP-03 的迁移部分还依赖 WP-04 的进程停止与恢复接口，可后置，不阻塞只读发现。

### 5.2 运行主线与后续能力

- P0 主线：WP-02 发现 → WP-04 启停 → WP-05 状态；WP-06 日志诊断通知、WP-10 菜单复用状态接口。WP-11 可在基础界面就位后并行。
- WP-07 依赖面板接口和 R-17 对应决定；WP-08、WP-09 依赖状态与备份服务，分别实现 restore 和升级引导，不互相依赖。
- P1：WP-13 公共加密/凭据与导出 → WP-14 导入；WP-15 Skills、WP-16 MCP 在写入引擎就绪后可按互斥写入范围并行，不强制互相等待。
- WP-18 CLI 业务命令按后端能力逐项接入；不能在导入/同步尚未实现时把相应命令判为通过。
- WP-12 自更新依赖 WP-22 的可测试更新包和 WP-04 的进程接管约定，不等最后发布时才验证。
- P2：WP-19 依赖公共加密/凭据、导入应用、写入事务与分域安全设计；同时遵守现有 P0 → P1 → P2 的交付顺序。

P2 的准入检查针对已经完成的 P1 依赖，不要求依赖 WP-19 的 CLI 同步命令提前通过。WP-18 的同步命令在 WP-19 就绪后完成联调；此前不能宣称 AC-10 全范围验收通过，避免形成阶段门与命令依赖的循环。

### 5.3 横向工作分成前后两段

- WP-20：实现前审查设计与验证用例；实现后执行相应安全检查。不能要求“功能实现验证已通过”作为实现该功能的前置条件。
- WP-21：写代码前只编制测试设计；授权后实现 fixture、fake runner、mock server 和测试代码，随业务 TASK 持续补充。
- WP-22：早期建立构建可行性与签名准备；后期执行制品验证、恢复检查及发布交接。实际签名、发布仍需对应授权。

首批 TASK 候选只覆盖工程骨架、公共接口、隔离测试基础、单实例约束、原子写原语和本地打包基础。其余 WP 保持规划粒度，按依赖满足情况滚动细化，避免一次生成大量空任务。

## 6. 验证设计与 TASK 候选标准

### 6.1 编码前设计，编码后执行

| 层次 | 写代码前准备什么 | 后续通过标准 |
|---|---|---|
| 文档核对 | 追踪矩阵、决策清单、依赖与写入范围 | 无悬空引用、依赖无环、没有未处置的阻塞 |
| 隔离逻辑验证 | 状态、加密、路径、幂等和各客户端配置的合成案例 | 授权后执行测试；正常/失败/取消/恢复实际结果符合预期 |
| 隔离系统集成 | 临时目录、fake 子进程、局部 mock 网络服务的设计 | 验证读写、并发和故障恢复；不碰用户家目录配置 |
| 目标环境验收 | 平台、测试账号、隔离数据根、权限、撤销和清理方案 | 另行授权后验证真实 CLI、Keychain、受控 WebDAV、GUI 和更新接管 |
| 发布验证 | 制品、签名、公证、安装升级回退和已知限制清单 | 证据齐备后才作支持声明；发布另行确认 |

mock 通过只能证明对应隔离场景通过，不能证明真实进程、钥匙串、系统权限或发布包可用。当前 IMP 的 mock 边界如需扩展，先完成批准与契约回写，再执行目标环境测试。

### 6.2 TASK 候选内容

候选不是正式 TASK。正式字段以治理机制支持的 schema 为准，不在协作包另建 TASK 状态副本。

每条候选至少写明：

- 所属 WP、范围、产物和前置依赖；
- 主责 FZ、REQ、AC、适用安全项；
- 允许/禁止写入路径及外部副作用；
- 实现检查、测试断言、证据位置、清理和回滚；
- `required_checks`，包含适用的稳定 `review:<scope>` 名称；
- 完成标准、集成要求和权威回写目标。

建议检查名为 `review:contract`、`review:tests`，并按范围添加 `review:security`、`review:platform`、`review:acceptance`。不适用的检查不机械套用。

后续 `RCP.checks` 必须匹配 required check 名称，记录 `passed/failed` 及具体证据；缺失或失败都阻塞关闭。证据至少能定位到被测提交、命令/方法、环境、预期与实际结果，不用“本地通过”代替。

### 6.3 并行与责任

规划中的责任角色是整理者、实现者、验证者和集成者；实际人选在 TASK 候选确认时指定，不在本轮创建其他 Codex 任务。

并行时先约定公共接口和互斥写入范围；适合时用独立 worktree。贡献者提交代码、测试和回执，集成者统一处理共享事实、报告构建物与索引。生产环境、全局同步及发布始终另行授权。

这些是准入检查清单，不另建一套评审生命周期，也不把交付阶段 P0/P1/P2 用作检查编号。

- 后续局部阻塞明确记录，未伪装成全功能已定稿。

**可以创建正式 TASK：**

- 用户确认相关 IMP 修订和首批范围；

- 由治理机制创建正式 TASK 并回填 IMP 关系，不自行伪造任务 ID。

**可以初始化工程及编码：**

- 首批正式 TASK 已获得执行授权；

- 只执行被授权的任务范围。此时才创建源码、测试代码、fixture 生成器和 CI 配置。

```text
实现/测试产物就绪

→ 必要评审、集成与回写完成
→ TASK 关闭
```

WP 和阶段不另设权威状态副本。交接材料包含：被测版本、产物位置、回执、AC 覆盖、失败恢复证据、已知限制和下一阶段环境要求。
