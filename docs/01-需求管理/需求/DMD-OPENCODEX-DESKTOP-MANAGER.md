> Revision 3，2026-09-14：确认需求分析结论（OQ-02 ~ OQ-09）并逐项回写——数据目录「引用优先、迁移可选」（§2.2）；托盘与原生菜单纳入 P0（§8，新增 AC-12，见 §9）；「品牌与许可边界」成为正式条款（新增 §11）；**Skills / MCP 扩展管理**正式纳入需求（新增 AC-11，见 §8 / §9 / §10）；确认**范围原则：本次原型全部功能均需实现**，P0/P1/P2 只表示顺序（§8）；安全评审阻塞项 B-1 ~ B-5 的结论写入 §5 / §8，并补入 AC-07 / AC-11。 此前 Revision 2，2026-09-12 根据用户确认回写；2026-09-12 确认软件名称为 **OpenCodeX-Desktop**；2026-09-13 追加 AC-09「应用自身版本更新」（见 §6 / §9）；2026-09-13 追加 AC-10「可选 CLI 控制面」（见 §8 / §9）。原始讨论与核验线索见 `COL-LOCAL-20260912-01`；本文件是稳定需求权威。

## 1. 问题与目标

OpenCodex 目前主要依赖命令行启动和观察。**OpenCodeX-Desktop** 的目标是提供本机发现、统一数据根、图形化启停、健康状态、日志入口、官方面板入口、Skills 与 MCP 扩展管理、加密配置迁移和 WebDAV 同步能力。

## 2. 已确认结论

### 2.1 技术选型

- 桌面壳确认采用 **Tauri v2 + Rust 后端 + Web 前端**。
- 第一阶段优先实现 macOS；跨平台能力在实现层预留抽象，但不作为 P0 验收范围。
- 复用官方 CLI 和 Web 面板，不自建 OpenCodex 代理核心。

### 2.2 安装与数据目录

- 不要求用户全局安装 OpenCodex，也不将 OpenCodeX-Desktop 定位为 npm 包管理器。
- 应用只负责**发现、展示、校验现有 npm 安装形态**，不执行 npm 安装、卸载、依赖解析或全局前缀管理。
- 支持**发现当前全局安装**并保持其可被识别、展示和作为兼容运行来源。
- 支持用户选择或切换 **`OPENCODEX_HOME`**。
- 数据目录采用**引用优先、迁移可选**：默认引用已有 `OPENCODEX_HOME` 所在位置、不搬动既有数据；仅在用户显式选择「迁移」时才执行移动。迁移前强制备份；目标不可写、空间不足或已有数据结构异常在检查阶段即阻断；迁移中断或校验失败必须自动回滚并保留原数据目录。
- 升级前必须支持备份。
- OpenCodeX-Desktop 所有自有产物统一放在一个可自定义的数据根中，并按用途划分；`OPENCODEX_HOME` 可以选择在统一数据根内，也可以由用户指定为独立路径。
- 不替代或包装官方 `ocx update` 的更新事务；只做升级前备份、状态检查、引导调用和结果展示。

### 2.3 启停模型

- P0 采用桌面壳直接托管 `ocx start` / `ocx stop` / `ocx restart` 子进程。
- 不安装或管理 launchd service。
- 不接管 `codex-shim`；如未来官方能力必须依赖 shim，再单独建需求确认。
- 启停结果、退出码、进程标识和最近错误需要进入状态面板。
- 对 `ocx status` 报告的 startup at-risk，提供检测与引导；涉及 restore 的动作必须由用户显式确认，不做自动覆盖式修复。

### 2.4 外部 provider 与 AiMaMi 共存

- AiMaMi 这类外部路由器接管 `~/.codex/config.toml` 的问题，**权威边界属于 OpenCodex CLI 本身**。
- OpenCodeX-Desktop 不得绕过、覆盖或直接改写外部托管配置。
- OpenCodeX-Desktop 负责识别外部 provider 接管、startup at-risk 等状态，并在 UI 中解释影响。
- 可以引导用户确认后调用官方 `restore`；引导文案必须说明这是官方修复路径，而不是桌面壳私有覆盖逻辑。
- OpenCodex CLI 自身的 provider 所有权、restore 行为或修复增强不在本桌面壳需求内。

## 3. 状态观测与日志

### 3.1 状态源

状态面板优先复用官方可机读能力：

- `ocx status --json`
- `ocx health`
- `ocx ready`
- `ocx doctor`

UI 状态至少区分：未发现、未运行、启动中、运行中、待就绪、异常、外部接管、at-risk、不可达。具体字段映射由 IMP 冻结。

### 3.2 展示内容

- 代理端口、PID / 进程标识、最近错误摘要。
- 安装路径、版本、`OPENCODEX_HOME`、Codex runtime 信息。
- startup 状态，包括 protection、rebootSafe、service/shim 是否缺失等可读摘要。
- 版本偏差或不可达状态需要给出明确原因与建议动作。

### 3.3 日志

- 默认展示服务日志；代理在线时可展示官方 observe 日志能力返回的内容。
- 代理离线时，状态面板必须说明相关日志能力不可用，不伪造空成功状态。
- 日志查看是只读操作。
- 不展示或记录 API key、token、完整 Authorization 头等敏感值。
- 提供打开日志文件或所在目录的能力，避免把大量日志直接塞进主界面。

## 4. 配置导出与导入

### 4.1 导出范围

- 导出内容按用户确认采用**全量配置**，包括 provider、路由、模型映射、启动相关设置和凭据。
- 敏感凭据不得以明文形式出现在导出文件的可读结构、仓库、日志或 UI 中。
- 导出文件必须是用户口令保护的加密容器；推荐在 IMP 中冻结强加密参数，例如 AES-256-GCM 与 Argon2id 派生口令。

### 4.2 导入流程

- 导入前校验容器格式、版本和完整性。
- 导入前自动备份当前配置。
- 导入前展示内容分类摘要，但敏感值必须掩码。
- 用户显式确认后才执行写入。
- 校验失败时中断，不部分写入。
- 不在仓库、日志、进程参数或界面中明文展示凭据。

## 5. WebDAV 同步

- 同步范围按用户确认采用**全量内容**，包括配置和敏感凭据。
- 所有包含敏感数据的对象必须先在客户端加密，再上传到 WebDAV。
- 同步默认采用冷同步：运行中不直接写关键文件，需要用户确认后才能执行覆盖。
- 执行覆盖前生成可恢复备份或快照。
- 检测到本地与远端冲突时提示用户确认；用户确认后允许覆盖，但必须保留被覆盖侧的可恢复备份。
- WebDAV 地址、账号、密码、加密口令等敏感配置不得写入仓库或日志。
- 与官方 `ocx connect` remote hub 的关系是并列能力：本需求不自建 hub，不替代官方 hub，只同步用户指定的 WebDAV 端点。
- **信任模型**：远端**一律视为不可信**。上传前必须客户端加密；完整性校验（哈希）只用于检测传输损坏与回放，**真实性由加密（AEAD）覆盖**，不得把哈希校验当作对恶意远端的防护。
- **TLS 行为**：WebDAV 连接必须校验证书；**校验失败默认拒绝**，且**不提供**"忽略证书"选项。

## 6. 升级边界

- 升级前必须生成备份。
- 应用可检测版本偏差并引导用户使用官方 `ocx update`。
- OpenCodeX-Desktop 不接管 npm、不管理依赖树、不修改 npm prefix、不重写官方更新事务。
- 升级结果需要展示成功、失败、备份位置和建议恢复动作。
- **应用自身更新（套壳）是独立能力**：桌面管理器提供自身的版本检查与更新，可区分 stable / beta 更新通道；下载包必须校验签名后才安装，安装完成后重启应用生效。
- 应用自更新**不接管、不替代**官方 `ocx update`；两套更新通道彼此独立，界面与文案必须让用户分清当前更新的是哪一个对象。
- 应用自更新重启**不得停止**由桌面壳托管的 OpenCodex 代理；重启后需重新接管并恢复状态展示。
- 应用自更新失败必须保留可回滚的上一版本，并展示失败原因与恢复建议；更新检查结果以**非阻塞通知**呈现，不打断当前操作。

## 7. 统一数据根

用户可选择一个自定义数据根，OpenCodeX-Desktop 按结构划分产物。具体目录名可在 IMP 冻结，但需求上必须包含：

| 区域 | 用途 |
|---|---|
| manager state | 桌面壳设置、数据根元信息、UI 偏好 |
| opencodex home | 可选承载 `OPENCODEX_HOME` |
| backups | 升级、导入、同步覆盖等动作前的备份 |
| logs | 桌面壳操作日志与旋转后的本地日志 |
| exports | 加密配置导出容器 |
| cache | 可丢弃缓存 |
| sync state | WebDAV 冲突记录、远端索引摘要、同步历史摘要 |

### 范围原则

- **本次原型中的全部功能都在实现范围内**，不做功能取舍。
- `P0` / `P1` / `P2` 与「可选」只表示**实现与交付顺序及前置依赖**，不表示"可以不做"。
- 因此需求分析阶段的「候选能力」档位不再使用；原型中出现的能力一律纳入需求，并需要对应的验收路径。
- 顺序依据：P0 为运行管理主线；P1 为需要安全评审的能力（配置迁移、扩展管理、CLI 控制面）；P2 为 WebDAV 同步。安全评审未完成不阻塞立项，但阻塞对应能力的实现。

### CLI 控制面（可选）

- 提供可选的 CLI 控制面，开关位于应用设置中，**默认关闭**；启用后才注册或暴露 CLI 入口，并明确提示开放的能力范围。
- CLI 是**运行中管理器实例的客户端**，经本地 IPC 委托实例执行，不产生独立的第二写入者；实例未运行时，只读命令应明确报错或降级，状态变更类命令不得绕过实例直接写状态。
- 命令能力限定在**管理器自有域**：发现与只读状态、`start/stop/restart`、数据根、备份、加密导出/导入、WebDAV 同步、自更新检查。
- **不提供**任何直接改写 OpenCodex 自身配置（provider、路由、模型映射）的写入通道；该类变更一律走官方 CLI。
- 变更层命令需运行实例与显式确认；破坏性操作必须带确认标志，其校验、备份与确认语义与 GUI 一致。
- 提供 `--json` 机读输出，并满足非交互与幂等要求，供脚本和 AI 代理使用。

### 扩展管理（Skills / MCP）

- **定位**：扩展管理是本期正式需求（P1），负责 Skills 与 MCP 两类**扩展配置**的图形化管理。
- **允许管理**：MCP 配置节点；Skills 目录同步。
- **禁止管理**：provider、路由、模型映射与 OpenCodex 核心运行配置。该类内容一律走官方 CLI，本产品不提供写入通道。
- **写入前提**：任何写入前必须生成可恢复备份；写入采用临时区 + 原子替换，避免部分写入；失败必须回滚。
- **可恢复性**：卸载 Skills、删除 MCP 配置等删除类操作必须可恢复，并明确恢复窗口。
- **凭据与敏感值**：环境变量默认掩码；不得在仓库、日志、界面或命令行参数中明文展示 token、API key 与环境变量值。
- **执行边界（MCP）**：MCP 的 `command` / `args` / `env` 具备执行本地程序的能力，必须展示执行边界并经用户显式确认，**不得静默执行任意本地程序**；不得把它作为普通表单字段处理。
- **多客户端**：扩展配置可落到多个客户端（如 Claude、Codex、Gemini、Grok、OpenCode、Hermes）；必须明确允许写入的客户端清单，并在多客户端配置不一致或外部应用改写后检测冲突、提示用户，不得静默覆盖。
- **与 OpenCodex 配置的关系**：写入 MCP 配置节点（含 `$CODEX_HOME/config.toml → mcp_servers`）属于**扩展配置**例外，不构成 provider / 路由 / 模型映射的写入通道；该例外的范围必须在 IMP 冻结并写入安全评审。
- **目标文件校验**：写入前必须确认目标配置是**普通文件**；若为符号链接、FIFO 或设备文件，或解析后路径越出预期根目录，必须拒绝写入并给出可读原因。
- **敏感值范围**：`env`、`args`、`headers` 一律视为**潜在敏感值**，默认掩码，且不得进入日志、错误信息或通知正文。
- **并发写入保护**：写入必须持有**跨进程文件锁**，并在写入前比对目标内容摘要；检测到外部改写时进入冲突待处理，不得覆盖（进程内锁仅作补充）。

## 10. 安全边界

- 任何凭据不得写入本仓库、Markdown、日志、命令行参数或未加密导出文件。
- P1 配置导出/导入和 P2 WebDAV 实施前必须完成安全评审。
- 敏感配置在 UI 中默认掩码，仅在明确输入口令或必要校验场景短暂解密。
- 备份必须可定位、可校验、可恢复；同步覆盖不得造成无法恢复的历史丢失。
- 可选 CLI 控制面默认关闭；启用后本地 IPC 必须做本机访问控制（受限文件权限与调用方校验），关闭时不得留下可被调用的监听端点。
- 扩展管理的写入范围严格限定在扩展配置（Skills 目录同步、MCP 配置节点）；provider、路由、模型映射与 OpenCodex 核心运行配置一律不可写。
- 扩展配置写入前必须备份，采用原子替换，失败可回滚；删除类操作必须可恢复。
- MCP 的 `command` / `args` / `env` 必须展示执行边界并经用户显式确认，不得静默执行任意本地程序。
- 环境变量与凭据默认掩码；扩展管理实施前必须完成安全评审，评审范围包含多客户端写入与冲突处理。
