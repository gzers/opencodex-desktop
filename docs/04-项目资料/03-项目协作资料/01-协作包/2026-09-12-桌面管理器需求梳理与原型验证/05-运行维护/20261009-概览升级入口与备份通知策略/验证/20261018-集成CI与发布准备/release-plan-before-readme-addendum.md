## 2. 最后一次发布确认的具体范围

全部独立准备和集成核验完成后，提交同一份决定：版本0.1.10、批准源码及仅发布说明产生的差异、Mac arm64/Windows x64资产、公开Release是否同时晋升stable、操作系统未签名策略、未验项/原失败的实际处置、回滚方案。未经明确接受的未验项仍是待处理项；不能把“允许发布”反推为自动化或原生用例passed。

确认后顺序：

1. main整合批准的产品源码，写入已审阅CHANGELOG版本段落和必要共享说明；核版本/源码/依赖锁/最终diff，提交推送，记录最终main SHA。源码/制品身份变化按实际影响验证，不重复无变化的Windows现场或资源采样。
2. 在该最终SHA创建v0.1.10并触发原Release流程，两个平台构建/更新签名资产进入草稿Release。核对实际checkout、版本、资产集合、摘要和三种更新签名，使用旧版信任公钥验证；构建失败只处置具体失败，不盲目重发。
3. 通过发布检查后执行原Publish Release流程。preserve-latest只公开并保留0.1.9的Latest；stable才投递0.1.10至稳定通道。两者须在最终决定中选定，不默认扩大通道授权，不创建beta来源制造验收条件。
4. 发布后匿名核固定版本与所选通道的latest.json、公开下载、版本/平台/资产摘要及签名；在批准的隔离方案验证更新/安装与实际版本回读，继续保护日常安装和真实数据。未获FZ50许可不执行官方包生命周期。
5. 观察并记录已批准的发布后运行范围和恢复场景。按实证/明确裁决回写REL/RUN、需求验收和TASK回执；仍有要求未证或用户待决定时保持进行中，不提前证书/关闭。
