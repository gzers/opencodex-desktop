# 组件与样式专题规划

日期：2026-10-15。项目：opencodex-desktop。产品：OpenCodex 桌面管理器。
状态：用户已授权目标模式执行P1～P5。专题入口、目录、基础/复合/平台样例与开发交接已落地，P4源码/DOM检查已执行，实屏评审仍待验。正式开发和生产验收随0.2.0实施；实际入口、逐节变化、检查与缺口见[交付与检查](组件与样式专题交付与检查.md)。

## 1. 结论与目标

当前前端是“已有公共底座、部分组件化、部分样式约定、页面仍有局部实现”，不能声称全部控件已标准化。推荐把旧玻璃实验专题扩展为统一的“组件与样式”专题，覆盖设计基础、基础控件、布局组合、复杂选择器、反馈与平台外壳，作为开发/设计共同查阅的入口。

沿用[唯一总原型](原型/index.html)。已新增非功能菜单项“组件与样式”，在同一活动原型目录维护，不新增第二套可编辑总原型。旧玻璃页保留历史引用和回退来源；当前规则以[UI规范](../../../02-项目核心/UI规范.md)为准，不恢复过期透明度/滤镜/强调色实验。

专题解决“标准是什么、有哪些尺寸/状态、哪里实现、哪些页面在用、什么还没验证”；正式dev gallery负责复用真实Vue组件验证落地。两者是设计样例与生产实现验收两个投影，不互相冒充。

### 2.2 组件族对照

| 组件族 | 正式前端当前情况 | 活动原型当前情况 | 计划处理 |
|---|---|---|---|
| Token / 主题 / 材质 / 档位 | tokens、materials、effects及app/appearance有集中实现 | glass-*与工具板已支持，但旧实验和局部覆盖并存 | 统一基础规范页和两主题×三档，标明采用状态 |
| 字体 / 图标 / 间距 / 圆角 / 层级 | Token已有，正文/代码字体有来源；不是每种都需一个Vue壳组件 | 文字/图标样例分散，旧glass仅部分 | 登记为设计基础，展示字号/字重/行高/长内容和图标/点击区域 |
| Button / Card / CardHeader | UiButton、UiCard、UiCardHeader已有并部分采用 | 有共用class，size类缺失/局部CSS仍有漂移 | 优先接入完整尺寸/状态矩阵，复用已有API |
| IconButton / Input / Textarea | 主要是class/原生元素，缺集中组件契约与完整预览 | 页面反复写DOM/CSS | 冻结尺寸/标签/错误/禁用等约定，按交互需要抽组件 |
| Checkbox / Radio / Switch / Slider | 原生语义结合CSS，多处页内实现 | 有用例和特殊推理slider，常规/专用混合 | 分开基础表单与复合控件，覆盖键盘/半选/未知状态 |
| Select / Menu / Popover | UiSelectMenu已有浮层/定位/键盘能力，尚不是所有Select/Menu的完整通用封装 | select-component和action-menu集中，复杂popover另有 | 按现有实现补一致契约和样例，不按有一个浮层就称全族完成 |
| Tabs / 锚点导航 / Sticky | 通用class和页面控制逻辑；主Tab统一适配已纳入0.2.0 | sticky-tabs组件已有，详情双层测量分域 | 专题给长页/窄窗/两层避让的互动场景 |
| Badge / Tag / Status | class约定为主 | 业务状态标签丰富但组件/语义分散 | 严重性/业务状态/计数分开示例，避免一个万能状态组件 |
| 表格 / 树表 / 长列表 | UiTreeTable有数据/键盘/焦点行为；普通表格仍按页面 | tree-table样式/结构与各业务表混合 | 数据展示族统一规范，保留业务列/排序职责 |
| SettingRow / Stack / Inline / Markdown | 两个patterns、两个layout已有；Markdown有受限渲染边界 | 相似布局由各页重复 | 把布局/组合/富文本纳入目录，复用生产组件 |
| Dialog / Modal | AppModal是壳层store适配组件，非纯基础Dialog | 共用openModal但各页正文/焦点策略扩展 | 规划纯Dialog外观/交互与壳层适配拆开，演示确认/详情/表单 |
| Toast / TaskProgress / Notification | Host与store/路由耦合，NotificationItem本身props/events；正式事件注册已存在 | 有统一宿主但部分旁路/专用桥接待收口 | 展示组件与事件机制分别登记；按WP-08计划接通 |
| 渠道模型选择器 | 固定main尚无对应生产组件 | model-picker打样页/业务弹窗共用实现，支持推理/Fast | 合入复合组件章节，复用现实现，不复制DOM |
| 节点选择与检测 | 正式模型配置域仍待实施 | 模型页内已有节点/逐项及批量检测mock | 列为领域复合样例，地址/凭据适配不进基础UI |
| 空态 / 加载 / 错误 / 进度 / 步骤 | 在多业务/宿主/模板中存在，尚非全族标准化 | 有大量业务内状态和结果页 | 形成通用组合规范；表单与业务详情继续归原流程 |
| 托盘 / Windows外壳 | 属平台/应用层，真实caption/tray有原生限制 | 专题mock已存在，但会改全局body或窗口模式 | 登记平台样例，抽展示适配；浏览器模拟不代表原生验收 |

标准化要分别判断“有规格、公共实现存在、业务已采用、验证通过”。纯原生控件配统一Token/契约也能标准化，不为了组件数量把每个span/input再包一层；复杂交互和共享外观需要可维护组件与样例。

## 3. 专题入口与页面布局

### 3.1 非功能菜单入口（必须交付）

推荐入口名“组件与样式”。放在已有外部原型工具板的“非功能菜单”，不加到产品业务菜单、设置页或发布软件导航中。路由为index.html#components，章节深链接如#components?section=buttons；已在非功能菜单接入。

渠道模型选择器、通知与反馈、托盘、Windows窗口及原型注释已归入专题章节。非功能菜单仅保留“组件与样式”，移除这些独立菜单入口；旧hash/query/截图路径保留兼容。原“0.1.10 维护”只是跳回概览并展开工具板，快捷入口同样取消，维护流程继续从概览/设置/诊断页的现有工具访问。原功能菜单仍返回各实际产品原型。

### 3.2 三个区域的责任

- 专题模式为独立全宽文档工作台，占满原型工具板左侧空间，不显示模拟软件窗口装饰。左侧约232px的品牌与组件目录、可搜索分组/组件名、sticky；点击只滚到锚点，手动滚动同步高亮，当前项可读且键盘可达。窄窗折叠为目录按钮，不压缩样例至不可读。
- 右侧是连续的完整样例正文，沿一个主滚动容器。不切换成“点一个组件才显示一小张卡”的碎片页；每节标题、组件完整示例、尺寸/状态对照、必要简短规则依次排列。长列表/内容允许合理局部滚动。详情/弹窗/选择器从本节实际触发，复用共享portal/通知宿主。
- 右侧仍用现有原型工具板。全局评审环境集中一次取值，章节专用参数随当前锚点显示；不在每个样例旁重复放主题/特效开关。

导航链接必须保留#components路由，不能把#buttons当成产品路由。刷新/返回/前进应恢复章节和环境；环境切换不重置组件输入、勾选或当前滚动。进入/离开专题保留原功能原型草稿，不把示例操作传给真实业务。

## 4. 工具板与效果矩阵

公共条件至少包括：亮/暗主题、高/中/低特效、100%基准与50/150/200%缩放、占满可用空间/最大1180px/最大900px样例内容宽度（生产窗口验收仍覆盖1180×760与900×600）、长文案/正常文案，以及按组件支持声明显示size/density。主题和效果是全局正交开关。

- 高：当前确认的玻璃/投影与允许持续运动；中：同一玻璃，停止装饰性持续运动；低：受控组件/通知/浮层实底并关闭环境光，功能和状态保留。沿当前UI规范，不继承旧glass页按系统减少动态自动降档的旧规则。
- 不恢复旧玻璃页的冷色滤镜、背衬颜色、透明度、强调浓度、主按钮玻璃等未采用实验参数。需要追溯时标为历史，不作为当前可配置产品能力。
- 字体/布局展示的是已有Token阶梯与实际fallback，不把组件样例的字号调节当新用户设置。窗口/文本缩放是测试条件，不把正文放大后裁字作为正常状态。
- 切换条件只更新当前原型评审状态/DEV fixture，刷新可按明示query恢复；不调用真实偏好持久化、IPC、下载、网络、系统通知或原生窗口操作。
- 每个组件显示可交互的默认/hover/active/focus-visible/disabled/loading/selected/error等适用状态。手动“强制展示态”与真实键盘/指针态分开标注，不把静态class当交互验证。
- 右侧通知展示应走同一宿主和demo事件注册；示例taskId唯一，切主题/章节不新增通知或覆盖其他任务。Demo重置只清本场景，不清业务通知。
- Windows示例最小化/关闭只影响样例子窗口，不隐藏组件专题本身；托盘菜单是浏览器形态预览，不能声称已验证系统菜单/Snap/DPI。

## 5. 组件登记与防偏离机制

已在活动原型建立component-catalog.js轻量组件目录，由目录生成分组导航、锚点和覆盖清单，不手工维护三份相互漂移的目录。原型样例与正式gallery按稳定ID建立映射，设计规格在docs，运行元数据和测试证据各归其责任；不复制规范正文作为第二事实源。

最小登记字段：稳定ID/名称/类别、规格来源、样例锚点与renderer、可选size/variant/density/state、适用主题/档位/平台、样例fixture、代码所属层/实现路径、业务消费者、owner/版本范围，以及“已登记/已有原型/已有正式组件/页面已采用/已验证”的独立状态。字段可用不可用要有原因，不显示假开关。

新增从未设计过的组件时：先查询目录 → 登记候选及所属层 → 用已有Token补样例/API与必要交互 → 核对亮暗/档位/尺寸/键盘 → 更新消费者映射。此流程是设计/开发约定，不额外增加逐项用户审批；业务唯一布局不强制冒充公共组件，仍须登记其组合规则或引用已有pattern。

使用建议随章节登记：每节具有默认规格、适用场景、切换条件、避免误用四项，标注已有规则/方案约定/建议待确认并链接依据。全部组件按所属章节引用这些说明；新增组件若无对应指导须先补齐。说明默认显示在样例下，采用状态仍单独折叠；不以新建议重写已确认规格。

组件目录与通知事件注册表分别维护：前者定义UI样例/实现，后者控制业务触发/投递/生命周期。通知示例引用合法事件，不能登记一个Toast组件就允许业务直接发通知。

检查分阶段执行：当前原型阶段核对目录ID/锚点唯一、原型renderer/fixture存在、样例与规格对应，并显式标出正式组件尚未实现或待迁移。生产引用覆盖、业务CSS护栏、依赖/构建/CI以及真实组件消费者检查随0.2.0开发落实。原生控件与专用平台/开发控件有明确例外，不用统计DOM标签数冒充覆盖。

## 6. 公共UI代码规划（仅规划，随0.2.0正式开发实施）

当前阶段只明确目标分类、职责边界、候选API和迁移顺序；正式组件实现、目录移动、DEV gallery扩展和业务替换均不在当前原型执行范围。

项目为Vue/Tauri应用，已有components/ui、layout、patterns；推荐保留这套分层，明确它们属于“公共UI类”，不为目录好看新增独立npm包或搬动全部features。候选目标结构：

    src/styles/                   # Token、语义表面、主题/档位配方
    src/components/ui/            # Button、Input、Switch、Select/Menu、Dialog等基础可交互控件
    src/components/layout/        # Stack、Inline、SplitPane/AnchorLayout等排列与滚动原语
    src/components/patterns/      # SettingRow、数据表/空态/步骤、纯展示复合选择器
    src/app/appearance/           # 主题、档位、缩放、可见性/原生外观策略
    src/app/feedback/              # 任务/Toast/Modal宿主与应用级发布/观察适配
    src/features/<domain>/        # 模型目录/能力/引用、通知实体、业务加载与提交
    src/dev/component-gallery/    # 直接引用正式组件、mock controller和交互场景

具体边界：

| 层 | 接受 / 负责 | 不承担的业务 |
|---|---|---|
| ui/layout | props/slots/emits、视觉/焦点/键盘、布局/可达性 | 不读业务store、Tauri、凭据或直接投递通知 |
| patterns | 同构数据/动作输入、设置行、步骤、复杂选择器视图 | 模型规则解析和实际执行/保存仍由业务adapter负责 |
| app hosts | 窗口级浮层、焦点/portal/层级、任务队列、通知投递适配 | 不把保存成功/业务恢复事实由标题猜出来 |
| features | 获取/解析业务数据、稳定引用、提交/核对和权限 | 不再重写公共Button/玻璃/字号规则 |
| platform/native | caption/tray/面板子WebView和原生菜单能力 | 不作为跨平台纯UI组件对所有环境声称可用 |
| dev gallery | 真实组件+无副作用fixture与场景工具 | 不读生产账户/真实设置，不进入正式构建 |

模型选择器建议纯视图留公共patterns、目录/有效能力/保存适配留features；NotificationItem可复用展示，但中心实体及publisher仍在通知域/应用层。AppModal/TaskProgressHost/ToastHost当前读store，按需要抽出纯视图后再移动宿主，不能只改目录名就宣布依赖标准化。具体文件重命名按逐项迁移计划执行，保留import兼容和现有消费者。

标准化不是所有控件都必须新建Vue文件：字体/间距/状态色归Token，轻量原生输入可共用契约与样式；复杂行为需要组件或hook。新公共API依真实消费者形成，避免一个包含所有业务store的万能UI目录。

## 7. 原型专题与生产gallery的交接关系

原型：扩展唯一总原型的专题路由和renderer模块；样例函数由业务弹窗及专题共同调用。现有model-picker已经具备此模式，可以沿用。托盘/Windows/通知当前全局模式先抽出fixture适配，不能用iframe嵌整套总原型或复制旧glass.html来充当组件实现。

后续0.2.0正式开发：扩展已有DEV gallery为相同目录/锚点和状态矩阵，直接import UiButton等正式组件；模块入口/dev mock controller不得调用真实IPC。业务Host用独立纯视图fixture或mock adapter展示，不能加载整个生产store导致启动网络/进程。正式build继续只含产品index，检查gallery/fixtures/非功能菜单未进入发布制品。 main不包含docs，正式组件和DEV代码不得在运行时依赖docs原型文件；两端通过稳定组件ID、规格引用和已检查映射对应，正式可执行样例仍从src组件导入。

历史迁移：旧glass.html/旧入口先保留固定证据和依赖；当前主入口改为组件专题后，旧链接转章节或标历史只读。保留旧model-picker、托盘、通知/Windows专题query/hash的兼容，不修改已保存截图或历史QA来伪造同版本通过。
