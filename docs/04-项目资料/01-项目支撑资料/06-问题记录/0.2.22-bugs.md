## S22-POST-01：保存时间未知与首次同步边界

### 发现证据

[用户原始截图](../../../../.adg/evidence/0.2.22/post-release-20261106/reported-sync-save-time/windows-sync-unknown-save-time.png)，字节摘要及静态复核见[证据记录](../../../../.adg/evidence/0.2.22/post-release-20261106/reported-sync-save-time/reported-evidence.json)。截图未展示实际软件版本/构建；按本轮发布后反馈登记0.2.22，不把截图当作已证明安装了该精确包。

### 已核对的触发规则

当前发行v0.2.22的sync_state.rs::compare_content不以“是否同步过”、上次同步记录或设备安装时间判断方向。顺序为：

| 所选内容状态 | 当前行为 |
| --- | --- |
| 云端无快照，本机有内容 | 上传，不因缺少历史同步记录被阻止。 |
| 本机所选内容确实为空，云端有所选内容 | 下载，先于保存时间判断。 |
| 所选内容完全相同 | 无需更新，不要求凭保存时间区分先后。 |
| 两端所选内容均非空且不同，两端时间可靠 | 按可靠内容保存时间选择上传/下载；同刻异内容另行阻止。 |
| 两端所选内容均非空且不同，任一侧时间不可靠 | 无法判定，禁止本次更新；本截图为两侧都未知的表现。 |

因此：不是仅历史版本会出现，也不是所有从未同步过的设备都会出现。新装设备若已带默认项、扫描已有客户端配置、导入对象或其它所选内容，只要这些内容缺少与当前摘要匹配的可靠保存凭据，也可能触发；“新安装软件”不等于“本机所选内容为空”。已经同步过的设备，若随后外部编辑/范围变化等使凭据不再覆盖当前所选内容，也可能触发。

file_objects.rs::object_fact要求所选原子全部具有匹配且可信的保存时间；任一未覆盖对象可使汇总时间变成“—”。content_versions.rs::observe对缺失/摘要不符的凭据给unknown；读取、升级、打包、同步操作时间不认证业务保存时间，无变化保存也不会补时间。因此不能建议单纯反复同步、重新安装或点一次无变化保存来保证消除本提示，也不能把第一次上传时间当作可靠内容时间。

### 尚待确认与后续边界

截图与静态代码尚不能确定该Windows设备的所选对象、是否含默认偏好/扫描存量/扩展资源、两端快照及具体缺失凭据。不能据此宣称已复现用户现场或确定是旧包兼容问题。

后续如进入修复，需单独讨论首次引导/历史内容建立可信基线的用户流程，并覆盖：全新空设备、全新但有默认/扫描内容、旧包迁入、新版正常保存后首次同步、曾同步后外部变化、只部分对象缺时间。保留未知时间不擅自覆盖保护，不能用统一填当前时间/上传时间/mtime绕过。此句为首次分析边界；2026-11-06用户随后明确采用同窗手动指定方向，并要求先做原型，替代此前“不新增强制选源”的本问题建议。软件仍未实施，下一修复版未定号，不读日常配置/Key、不请求真实WebDAV。


### 2026-11-06 用户采用与原型先行

用户提出：在同步弹窗增加可额外强制选择上传或下载的选项，计划先设计原型。该决定在本问题内替代此前未知时间只能停止、不能手动选源的限制；旧已发布需求/任务/证书不倒改，也不将原型实现计为软件修复。

- 沿唯一总原型 index.html#sync?tab=webdav 的原公共“同步预览”增加“同步方向”：自动判断（每次打开默认）、强制上传、强制下载；不新增第二层强制选择弹窗。
- 用户选方向后重新生成本次来源、变化清单和确认上传/下载按钮，不因点击选项直接执行。手动模式明确覆盖方向/所选范围，下载默认勾选更新前备份；取消/X/Escape不更新，关闭重开恢复自动。
- 手动方向不补造保存时间，也不绕过连接读取失败、预览后内容/范围/连接变化、凭据/口令、强ETag/CAS、并发保护；无来源内容阻止，内容相同无需写入。强制只替代本次按时间判新，不代表任意覆盖或全量镜像删除。
- 原型复用现有字号/模态/变化清单，纯内存示例，不访问日常配置、不发真实API/同步。实际实现和最终采用视觉仍待本轮原型评审。

## S22-POST-02：管理器已改名，Codex仍显示旧渠道名

用户明确补充：在0.2.22更新后修改。两张[原图与摘要](../../../../.adg/evidence/0.2.22/post-release-20261106/reported-channel-name/reported-evidence.json)分别显示管理器Krill、Codex选择器Krill-1/gpt-6.1-sol等；用户本次强调是渠道名称，不将其登记为模型ID修改问题。

正常代码链：ChannelEditor.editName → renameChannelLabel（合法/未占用名称应分配相应内部provider键）→ 单渠道保存事务迁移当前引用 → 明确重启准备中的运行服务reload/目录刷新 → Codex重启/读取当前目录。列表“未修改”仅说明该界面当前没有草稿，不能证明运行服务或Codex已采用新名。

另一个待复现分支：历史布局保存的显示名与raw provider键本来就可能分离（snapshot保留布局label）。若进入0.2.22时已经label=Krill、provider=Krill-1，再输入相同label会被renameChannelLabel视为无变化；后端provider_renames也跳过相同provider键。因此“历史显示名已改、运行键仍旧”与本轮全新改名测试不是同一个路径，值得单独验证；尚无用户实际配置证据，不能认定就是此次根因。

当前尚缺：真实保存后的raw provider键/name/模型目录引用是否更新、运行服务是否重载、是否已安装并实际使用2.97.0-post021.ownerquery.2、保存后服务及Codex是否完整重启。用户仅确认更新后修改，不能擅自补齐其他答案。后续只需脱敏状态/版本及受控读回，不要求提供Key，不先改日常配置，也不以旧Windows隔离通过代替用户现场排查。当前未修复、未新发版。

### 后续修复验收边界

按整个新增渠道向导核对两步，而不是只移动默认协议：标签/控件独立行、控件整行宽、间距/对齐、阶段标题与步骤、公共头部X/内容滚动/底部操作；认证/Key、地址说明、模型获取/加载/失败/空清单、搜索/选择/清除、手动精确ID与返回连接/取消/加入草稿均逐项对照，不能无说明替换能力。原型的“静态演示/勿填真实Key”属于原型说明，正式软件不照抄mock提示。

保留原13px标准字号与100%缩放语义，不依据单张截图盲目再调全局字号、材质或宽度。后续在macOS/Windows用实际弹窗验证常用及窄窗口、缩放、长模型ID、错误/加载态和控件不串行/不溢出；返回保留连接和已选模型的合理状态，取消不加入草稿、不持久写入，加入草稿与正式保存继续分开。共享组件若也用于复制/编辑连接，仅核对受影响消费者，不扩大到无关渠道详情重设计。当前仅登记，未修复、未测试软件、未发布。
