# 需求分析计划

## 1. 计划定位

本计划用于把 `DMD-OPENCODEX-DESKTOP-MANAGER` revision 2 转化为可评审、可追踪、可进入 IMP 的需求分析结论。

本阶段不是代码实施，也不创建生产配置或真实同步数据。所有原型和验证使用 mock 数据；不得读取、记录或展示真实凭据。

## 2. 分析目标

1. 把用户目标拆成可验证的用户场景、业务规则和系统边界。
2. 明确 P0、P1、P2 的范围、依赖、风险和进入条件。
3. 通过交互原型验证 P0 主流程和关键异常状态。
4. 冻结进入 IMP 所需的技术契约输入，而不是提前设计实现细节。
5. 建立需求到验收标准、原型、风险和后续任务的追踪关系。

## 3. 当前基线

### 已确认

- 技术方向：Tauri v2 + Rust 后端 + Web 前端。
- 第一阶段：macOS 优先；不把跨平台作为 P0 验收范围。
- 只发现、展示和校验现有 npm 安装，不管理 npm。
- 支持选择或切换 `OPENCODEX_HOME`，并维护可自定义的统一数据根。
- P0 直接托管 `ocx start / stop / restart` 子进程。
- 不安装或管理 launchd，不接管 `codex-shim`，不替代官方 `ocx update`。
- 检测外部 provider 接管和 startup at-risk，但不直接覆盖外部配置。
- P1 全量加密配置导出/导入；P2 全量加密 WebDAV 同步、冲突提示和覆盖前备份。

### 尚需分析冻结

- 统一数据根的目录布局、初始化、切换和迁移规则。
- 官方状态命令到 UI 状态枚举的字段映射。
- 子进程生命周期、超时、退出码、取消和异常恢复行为。
- 导出容器格式、口令派生、版本兼容和错误处理。
- WebDAV 同步清单、冲突判定、覆盖策略和备份保留规则。
- P0 验收环境、mock 数据和可重复测试方式。

## 5. 分析工作流

### 5.1 需求基线

- 从 DMD revision 2 提取目标、范围、非目标、AC 和安全边界。
- 为每条需求分配稳定编号，标记为 `confirmed`、`derived`、`open` 或 `blocked`。
- 对用户确认、现状观察、官方能力和设计假设分开记录。
- 对可能改变范围的内容建立问题清单，不直接当作事实写入 DMD。

### 5.2 场景分析

至少覆盖以下角色和场景：

- 首次启动：发现 `ocx`、展示版本和路径、选择数据根。
- 正常运行：启动、停止、重启、健康状态、端口和 PID 展示。
- 异常运行：未发现、启动失败、at-risk、外部 provider 接管、代理不可达。
- 日常观测：只读日志、脱敏、打开日志位置、打开官方 Web 面板。
- 配置迁移：导出、口令保护、校验、备份、导入、确认、失败恢复。
- WebDAV：加密、上传、远端变化、冲突、覆盖确认、恢复备份。
- 升级：升级前备份、官方更新引导、更新失败后的恢复建议。

每个场景都要记录前置条件、用户动作、系统响应、可见状态、失败处理和可恢复性。

### 5.3 原型验证

原型优先验证 P0，不连接真实 CLI、文件系统、WebDAV 或凭据：

- 安装发现与 `OPENCODEX_HOME` 选择。
- 统一数据根和产物分类展示。
- 启动、停止、重启及操作中状态。
- 健康、at-risk、外部接管和不可达状态。
- 最近错误摘要、日志入口和官方 Web 面板入口。
- 备份前确认、不可逆动作确认和失败恢复提示。

原型必须包含 loading、empty、error、selected、disabled、confirmation 和 success 状态。原型中的稳定交互规则才进入后续 IMP 输入；纯视觉探索不回写 DMD。

### 5.4 契约分析

分别冻结以下契约输入：

- 发现契约：可发现路径、版本、可执行文件校验和失败原因。
- 数据根契约：路径选择、目录创建、切换、已有数据保护和恢复。
- 进程契约：命令、参数、环境变量、工作目录、生命周期、超时和退出码。
- 状态契约：官方命令来源、刷新策略、状态优先级和 UI 映射。
- 日志契约：来源、脱敏、离线能力、大小限制和只读行为。
- 迁移契约：容器版本、完整性校验、加密参数、备份和回滚。
- 同步契约：对象清单、加密边界、版本/快照、冲突和覆盖前备份。

### 5.5 安全分析

- 标记路径、配置、日志、备份、导出文件、WebDAV 凭据和加密口令的数据敏感级别。
- 明确任何敏感值不得进入仓库、Markdown、日志、命令行参数或未加密文件。
- 分析丢失口令、损坏容器、部分写入、网络中断、远端被篡改和覆盖误操作。
- P1/P2 在安全评审未完成前只允许需求分析和 mock 原型，不进入真实实现。

### 5.6 验收设计

每条 AC 至少配套：

- 一个正常路径；
- 一个失败或不可达路径；
- 一个取消或用户拒绝路径；
- 一个恢复或回滚路径；
- 所需 mock 数据、环境前置条件和可观察结果。

验收不得只验证按钮是否可点击，必须验证状态、数据落点、备份可恢复性和敏感信息不泄露。

## 7. 评审门与进入 IMP 条件

### Gate A：范围门

- P0、P1、P2 和不包含项无冲突。
- 外部 provider、npm、launchd、`codex-shim` 和官方 update 的边界明确。

### Gate B：交互门

- P0 原型覆盖主要流程和异常状态。
- 所有不可逆或可能覆盖数据的操作都有确认、备份和结果反馈。

### Gate C：安全门

- P1/P2 的敏感数据流、加密边界和恢复路径完成安全评审。
- 没有把明文凭据带入产物、日志或测试数据。

### Gate D：验收门

- AC-01 至 AC-13 都能映射到场景、输入、动作和可观察结果。
- 验收环境和 mock 数据可重复构造。

### Gate E：移交门

- 未决事项已关闭，或明确记录为 IMP/TASK 阻塞项。
- 稳定需求已回写 DMD。
- IMP 输入至少包含目录布局、状态协议、进程模型、加密格式、同步规则和验收环境。

未通过 Gate E 前，不创建实施 TASK，不声称需求已完成。

## 8. 当前首批动作

1. 建立需求编号、术语表和开放问题清单。
2. 先完成 P0 场景图与交互原型。
3. 以原型暴露的状态和边界补齐 P0 契约输入。
4. 并行准备 P1/P2 安全评审材料，不提前实现真实迁移或同步。
5. 完成需求追踪和验收矩阵后，再召开一次需求评审。
6. 评审通过后回写 DMD，并创建 IMP。
