# 通知与反馈体系规划

> 状态：方案草案，已完成 HTML 结构审计，待原型修订与用户确认后回写项目核心与实施契约  
> 日期：2026-09-18  
> 适用范围：OpenCodeX-Desktop 桌面壳的操作反馈、异步通知、任务进度、日志和确认交互

## 1. 规划目的

当前界面中的 Toast、通知中心、Modal、操作进度、页面内错误和日志都在表达“发生了某件事”，但来源、持久性、触达方式和关闭条件没有统一定义，导致：

- 同一事件可能同时出现在 Toast、通知中心和日志中，重复打扰；
- 操作成功、后台状态变化、风险提醒和技术诊断混用同一种通知语义；
- 用户无法判断某条信息是否需要处理、是否可以忽略、是否会自动消失；
- 面板页、概览页和诊断中心的反馈入口不完全一致。

本规划先建立统一的事件分层和展示规则，后续再拆分领域实体、状态字段、前端组件与验收场景。

## 2. 当前展示渠道

| 当前渠道 | 现有职责 | 主要问题 |
|---|---|---|
| Toast | `showToast()` 展示操作成功、失败、复制、刷新等结果 | 时效固定，无法表达进度和后续动作 |
| 顶部通知中心 | 展示未读通知，支持分类、已读、删除 | 当前 `NotificationItem` 未区分来源、展示渠道和处理状态 |
| 通知详情 Modal | 展示通知全文与「前往处理」 | 普通详情、确认弹窗、风险确认共用 Modal 语义 |
| 操作进度浮层 | 当前用于启动、停止、重启等长任务 | 尚未与通知中心、日志和终态统一 |
| 页面内状态 | 环境门禁、面板加载、运行状态、错误状态 | 需要明确哪些状态不应再额外弹 Toast |
| 日志历史 | 展示技术过程和诊断内容 | 与通知的事实来源和关联关系尚未定义清楚 |

## 3. 目标分类

### 3.1 操作反馈

用于反馈用户刚刚发起的短操作结果，不进入通知中心。

典型场景：

- 保存偏好成功；
- 复制命令成功；
- 删除或清理完成；
- 日志目录打开失败；
- 启动指令已发出。

展示规则：

- 渠道：全局 Toast；
- 位置：窗口右上角，避开原生控制区、标题栏和通知面板；
- 尺寸：宽度 `320–380px`，最多 3 行；
- 成功 / 信息：自动关闭约 3–4 秒；
- 失败：自动关闭约 6 秒；存在后续动作时提供一个轻量动作按钮；
- 不产生未读数量；
- 需要长期追溯时另写日志，但不自动复制成持久通知。

### 3.2 操作任务

用于持续时间不确定、需要等待后端终态的操作。

典型场景：

- 启动、停止、重启 OpenCodex；
- WebDAV 同步；
- 配置导入 / 导出；
- 应用更新；
- 扩展导入、批量写入或恢复。

展示规则：

- 渠道：任务进度卡，不使用阻断式 Modal；
- 位置：窗口右上角任务区，位于 Toast 下方；
- 尺寸：宽度 `360–420px`，单任务高度建议不超过 `240px`；
- 展示 spinner、当前阶段、当前状态和可用动作；
- 「关闭 / 后台运行」只隐藏任务卡，不取消后台任务；
- 后端进入成功、失败、取消或超时终态后关闭进行态；
- 成功终态转为一次操作反馈 Toast；
- 失败终态保留错误摘要，并视情况生成通知中心记录；
- 每个业务域默认只允许一个活动任务，重复触发应复用或拒绝。

### 3.3 操作性通知

用于用户暂时离开当前页面后仍需要知道，或需要后续处理的事件。

典型场景：

- OpenCodex 启动失败且可重试；
- WebDAV 发生冲突；
- 检测到外部 provider 接管；
- 应用更新可用；
- 数据目录切换需要重启；
- 扩展写入发现外部文件变更。

展示规则：

- 渠道：通知中心和通知历史；
- 位置：顶部铃铛统一入口；面板页也应可访问；
- 尺寸：通知面板宽度约 `360–400px`，最大高度约 `480–520px`；
- 有未读数量，但不通过持续 Toast 反复打扰；
- 点击后标记已读，并进入详情或处理动作；
- 未处理前不自动删除；
- 处理成功后标记已解决，可保留历史；
- 支持单条删除、全部已读、清理已读和按保留期清理。

### 3.4 日志型记录

用于记录技术事实、审计事实和排障细节，不作为用户提醒的替代品。

典型场景：

- `start` / `stop` / `restart` 指令开始、返回和终态；
- 状态从 `starting` 进入 `pending`、`running` 或失败；
- 同步阶段、冲突判定、备份和恢复结果；
- 外部命令退出码、错误分类和日志 ID；
- 通知生成时的关联事件。

展示规则：

- 渠道：诊断中心 → 日志历史；
- 不弹 Toast；
- 不进入通知未读数量；
- 追加时间、来源、操作 ID / 日志 ID和脱敏摘要；
- 日志是事实记录，不能通过“已读”改变；
- 按现有日志轮转和保留策略清理。

### 3.5 阻断式确认

用于高风险、不可逆或会覆盖数据的决策，不属于普通通知。

典型场景：

- 删除扩展；
- 清理日志或全部通知；
- 导入配置；
- 覆盖同步；
- restore 前确认；
- 可能修改数据目录的切换。

展示规则：

- 渠道：居中 Modal；
- 尺寸：普通 `480px`，复杂事实摘要 `680–720px`；
- 必须有明确的确认和取消动作；
- 不自动关闭；
- 可使用 Escape 取消，但高风险动作不能通过点击空白直接确认；
- 确认后转入操作任务或操作反馈。

### 3.6 页面内状态

用于表达当前页面或当前区域持续存在的状态，不应重复生成普通通知。

典型场景：

- 环境检查中、缺少 Node.js、缺少 OpenCodex；
- 面板加载中、面板不可达、面板加载超时；
- 日志读取失败；
- 设置字段校验失败；
- 当前运行状态为 `starting`、`pending`、`unreachable`。

展示规则：

- 渠道：对应页面或组件内部；
- 生命周期与问题条件绑定；
- 条件恢复后自动消失或恢复正常视图；
- 允许提供重试、打开日志或浏览器兜底等动作；
- 不因每次状态轮询重复生成 Toast 或持久通知。

## 4. 统一事件生命周期

统一采用以下事件链：

```text
事件发生
  ├─ 用户短操作 ─────────→ 操作反馈 Toast
  ├─ 长时间任务 ─────────→ 操作任务 → 成功/失败终态
  ├─ 需要后续处理 ───────→ 操作性通知 → 已读 → 已解决/删除
  ├─ 技术事实 ───────────→ 日志型记录
  ├─ 高风险决策 ─────────→ 阻断式确认 → 操作任务
  └─ 页面局部状态 ───────→ 页面内状态
```

同一业务事件允许同时产生：

- 一条日志型记录；
- 一个当前操作任务或操作反馈；
- 必要时一条操作性通知。

但不应同时产生多个同类提醒。例如，启动失败不能同时堆叠多条相同 Toast。

## 5. 事件示例

| 事件 | 主展示 | 辅助记录 | 不应出现 |
|---|---|---|---|
| 启动指令已发出 | 操作任务 | 日志 | 持久通知 |
| 启动成功 | 操作反馈 Toast | 日志 | 通知中心未读 |
| 启动失败且可重试 | 错误 Toast + 操作性通知 | 日志 | 阻断 Modal |
| 面板加载中 | 页面内状态 | 可选日志 | 通知中心 |
| 面板加载失败 | 页面内错误 + 可用动作 | 日志 | 重复 Toast 堆叠 |
| 同步进行中 | 操作任务 | 日志 | 普通 Toast |
| 同步冲突 | 操作性通知 | 日志 | 自动消失 Toast |
| 更新可用 | 操作性通知 | 日志 | 概览新增重复卡片 |
| 清理日志前 | 阻断式确认 | — | 直接执行 |
| 清理日志完成 | 操作反馈 Toast | 日志 | 持久未读通知 |

## 6. 候选事件字段

现有 `Notification` 实体保留 `level`、标题、正文、时间、已读和动作引用。以下字段作为后续扩展候选，当前不冻结：

| 字段 | 用途 |
|---|---|
| `event_type` | `operation_feedback`、`operation_task`、`attention`、`log`、`confirmation`、`inline_state` |
| `source` | `user_action`、`runtime`、`sync`、`update`、`diagnostic` |
| `operation_id` | 关联同一长任务的开始、过程和终态 |
| `dedupe_key` | 防止轮询或重试产生重复通知 |
| `resolved_at` | 记录问题何时被处理完成 |
| `expires_at` | 仅用于可过期的低优先级信息 |
| `surface` | 明确允许的展示渠道，避免调用方自行决定 |

## 7. 全局展示层规划

通知宿主应提升到应用壳层统一管理，避免各路由各自挂载：

- `App.vue` 挂载全局 Toast Host；
- `App.vue` 挂载全局 Task Host；
- 顶部铃铛与通知面板改为全局入口；
- `AppModal.vue` 只负责确认和详情，不负责普通状态提示；
- 日志由诊断中心读取，不直接复用通知列表；
- 面板、概览、设置和诊断中心共用同一套事件路由。

## 8. 候选关闭策略

| 类型 | 成功 | 失败 | 用户主动关闭 |
|---|---|---|---|
| 操作反馈 | 自动关闭 | 延长显示或手动关闭 | 允许 |
| 操作任务 | 进入成功终态并收口 | 保留错误摘要 | 只隐藏，不取消 |
| 操作性通知 | 标记已解决 | 保持未解决 | 允许删除，但不伪造已解决 |
| 日志型记录 | 不关闭 | 不关闭 | 只能按保留策略清理 |
| 阻断式确认 | 确认后关闭 | 保持并提示原因 | 取消关闭 |
| 页面内状态 | 条件恢复 | 持续显示 | 通过重试或离开页面结束 |

## 11. 当前原型 HTML 审计结果（2026-09-18）

本节基于当前 `原型/index.html` 的 HTML、CSS 和内联脚本审计，不包含截图视觉验收和真实键盘操作验收。结论用于交给后续对话修改原型。

### 11.1 已确认合理

- 已拆分六类反馈渠道：操作反馈、操作任务、操作性通知、日志型记录、阻断式确认、页面内状态。
- 通知中心与通知历史共用 `notifications` 数组，删除和已读操作具有同步基础。
- 通知专题可通过场景表演示触发时机、主展示、辅助记录、关闭条件和不应出现的渠道。
- 通知、任务卡和 Toast 已具备独立展示宿主，后续可以继续复用，不需要重新设计入口结构。

### 11.2 必须修订

| 优先级 | 问题 | 当前证据 | 修订要求 |
|---|---|---|---|
| P0 | 初始未读数量不一致 | 初始角标写死为 `3`；通知对象未显式设置 `read`；渲染时却按 `!item.read` 统计 | 所有通知显式设置 `read`；删除独立未读计数；角标只从同一数据源计算 |
| P0 | 任务卡没有接入正常操作 | `.task-host` 在非 `notif-mode` 时隐藏；概览启动动作只切换状态，不创建任务卡 | Task Host 提升为全局真实渠道；启动、停止、重启、同步等操作都能在正常路由显示任务 |
| P0 | 任务和 Toast 动作按钮不可操作 | `showTask()` 生成按钮但未绑定事件；Toast action 仅生成按钮文本 | 为“后台运行 / 取消观察 / 取消同步 / 改用文本框”等动作绑定行为；未实现时不要展示为可点击按钮 |
| P1 | 已读不等于已解决 | 当前只有 `read` 字段；场景表却使用“已读 → 已解决” | 区分 `read`、`resolved`、`deleted`；风险和冲突通知不能仅靠已读结束生命周期 |
| P1 | “清理全部通知”与文案冲突 | 文案承诺保留未确认动作摘要，但实现直接 `notifications=[]` | 清理全部默认只清理已解决通知；若包含未处理通知，必须改文案并增加二次确认 |
| P1 | Modal 关闭规则未实现完整 | 只绑定确认、取消、删除按钮，没有 Escape 和遮罩行为 | Escape 可取消；点击遮罩只允许取消，不得确认；打开时设置焦点并关闭后恢复焦点 |
| P1 | 通知条目键盘不可操作 | 使用 `div[role=button][tabindex=0]`，没有 Enter / Space 处理 | 优先改为真实 `<button>`；否则补齐键盘事件和焦点样式 |
| P1 | “查看日志”跳转不保证进入日志 Tab | `notificationJump()` 只调用 `setRoute('logs')`，不显式设置诊断 Tab | 跳转日志必须同时激活“日志历史”，跳转通知历史必须激活“通知历史” |

### 11.3 语义与演示层调整

- 场景表的“**不应出现**”建议改名为“**默认不自动出现**”，否则用户点击通知后打开详情 Modal 会与表格语义冲突。
- “通知专题”可以继续作为审计入口，但不应隐藏正常路由中的 Toast、任务卡和页面状态；专题只是场景切换器，不应成为唯一可见渠道。
- `operation_id`、`dedupe_key`、`resolved_at` 等字段当前只在规划表中出现，原型至少应通过 mock 数据表达去重和解决后的状态变化。
- `sync-done`、更新成功等低风险成功事件不应默认进入持久未读通知；优先使用 Toast 或页面状态。

### 11.4 后续对话修改顺序

2. 将任务宿主接入正常路由操作；

5. 修正清理、Modal、键盘和日志 Tab 跳转；

## 12. 通知背景确认（2026-09-19）

用户要求通知背景统一采用所附截图中的选中组合：第一排「轻磨砂 + 滤镜」，第二排「无色（中性）」。对应原型 `notifMaterial=glass`、`notifTint=off`，不是冷色滤镜。

- 本项已确认；通知中心面板、Toast 卡片、任务卡统一采用该组合，不再并列推荐纯透明、实底或冷色滤镜。
- 参数和适用边界已写入 `docs/02-项目核心/UI规范.md` §2.2，本草案只登记确认依据，不复制另一套参数。
- 原型入口说明、执行计划和 IMP 的候选说明同步修正；原型打样按钮及生产实现由执行对话核对后调整。
- 本次只确认背景材质，不代表通知位置、系统触达、关闭时间或其他待确认事项同时获批，也不代表实机视觉验收已完成。
