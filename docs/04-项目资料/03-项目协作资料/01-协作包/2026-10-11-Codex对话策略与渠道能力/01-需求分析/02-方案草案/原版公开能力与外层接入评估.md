日期：2026-10-16，Asia/Shanghai。授权：用户在重申不修改 OpenCodex 后要求“继续评估”。本轮完成公开入口源码核对和隔离纯函数检查，记录外层方案取舍；未请求 Krill、调用生产管理写接口、修改原版或启动网关开发。

后续用户已同意[渠道配置驱动与出站增强方向](../03-确认与评审/20261016-渠道配置驱动与互斥模式方向确认.md)。本文件保留当时的来源观察和隔离检查；下文“完整 Krill 会话前置分流”的推荐已被后续选择替代，不是当前实施方向。当前先验证原版转发后、到渠道前的出站位置，响应原样回传。

## 当前判断

**Ultrafast 的请求传递已有原版基础，适合先验证复用；Krill 新版上下文管理仍缺少原版路径的完整条件。**若要求每条请求始终经过原版 OpenCodex，当前观察没有证明仅靠公开配置可以满足全部目标。若允许外层对完整 Krill 能力会话建立独立通路，则有可评估的接入位置，但尚未验证协议、认证与客户端能力声明，不能宣称已可用。

本轮实现依据是本机 `@bitkyc08/opencodex` **2.84.0 包内源码**，不声称该版本就是当前运行服务或最新发布。初始版本差异及官方资料见[前序调研](官方核实与本机源码调研.md)。

## 已找到的公开入口与实际边界

| 项目 | 实际核对 | 判断 |
|---|---|---|
| Ultrafast 总开关 | CLI 能力描述列出 `ocx system settings --ultra-fast-tier <on|off>`；实现通过 `PUT /api/settings` 设置，随后 `GET /api/settings` 回读 | 有原版公开入口，可以由管理层集成；本轮未执行该写命令 |
| 渠道模型档位能力 | 管理 API 的 provider PATCH 支持 `modelSupportsServiceTier`，能按模型声明布尔能力 | 可以表达是否允许速度档，不能把布尔支持等同于 Ultrafast 已授予 |
| Ultrafast 模型目录 | `ultraFastTier` 只保留精确旧模型行中由操作者提供的 Ultrafast 声明，不自动产生；custom-models 的读取 / 创建字段未提供任意速度档声明入口 | 尚未找到本项目可采用的完整公开声明流程。客户端默认 `service_tier`、模型面板选择与目录发布应分别验证，不能私改代理生成文件补齐 |
| Ultrafast 请求决策 | 原版 Responses 可在合适的继承策略下保留调用者 `ultrafast`；强制 Fast 可改为 `priority`，强制默认可删除 | 请求层具备条件，但还需核对实际运行配置、最终序列化与 Krill 反馈 |
| 新版上下文能力声明 | routed 模型目录规范化明确删除 `supports_experimental_context` | 仅在前面转发 history/notes 不能自动使客户端启用能力；目录声明也是接入边界 |
| history/notes 转发 | 端点已有实现，目的地仍取规范官方 ChatGPT 上游，凭据与会话归属按官方账号路径处理 | 给 Krill 配普通 Responses 地址和 API Key，不足以使该独立调用跟随 Krill |
| 原生压缩 | 非官方目的地的触发请求可能先变成摘要请求；原生 compact 入口有目的地条件 | 出口层无法从摘要请求还原原生协议；后台调度 + Krill 模型摘要仍可另行验证，不能标成原生压缩 |

公开入口来自本机原版能力描述与管理路由源码，而非已完成运行时协商。所有入口在集成前需核对选定版本的实际可用性、鉴权和响应；不把内部函数当插件接口。

## 隔离检查及其证明范围

本轮使用包内附带 Bun，直接导入原版 `providers/fastwire.ts` 和 `codex/catalog/operator-tiers.ts` 的纯函数，在内存构造能力与档位输入；不运行代理，不加载真实渠道配置，不读取认证文件，不发送请求。共 **12 项通过，0 项失败**。

| 范围 | 观察 |
|---|---|
| Responses 档位 | 继承且允许传递时保留 `ultrafast`；强制 Fast 改为 `priority`；强制默认、能力不支持或 wire 禁止时删除 |
| 未分类渠道与 Chat wire | 未分类 Responses 按调用者传递权限处理；Chat wire 未 opt-in 时删除，明确允许后可保留 |
| 模型目录保留 | 开启 opt-in 可保留操作者声明；关闭会移除；没有操作者声明时不会凭空生成，模板中的声明也不算操作者授权 |

这证明原版决策函数的行为，**不证明**真实请求最终到达 Krill、上游接受档位、桌面面板显示入口、history/notes 可用或后台压缩并发正确。

检查源、结果记录和 12 份原版来源指纹保存在 [`.adg` 证据目录](../../../../../../../.adg/evidence/OCX-CHANNEL-CAPABILITIES-20261016-EXTERNAL-ASSESSMENT/)。源文件是在执行同一份内联脚本后保存，结果记录明确标注来自本聊天工具执行结果；不是正式验收回执或证书，没有重跑或声称完成线路测试。

## 外层位置比较

| 位置 | 能否补齐 | 主要限制 |
|---|---|---|
| 只增加 Desktop 设置 UI | 可管理原版已有公开能力，不能创造新协议 | 无法改变原版目录清理、上下文目的地和压缩转换行为 |
| OpenCodex 与 Krill 之间 | 可以代理实际已发出的请求；不作为完整原生能力方案 | 上下文调用可能在内部已被拒绝，压缩触发可能已被转换，出口收到的内容已不完整 |
| Codex 与 OpenCodex 之间，只分流 history/notes | 尚未证明，不建议作为首个联调候选 | 模型目录仍可能抹掉能力；正文与上下文操作服务身份未必一致；普通故障切换可能改变正文上游 |
| Codex 与 OpenCodex 之间，分流完整 Krill 能力会话 | 外层候选中较完整，适合作为需要全部能力时的验证对象 | 新增本地数据面、目录与身份管理；高级会话不再经过 OpenCodex，日志和用量需独立表达 |
| 等待上游原版支持 | 满足全部流量仍经原版的边界 | 可用时间和具体支持范围由上游决定，本项目不通过补丁填补 |

普通渠道可以继续使用原版 OpenCodex。外层候选仅承担明确选择的 Krill 能力会话，不复制整套渠道路由算法；但只要承担该流量，它就具有网关职责，应如实评估维护成本，不能称为零侵入即可生效的开关。

## 完整 Krill 通路的最小边界

若后续选择外层方案，应把它做成与原版独立的模块或进程，形态尚未选定，范围至少覆盖：

1. **明确选择与固定路由**：只有明确的 Krill 能力会话进入此路径；普通会话转发到原版。客户端选择器与上游模型 ID 要正确映射，不能将本地渠道前缀发送给不识别它的 Krill 服务。
2. **模型目录与客户端认证**：通过客户端正式配置接口提供能力声明，验证 history/notes 工具确实出现。Krill 教程中的个人令牌、账号校验和 `CODEX_AUTHAPI_BASE_URL` 要验证其作用；仅有模型 API Key 替换不足以证明客户端可以启用。不得伪造账号能力。
3. **协议完整性**：正文、所选压缩路径或 history/notes、SSE / 实际使用的 WebSocket 及必要协议元数据保持一致；不从已经转换后的摘要反向重建原生状态。
4. **自己的会话服务身份**：根据被上游接受的模型请求，关联调用者、根会话、目的地和对应凭据引用。history/notes 可能没有模型名，应沿已证明的会话关系处理，不再随机选渠道；不依赖 OpenCodex 私有内存归属表。
5. **重启与失败行为**：最小必要状态的保存 / 重新证明、凭据轮换、过期、取消及重复写入均须设计。不能因状态缺失就猜默认渠道，笔记追加也不能盲目重试。
6. **运维与更新边界**：独立监听端口、启动和退出、健康状态、最小脱敏日志、用量归属、版本探测和停用回退；不修改原版安装目录，不私读其密钥文件，不接管其内置路由状态。

两种上下文策略的互斥、客户端重启与配置作用域仍沿用[模式补充](../03-确认与评审/20261016-上下文管理补充与模式互斥.md)的待验证边界。将请求分流到不同渠道，不会自动使共享客户端配置变成会话级开关。

## 推荐顺序与未满足条件

建议先用原版公开配置验证 **Ultrafast 请求传递**及**后台调度 + 现有摘要路径**，分别报告可用范围。原生压缩和新版上下文管理仍按未贯通处理。

若用户要求立即覆盖全部能力，最值得进一步验证的是“原版普通通路 + 外层完整 Krill 通路”。下一阶段应先做独立、可丢弃的协议验证：模型目录识别与认证 → 正文 → history/notes 或原生压缩 → 后续工具调用与续聊 → 取消与重启 → 普通通路回归，再决定产品实现。它仍是候选，不代表用户已经接受高级会话绕开 OpenCodex 数据面。

如果所有会话必须保留 OpenCodex 的日志、用量、组合路由和故障切换，则该外层分流不满足要求；在原版公开能力不足时，应等待上游正式支持。

本轮没有运行真实 Krill 验证、修改配置、安装更新、创建新常驻服务或启动生产实现。
