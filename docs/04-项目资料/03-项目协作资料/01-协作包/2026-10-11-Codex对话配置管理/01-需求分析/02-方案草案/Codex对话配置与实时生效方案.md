2026-10-27 执行架构复核见[对话策略执行架构与 OpenCodex 扩展边界](../../../2026-10-16-渠道特殊能力与代理兼容/01-需求分析/02-方案草案/20261027-对话策略执行架构与OpenCodex扩展边界.md)。现已确认本机 2.84.0 的出站插件只在选路后提供 url / headers / transport，不足以承担通用作用域策略；原生子 Agent defaults 与角色装载顺序也需按实际执行器解释。当前全局页已迁到“设置 → 对话策略”，不再保留对话全局 Tab。

## 1. 需求与当前可行性

| 需求 | 已有依据 | 仍需补齐 |
|---|---|---|
| 全局命名模型 | Codex 保持命名行为；OpenCodex 有标题等 helper 的 shadow-call 路由 | 验证命名调用的关联与实际路由范围，不把 broad helper 路由承诺为仅影响标题 |
| 搜索模型自定义 | OpenCodex 2.78.0 有 webSearchSidecar backend / model / reasoning | 覆盖范围不含所有搜索；项目 / thread 路由和统一搜索回退链需执行端支持 |
| 子 Agent 自定义 | 有推荐 roster、指导默认值、原生默认同步、fallback、并发 / 指令等入口 | V1 / V2 差异；通用新角色、权限、独立 Fast 和各字段读取时机继续验证 |
| 全局、项目、thread 配置 | 本机 Codex 有原生 project/list 和 thread/list，稳定 ID 与项目筛选已实测 | 将对象身份关联到真实模型请求和父子 Agent，执行局部策略 |
| 保存后实时生效 | 同 app-server 的 thread/settings/update 可改变下一轮实际模型 / effort | 连接实际拥有该对话的实例；搜索、child 等分别按真实读取点展示 |

能力基线为 OpenCodex 2.78.0、Codex CLI 0.162.0-alpha.2（experimentalApi 开启）。其它版本由适配器报告支持情况，不因缺少单项能力禁用整个配置页。

## 2. 先明确执行边界

现有 Desktop 负责管理进程、官方页面及 shim，并未接管所有 Codex App / CLI 请求。新增配置页或本机策略文件不会自动改变外部对话。

本方案分为三部分：

1. **配置管理**：Desktop 编辑策略、保存作用域覆盖、展示继承与生效状态。
2. **对象发现**：通过目标 Codex 数据源读取项目、thread、归档和父子关系；发现缓存不作为另一份项目事实源。
3. **执行适配**：OpenCodex 请求路径执行代理策略；实际拥有 thread 的 Codex 实例执行其支持的会话设置和 Agent 创建配置。

全局 sidecar / shadow-call 等设置可复用现有管理 API。项目 / thread 覆盖需要 OpenCodex 的请求级策略接入或等效的明确上下文传递；目前没有本方案所需的通用作用域接口。原生 Agent 指令、权限和并发不能靠代理改模型字段代替。

新开 app-server 可以用于能力探测和读取持久化记录，**不等于连接已运行的桌面实例**。同一临时 CODEX_HOME 的双实例测试已证明：第二实例能读 thread，但不能直接 settings/update 第一个实例已加载的 thread。连接当前执行实例的方式是后续首要验证项。

若需要补 OpenCodex 能力，后续明确官方接口扩展或适配层的交付、版本兼容方式；不默认本仓 UI 修改就能完成全部目标。

## 3. 作用域、身份与配置事实源

### 3.1 继承语义

普通配置字段的优先级为：原生默认 → 全局协作设置 → 项目覆盖 → thread 覆盖 → 本轮显式值。各字段独立继承；模型等字段先合并，再由执行适配器转换成原生参数。

当前此分层用于搜索和子 Agent；命名模型是全局专用字段，只在全局配置页编辑。项目 / 对话策略不保存命名字段，也不通过导入将全局命名配置映射到局部对象。

- 选择“继承”：删除当前层覆盖，重新计算有效值。
- false：明确关闭，不是缺省；不得用真假值判断是否继承。
- 空列表：明确无候选 / 无条目（是否允许由字段定义），不是继承；列表整体替换，不暗中拼接。
- null：仅在该字段定义允许时代表一个显式值；不统一映射成“清除原生设置”。
- 强制 cap、模型可用性和原生权限限制在普通值合并后执行；本轮显式值不能绕过这些限制。

Codex 的 turn/start.model / effort 会留到后续轮次；传 null 也不恢复新的全局默认。撤销覆盖或结束一次性选择后，需要按最新策略重新解析、显式更新受影响的原生字段。更新按同一 thread 排序，不能恢复一个早已过时的旧快照覆盖用户新选择。

“仅本轮”只在能控制该 thread 下一轮开始或原生本身提供一次性字段时提供。接入点不足时显示真实持续范围，不能把持久会话参数包装成一次性参数。

### 3.2 对象身份与发现

对象键由宿主 / Codex 数据源身份及原生 projectId、threadId 组成。名称和 cwd 用于显示、搜索及旧版本的候选匹配，不替代稳定 ID。跨设备导入需要确认对应关系，不能按同名自动套用。

优先读取 project/list；thread/list 按 projectId 分页加载。不传 projectId 是全部，null 是未分配项目；归档 / 非归档分别查询。需要包含 child 时显式选择 sourceKinds，并使用原生 parentThreadId / sessionId 关系；sessionId 不是唯一 threadId。

child 创建需要保留父执行上下文与策略来源，并核对原生装载顺序。2026-10-27 已读 Codex 实现先处理显式 spawn 值、agents 默认及父值，再应用角色配置，角色可再次覆盖 model / effort；因此前稿“角色默认总低于项目 / thread 明确选择”的建议不能当作已有原生行为。第一阶段尊重原生优先级，展示期望值与最终采用，不通过额外出口改写制造另一套角色规则。角色自己的指令与权限不通过普通模型覆盖隐式放宽。

请求缺少可确认身份时只应用已确认的全局策略，显示“局部策略未匹配”。标题 helper / sidecar 是否携带足够关联信息需分别验证；不解析用户提示词中的路径来猜归属。

项目改名、thread 归档不视为原生 ID 失效，但配置保留由生命周期规则决定。按用户后续建议，确认 thread 归档 / 删除后自动清理它的专属覆盖，取消归档后继承当前上层；项目确认删除后清理项目目录，仍存在的对话覆盖跟随实际新归属迁移。列表暂不可用或分页缺项时保留配置待校准，不能据此删除。执行前无法定位对象则不宣称已应用，不为每次保存增加强制在线检查。具体规则见 [生命周期清理](独立配置存储与事件订阅适配方案.md#75-项目与对话生命周期清理)。

### 3.3 数据所有者

| 数据 | 所有者 / 存储 | 同步边界 |
|---|---|---|
| 已有 OpenCodex 全局配置字段 | OpenCodex 配置及管理 API；Desktop 读写适配 | 不另存一份无来源的全局值；外部改动读回后显示 |
| 新增全局行为、项目 / thread 覆盖 | Desktop 活动根内全局文件、按 source / project 分目录的项目文件及按需 thread 文件 | 三级均默认排除 WebDAV，同步需显式选择；项目删除、thread 归档 / 删除时自动清理 |
| 原生角色、Codex 默认配置 | Codex 原生配置；显式选择同步时才写入 | 文件写成功不等于运行中会话已加载 |
| 项目 / thread 身份与父子关系 | Codex 为事实源；Desktop / 执行端缓存索引 | 数据源切换和迁移重新解析绑定 |
| 执行策略快照 | 执行端按策略修订、作用域和执行边界生成 | 可记录采用的修订号；不靠切换全局 config 模拟局部覆盖 |

现有全局字段经适配器组成统一的有效配置视图；新增分层策略由 manager-state 持有。执行快照引用实际参与继承的作用域文件身份、修订及摘要，与执行端接收 / 采用状态分别展示；不同配置源不能互相覆盖。

模型目录、渠道能力仍由原模型配置方向提供，本包只引用其模型身份与能力，不复制第二套模型目录。

用户策略采用全局 / 项目 / thread 分层文件，本机来源绑定独立保存，操作状态按项目分散并有界保留，发现列表另作缓存；文件结构、自动清理、事件订阅、备份及 0.1.10 适配详见 [独立配置存储与事件订阅适配方案](独立配置存储与事件订阅适配方案.md)。配置事件与实际执行事件用于闭环，定时刷新按缺口补充；存储在活动根中不意味着自动进入现有偏好备份。

WebDAV 默认不包含本包的全部作用域；手动导出 / 导入与本机备份各自选择范围，不自动开启 WebDAV 或更改其选择。详细安排见 [导出与 WebDAV 默认范围](独立配置存储与事件订阅适配方案.md#81-导出与-webdav-默认范围)。

## 4. 各项功能

### 4.1 全局命名模型

按用户评审修订，仅在全局页提供“命名模型”，可沿用原配置或选择模型；命名触发、提示词及手工标题管理继续由 Codex 持有。项目和对话页不显示命名分区，局部策略不保存相关覆盖。

OpenCodex 可重定向辅助调用模型，但现有 shadowCallIntercept 按源模型匹配，可能同时影响提交信息等 helper，不保证仅影响标题。生产接入应核对实际范围；如果缺少标题专用能力，就说明影响范围或待接入，不为补缺口重新引入自建命名任务。

原生 thread/name/set 的前序探针结果保留为能力证据，不据此要求 Desktop 接管触发、首轮 / 每轮命名、提示词、关闭自动命名或标题竞争控制。这些前序候选从当前产品范围移除；不将用户选择解释成对 Codex 原生命名行为的新保证。

用户后续明确要在对话过程中手动点击“按当前内容重新命名”。这是显式一次操作：读当前内容、用已保存的全局模型生成候选、预览 / 编辑后采用，不重新引入逐对话命名配置或自动每轮触发。[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)说明 thread/name/set 可更新 loaded thread 或持久记录并发出 name/updated，证明已创建对话的名称可再次更新；不证明当前 Desktop 已接入生成或回写服务。原型操作与边界见 [标题更新交互](对话页交互方案.md#41-对话期间更新标题)。

### 4.2 搜索模型

搜索配置页先显示当前执行路径，再显示该路径支持的字段：

| 路径 | 模型配置范围 |
|---|---|
| OpenCodex routed 搜索 sidecar | backend / model / reasoning；候选受对应认证和搜索执行器能力约束 |
| 上游 passthrough 原生 hosted search | 不走该 sidecar；不能声称 sidecar 模型改变了此路径 |
| Exa 等搜索服务 | 以搜索服务配置为主，不要求其拥有 LLM 模型 / effort |
| 其它搜索工具或 /alpha/search | 单独识别；没有证据时不并入 sidecar 覆盖范围 |

“跟随回答模型”只有在所选 backend 接受该模型时才可执行。切换 backend 时重新计算模型 / effort 的有效组合，不盲目继承旧 backend 的不兼容参数。

现有 sidecar 无通用搜索 fallback 数组；回退链仍是候选新增能力，不借用子 Agent fallback 冒充。无执行适配时保留意图并说明未接通。搜索 plan 内使用已解析设置；新的保存影响下一次 plan 构建，不承诺当前循环下一次搜索即时切换。

管理 GET 未回显 reasoning 的缺口由适配器如实表示为“读回未知”，不当成空值覆盖，也不当成“已观察到采用”。仅改模型和切换搜索启用状态分别报告，因为后者还可能写入原生搜索配置。

### 4.3 子 Agent

| 类别 | 已知边界 |
|---|---|
| 推荐 roster 与指导提示 | subagentModels、injectionModel / effort 等不等于硬性默认 |
| 原生默认值 | syncCodexSubagentDefaults 由原生注入路径处理；需区分标志已保存、原生已写入、执行器已加载 |
| 回退与 effort cap | 代理按请求执行；cap 在 OpenCodex multiAgentMode=v1 时不应用，不能一概承诺强制生效 |
| 并发、深度、公共指令 | 原生字段及 V1 / V2 路径不同，max_depth 为 V1；不等价于跨项目全局调度预算 |
| 已有角色映射 | 当前 OpenCodex 角色管理依赖 LazyCodex / omo，仅改已有角色的 model / effort |
| 新角色、角色权限、独立 Fast | 继续核对 Codex 原生与执行适配，尚不承诺通用支持 |

角色 / 指令 / 工具权限以创建时的原生装载点为边界；不得只靠模型路由声称实现权限或并发控制。已有 child 的后续请求仍可能受 live cap / fallback 影响；“整个 child 生命周期模型绝不变”不是当前原生保证。

本方案新增作用域策略建议随父 turn 快照继承至 child；用户中途保存影响下一父 turn。已运行任务不因降低并发而取消，新增任务何时等待由执行器决定，并注明限制作用于哪个父线程树。若另需跨项目总并发，是独立调度需求，不顺带假设已存在。

## 5. 解析到执行的最小闭环

1. 发现层确认数据源、project / thread / 父子关系；执行端确定它能控制的边界。
2. 按策略修订合并全局、项目、thread 和显式值，解析模型能力及适用 cap。
3. 生成执行端允许的配置快照。代理局部设置使用请求级副本；原生字段通过实际拥有 thread 的执行器应用。
4. 发出请求或创建 child，记录策略修订、作用域来源、执行路径和最终模型；失败保留具体未应用原因。
5. 临时覆盖结束或撤销时按最新有效策略恢复持久参数，下一次执行观察实际采用结果。

**局部设置不得通过反复 PUT 全局管理 API 或改写全局 config.toml 实现。** 全局 API 只用于用户选择的全局操作。

需要区分三个时间单位：一次用户 turn、一次模型 HTTP 请求、一次 sidecar 搜索循环。新增作用域策略建议冻结于父 turn 起点，期间 child 继承该修订；若接入端只能看到 HTTP 请求，则按请求冻结并明确展示限制。不能把“下一请求”同时用于三者。

现有 OpenCodex live 全局设置仍按各自读取点变化。这与拟新增的 turn 级策略快照分别记录，不宣称 Desktop 已经改变了原生生命周期。

## 6. 实时生效矩阵

| 变更 | 本次可支持的结论 | 条件 |
|---|---|---|
| UI、策略保存、来源显示 | 保存后立即更新界面 | 不代表执行端已经采用 |
| 原生 thread 名称 | name/set 后可读回，无需重启 | 已验证隔离实例；外部 App 的列表刷新另行接入 |
| 已加载 thread 的模型 / effort | settings/update 后下一轮采用，无需重启 | 必须连接实际拥有 thread 的实例；已用本地实际请求验证 |
| 全局 sidecar 模型 / reasoning | live config 后续 plan 构建读取 | 仅适用 sidecar 路径；此项为源码证据 |
| sidecar 启停 | 代理行为与原生搜索注入分别生效 | 原生已加载会话何时重载还需测 |
| shadow-call 目标模型 | 后续匹配的 helper 请求读取 | 不等于触发命名，也不保证仅标题；源码证据 |
| 子 Agent roster / 指导提示 | 后续相关请求生成指导时读取 | 不保证模型服从建议 |
| 子 Agent 原生默认、角色、并发 / 深度 | 依字段装载点，需新创建 / 重载与否分别验证 | 不因管理 API 返回成功就标为热生效 |
| 代理 cap / fallback | 后续适用代理请求按原生实现读取 | 模式限制及已运行 child 行为单列 |
| 新增项目 / thread 策略 | 执行接入后，建议下一父 turn | 当前仅方案；禁止承诺保存即生效 |
| Codex 全局 config 写入 | 本次测试中：新 thread 采用，已加载 thread 保留原模型 | 不必笼统要求完整重启；其它字段逐项确认 |
| provider / 目录变更 | 按 catalog 刷新机制确认 | 本次未测，不统一判为立即或必须重启 |

状态分为“已保存”“执行端可用”“已观察到采用”，附具体的下一轮 / 下一 plan / 需新建等边界。尚无接口的字段显示原因并可保留草稿，不用一次失败禁用整个页面。

## 7. 已有验证与下一步

[审计报告](../03-确认与评审/20261011-方案逻辑与可行性审计.md)记录了 8 项实测和源码依据，[测试说明](../../03-测试验收/README.md)提供复跑方式。最小验证不依赖需求冻结，也不代表生产功能开发已启动。

下一步优先验证实际执行端连接，再以两个项目同时请求不同搜索配置检验隔离和来源；然后补一个父子 Agent 的继承验证。命名仅验证全局模型路由和实际调用范围，触发沿用 Codex。各项可以独立推进，不新增统一审批门禁。
