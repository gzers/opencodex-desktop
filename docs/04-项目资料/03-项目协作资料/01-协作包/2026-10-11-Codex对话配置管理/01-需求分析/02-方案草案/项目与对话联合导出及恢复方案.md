# 项目与对话联合导出及恢复方案

日期：2026-10-13（Asia/Shanghai）。状态：用户补充需求及候选设计；已有当前版本的隔离可行性验证，生产导出 / 导入未实现；版本和开发时机未定。

用户提出：

> 其实这个还涉及到一个问题，项目，对话文件时都要支持导出，因为能导出项目对话子agent配置，要是对话不能导出，是不是就没有意义？

本文补齐此前“只导出对话配置”的边界，关联 [独立配置存储与事件订阅适配方案](独立配置存储与事件订阅适配方案.md) 和 [原型准备度评估](../03-确认与评审/20261013-原型准备度与模型模版边界评估.md)。

同日用户进一步明确仅用于临时重装恢复；首批以显式本地恢复包为核心，日常 / 跨设备历史同步不进入必做范围，对话在同步页默认不勾选。未归档容量统计及入口收敛见 [临时重装用途](../03-确认与评审/20261013-对话体积与导出空间评估.md#7-后续澄清未归档容量与临时重装用途)，下文阅读 / 留档用途仍为可选方向。

## 1. 结论与范围

项目和对话内容应支持导出，并能与它们的对话配置一同打包。仅配置导出仍有复用设置、复制到另一个项目 / 对话和备份的价值；但若用户目的是迁移原任务与上下文，只导出原 ID 上的配置无法形成完整闭环。

因此保留配置独立导出，同时增加项目 / 对话联合导出。三个用途共用选择、预览与完成反馈，不建立互不关联的导出系统：

| 用途 | 导出内容 | 接收端用途 |
|---|---|---|
| 仅配置 | 所选作用域的命名 / 搜索 / 子 Agent 覆盖、必要上层配置和模型引用 | 映射到已有或另建的项目 / 对话，复用设置 |
| 对话记录 | 项目 / 对话元数据及可读取的历史，输出可阅读记录与结构化数据 | 阅读、留档；不能只凭 Markdown 承诺原会话恢复 |
| 项目 / 对话包 | 元数据、所选历史与关联配置；适配器支持时附原生可恢复记录及必要资源 | 映射对象和模型后恢复配置；原生恢复受支持时继续对话 |

用户此轮明确的是项目 / 对话也要能导出；下述包格式、导入选项和默认交互是闭环建议，尚未全部确认或实现。项目指 Codex 项目对象及其所选对话，不默认等同完整 Git 仓库、源代码或整个工作目录压缩包。附件和产物可另选；项目源码迁移如需要，应与既有 Git / 工作区交接分别安排。

## 2. 配置与历史分别持有

项目 / 对话协作 JSON 仍只保存策略和引用，不写入对话正文。Codex 持有项目对象、对话历史和父子关系，Desktop 在显式导出时读取并组包；不在日常配置目录同步维护第二份完整历史。

- 项目导出可选择该项目的全部或部分对话，明确活动 / 归档范围；按分页取得完整所选清单，不把当前可见第一页当成全部。
- 对话导出包含其记录与专属覆盖；还可以携带关联子 Agent 对话，预览主 / 子对话数量及缺项，不能只导出主对话中的子 Agent 摘要却称为完整子树。父子与 fork 关系分别保留，不把 sessionId 当成所有记录的唯一 ID。
- 配置包含当前自有覆盖，必要上层策略由用户选入；展示“仅本层 / 携带上层”。记录有效配置及来源作为快照供核对，不自动将继承值展开成固定覆盖，也不把快照当作已执行证明。
- 已确认归档后按前述规则清掉的专属覆盖，当前只能导出仍存在的历史与上层设置；不能凭空重建旧覆盖。已有备份 / 导出包可单独查看或提取旧策略，正常导入仍按对象生命周期处理。
- 当前运行中的对话建议导出到最后一个可确认完成的 turn，预览截止点；若选择包含未完成项，标明部分记录。导出不暂停或取消任务，不重放工具调用。
- 元数据、配置修订和对话截止点记录在清单中；不同来源之间不宣称同一原子快照。导出期间相关配置改变时明确使用的修订，必要时重新收集，避免包中说明与实际内容错位。

## 3. 候选包结构

日常管理继续按项目分文件；只有用户导出时生成包。格式名与 schema 仍待实现冻结，可用 ZIP 容器承载分文件，避免又汇总为无限增长的单份策略 JSON：

~~~text
<项目或对话导出包>/
├── manifest.json                        格式 / 来源版本、选择范围、能力与完整度
├── project.json                         项目名称、根目录描述及包内对象引用
├── policies/
│   ├── global.json                      仅用户选择携带上层时存在
│   ├── project.json                     项目覆盖，缺省代表无自有覆盖
│   └── threads/<export-thread-key>.json 对话覆盖，仅有自有设置时存在
├── threads/<export-thread-key>/
│   ├── metadata.json                    标题、来源 ID、归属与父子 / fork 关系
│   ├── transcript.md                    可选：阅读用途的主要表示或附带副本
│   ├── history.jsonl                    可选：结构化记录用途的主要表示
│   └── native/                          可选：原生恢复用途的主要载荷与版本描述
└── assets/                              用户选择且能够读取的附件 / 产物
~~~

单个无项目对话包不强制生成 project.json。原生载荷可以是 rollout 或目标版本采用的其他原生存储形式，不把 JSONL 视为所有未来版本唯一事实格式。前述 collaboration-bundle.json 继续用于仅配置备份 / 导出；联合包复用同一策略序列化和解析规则，不能另建互不兼容的配置格式。

上述历史表示按用途选用，不默认把同一历史存三份。原生恢复包以 native 载荷为主，阅读副本按需生成；轻量记录可减少工具细节但不得称为无损原生恢复。体积预览、流式压缩与 ZIP64 适配见 [对话体积与导出空间评估](../03-确认与评审/20261013-对话体积与导出空间评估.md)。

包内使用独立 export 对象 key，原 source / project / thread ID 作为来源记录；关系指向包内 key。文件清单标明大小 / 摘要、来源版本、记录截止点、完整 / 部分 / 不可用，以及附件实际内容或仅引用。远端链接或本机绝对路径不等于附件已打包；原路径只用于迁移建议，目标工作目录需要重新选择。

模型只携带身份引用与必要说明，复用现有模型映射服务。包不自动携带渠道凭据、模型模版库、制模助手执行偏好或整个 CODEX_HOME / 数据库。原生载荷可能包含历史模型设置、指令和工具记录，它们作为历史保留，不自动成为目标设备的活动连接、权限或子 Agent 默认。

长对话和大项目按分页 / 流式收集，逐文件进度及失败项可见；用户可重试失败项或导出明确标记的部分包。读取不到原生数据时仍可提供可阅读记录与配置，但将“原生恢复不可用”作为包能力，不伪称完整迁移。

## 4. 导入与继续对话

导出必须区别阅读用途与恢复用途。配置导入可以先独立实现；原生恢复必须在对应版本和目标来源验证后提供。候选导入流程为：

1. 预览包中的项目、主 / 子对话、配置及附件完整度，显示当前可提供的恢复方式。
2. 选择目标 Codex 数据源、已有 / 新建项目及工作目录，映射模型引用；同名不自动等同。
3. 仅配置可绑定到选定的已有项目 / 对话；联合包原生恢复默认形成新对象，不直接覆盖活动原对话。
4. 原生适配器生成或读回目标 projectId / threadId，记录包内 key → 新 ID 的映射，再保存对应作用域覆盖。父子 / fork 关系能恢复多少单独说明；只恢复了主对话时不宣称整个子 Agent 树已恢复。
5. 在目标真实读取点重新解析配置；历史采用记录不作为新环境的已采用，未决命名、模型请求和工具任务不自动重放。保留原标题，不补跑历史首轮命名。
6. 显示“记录已导入 / 配置已绑定 / 可继续对话”各步的真实结果。导入成功后，用户再选择打开并继续，不因导入而自动开始 turn 或付费模型调用。

若导入原生记录成功、配置映射失败，保留已导入对话和未完成步骤，允许补配；重试复用已生成映射，不重复新建对话。只导入成 Markdown 或 JSON 留档时提供阅读 / 提取配置，不把它注入 history 参数后包装成原生恢复。将记录作为资料启动新对话可以另作选项，并明确上下文经过选择或整理，不等同原会话恢复。

原对象确认已归档 / 删除时，正常配置恢复不向其重新激活旧覆盖；联合包显式“导入为新对话”以新 ID 接收设置。新对象与原对象不同，不与此前归档清理规则冲突。对象映射只保留本次导入必要关系和来源追踪，不建设全部历史 ID 的永久全局汇总。

## 5. 删除、备份与 WebDAV

项目删除 / 对话归档清理的是本机活动对话配置、相关状态和专属派生资源；已经生成的独立导出文件不随原对象操作被删除。导出包是用户保留的时间点副本，沿自己的文件 / 备份保留规则处理。旧副本可查看，但不会因导出目录存在就重新激活活动配置。

WebDAV 默认排除本包对话配置，也默认不包含项目 / 对话内容与联合包。以后用户选择对话配置同步，不隐含开启对话历史同步；历史是独立内容范围，应另行显式选择。文件导出 / 导入不改 WebDAV 选择；普通同步不递归上传 exports、原生会话目录或本机备份。

当前首批用途是本机临时重装：手动导出到重装后仍可访问的位置，再导入恢复。同步页对话始终作为默认未选的独立范围，通用预设、缺字段升级和本地恢复包的导出 / 导入不会自动勾选。用户本次不使用 WebDAV 历史上传；不为完整恢复包建立默认远端副本或强制历史同步能力。

协作策略备份仍按已登记范围保存，不能把它描述成完整项目 / 对话备份；需要原任务恢复时使用联合导出或以后单独登记的内容备份范围。不要因增加联合包就让每次策略保存都重读 / 重存全部对话历史。

## 6. 当前能力核对与隔离验证

2026-10-13 核对官方 [Codex App Server 文档](https://learn.chatgpt.com/docs/app-server)：已有保存历史的读取、resume 和 fork 能力；这为历史导出和会话恢复提供基础，不等于官方已承诺任意项目 / 对话包跨设备导入格式。具体原生字段还核对了当前本机 CLI 0.162.0-alpha.17.2 的 experimental JSON Schema：

- `thread/read.includeTurns` 可读取历史；长历史还有 turns / items 分页入口，是否支持具体存储后端需要探测。读取结果是会话视图，不自动等于全部原生恢复数据。
- `project/import` 接收项目元数据和 thread ID 列表，不接收聊天正文；需要先获得目标对话再关联项目。
- 未发现通用 `thread/export` / `thread/import` 方法。`thread/resume.history` 标明不稳定、仅 Codex Cloud，不用于通用导入。resume / fork 的 path 也标为不稳定，不能据 schema 存在承诺可用。

为验证最短链路，在实现 main 工作区的 `test/codex-collaboration/probe_export_roundtrip.py` 复用已有隔离 helper，使用两个临时 HOME / CODEX_HOME、同一 CLI 和本地 Responses 替身。没有访问用户真实对话或付费模型。结果见 [原始回执](../../../../../../../.adg/evidence/COL-LOCAL-20261011-01/export-roundtrip-20261013.json)：

| 检查 | 观察结果 |
|---|---|
| 读取保存历史 | 返回一轮合成用户 / 助手历史与原生记录 |
| 任意暂存路径直接 fork | 未成功，返回 no rollout found；不能直接采用该路径作为正式导入 |
| 按原生 sessions 布局复制再 fork | 成功；接收端未复制源 SQLite 数据库 |
| 新对话与原历史 | 生成新 thread ID，一轮历史保留 |
| project/import | 创建新项目并关联新 thread，读回项目绑定一致 |
| 下一轮继续 | 实际发给本地替身的输入含旧助手响应和旧用户消息；保存后为两轮 |

共 5 项正向检查通过，另记录 1 项直接暂存路径失败；最终运行 2 个本地替身请求。只能证明同版本、同平台、隔离新实例的原生记录迁移与继续链路可行，不证明 Desktop 当前会话接入、产品包格式、策略绑定、跨版本、附件或父子树完整恢复。

生产适配器需要处理原生载荷的导入暂存、ID 冲突、登记与清理，优先在隔离暂存中生成新身份，再通过目标来源受支持的方式接入；不能直接把试验中的文件复制变成覆盖用户 sessions 或数据库的操作。实际执行实例接入仍是原包未决问题。实验性能力允许继续做 mock 与分阶段实现，不作为所有功能一起通过才可设计的门禁。

## 7. 原型与实施增量

仍沿 [唯一产品主原型](../../../../../01-项目支撑资料/01-产品原型/原型/index.html) 设计，不新增另一套对话客户端或模型模版原型。本包基础配置原型仍可开始；第一轮导出交互应补以下闭环：

- 项目 / 对话的“导出”入口带入当前对象，选择仅配置、对话记录或联合包；联合包预览历史、子 Agent 对话、上层配置和附件。
- 项目范围按全部 / 所选对话组织，显示归档与关联子对话是否纳入；记录截止点与缺项清楚。
- 导入预览区分仅阅读、绑定配置和原生恢复；演示新项目 / 新对话 ID 映射、目录 / 模型待匹配及部分完成。
- 已生成包不受原对象归档清理影响，恢复新对象不自动启动任务；WebDAV 仍默认未选择，勾选配置不顺带勾选历史。

配置文件中不出现对话正文，模型模版仍只管理模型规则；项目 / 对话内容的导出与关联迁移归本包的对象管理边界。若后续做独立内容备份模块，可复用导出服务，仍保持配置与内容的范围可分别选择。

实施先做完整分页读取与可阅读 / 结构化导出，再加联合打包及配置映射；原生恢复按版本验证后接入。最小验收分别检查记录是否完整、关系是否有缺项、策略是否绑定正确，以及继续对话是否包含预期上下文，不能以成功生成 ZIP 代替任务迁移验收。

后续用途澄清后，首批顺序调整为：核对目标版本原生恢复 → 所选未归档历史与配置本地联合打包 → 重装后的路径 / 模型 / ID 映射与继续验证。可阅读 / 结构化单独导出可复用读取层后续补充，不再作为先于恢复包的交付前置条件。原型主流程聚焦“导出重装恢复包 → 本地文件 → 导入恢复”，不是完整历史管理客户端或周期同步产品。

本轮完成方案回写和上述隔离探针，没有制作 HTML 原型，没有实现或执行真实对话导出、导入、项目迁移或 WebDAV。

## 8. 同日补充：容量与大包处理

用户进一步询问对话是否很大。仅文件元数据统计发现，本机活动 / 归档共 192 个原生历史文件约 12.69 GiB，中位数约 1.57 MiB，最大单个约 10.09 GiB；文件数不等于独立主对话数，未检查超大记录原因或压缩率。详细统计与边界见 [容量评估](../03-确认与评审/20261013-对话体积与导出空间评估.md)。

据此调整首轮方案：按用途选择主要历史表示，完整包流式压缩并支持 ZIP64，导出前按对象与内容类别显示大小；子对话与附件明确选择，不自动复制整个项目。已有导出包按自身保留规则处理，归档配置清理不删除原生历史。压缩与导入峰值容量按真实流水线计算；当前只做统计与设计，没有压缩或读取用户正文。
