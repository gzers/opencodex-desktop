
### 3.2 当前原型需要保留的最新方向

以下来自 2026-09-19 原型入口说明；阶段 0 仍需与 HTML 和确认记录对齐：

- 宽栏 244px、面板窄栏 64px；Logo 与导航图标的横向位置在宽窄切换时不跳动，仅收起相应文字。

- 分类 tab 为透明底、自然宽度和底部指示线；分类计数为中性半透明，未读点与铃铛角标单独保留语义。
- 通知条目为半透明卡片，右侧垃圾桶垂直居中；状态标签是行内小标签，不能被正文 `span` 规则拉满。
- 通知面板、Toast、任务卡支持“收起到铃铛”；收起不等于已读、已解决、删除或取消任务，并有减少动态效果的降级。
- 通知内控件沿用小一档样式；取消动作使用半透明风险色。正文、条目主体、tab、删除键与收起键不能被泛化按钮规则一起覆盖。
- 通知背景已按用户截图确认（2026-09-19）：采用 `glass` + `off`，即轻磨砂、无色（中性）。统一执行 `docs/02-项目核心/UI规范.md` §2.2，不再重复询问材质选择，不把旧打样开关迁入正式软件。
- 面板快捷浮层采用相同材质规范；滚动条不常驻，悬停或滚动时显示，结束后按原型淡出。

- 原型最小窗口与 Tauri 配置最小窗口不一致时，明确双端验证尺寸，不静默改动平台窗口约束。

### 4.2 必须明确的语义

- 六类是反馈职责和展示渠道，不是六种都必须持久化为 `Notification` 的实体类型。操作任务、通知、技术日志、确认请求分别定义，使用操作/事件标识关联。
- 类型、严重程度、业务分类与触发来源分开。现有 `info / warning / danger` 不未经兼容设计就替换为 Toast 的 `success / error`。
- `read`、`resolved`、`deleted` 是不同维度，不是“读了就解决”的线性状态链；关闭详情、收起浮层不修改业务结果。
- 区分自动验证已恢复、用户确认知悉、手工标记处理。不能将用户点击“已解决”解释为服务实际恢复。
- 定义 `operation_id`、去重键、创建/更新/已读/解决/删除时间、动作目标、日志关联及可过期条件；原型简写不得不加说明直接成为正式 DTO。
- 过期与清理资格不等于删除；未解决风险、进行中任务、需要用户决策的事项不得静默过期清除。
- 启动指令发出、子进程创建、进程运行、ready、官方页面加载是不同事实；只能展示已收到的阶段证据，不能靠固定延迟伪造成功。
- UI 等待超时与后台任务失败分开；隐藏卡片、停止观察、请求取消、已取消必须分别定义。
- 重复轮询不产生重复提醒；同一操作终态只触达一次。默认选一个主展示渠道，日志可同时记录，但不能反复叠加 Toast / 卡片 / Modal。
- 通知中心和通知历史是同一份实体的投影，技术日志仍是独立事实记录。正式运行不得由演示种子冒充真实通知。

**完成条件**：§16、状态章节、FZ-43、验收矩阵无冲突；现有编号不被复用成另一语义；候选不被冒认通过。

## 5. 阶段 2：编写 UI 规范

维护 `docs/02-项目核心/UI规范.md`（已存在时就地修订，不另建第二份），登记到该目录 README。确认后的视觉参数只维护这一份，原型说明与 IMP 引用它；未确认参数留在方案材料中。

规范至少覆盖：

1. **窗口与布局**：控制行、品牌区、导航、宽窄切换、内容圆角、描边归属、滚动容器、安全区与弹层定位。
2. **设计令牌**：亮/暗/跟随系统的颜色、玻璃底板、模糊、描边、阴影、字体、间距、尺寸、圆角、层级和动效；从当前原型提取，不重新发明视觉风格。
3. **基础控件**：Button、IconButton、Tab、Select、Input、Switch、Badge、Card 的变体、尺寸与默认/悬停/按下/焦点/禁用/加载/错误状态。

7. **边界**：原型外部菜单和场景切换器不属于正式软件；原生窗口按钮由系统提供；官方页面内部样式与管理器壳层分离。

每条视觉规则附“原型选择器/状态 → token → 组件”映射。固定尺寸需注明逻辑/CSS 像素与适用范围，不能把截图物理像素直接复制为 CSS 尺寸。

**完成条件**：后续实现无需猜测常用尺寸与变体；原型、UI 规范、IMP 的职责清晰；两套互相覆盖的样式规则已列出迁移方式。

## 6. 阶段 3：组件化与样式规范化

先盘点已有组件再最小拆分；沿用 Vue、Pinia、现有测试和构建工具，不为本轮另换组件库、CSS 框架或状态管理方案。

| 层 | 建议边界 | 不应承担 |
|---|---|---|
| 应用壳 | 复用/整理 `AppSidebar`、品牌、窗口控制区、内容容器与全局反馈入口 | 复制原型浏览器窗口装饰、真实业务命令 |
| 基础 UI | 按实际复用提取按钮、图标按钮、Tab、徽标、卡片、表单控件 | 每个页面各写一份同名视觉变体 |
| 反馈展示 | `ToastHost`、`TaskProgressHost`、`NotificationCenter`、`NotificationItem`、详情/确认 Dialog、InlineState | 直接调用 `ocx`、自己推断任务成功 |
| 业务状态与适配 | 通知、任务状态及平台适配；由现有 controller/store 渐进拆分 | 同一事件由多层各弹一遍反馈、复制多份通知数组 |

- `tokens.css` 管公共设计值；`base.css` 收敛为重置和必要全局基础；布局、控件、业务页面样式分层或归属组件。
- 状态通过明确 class/属性驱动，避免 `.notification-panel button`、`.notification-item span` 这类广域规则误伤 tab、图标键和状态标签。
- 清理重复覆盖需先迁移调用点，不能整体删除旧 CSS 再补丁式修复。共享 token 不复制到多个组件。
- 业务页面复用同一套 props / emits / slots；仅表现层拆分，不顺手改写无关业务流程。
- 通知逻辑保持单一事件来源、统一去重和终态处理；Modal 不再同时拥有各种长任务状态。
- 普通 Web 与桌面调用分离：Web 审计使用显式测试适配，不将真实 IPC 失败静默当成 mock 成功。

**完成条件**：至少一个通知流和概览页使用新组件贯通；既有业务回归通过；没有新增隐式旁路接口和整页重写。

## 7. 阶段 4：复刻当前原型

按“壳层 → 通知六类 → 概览 → 拓展 → 日志/诊断 → 设置各分区 → 面板壳层 → 托盘/菜单”的顺序逐块迁移；每块与阶段 0 的同版本基线比较。

- 覆盖原型中现有路由和设置分区，不只调整通知面板；静态布局、状态、交互与真实数据绑定同时核对。
- 不复制原型固定版本号、示例端口/PID、未读数量、模拟错误、场景定时器和评审工具到正式页面。
- 正常路由与通知专题要调用相同组件；只用于审计的场景入口限开发/测试环境，不能随正式界面暴露。
- 概览的 spinner、进度收起、失败重试、面板加载提示必须使用真实状态，且主导航在异步等待期间可用。
- 改动壳层时同步核对 Rust 子 WebView 的坐标与尺寸校验；不能再发生 CSS 28px 与后端 44px 不一致、最小宽度越界等问题。
- 官方面板不重绘、不随发布包复制官方快照，也不通过放宽 URL 白名单、凭据边界或管理器 IPC 权限解决嵌入问题。
- 原生子 WebView 与 DOM 不是同一合成层，不能假定 `z-index` 提高就能盖住官方面板。确定通知/Modal 的原生承载或协调显示方案，并保证面板页也有可用入口、不会遮挡点击或留下透明点击层。

**完成条件**：各路由已迁移；未迁移部分有明确清单；视觉差异有出处；正式行为不依赖原型模拟。
