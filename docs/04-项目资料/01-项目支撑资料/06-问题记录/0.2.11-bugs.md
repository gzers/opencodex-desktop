## WP-69：重启 Codex 后仍显示「已保存 · 待重启」

**优先级**：P0（状态永不收敛，且用户被要求做一件事却看不到结果）
**位置**：模型 → 渠道模型 → 状态区（Tab 右侧）
**用户原话**：「重启 codex 了但是还是显示待重启……而且当前写入后也不能生效。」
**状态**：已定位（2026-10-26），**本轮只记录，不实施**

### 现象

用户重启 Codex 后，状态区仍显示「已保存 · 待重启」。且用户认为「当前写入后也不能生效」。

### 根因：状态由「计划是否 committed 且有变化」决定，与重启无关

`client_state::target()` 的判定（`client_state.rs:85-100`）：

```rust
if plan.phase != "committed" || !changed(&plan)? { continue }   // 只找已提交且有变化的计划
```

`project()` 随后把「有 target 但状态未确认」映射为 `RestartRequired`。关键点：

1. **这个状态与用户是否重启无关**——它只看磁盘上是否有一条 `committed` 且有变化的计划。
2. **只有用户点「我已重启，检查」并确认后才会消失**。用户重启 Codex 这个动作本身不会被感知。
3. 因此「重启了一百次仍显示待重启」是必然结果，不是偶发。

### 「写入后也不能生效」：实测配置与计划不一致

本机最近一条 `committed` 计划 `b709d00a`（2026-10-26T04:18:48Z，55 个模型），与 `opencodex-home/config.json` 比对：

| provider | 字段 | 计划写入 | 实际文件 |
| --- | --- | --- | --- |
| `FeiMao-CNM` | `apiKey` | `None` | `sk-dde2…`（有值） |
| `FeiMao-CNM` | `name` | `None` | `FeiMao-CNM` |
| `openai` | `note` | 有长句 | `None` |

差异只有 3 处，其中 `apiKey` / `name` 属本机引用与回显字段；`openai.note` 需要单独确认是否本就不写。**但「不一致」本身说明：那次写入没有把 config.json 写成计划的样子**，所以「不能生效」可能不是重启问题。

### 用户提出的方向（已认可）

> 「要不就直接跟那个模型配置文件比对就行了，是否生效也不管，自行重启就肯定生效，逻辑就没有那么复杂。」

> 「这个是执行完的通知提示就行了。」（不要状态）

这个方向可以把状态机整体删掉：保存 = 写文件 + 读回比对 + 一条通知。

### 官方已有能力（重要，避免自研）

`ocx sync` 已经提供用户要的全部能力：

| 能力 | 官方实现 | 说明 |
| --- | --- | --- |
| 同步模型 | `ocx sync` | 按已连接提供商重写 Codex 模型目录 |
| 重启 Codex | `ocx sync --restart-codex` | 重启 app-server **并完全退出重启 Codex 桌面端**（mac/Linux/Windows）；**会结束进行中的对话** |
| 只重启服务 | `ocx sync --restart-app-server-only` | 只重启 app-server，桌面端不动 |
| 刷新缓存 | `ocx sync-cache [--restart-codex]` | 从当前目录刷新 Codex 模型缓存 |

因此「立即重启 / 稍后重启」不需要自研进程控制，直接调官方命令即可。

### 实测：`ocx sync` 不会污染配置（初步）

在隔离的临时 `OPENCODEX_HOME` 里跑 `ocx sync`：

```
[opencodex] Codex write refused (service-home): this proxy could not prove it owns the installed service homes,
so catalog sync and Codex config injection were skipped.
```

写入前后 `providers` 与 `modelPickerOrder` **完全未变**。说明它有归属校验，不会盲写别人的配置。

**但这个结论只在隔离环境成立**，真实环境（管理器已注入过 Codex）下 `sync` 是否会覆盖管理器的写入**尚未验证**——这是实施前必须验的第一件事。

## WP-69 验证结果（2026-10-26，只读验证，未改代码）

验证目标：确认「复用官方 `ocx sync --restart-codex`」这条路是否可行。结论：**能力可用，但不能整段复用**，需要拆开用。

### 一、`--restart-codex` 确实能重启 Codex 桌面端（源码确认）

`src/codex/desktop-app-restart.ts` 文件头写明了设计动机，直接回答用户的问题：

> `--restart-codex` used to signal only `codex app-server` / `codex-code-mode-host` processes, and on every platform that turns out not to refresh the model picker. The app-server it signals is a CHILD of the desktop app… the app simply respawns it while the renderer keeps the roster it built at launch. **The only thing that reliably refreshes the picker is restarting the shell that owns it.**

即：**只重启 app-server 不会刷新模型选择器**，必须重启整个 Codex 桌面壳。所以：

| 能力 | 命令 | 是否有效 |
| --- | --- | --- |
| 刷新模型选择器 | `--restart-codex`（重启桌面壳） | ✅ 唯一可靠 |
| 温和重启 | `--restart-app-server-only` | ❌ **不刷新选择器**（官方实测结论） |

← 这直接回答了 WP-69 待裁决第 1 条：**不能选 A2**，只能彻底重启。

### 二、重启的代价是明确的

同一文件注明：

> quitting the app ends live conversations and that is a larger consent than restarting a background helper.

流程：优雅关闭 15s → 强制 5s → 拒绝或重启。全程 **fail closed**（读不到进程身份就不杀，宁可选择器陈旧也不误杀）。

所以「立即重启 / 稍后重启」的二次确认文案必须写明「会结束进行中的对话」。

### 三、`ocx sync` 不只是重启，它会重写配置（关键风险确认）

`src/codex/sync.ts` 的返回结构显示它做三件事：

| 字段 | 含义 |
| --- | --- |
| `catalogWritten` | 写模型目录 |
| `cacheSynced` | 刷新 Codex 缓存 |
| `status: applied / catalog-only / skipped / refused` | 配置注入结果 |

也就是说：**`ocx sync --restart-codex` = 重写目录 + 刷新缓存 + 重启桌面壳**。管理器已经用 `ocx provider apply --baseline` 写过 config.json，再跑一次 sync 会**按已连接提供商重算一遍目录**，可能覆盖刚写的内容。

这确认了 WP-69 待裁决第 5 条的风险是真实的，不是理论担忧。

### 四、归属校验会让副本环境直接拒绝（三次实测）

| 环境 | 结果 | config.json 是否变化 |
| --- | --- | --- |
| 仅复制 config.json 到临时目录 | `Codex write refused (service-home)` | **未变**（sha256 相同） |
| 复制 config.json + service-state.json | 同上 | **未变** |
| 改写 service-state 路径指向副本 | 同上 | **未变** |

原因（`src/service/state.ts:174-191`）：归属校验比对 `codexHome` / `opencodexHome` 的真实路径，副本路径不匹配就拒绝，且**明确 fail closed**——`catalog sync and Codex config injection were skipped`。

**这是一个好性质**：官方不会盲写别人的配置。但也意味着「在隔离副本上验证 sync 覆盖行为」这条路走不通，只能在真机验证。

### 五、由此得出的结论（修正设计）

原草案「保存后调 `ocx sync --restart-codex`」**不可行**——它会把管理器刚写的目录重算一遍。正确拆法：

| 步骤 | 用什么 | 说明 |
| --- | --- | --- |
| 写配置 | 管理器现有链路（`ocx provider apply --baseline`） | 不动 |
| 读回比对 | 直接读 `config.json` | 不碰运行时 |
| **只重启不重写** | **需要确认官方是否有单独的重启入口** | 见下 |

**新的未知点**：`--restart-codex` 是 `sync` 的子选项，官方是否提供「只重启、不重写目录」的独立命令？若无，则要向官方确认 `sync` 的 `catalog-only` 分支能否跳过重写，或由管理器自己实现桌面壳重启（但那就回到自研进程控制，与「复用官方方法」相悖）。

### WP-69 验证结果（续）：`sync-cache --restart-codex` 是可行解

上一轮遗留的两个问题，读官方源码后已有确定答案。

#### 一、没有「只重启」的独立命令，但 `sync-cache` 等价可用

`ocx help --all` 里带 `--restart-codex` 的只有两条：`sync` 与 `sync-cache`。没有纯粹的重启命令（`ocx restart` 重启的是**代理**，不是 Codex）。

两者区别（源码 `src/cli/dispatch.ts:532-600` + `catalog/retained-sync.ts:721-767`）：

| 命令 | 拉取上游 | 写 catalog | 写 config.json | 写 models_cache | 重启 Codex |
| --- | --- | --- | --- | --- | --- |
| `ocx sync` | ✅ 会 | ✅ | ✅ 注入 | ✅ | ✅ |
| **`ocx sync-cache`** | ❌ 不 | ❌ 不 | **❌ 不** | ✅ | ✅ |

`invalidateCodexModelsCacheWithPermitOutcome` 全文只写一个文件：

```rust
const cachePath = join(owningCodexHome, "models_cache.json");
```

它读**现有 catalog**（管理器刚写的那份）→ 重算 `models_cache.json` → 然后按 `restartScope` 重启。**完全不碰 config.json**。

**结论**：`ocx sync-cache --restart-codex` 就是「只重启不重写配置」的那半个能力。原草案的风险（覆盖 manager 的写入）不存在——因为用的是 `sync-cache` 而不是 `sync`。

#### 二、重启是幂等且安全的（源码保证）

`dispatch.ts:560-570` 的注释写明：

> An identical cache is a successful no-op, not a failed refresh. **Only a real write should restart Codex**; a missing catalog or contended writer is also a benign skip.

即：**缓存没变就不重启**。这意味着：

- 重复点「立即重启」不会反复杀进程；
- 拿不到 catalog 或锁被占用时是「跳过」而非失败（exit 0）。

另外 `--json` 输出结构化结果，便于管理器判断真实结局：

| 字段 | 含义 |
| --- | --- |
| `ok` | 是否可视为成功（含 benign skip） |
| `wrote` | 是否真的重写了缓存 |
| `skipped` / `skippedReason` | `unchanged` / `contended` / `no_catalog` |
| `codexHome` | 归属的 Codex home（可核对） |

### WP-69 验证结果（续二）：比对字段清单已确定，且发现一处真实的写入缺口

上一轮遗留：`openai.note` 该不该排除。答案：**不该排除，它是 PUBLIC，且确实丢了**。

#### 一、字段分类有现成权威常量（不用手写白名单）

管理器自己的 `provider_fields.rs` 已有四类，`public_from_raw()` 只保留 `PUBLIC`：

| 常量 | 字段（节选） | 比对时 |
| --- | --- | --- |
| `PUBLIC` | `adapter`、`baseUrl`、`models`、`note`、`disabled`、`codexAccountMode`… | ✅ **比** |
| `PRIVATE` | `proxy`、`apiKey`、`apiKeyPool`、`headers`、`mcpServers`、`desktopExecutor` | ❌ 不比 |
| `RUNTIME` | `apiKeySelectionRevision`、`_apiKeyAttempt`、`initialModelSelection`、`modelMaxInputTokens`、`xaiResponsesDefaultVersion`、`zaiResponsesDefaultVersion` | ❌ 不比 |
| `ECHO` | `name` | ❌ 不比 |

**比对清单因此确定**：

```
providers 只取 PUBLIC 字段  +  modelPickerOrder  +  disabledModels
```

好处：清单来自代码常量，不随官方升级漂移，也不需要手写。

#### 二、`openai.note` 是真实丢失（更正上一轮的猜测）

| 位置 | `openai` 字段 |
| --- | --- |
| 计划 `b709d00a.nextProviders` | `adapter, authMode, baseUrl, codexAccountMode, disabled, newModelPolicy, **note**` |
| 实际 `config.json` | `adapter, authMode, baseUrl, codexAccountMode, disabled, newModelPolicy` |

`note` 在计划里有、文件里没有。**不是比对选错字段，是写入真的少了一个 PUBLIC 字段。**

#### 三、根因方向：官方 `PUT /api/providers` 会重建 provider 行

写入链路：

```
管理器 → ocx provider apply --baseline X --file - --json --yes
        → PUT /api/providers（服务端权威）
        → 服务端按请求体重建该 provider
```

官方 `src/cli/provider-batch.ts:62-70` 明确：`apply` 走 **`PUT /api/providers`**（服务端 authoritative compare-and-swap），不是直接改文件。

而 `src/server/management/provider-overwrite-carry.ts` 的注释写明这套机制的核心风险：

> `POST /api/providers` with an existing name **replaces the stored row with a candidate built from the request**. The dashboard form cannot send the fields below, so a save that omits them **used to drop them**.

即：**服务端按请求体重建行，请求里没带的字段就没了**。

这条链路解释了 `note` 为什么会丢：要么管理器编译出的 `nextProviders` 在传给 `apply` 前就少了它，要么服务端在校验/规范化时剥掉了它。

#### 四、这对 0.2.12 的影响（重要）

如果「写入会丢 PUBLIC 字段」是普遍现象，那**改判据为「读文件比对」反而会暴露更多问题**：

| 情形 | 旧判据（比运行时） | 新判据（比文件） |
| --- | --- | --- |
| `note` 丢失 | 判为一致（运行时不看 note） | **判为不一致 → 通知「未完整写入」** |
| 用户观感 | 「明明写好了却说待重启」 | 「说未完整写入，但配置其实能用」 |

**所以 0.2.12 不能只改判据**，得先确认 `note` 丢失是「本来就不该写」还是「该写没写」。
