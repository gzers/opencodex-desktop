范围、边界和能力

先把边界说清楚，后面才不会返工。这一册回答三个问题：哪些功能要做、哪些明确不做、这些功能怎么对应到验收标准。

Principle

范围原则只有一句话

原型里出现的功能都要实现。P0 / P1 / P2 只表示先做后做和前置依赖，不表示可以不做，也不表示可以砍。这条在 2026-09-14 由你确认过，并写进了需求 revision 3。

P0

运行管理主线

发现、数据目录、启停、状态、日志诊断、官方面板、风险识别与 restore、官方升级引导、托盘与菜单、关于页。

P1

要先过安全评审的

配置迁移（导出/导入）、扩展管理（Skills / MCP）、CLI 控制面、应用自更新。

P2

WebDAV 同步

全量客户端加密同步、冲突处理、覆盖前备份。排在最后是因为它依赖加密容器和写入引擎先就位。

Scope

做哪些、明确不做哪些

做

  • 发现并校验本机已有的 OpenCodex 安装（npm 形态）
  • 托管官方 ocx start / stop / restart 子进程，展示健康、端口、进程标识、最近错误
  • 日志只读脱敏、运行环境诊断、内嵌官方 Web 面板
  • 加密的配置导出 / 导入，以及经 WebDAV 的加密同步
  • Skills 与 MCP 统一管理，并分发到多个客户端
  • 两条独立更新通道：OpenCodex 本体升级引导、应用自身更新
  • 托盘、macOS 原生菜单，以及默认关闭的可选 CLI 控制面

不做

  • 不重写 OpenCodex 核心，不绕过官方 API
  • 不管 npm（安装、卸载、依赖解析、全局前缀）
  • 不替代官方 ocx update 的更新事务
  • 不安装或管理 launchd，不接管 codex-shim
  • 不写入 provider、路由、模型映射等核心运行配置
  • 不自动覆盖外部 provider 托管的配置，只检测、解释、引导官方 restore
  • 不明文迁移或同步凭据
唯一的例外：扩展配置可以写。具体是 Skills 目录同步和各客户端的 MCP 服务器节点。除此之外的一切 OpenCodex 配置仍然不可写，一律走官方 CLI。这也是安全评审里被反复盯住的边界。
