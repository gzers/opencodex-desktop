### S18-01：新版快照覆盖旧版与单一预览确认（2026-10-31修订）

- 用户原话：“应该就是按照新的版本覆盖旧的版本顶层逻辑，但是要有个弹窗展示改了什么，然后再确认或者取消。而不是还有双向同步的概念。”用户随后“同意”，并补充同步下载和导入前默认勾选备份。
- 已采纳以一份已保存配置快照为版本比较单位：本机较新时以本机快照更新云端，云端较新时以云端快照更新本机；一次操作只使用一份来源快照，不再逐对象各挑一端新版混合成“双向更新”。实际只覆盖已选范围，未选对象、本机专属配置和官方原生openai继续按既有范围规则保留。
- 点击“同步”先读取并展示“同步预览”：本次来源、版本时间、覆盖范围、实际新增/更新等变化；读取比较阶段不覆盖本机或云端。底部仅“取消 / 确认更新”，确认后执行覆盖，取消不写入；一致时提示无需更新。上传、下载是后台传输事实，不要求用户选择或理解双向合并模式。
- 下载更新和文件导入的同一预览窗默认勾选“更新前备份”，详见S18-03最新确认；不另开备份确认窗。正常完成沿注册通知展示结果，不再要求采用、转页保存或处理旧计划。
- 版本时间属于内容快照，传输、复制、打包不使旧内容变新。相同时间不同内容、无可靠版本及设备时钟偏差的确定规则仍需细化；新版覆盖不意味着把任意文件mtime当版本。手动恢复历史备份另按用户所选备份，不受普通同步只取新版的规则限制。
- 后续验收：本机快照新、云端快照新、内容一致、选中范围外内容保留、预览期间不写、取消不写、确认备份后写入、跨设备来回修改后以同一来源版本正确覆盖；不得再以原按对象双向更新mock通过证明该流程已完成。

### S18-02：Windows启动与内嵌面板

- “已启动、网页能打开、内嵌打不开且报启动失败”为用户观察；用户怀疑两者相关，当前没有证据证明唯一根因。不能预先归因于端口、WebView2、代理、缓存或权限。
- 后续沿同一Windows实例核对实际运行进程/所选来源、健康检查响应、浏览器可用地址与内嵌实际地址、WebView加载错误及启动任务终态。网页入口是当前症状中的可用路径，不能作为内嵌功能已修复的验收。
- 保留现有原型面板/错误/通知样式；如代理已健康但内嵌失败，应报告页面加载问题，而不是把进程启动结果误判为失败或重复启动。

### S18-03：统一流程，并入前轮已观察问题

1. **旧“未配置”错误残留**：前轮本机端点/密码文件存在，实际测试返回“WebDAV连接成功”；刷新本地“导入的连接”列表后旧错误消失。地址或密码是否可用与同步准备是否成功应分别展示；保存/重试成功后不得继续保留旧的 `application is not configured yet` 作为当前失败原因。旧错误的具体最初触发点未保留，不倒推为用户未填密码。
2. **同名MCP多源问题**：实际重新准备时返回“多个客户端的同名MCP定义不同，请先明确采用来源”；已只读定位选中项为node_repl，Codex与Claude定义不同，差异字段含env、env_vars、type。本轮不复制秘密值、不修改任一客户端。需在统一流程中明确对象和来源，避免一个未说明的同名对象阻断其余全部配置；不能静默选任意来源。2026-11-01复核：新版快照预览没有覆盖这一步，成因、键名缺陷、已确认规则与分工见下文“S18-03 MCP多源复核”。
3. **ETag提示与结果不一致**：用户截图报“该WebDAV未提供强ETag，不能安全发布配置”；源码表明准备、发布前后读回均可触发该检查。随后只读GET观察到有效强ETag，本地计划phase=published，远端指针对应本机最后上传且载荷SHA256与冻结摘要一致。只能证明核对时该份内容已发布，不能据此推断截图那次响应究竟缺失、为弱标识还是已被后续重试更新，也不能认定服务器永久不支持。缺少该次原始响应日志，原因保留待查。
4. **方案梳理范围**：文件导入/导出与设备间WebDAV同步各自职责、范围选择及保存、更新方向、准备与执行、同步结果、错误恢复和旧上传计划/比较状态残留统一梳理。基础文件写入/读取和传输错误需有具体原因，传输成功就展示成功；必要的失败恢复在内部完成，避免新增用户反复核对的门槛。

#### S18-03 MCP多源复核（2026-11-01）

用户追问：“当前软件存在同步报错，多个客户端的同名MCP定义不同，请先明确采用来源。这个新设计下是否解决了？”

**结论：未解决。** 2026-10-31确认的新版快照覆盖只决定本机快照与云端快照哪份较新；该报错发生在更早一步的生成本机快照时，同步在预览窗出现前就已中止。正式软件尚未开发，原型和上文候选规则也把MCP多源列为待定，所以新设计目前没有覆盖这个问题。

**报错机制（源码只读，相关文件v0.2.18与当前分支一致）**：

- `apps/desktop/tauri/src/modules/sync/portable_assets.rs` 的 `export()`：所选MCP不在受管定义 `manager-state/mcp-definitions.json` 时，读取六个客户端的原始定义，按JSON完全相等去重，多于一份即返回该错误，经 `model_config/file_objects.rs` 让整次文件导出或WebDAV同步失败。比较的是各端原值，没有先按客户端格式归一。
- 管理器新增或投影MCP时，`extensions/projection.rs` 的 `source_server_definition` 先取受管定义，否则按客户端顺序取第一份（Codex在前）；写入后只把名称记入 `extension-config.json` 的 `servers`，不保存所用定义。受管定义目前只在同步导入时写入。因此管理器自己投影出去的副本，下次导出仍被当作独立来源比较。
- 源码推断（未复现）：投影时 `adapt_shape` 会补写 `type`，OpenCode 还会把 `env` 改名为 `environment`。即使各端都从同一定义投影，只要格式适配改了字段，导出比较原值也可能判为多源。

**本机实际数据（只比字段名和是否相等，未复制值）**：

- node_repl 只存在于 `~/.codex/config.toml` 与 `~/.claude.json`；Gemini、Grok、OpenCode 配置文件不存在，Hermes 无MCP节点。管理器 `servers` 已登记 node_repl、六个客户端均启用，受管定义文件不存在；同步范围只选了这一个MCP。
- 两份的 command、args、startup_timeout_sec 相同。`type` 只在Claude一侧（投影时补写），`env_vars` 只在Codex一侧；`env` 键集合相同，有4个值不同：应用版本号（Codex 26.1023.50603，Claude 26.917.62051）、CLI路径、插件缓存路径中的版本号、可用浏览器后端列表（Codex多一项）。
- 判断（有证据，无写入日志可证实）：`~/.claude.json` 顶层只有 `mcp_servers`，没有Claude Code自身的状态字段，像是管理器写出的文件。Claude 那份是管理器早期从 Codex 26.917 投影的副本，Codex 应用升级后自行重写了 config.toml，副本没有跟随更新。这是同一来源的版本漂移，不是两份独立维护的定义，格式归一消除不了 env 值差异。

**客户端MCP键名不一致（已见于扩展包核实记录）**：`extensions/mod.rs` 把六个客户端的MCP键都设为 `mcp_servers`，读取只按这个顶层键查找，写入也不转换键名。[多Agent平台扩展管理](../../03-项目协作资料/01-协作包/2026-10-14-多Agent平台扩展管理/README.md)包的“20261031-平台扩展配置信息核实记录”（尚未提交）已按官方文档核对：Claude Code 为 `~/.claude.json` 顶层 `mcpServers`（另有 local 作用域 `projects.<abs>.mcpServers`），Gemini 为 `mcpServers` 并有独立 enablement 文件，两者代码错误；Grok 实际为 `~/.grok/config.toml` 的 `[mcp_servers.<n>]`，代码和契约却指向 `.grok/user-settings.json` 数组；OpenCode V1 为 `mcp.<n>`、V2 为 `mcp.servers.<n>`，local 型 command 为数组、环境变量键为 `environment`；Codex、Hermes 与代码一致。[集成与安全边界§2.2](../../../02-项目核心/集成与安全边界.md)中 Grok、OpenCode 两行也与上游不符，本节首版照抄契约，已据核实记录更正。管理器写给 Claude、Gemini、Grok、OpenCode 的MCP很可能不被这些客户端读取，读回的也不是实际生效的配置。该记录列明修正范围（契约§2.1～2.3、user_target、按嵌套键路径读写、测试 user_paths_match_fz22、清理 `~/.claude.json` 错误键），2026-11-01已确认归扩展包，具体修改随该包排期。键名修正后本次 node_repl 冲突会随之消失。但管理器登记 node_repl 对六个客户端均启用，若只改键名，下次投影会把它写进 Claude 实际读取的位置，使 Claude 加载 Codex 应用的 node_repl（推断，未验证）。跨设备同步已按下文规则3默认排除 node_repl，扩展包迁移旧节点前仍要先定它是否参与投影。

#### S18-03 概览状态排版与状态色统一（2026-10-31 二次反馈）

用户指出三卡字体样式不一致、未加载时的空心圈与「尚未检查」很别扭、图标与文字未垂直对齐，并要求把状态色定义清楚避免后续走偏。

根因：紧凑模式（`html[data-overview-size=compact]`，窄窗或打开过弹窗后触发）把 `.mod-status` 降到 11px，但版本行自己写死 `font-size: var(--text-label)`（12px），三卡字号分裂；`.mod-status span` 的 `min-height:18px` 又作用到内层圆点，把 7px 圆点拉成 18px 竖条；未检查时画空心圈再配「尚未检查」属于把“没有数据”渲染成状态。
