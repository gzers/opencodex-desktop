## 8. 特殊平台处理

**Claude Desktop**：先按 `desktop-3p-paths.ts` 的逻辑检测标准模式还是 3p 模式，决定读 `Claude/` 还是 `Claude-3p/`，`CLAUDE_USER_DATA_DIR` 优先。本地 MCP 改完要完全退出 app 才生效。Skills 和远程连接器只能在 app 里按账户管理，Desktop 只给引导。

**Cursor**：Cursor 自己的 `mcp.json` 和 OpenCodex 的 `provider.mcpServers` 并存。以哪份为准，或者两份都显示并标出重复，由适配器评审决定。

**DSH**：没有开关字段，停用就是删除条目。删除前保存原条目，恢复时原样写回。写入时要遵守 serverName 规则，序列化时保留 `!!js` 标签。

**Prime**：没有项目级，UI 里禁用项目级选项。Prime 自己加锁，Desktop 的锁要能与它协同。Skill 可能是 Python 包，投射前要能识别。

**Raycast**：MCP 没有公开文件，只做“在 Raycast 内配置”的引导状态。Skills 可以投射到四个目录之一，目录名必须等于 frontmatter 的 name。Raycast 只扫顶层，不能用嵌套目录或改名的软链。

**T3 Code**：显示为“跟随 Claude Code / Codex”。T3 Code 用 `-c` 注入的条目不在文件里，Desktop 读不到，也不写。

**Gentle Shell**：link 模式下与 Pi 是同一组文件，不能当成两个目标。先读 `~/.gentle-shell/config.json` 判断模式，link 模式下显示为 Pi 的别名。

**Pi 与 OMP**：Pi 的 `!command` 会在加载配置时执行命令，Desktop 不生成这种写法，读到时标为风险。两者的覆盖变量同名，探测路径时要区分。OMP 的 `enabledProviders` 默认为空，所以默认不读外部平台的用户级配置，项目级默认读。

**WorkBuddy AI 与 Qoder CN**：两者都是变体产品，路径多为参照主产品推断。`~/.qoderwork` 不是 Qoder CN 的目录。

**Aside**：推断是 aside.com 的 agent 浏览器，与 asidehq.app 不是同一个产品。模型文件按 account 分目录，目标身份要包含 account。app 运行时会改写配置，写入前必须完全退出。

**omo**：一个名字对应三个产品。第一个是 senpi，路径是 `~/.senpi/agent`，与 OpenCodex 写的 `~/.omo/agent` 不一致，README 写明没有 Skill 系统。第二个是 LazyCodex，路径是 `~/.omo/omo.jsonc`，它还会在 Codex 的 config.toml 里写段落，改 Codex MCP 时要保留。第三个是 oh-my-opencode。

**Droid**：切换项目级 server 时，Droid 会在用户级 `mcp.json` 留下带状态的副本。Desktop 要识别这类副本，不能当成用户自己添加的条目。organization 托管配置只显示，不覆盖。

## 9. 主要发现

1. **MCP 键名分裂**：多数平台用 `mcpServers`。用 `mcp_servers` 的只有 Codex、Grok、Hermes；用 `mcp.<n>` 的是 OpenCode V1 和 Kilo；用 `mcp.servers` 的是 OpenCode V2、OpenClaw、ZCode；DSH 是插件数组。Desktop 现有代码只按顶层键读写，表达不了 `mcp.servers` 这类嵌套路径，也表达不了 Claude Code 的 `projects.<abs>.mcpServers`。适配器要按平台映射键路径，对应 INT-F-2。
2. **开关字段要按平台翻译**：写法有 `enabled`、`enabled:false`、`disabled`、`enable:false`、`disabledServers`、`mcp.excluded` 等，Gemini 另有独立的 enablement 文件。DSH 没有开关字段，停用前要保存原条目。
3. **传输取值要按平台翻译**：写法有 `streamable-http`、`streamableHttp`、`httpUrl`、`transport:"sse"` 等。Pi 和 DSH 不支持 sse，Claude Code 已弃用 sse。
4. **env 引用写法有多种**：`${VAR}`、`${VAR:-default}`、`${env:NAME}`、`{env:VAR}`、`!!js process.env.X`、`{env:"VAR"}`、`bearerTokenEnvVar`。Desktop 只保存变量名，具体写法由适配器按平台生成，凭据不落明文，对应 INT-F-3。Pi 的 `!command` 会在加载配置时执行命令，Desktop 绝不生成，读到时标为风险。
5. **`.agents/skills` 被 15 个平台读取**：Codex、Gemini、Cursor、Pi、OpenClaw、Kimi、DSH、Command Code、Raycast、MiniMax、Droid、Grok、OpenCode、Hermes（仅项目级）、Kilo。不读它的有 Claude Code、gjc、Prime、Cline。OMP 的 agents 来源受 enable 开关控制，Qoder CN 只有 IDE 文档提到读这个目录，这两个不计入 15 个。建议优先写共享目录，只给不读它的平台补写专属目录。UI 要标出哪些平台是经共享目录读到的，并防止同一 Skill 重复加载。
6. **交叉读取**：Grok、OMP、MiniMax、ZCode、Command Code 会读其他平台的配置。`.mcp.json` 被 Claude Code、Qoder、Qoder CN、OMP、gjc、MiniMax、Command Code、Grok 共用，同一条目可能在多个平台同时生效。“实际生效”视图里要标出来自其他平台的条目，停用时提示会影响哪些平台。
7. **只能在 UI 管理或无法投射**：Raycast 的 MCP、Claude Desktop 的 Skills 和远程连接器、T3 Code、Aside、omo。这些用引导状态或跟随状态代替开关。
8. **作用域限制**：Prime 没有项目级；MiniMax 的项目级只读；Codex、gjc、Pi、Kimi、Hermes 的项目级需要信任；Qoder CN 的 .mcp.json 需要审批；Droid 的 CLI 只写用户级；Claude Code 多一个 local 作用域。作用域选择器要按平台禁用或提示。
9. **共写风险**：MCP 与模型同文件的平台共 9 个，Skills 与模型同文件的平台共 5 个，都走 INT-F-1，见第 7 节。Command Code、DSH、Prime 自己加锁，协同方式列入第 11 节。
10. **本机残留错误键**：`~/.claude.json` 里有孤立的 `mcp_servers`，与 Desktop 代码把 Claude 的 mcp_key 写成 `mcp_servers` 对得上，见第 10 节。
11. **Codex Skills 目录有分歧**：契约和代码写 `~/.codex/skills`，官方文档写 `~/.agents/skills`，本机两个目录都在用，见 1.4。
12. **原型已按本记录更新**：2026-10-31 扩展业务页的平台目录已由 24 项换为 30 项，见[原型说明](../05-原型/README.md#2026-10-31-平台数据按核实记录更新)。[管理形式建议](多平台扩展管理形式建议.md) 第 97 行的“23 项目录”仍列为后续事项。
