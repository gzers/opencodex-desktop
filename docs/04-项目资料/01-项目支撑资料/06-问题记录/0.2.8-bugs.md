## WP-65：保存预览里看不到模型，只有一屏提示文字

**优先级**：P0（保存前的唯一核对入口失效）
**位置**：模型 → 渠道模型 → 保存 → 保存预览
**用户原话**：「为什么原型能有保存预览，但是当前软件版本没有看到？」
**状态**：已定位、已修（2026-10-25，PR [#17](https://github.com/gzers/opencodex-desktop/pull/17)，提交 `5ba8c1356`）

### 现象（两张对照）

| 侧 | 看到什么 |
| --- | --- |
| 原型 | 顶部「模型激活数 89/100　基础模型 63 · Fast 24 · 系统占用 2」→ 渠道卡（NewApi 17/30、A6api 32/104）→ 每个型号一个可点标签 |
| 软件 | 同一个标题「保存预览」、同样的激活数摘要，**下面整块是灰色提示文字**：A6api：模型 claude-haiku-4-5 未在当前清单发现，保留选择待核对…… 一直排到弹窗底部，渠道卡与型号标签一个都看不见 |

两张截图的摘要数字能对上：原型「系统占用 2」、软件「系统占用 70」；软件提示条数与 70 同量级——不是「没渲染」，是**被提示挤走了**。

### 根因

不是「软件没有保存预览」——保存即预览在 0.2.7 就落地了，0.2.8 又补了系统占用与徽标。真实原因是**布局竞争**：

1. 后端投影 compiler.rs:298-303 对每个「已选但当前清单里没有」的型号发一条 notice：`{渠道}：模型{id}未在当前清单发现，保留选择待核对`。
2. 前端 SelectorPreviewDialog.vue 把它们**逐条平铺在弹窗底部**（p v-for notice）。
3. 弹窗主体是 display:flex + column + max-height:620px；渠道/型号区是 flex:1 1 auto 且 min-height:0，而每条 notice 是 flex:none 的固定高度行。

于是 notice 越多，flex:1 的列表被压得越小，而 min-height:0 允许它被压到 **0**。实测（注入递增 notice 条数，读列表高度）：

| notice 条数 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 8 | 12 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 列表高度 px | 558 | 497 | 436 | 375 | 314 | 253 | 192 | 70 | **0** |

真实账号里 70 条提示（系统占用 + 未发现型号）远超这个阈值，所以清单区高度归零：用户看到的就是满屏提示。

### 为什么原型没有这个问题

原型的预览只渲染「渠道卡 + 型号标签 + 系统占用分组」，**没有 notices 这个概念**（在 model-config.js 里搜索「未在当前清单发现」为 0 命中）。原型数据是内存 mock，不存在「已选但清单缺失」的行，所以它天然不会撞上这条布局路径。

也就是说：这不是「软件没实现原型」，而是**软件多了一类原型没有的真实数据**，而这条数据没有按原型的密度规则排布——它被当成正文段落逐条刷屏，与 §36 的归属规则相反。

### 修法

| 项 | 改法 | 依据 |
| --- | --- | --- |
| 提示形态 | 逐条 p → 默认收起的 details，标题只写「N 项待核对提示」 | 与同弹窗「另有 N 项字段变化」同一形态（§38.3） |
| 高度 | details 设 flex:none，展开后列表自身 max-height:112px + overflow:auto | 提示不得参与上方列表的高度分配 |
| 兜底 | 列表区 min-height:180px（原 0） | 任何附加区块都不能把唯一核对区压成 0 |
| 默认态 | 收起 | 待核对项属「需要处理的结果」，不该在核对弹窗里以正文形式铺开 |

修后实测（同注入脚本）：notice 0 → 557px，6 → 191px，8 → **180px（兜底生效）**，12 → **180px**。列表不再归零。

### 回归

- 新增单测：40 条 notice 下 details 默认收起、标题为「40 项待核对提示」、40 个 li 全在、两个渠道卡仍在、列表仍是独立滚动区。
- selector-preview-dialog.test.ts 14 项通过；vue-tsc --noEmit 通过。

### 未做（需裁决）

- **「系统占用 70」的含义**：摘要第三项现在直接取目录里 pickerVisible=false 的行数，与原型 mock 的 2 不是同一量纲。数字对不对要看它是否等于官方目录里的隐藏条目数，属数据口径问题，本修复不动。
- **提示是否该按渠道合并**：70 条里多数是同一渠道的连续未发现型号，可聚合成「A6api：18 个已选型号不在当前清单」；但这会改后端 notice 契约，需先定口径。
- 触屏长按与窄窗（≤900px）下 details 展开后的滚动表现未实屏复核。

## WP-66：保存/客户端状态在列表页被拆成三处，且互相矛盾

**优先级**：P1（可读性 / 状态可信度，不是功能不可用）
**位置**：模型 → 渠道模型 → 列表页顶部（Tab 右侧 + 表格上方两行）
**用户原话**：「这个状态展示应该这样显示吗？原型没有这样做吧，这次先不改，做记录分析。」
**状态**：**已记录，本轮不改**（2026-10-25）

### 现象

同一屏里同时出现三处状态，且彼此打架：

| # | 位置 | 文案 | 语气 |
| --- | --- | --- | --- |
| 1 | Tab 右侧策略框 | `● 保存待核对` | 红（danger） |
| 2 | 表格上方第 1 行 | `已写入 · 待重启 Codex` + `重启后重新检查` | 中性 tag + 文字按钮 |
| 3 | 表格上方第 2 行 | `上次保存尚未完成核对` + `查看原保存结果` | 中性 tag + 文字按钮 |

1 说「待核对」，2 说「已写入」，用户无法判断到底写没写。实际上它们指向**两次不同的保存**：1 是本次未完成的保存计划，2 是更早那次已提交、尚待重启的保存——但界面上没有任何区分，并排放着就是自相矛盾。

### 原型怎么做（实测，非印象）

用原型自带的 `pending-draft` 场景（草稿有未保存修改 + 上次保存待重启）实测：

| 项 | 原型 | 软件 |
| --- | --- | --- |
| 状态区形态 | **单行**，高 34px，在 Tab 栏右侧 | **三处**：Tab 右侧 + 表格上方两行 |
| 保存状态 | 一个框：`未保存修改` + 框内子标签 `上次保存待重启`（`.mp-policy-pending`，带 `·` 前缀） | 拆成 1 个红框 + 1 行 tag |
| 客户端检查入口 | **图标键** 28×28，只有 `aria-label=重启后重新检查`，无可见文字 | **文字按钮** ~90px 宽「重启后重新检查」 |
| 「查看原保存结果」 | **不存在**（原型全局搜 `原保存结果` = 0 命中；`保存结果` 只作为状态词出现） | 新增了一个文字按钮 |
| 表格起始 y | 256px | 303px（多占 47px） |

原型在 `index.html:658` 与 `:3753` 两处写死了这条原则：

> 统一操作结果：同一结果只在一个承载处，取消/部分完成/待确认/待重启各有真实结论（数据与状态 §5.8）。

软件的现状正好是这条原则的反例：把「待重启」这一件事同时画在状态框里和表格上方，还各配了一个入口。

### 根因（两处叠加）

1. **状态模型不同**：原型只有一个 `pending` 布尔 + 一个 `client` 字符串，且 `client` **从不渲染到列表页**（只在保存记录里用）。软件有 `savePlan.phase`（保存事务阶段）与 `clientState.status`（客户端加载态）两套独立状态，界面把两套都摊开显示，于是同屏出现两个「关于保存的结论」。
2. **入口没按原型的密度收**：原型的辅助入口是 28px 图标键（`mp-rail-helpers`），软件做成了带文字的按钮；而「查看原保存结果」是软件自加的，原型没有对应位置。

### 为什么这次不改

改法有分支，需要先定口径，不能凭感觉动：

| 分支 | 做法 | 代价 |
| --- | --- | --- |
| A | 完全按原型收：客户端检查改回图标键、删「查看原保存结果」、待重启并进策略框子标签 | 「保存结果」详情页就没有入口了，需确认它是否可只从通知中心进入 |
| B | 保留两处但明确区分：状态框只表达「本次事务」，表格上方只表达「上一次已提交的结果」，各加一行时间/来源说明 | 与原型不同，属新增规格，要先进原型 |
| C | 合并成一个状态框的多个子标签（待重启 / 待核对 / 未确认），入口统一进通知中心 | 改动面最大，涉及 §31 通知宿主 |

按 §36「原型没有的内容不得自由发挥成正文」与 §40 的裁决方式，A 最贴合已有契约；但它会删掉一个用户可能正在用的入口，所以需要你定，而不是我替你定。

### 顺带记录的两个观察（同源）

- 状态框 `● 保存待核对` 带一个圆点前缀，原型 `.mp-policy-chip::before` 是 7px 圆点、无 `●` 字符；软件用的是文字 `●`。视觉上近似，但形状与对齐不完全一致。
- 软件 `clientLabel` 把 `not_required` 也写成「已写入 · 无需新增重启」，与 `restart_required` 的「已写入 · 待重启」只差后半句，扫视时容易看成同一个状态。

## WP-67：状态展示没有状态码，只有散落的中文标签（统一化的前提缺失）

**优先级**：P1（架构性，非单点缺陷）
**用户问题**：「考虑这个状态编码去做统一状态展示处理可以吗？」
**状态**：**分析（本轮不开发）**，2026-10-25

### 结论先行

可以，而且**应该做**；但当前缺的不是「一个统一的状态组件」，而是**状态码本身**。原型有 9 个稳定 id（clean / dirty / staged / over-budget / saving / pending / failed / stopped / uncertain），软件**一个都没有**——17 处状态显示各自直接写中文 label 字符串。没有 id 就没有可统一的对象，先做组件必然做错。

## 一、原型这一处到底是什么

用户选中的「未修改」是 span.mp-template-state.mp-policy-chip，来自 model-config.js:437-440 的 channelPolicyStatusHTML()。它不是一个孤立标签，是一套**状态编码**的输出端：

| 层 | 原型实现 |
| --- | --- |
| 状态码 | data-channel-state = clean、dirty、staged、over-budget、saving、pending、failed、stopped、uncertain（9 个） |
| 文案表 | channelPolicyStates（id → [label, tone] 单一映射） |
| 判定 | channelPolicyState() 按固定优先级归约出一个 id |
| 渲染 | 一个函数输出 chip，tone 只有 5 类 |
| 附带 | data-policy-example 九态样例（注释 08）+ title 上下文 |

tone 词表也只有 5 个：neutral / warning / danger / info / success（原型 .mp-template-state 的 5 条选择器；全原型计数 danger 11 次、warning 19 次等，全部落在这 5 类）。

**但请注意：原型自己也没统一全站。** mp-template-state 只在 model-config.js 出现 10 次，其它页面各写各的：maintenance-ui 用 .mnt-status、extension-manager 用 .xp-target-state、model-picker 用 .mpk-chip-*、同步页干脆没有状态标签（用文案段落）。所以「按原型做统一状态展示」这件事，原型只能提供**模型页这一套的语义与 tone 词表**，不能提供全站既有实现——全站统一属于新增规格，要先进原型。

## 二、软件现状（实测）

### 2.1 没有状态码

- 全仓 data-channel-state = **0 命中**；也没有 stateId / statusId 之类概念。
- 状态表达方式是 computed 直接返回 {label:'保存待核对', tone:'danger'}——中文文案就是状态本身。
- 原型 9 个 id 在软件里对应命中：pending 18 处、failed 44 处、stopped 15 处，但那是普通英文单词的偶然命中，**不是枚举**；clean / dirty / staged / over-budget / uncertain 五个核心 id = **0**。

### 2.2 tone 词表已经分裂成三套

| 值 | 出现次数 | 有无样式 |
| --- | --- | --- |
| bad / ok / busy | 3 / 2 / 2 | 有（overview-check-value、motion-check-value） |
| danger / warning / success / info / neutral | 2 / 2 / 2 / 1 / 1 | **部分没有**（.tag.danger 有，.tag.warning 与 .tag.success **无定义**） |
| warn / muted | 1 / 1 | warn 只在 ClientsPanel 自建类里成立 |

同一语义三种名字：warn（扩展页）、warning（模型页）、bad（概览/画质）。改一处样式不会连带生效，只能逐个补。

### 2.3 同一状态在不同文件说法不同（这不是风格差异，是事实冲突）

ClientLoadStatus.vue 与 ChannelsView.vue 各有一份 clientState 文案表，同一个后端状态两种写法：

| 后端状态 | ClientLoadStatus | ChannelsView |
| --- | --- | --- |
| restart_required | 已写入 · 待重启 Codex | 已写入 · 待重启 Codex |
| pending_verification | 运行目录一致 · 待客户端验证 | **已写入** · 待客户端验证 |
| runtime_changed | 运行配置已变化 · 待重新比较 | **运行配置变化** · 待核对 |
| not_required | 本次无需重启 | **已写入** · 无需新增重启 |

后两组在「是否已经写入」这一点上说法不一致。这正是 WP-66 看到的三处矛盾的来源之一：**同一个状态被两处翻译，且翻译结果不同**。

### 2.4 后端的 phase 有 21 个值，前端只认识 4 个

runtime.rs 里 plan.phase 的赋值共 21 种：prepared、applying、committed、compensated、compensating、verified_partial、providers_written、credentials_registered、order_written、runtime_verified 等。

前端 ChannelsView.vue:73 只对 4 个值有分支：

    !['prepared','committed','compensated'].includes(phase) ? {label:'保存待核对',tone:'danger'} : …

即：**其余 17 个中间态（含 applying、verified_partial、compensating）全部被压成同一个红字「保存待核对」**。用户无法区分「正在写」「部分核实通过」「正在回滚」——而这三件事的应对方式完全不同。

这是统一化最该解决的实际问题，不只是美观。

## 三、为什么现在直接做组件会做错

1. **无可统一的对象**：没有状态码，组件入参只能是中文 label，等于把文案搬个地方，语义仍散落。
2. **tone 没有唯一词表**：三套并存，组件一旦定下 5 类，18 个消费点里至少 6 处要改语义判断，而判断逻辑现在还写在各自的 computed 里。
3. **后端单据没对齐**：21 个 phase 若要显示成有意义的少数几种结论，必须先定义「哪些 phase 归为已写入 / 待核对 / 已回滚」，这是语义决策，不是样式决策。
4. **原型只覆盖一页**：全站统一属新增规格，按 §36 / §40 应先回写原型，不能在软件里自由发挥。
5. **已有约定要求先登记**：components/registry.ts 的 kind 只有 component / recipe / platform / prototype_only，新增公共组件需登记并接 gallery；UI规范 §3 明确「页面状态标签 .tag」是既有公共配方，直接新造一套会形成第三套。

## 四、建议路径（若将来批准）

分四步，前两步是文档与契约，不写组件：

| 步 | 内容 | 产出 | 是否需先改原型 |
| --- | --- | --- | --- |
| 1 | 定 **tone 唯一词表**：neutral / info / success / warning / danger 五类，废弃 ok、bad、busy、warn、muted 别名 | UI 规范新增一节 | 否 |
| 2 | 定 **状态码表**：把原型 9 态 + 后端 21 phase 收敛成结论级状态（预计 7～9 个），并写明每个 phase 归属 | 数据与状态 §5.8 补充 + 映射表 | 否 |
| 3 | 原型补「统一状态标签」样例（跨页同一组件的外观与密度），确认后再进软件 | 原型 + 注释 | **是** |
| 4 | 软件实现 UiStatusTag（入参 = 状态码 + tone，不接中文），逐页替换 17 处消费点，加源码门禁「禁止新增 data-tone 别名」 | 组件 + registry + gallery + 门禁 | 否（做完第 3 步后） |

第 2 步是真正的难点，也是价值所在：**把 21 个 phase 压成用户能行动的少数几种结论**。举例可考虑的归并（仅为示意，未定稿）：

- prepared → 未开始写入
- applying、providers_written、order_written、writing_*、registering_new → 正在写入
- committed、runtime_verified、credentials_verified → 已写入
- verified_partial → 部分核实（需核对）
- compensating、compensating_direction → 正在回滚
- compensated → 已回滚

## 五、与 WP-66 的关系

WP-66 是这一条的**症状**：三处状态并存，且「待核对」与「已写入」互相矛盾。根因有两层，WP-67 是更深的一层：

- 表层（WP-66）：把两套状态（savePlan / clientState）都摊在列表页，且没按原型密度收住入口。
- 深层（WP-67）：状态没有 id、tone 三套词表、同一状态两处翻译、21 phase 压成 1 个红字。

**只修 WP-66 会把矛盾藏起来，只有做 WP-67 才能让状态可信。** 建议顺序：先 WP-67 的第 1、2 步（定词表与状态码），再回头一并修 WP-66 的布局。

## 六、本轮边界

- 未改任何代码、未改原型；仅新增本记录。
- 未验证：真实账号下 verified_partial 与 compensating 的实际出现频率（决定归并粒度）；窄窗与触屏下 chip 的换行表现。
