# Desktop0.2.22渠道保存基线诊断

2026-11-10，用户截图提示“未写入：保存基准已变化，请重新核对；当前输入已保留。”用户询问是否由OpenCodex2.99引起。本轮只分析和隔离复现，未读取日常配置、运行服务或执行真实保存。

## 结论

这是Desktop自身的前端保存基线冲突，不是截图已经证明上游2.99拒绝写入。精确文案在v0.2.22 commit1b5c8402dc340540711efa2c2c2037bce673a479的features/models/store.ts:273；ChannelsView.vue:145加上“未写入：”后与截图完全一致。

saveAllChannels在任何model_file_save IPC前检查expected、channelBaseline和snapshot.policyDigest，任一不一致立即抛错。它不访问2.99的提供方JSON编辑器PUT路由，也不需要2.99才能触发。后端真正文件冲突使用另一个file_changed错误及文案。

## 已复现触发链

1. 页面从文件摘要A读取，用户修改渠道/模型，草稿未保存。
2. 后来store.load拿到文件摘要B。load总是替换snapshot，但因草稿有编辑而保留channelDraft及channelBaseline=A。
3. 再点击列表保存，expected=A、channelBaseline=A，但snapshot.policyDigest=B，前端直接拒绝；未调用文件写入IPC，草稿保留。再次点保存仍是同样状态，单纯重复点击不能解开。

ModelsRoute.vue:84～88在挂载和model-config-changed事件调用load；切页重新挂载或其它配置操作触发事件是可达入口。此处只证明刷新路径可达，不反推用户本次具体做过哪种操作或何进程改过文件。

使用原版tag的真实Pinia store与ChannelsView，模拟API回执，5项验证通过：正常保存；相同模型策略但不同文件摘要在脏草稿刷新后拒绝且重复保存无效；实际点击确认产生截图完全一致Toast；同摘要刷新可继续保存；真实模型字段变化保持冲突并保留草稿。整个验证没有OpenCodex运行包，所以“必须2.99才出现”已被反例否定。不同摘要回执是合成输入，不能以此声称真实2.99只改了某个记账字段。

原版Rust snapshot_value以整个config.json字节SHA256给policyDigest；后端manager_view_digest/runtime_only_change已排除部分modelDiscovery及Claude appliedAt等记账字段。但前端此拦截发生在调用后端前，未机会使用该有限语义比较。这给出“仅后台记账改写也可能使保存被提前拦截”的具体链；仍不能取消真正外部编辑的乐观并发保护。

## 与已记录POST-04的关系

此前2.99的provider editor baseline is stale是内置面板公开DTO与磁盘读取/归一化不一致的HTTP保存入口。当前是Desktop模型渠道列表的本机store状态分歧；错误类别相近，代码路径和已复现原因不同。作为POST-04的Desktop保存子问题单独跟踪，不把两者写成已证明同一根因，也不另扩版本范围。

2.99可能更频繁改写配置并触发这条旧缺陷，但任何导致新摘要的其它写者/格式变化/真实外部编辑也可触发。截图无法确定实际运行包版本、改变字段和写者；本轮不冒称用户现场已精确归因。0.2.23/后继新store不能仅凭版本号断言已修复，需按对应实现补同场景回归。

## 后续修复与使用边界

读取更新不能只替换snapshot造成双基准悬空。应绑定草稿原基线与新观察分别保存：仅记账/格式变化经同一语义合同核对后可安全推进基线；真实渠道变化要列冲突/明确重核并保留草稿、Key意图和导入来源，再允许提交。最终写入时仍由后端锁内重新核验，不能简单把channelBaseline改成最新摘要或删掉assert来覆盖别人修改。

已有“还原修改”会从新snapshot重建草稿并清掉未保存凭据意图；它是放弃草稿，不是无损重核。不能直接建议用户点击还原/重启来修复而不说明未保存输入会丢失。当前截图表明本次尝试没有执行文件写入，不代表先前其它操作均未写入。

证据：.adg/evidence/0.2.23/post-release-20261110/desktop022-save-baseline/。首轮UI测试快照缺少tagged tauri/config注册表而未执行用例，原失败保留；补齐同tag配置后5例通过。API均为合成回执、无网络/秘密/日常文件访问；临时快照及依赖链接已清理，软件源码未改。
