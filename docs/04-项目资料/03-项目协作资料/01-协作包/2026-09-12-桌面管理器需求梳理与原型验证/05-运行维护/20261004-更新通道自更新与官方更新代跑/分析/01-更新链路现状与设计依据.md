# 更新链路现状与设计依据

> 2026-10-04 分析／设计快照；当前归属与发布状态见 [维护摘要](../README.md)。

维护 ID：MNT-OPENCODEX-DESKTOP-20261004-03。分析日期：2026-10-04。承接 [MNT-02 更新通道现状与证据](../../20261004-更新通道与配置分层/分析/01-更新通道现状与证据.md) 与 `REL-OPENCODEX-DESKTOP-03` 的延期项；只给设计要点，不预写执行结果。

## 1. 三条链路复述

| 链路 | 更新对象 | 0.1.2 状态 |
|---|---|---|
| 桌面管理器自身自更新（Tauri Updater） | `OpenCodeX Desktop.app` | 端点/公钥/制品管线三处仍占位 |
| 官方 OpenCodex 版本卡片（管理器内） | 只读展示 `ocx --version` | 只做本地事实，无远端比较 |
| 官方本体更新 | `@bitkyc08/opencodex` | 由用户终端执行；官方面板更新器对托管/自定义前缀不安全 |

## 2. 桌面自更新（U-01 / U-02）实施要点

- 端点：改用本仓库 GitHub Releases 的 `latest.json`（stable）与 `beta.json`（beta）作为 `endpoints`，替换 `runtime.defaults.json` 中 `updates.desktop.channels` 的占位地址。
- 公钥：用 `tauri signer generate` 生成 minisign 公私钥；公钥写入 `tauri.conf.json` 的 `pubkey`（编译期常量，不可运行时配置）。
- 制品：`tauri.conf.json` 打开 `bundle.createUpdaterArtifacts`；`release.yml` 注入 `TAURI_SIGNING_PRIVATE_KEY`，产出 `.sig` 与 `latest.json` 并作为 Release 资产。
- 命令层：`commands/update.rs` 已按当前通道端点构建 updater；需确认真实端点的 `latest.json` 结构与 `{{target}}`/`{{arch}}` 模板一致。
- 安全边界：TLS 校验、签名校验保持；失败保留上一版本。

## 3. 官方版本卡片（U-03）实施要点

- 新增只读远端查询：`npm view @bitkyc08/opencodex@latest version` 与 `dist.integrity`（带超时、脱敏、失败不改写本地状态）。
- 与本地 `runtime.json` 的 `resolved_version` 比较，显示「有可用更新」。
- 查询（只读）与安装（写）分开；查询不产生副作用。
- 保留既有「官方卡片只跑本地 `ocx --version`」为基线，新增远端结果作为增强展示。

## 4. 代跑官方更新（U-04）实施要点

- **复用**桌面管理器已有的受控安装 `install_runtime`（`apps/desktop/tauri/src/modules/runtime/install.rs`，命令 `commands/runtime.rs::install_runtime`）：`InstallSource::Registry { version: <tag>, proxy }`，`prefix` 取当前登记前缀。
- 覆盖既有安全路径：`npm install --prefix <前缀>`（不落全局）、`.runtime-manifest.json` 记录、离线包、代理、`allow_scripts`、取消、重启提示。
- **不**调用官方面板更新器去改托管 / 自定义前缀（其对布局的假设不成立）。
- 候选绑定：先解析 tag 成确定版本，再安装该版本与完整性信息，避免浮动 `latest`。

## 5. C 阶段存储迁移（可选）

- 是否纳入 0.1.3 待评审；若纳入，须交付磁盘嵌套 + 容器 / 同步兼容投影，并复用 0.1.2 的迁移引擎与沙箱测试。

## 6. 限制与边界

- 生成签名私钥与写入 CI secrets 属发布安全操作，需单独确认。
- 端点可配置、**公钥不可运行时配置**，是安全边界。
- 查询远端会产生网络访问，需超时、脱敏与失败不改写本地状态。
