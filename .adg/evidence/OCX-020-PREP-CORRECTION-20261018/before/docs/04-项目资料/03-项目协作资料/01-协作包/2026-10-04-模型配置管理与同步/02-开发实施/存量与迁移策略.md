## 1. 现状与存量分类

### 1.1 四类实际存量

| 存量类型 | 来源与用户可见性 | 0.2.0处理策略 | 备注 |
|---------|------------|----------|-----|
| **0.1.10 DB存量** | 已发布用户本机运行数据库（models表），路径：`~/Library/Application Support/OpenCodeX/data.db` | 初次启动时自动检测、备份、身份映射、三级验收后迁移到新schema | 含active/inactive型号，只迁active=1的记录 |
| **OpenCodex运行配置** | Codex主线2.69.0对应的渠道/提示词/模式选择（非Desktop管理） | 检测依赖，保留隔离存储；不建立Desktop → Codex双向同步 | 调研证据见本地调研依据.md§VersionMatrix |
| **原型示例与演示数据** | 产品原型中嵌入的mock模版（用于UI演示） | 独立基线，不与真实迁移混合，发布前清理 | 不作为生产模版库的初始值 |
| **旧导出格式与跨机移植** | 用户手动导出的0.1.10兼容json或WebDAV上传 | 作为导入入口，merge到草稿待确认采用；旧格式与新schema冲突时记录差异 | WP-04双文件导入导出管理 |

**关键约束**：
- 不为不存在的历史假设新增迁移器；生成存量证据优先于编码
- 初次建库 ≠ 迁移旧库；新用户不触发migration逻辑
- 旧客户端（0.1.10）安装0.2.0时触发一次迁移；回滚需专用恢复工具

## 2. 初次建库契约

### 2.1 四步初始化流程

**前提**：0.2.0首次启动，检测是否存在可迁移的0.1.10 DB

```
Step 1: 种子数据加载
  ├─ 检查: {APP_DATA}/opencodex_0110.db 是否存在
  ├─ 存在 → 进入迁移流程 (§3)
  └─ 不存在 → Step 2 (新用户)

Step 2: 身份生成与基线冻结
  ├─ 创建内置基线模版集合
  │  ├─ templateId: UUID v4 (保留不变)
  │  ├─ revisionId: 时间戳 + 短标识 (保留不变)
  │  ├─ source: "builtin"
  │  └─ mutable: false
  ├─ 生成初始 model-family-templates.json
  └─ 初始化空 model-policy.json (渠道无默认采用)

Step 3: 完整性检查
  ├─ 校验 templateId 无碰撞
  ├─ 校验 revisionId 递增且唯一
  ├─ 校验 MatchRules 无自相矛盾
  └─ 校验文件可读可写 (权限检查)

Step 4: 隔离存储
  ├─ 存放路径: {APP_DATA}/model/templates/
  │  ├─ model-family-templates.json (只读指针 + 版本正文)
  │  ├─ model-policy.json (渠道采用引用)
  │  └─ .backup/ (多版本历史)
  └─ DB连接: {APP_DATA}/opencodex-0.2.0.db
     ├─ 表: model_templates (新schema)
     ├─ 表: model_policies (引用指针)
     └─ 表: migration_audit (迁移历史)
```

## 3. 升级路径：三阶段迁移流程

### 3.1 Phase 1：备份与检测

```
前提条件检查：
├─ opencodex_0110.db 存在且可读
├─ 版本号确认为 0.1.10
└─ 数据库表结构与预期相符

执行备份：
├─ cp {OLD_DB} {BACKUP_DIR}/opencodex_0110_{timestamp}.db
├─ 记录备份路径到 migration_audit
└─ 备份文件置为只读 (chmod 444)

异常处理：
├─ DB打开失败 → 降级为"仅新建"，记录失败原因
├─ 表结构不匹配 → 提示"数据库可能已损坏"，建议用户恢复
└─ 备份失败 → 中止迁移，保留0.1.10原状
```

### 3.2 Phase 2：身份映射

```typescript
// 伪代码：字段映射与身份生成

interface OldRecord {
  id: number;
  name: string;
  endpoint: string;
  active: 0 | 1;
  // ... 其他字段
}

interface NewRecord {
  templateId: UUID;       // 新生成
  revisionId: string;     // 时间戳 + 短标识
  name: string;           // 保留
  description: string;    // 从 endpoint 推断
  source: "migrated";     // 标记来源
  createdAt: timestamp;   // 使用旧 DB 的修改时间
  config: {
    endpoint: string;     // 直接复用
    protocol: string;     // 从 endpoint 推断 (openai-api / anthropic / custom)
    window: number;       // 使用已知模型的默认窗口
    modal: "streaming";   // 默认流式
  };
  matchRules: {
    protocol: string;     // 推断的协议
    channel: "all";       // 初始化时不限制渠道
  };
}

// 生成映射表（用于恢复及对账）
const migrationMap: Record<oldId, NewRecord> = {};
for (const oldRecord of oldRecords) {
  if (oldRecord.active === 0) continue; // 跳过非活跃

  const templateId = generateUUID();
  const revisionId = `${Date.now()}_${shortHash()}`;
  
  migrationMap[oldRecord.id] = {
    templateId,
    revisionId,
    name: oldRecord.name,
    description: inferFromEndpoint(oldRecord.endpoint),
    source: "migrated",
    createdAt: oldRecord.modifiedAt || Date.now(),
    config: { endpoint: oldRecord.endpoint, ... },
    matchRules: { protocol: inferProtocol(oldRecord.endpoint), ... }
  };
}

// 记录映射表（用于失败恢复）
await writeMigrationLog(migrationMap);
```

### 3.3 Phase 3：三级验收与提交

```
Level 1: Schema 校验 (dry-run)
├─ 转换后的每条记录必须满足生产 schema
├─ 检查冲突字段 (templateId 碰撞、revisionId 递增性)
├─ 如有异常 → 记录详细错误，不进行下一级

Level 2: 事务隔离写入
├─ 开启事务，执行所有INSERT
├─ 不实际提交 (rollback 前验证约束)
├─ 校验外键、唯一性约束
├─ 如有异常 → rollback，保留0.1.10 DB不变

Level 3: 原子性提交
├─ 再次开启事务
├─ 逐条INSERT新记录
├─ INSERT migration_audit 记录
├─ COMMIT (一体原子)
├─ 验证旧 DB 标记为"已迁移"(readonly flag)
└─ 返回成功与迁移计数
```

## 4. 故障与恢复链

### 4.1 五类故障场景

| 故障类型 | 检测点 | 恢复策略 | 用户影响 |
|---------|--------|----------|----------|
| **导入中断** | Phase 3 事务提交前中断 | 自动 rollback，保留 0.1.10 DB 不变 | 可重新尝试迁移 |
| **字段冲突** | Phase 3.1 dry-run 校验失败 | 提示冲突字段列表，提供"跳过/手动映射"选项 | 需用户介入决策 |
| **数据库损坏** | 打开 0.1.10 DB 失败 | 尝试从最近备份恢复，无备份则降级为"仅新建" | 旧数据丢失风险，提示检查备份 |
| **revisionId 碰撞** | Phase 2.2 UUID 生成重复（极低概率 <10^-15） | 重新生成 UUID；记录碰撞日志 | 无，自动重试 |
| **用户主动回滚** | 迁移完成后用户选择"恢复0.1.10"选项 | 调用备份恢复工具，清除0.2.0 DB | 丢失迁移后新增数据；需明确警告 |

### 4.2 恢复链集成

```typescript
interface MigrationAudit {
  id: UUID;
  fromVersion: "0.1.10";
  toVersion: "0.2.0";
  timestamp: number;
  status: "success" | "partial" | "failed";
  recordCount: number;
  backupPath: string;
  errorLog?: string;
  mappingLog?: string;  // 身份映射记录，用于对账
}

// 恢复入口
async function restorePreviousVersion(auditId: UUID) {
  const audit = await db.query(
    "SELECT backupPath, errorLog FROM migration_audit WHERE id = ?",
    [auditId]
  );
  
  if (!audit || !fileExists(audit.backupPath)) {
    throw new Error("Backup not found");
  }
  
  // 调用备份管理器
  await backupManager.restore(audit.backupPath);
  
  // 清除 0.2.0 数据
  await newDB.exec("DROP TABLE IF EXISTS model_templates, model_policies, migration_audit");
  
  // 记录恢复事件
  publishEvent("migration.rollback", { auditId, timestamp: Date.now() });
}
```

## 5. 迁移验收样例

### 5.1 E2E Fixture：升级场景

```yaml
# test/fixtures/migration/0110-to-020-upgrade.yaml
name: "0.1.10 典型用户升级测试"
scenario: "用户从0.1.10升级到0.2.0，系统自动迁移三个模型配置"

GIVEN:
  - 旧数据库位于: /tmp/test-old.db
  - 旧表 models 包含记录:
      - { id: 1, name: "GPT-4", endpoint: "https://api.openai.com/v1/...", active: 1 }
      - { id: 2, name: "Claude-3", endpoint: "https://api.anthropic.com/...", active: 1 }
      - { id: 3, name: "DeepSeek", endpoint: "https://api.deepseek.com/...", active: 0 }
  - 新数据库 0.2.0 尚未初始化
  - 备份目录: /tmp/backups

WHEN:
  - 执行 `migrateFrom0110()`

THEN:
  - 备份文件存在于: /tmp/backups/opencodex_0110_*.db
  - 新数据库 model_templates 表包含 2 条记录（仅 active=1）
  - 每条记录必含:
      - templateId: UUID v4 格式
      - revisionId: 时间戳+短标识格式
      - createdAt: Unix 时间戳
      - source: "migrated"
  - migration_audit 表记录 1 条：fromVersion="0.1.10", recordCount=2, status="success"
  - 旧数据库标记为 readonly，保持不变

VERIFY_ROLLBACK:
  - 调用 `restorePreviousVersion(auditId)`
  - 新数据库被清空 (model_templates 记录数=0)
  - 旧数据库文件完整性校验通过 (md5 匹配)
  - 恢复事件已发布: "migration.rollback"
```

### 5.2 单元测试位置

**将创建以下测试文件**（实施时补充）：

- `test/unit/migration/identity-mapping.test.ts`
  - 验证 templateId 无碰撞
  - 验证 revisionId 递增性
  - 验证 UUID 生成的确定性（given seed）

- `test/unit/migration/dry-run-validation.test.ts`
  - 验证 schema 校验逻辑
  - 验证冲突检测与错误消息
  - 验证字段映射的正确性

- `test/integration/migration/full-upgrade-flow.test.ts`
  - 端到端迁移测试（包含备份、三级验收、提交）
  - 验证旧 DB 完整性保留
  - 验证恢复链可用性

**测试运行约束**：
- 使用隔离的测试 DB，不修改用户数据
- 所有测试在 CI/CD 中按顺序运行，避免竞态
- 迁移成功率应 ≥ 99%（即使字段冲突也应优雅降级）
