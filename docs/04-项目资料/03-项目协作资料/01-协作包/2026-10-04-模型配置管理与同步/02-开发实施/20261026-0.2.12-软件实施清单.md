## 0. 一句话结论

五条问题分三组，**共用一套「时效」语言**（瞬时 → 短期 → 长期），但互不阻塞：

| 组 | 包含 | 性质 | 风险 |
| --- | --- | --- | --- |
| A. 保存通知化 | WP-69 | **删**状态机，改成一条通知 | 中（动保存主链路） |
| B. 时效统一 | WP-70 + WP-73 | 一套判定，三处出口 | 低（纯前端 + 删死字段） |
| C. 测速闭环 | WP-72（+ WP-71 清理入口） | 认证接进探测链 | 中（碰凭据边界） |

**建议顺序：B → C → A**。B 是纯前端且立刻消除刷屏；C 修好测速后 B 的失败卡才不再产生；A 最后做，因为它是唯一会中断对话（重启 Codex）的一条。

## 1. 组 B：时效统一（建议先做）

### B-1 WP-73 悬浮任务卡堆积

| 段 | 内容 |
| --- | --- |
| 现象 | 右上角堆 10 张「节点连接检测 · 未完成」，压住渠道表格 |
| 根因 A | tasks.ts:34 淘汰白名单只有 succeeded / stopped，**failed 永不入候选**，超 24 条直接 break |
| 根因 B | useNodeMeasurements.ts:15 每次 measure 都新 UUID → 同一件事重做 N 次 = N 张卡，无合并维度 |
| 根因 C | AppTopbar.vue:62 togglePanel() 调 expandAll()，**点铃铛把所有收起全反悔** |
| 根因 D | base.css:336 只有高度上限，**无条数上限** |
| 修法 | ① failed 入淘汰候选（超限淘汰最老终止态）② node_measurement 按 kind+channelId 合并为一张（显示「×N」）③ 终止态 8 s 后 collapsed=true（**不删除**）④ 删掉 togglePanel 里的 expandAll ⑤ 同时最多 3 张 |
| 断言 | 连点 10 次「检测全部节点」→ 任务卡始终 ≤ 1 张（合并）；点铃铛不展开任何卡；终止态 8 s 后自动收起且铃铛里仍在 |
| 原型 | **必须同步改**：原型目前只有「单张收起」，无 TTL / 合并 / 上限 |

## 2. 组 C：测速闭环

### C-1 WP-72 列表测速恒定缺认证

| 段 | 内容 |
| --- | --- |
| 现象 | 渠道列表 → 服务节点下拉 → 检测节点，一律「认证失败」 |
| 实测 | 同一地址不带 Key → 401（1.02 s）；带 Key → 200（0.69 s）。**端点通、链路通，只是没带 Key** |
| 根因 ① | ChannelNodeSelect.vue:9 `useNodeMeasurements(() => props.channel, () => '')` —— 取 Key 函数恒返回空串 |
| 根因 ② | upstream.ts:33 读现有渠道时写死 `credentialRef: null`；实盘 26 渠道仅 1 个有 ref |
| 后果 | discovery.rs:130-142 拿到 provided/stored 全 None → 不带认证头发出 → 401 → discovery_auth |
| 修法 | ① discovery 在 provided 与 credential_ref 都空时，按 providerId 去 config.json 读该渠道 apiKey ② **必须校验节点 URL 与 baseUrl 同源**（scheme+host+port）才携带 ③ 失败分「服务拒绝」与「该节点无可确认凭据」两种原因 ④ 三处入口（列表下拉 / 详情 / 读取弹窗）统一取 Key 口径 |
| 断言 | 列表下拉点「检测节点」→ 真实返回耗时与模型数；节点 URL 改到别的域名后不再携带旧 Key；无凭据时文案不是「认证失败」 |
| 依赖 | 无（可独立做） |
| 注意 | **不新增凭据存储**，不把官方 Key 复制进钥匙串（符合「就是写入文件」口径） |

### C-2 WP-71 通知中心一键清理

| 段 | 内容 |
| --- | --- |
| 现状 | 后端 clear_notifications 有、store clearAll() 有（store.ts:113），**面板就是没按钮**；clearAll 全前端只有 stores/app.ts:661 一处委托 |
| 原型 | index.html:3007-3008 **只有 2 个**：历史 / 全部已读 |
| 软件改前 | **3 个**：历史 / 全部已读 / 清理已解决（多出来的「清理已解决」原型没有） |
| 修法 | ① 保留 历史 / 全部已读 ② 「清理已解决」并入清理入口，不单占位 ③ 新增「清理」→ 二次确认「将清理 N 条（含 M 条未处理）」→ clearAll() ④ 清理时顺带跑一次保留期清理 ⑤ **不新增后端命令** |
| 副产 | 修设置页语义错位：`cleanup_local_notifications` 实际就是清空全部（cleanup.rs:57-62），文案却写「按保留期清已读」 |
| 断言 | 面板按钮数回到原型口径；点清理能清掉全部（含未读）且二次确认写明数量 |
| 原型 | **也要改**（新增清理入口） |

## 3. 组 A：保存通知化（最后做）

### A-1 WP-69 删状态机，改成一条通知

| 段 | 内容 |
| --- | --- |
| 现象 | 重启 Codex 后仍「已保存 · 待重启」；且写入后不生效 |
| 根因 | client_state.rs:85-100 只看磁盘是否有 committed 且有变化的计划，**与用户是否重启无关** |
| 用户口径 | 「就是写入文件，然后重启肯定生效」+「执行完的通知提示就行了」 |
| 目标流程 | 点保存 → 预览 → 确认 → `ocx provider apply --baseline --file - --json --yes` → ok 则通知「已写入」+ [立即重启 Codex] / [稍后]；失败则通知「未写入」+ [重新保存] |
| 要删 | restart_required / pending_verification / user_confirmed / runtime_changed 四态；check() 运行时读取；客户端核对弹窗；verified_partial 判定；**不做 file_truth 比对** |
| 要留 | abandon / 撤回（崩溃兜底）；0.2.11 的「check 不被无关计划阻塞」 |
| 重启入口 | `ocx sync-cache --restart-codex`（只写 models_cache.json，**不碰 config.json**；缓存没变则不重启，幂等）；**不要用 `ocx sync`**（会重写目录） |
| 断言 | 保存成功 → 通知 1 条 + 两个按钮；点「立即重启」→ Codex 重启且选择器加载新模型；点「稍后」→ 只关通知，无残留状态 |
| 风险 | 「立即重启」会中断正在进行的对话，**二次确认必须写明** |
