## 0. 先纠正一个前提（本轮最重要的发现）

WP-67 初稿说「项目里没有统一做法」，**这是错的**。核对后发现项目里已经有一套**成熟且正确**的统一状态机制，只是有两个页面没接入：

| 已有资产 | 位置 | 作用 |
| --- | --- | --- |
| `StatusMatrix` 四类枚举 | `contracts/runtimeStatus.ts` + `tauri/src/types/status.rs` | `RuntimeState`(11) / `ConnectionState`(7) / `OperationState`(8) / `HealthState`(4) |
| **单一文案表** | `lib/labels.ts` | `RUNTIME_LABELS` / `CONNECTION_LABELS` / `OPERATION_LABELS` / `HEALTH_LABELS`，附文件头注释「界面**不得**直接渲染原始值」 |
| **派生态** | `features/runtime/scenarios.ts` | 枚举 → `{label, pillClass, badgeClass, health, actions}`，把「文案 + 视觉 + 可用动作」绑在一处 |
| **视觉 tone 类** | `styles/base.css:216-222` | `.state-pill` + `state-running / state-starting / state-pending / state-warn / state-bad / state-muted`（5 类 + 1 中性，带 8px 圆点） |
| 连接态派生态 | `features/sync/states.ts` | `ConnectionState` → `{tag, conn, conflict, actions}` |

所以**不需要新建架构**，需要的是**把已有机制接入剩下两个域，并补一个它没覆盖的域**。这比 WP-67 初稿估的代价小得多。

### 那到底缺什么（三件，都是具体的）

| # | 缺口 | 证据 |
| --- | --- | --- |
| 1 | **模型保存域不在四类枚举里** | 23 个 `plan.phase` 是 model_config 私有字符串，既不属于 `OperationState` 也不走 `lib/labels.ts`；前端只认识 4 个，其余压成红字 |
| 2 | **模型页 / 扩展页自建了第二套 tone** | `data-tone="warning"`（ChannelEditor、ModelsRoute、ClientsPanel 用 `warn`），而公共的是 `state-warn`/`state-bad`；且 `.tag.warning` / `.tag.success` **无 CSS 定义** |

## 1. tone 唯一词表（评审项 A）

### 1.1 现状：3 套并存

| 词表 | 值 | 用在哪 |
| --- | --- | --- |
| **公共（已有）** | `state-running / state-starting / state-pending / state-warn / state-bad / state-muted` | 顶栏状态胶囊（`AppTopbar`）、托盘 |
| 模型/扩展页自建 | `data-tone = success / warning / danger / info / neutral` | `ChannelEditor`、`ModelsRoute`、`ClientsPanel` |
| 零散 | `bad / ok / busy / warn / muted` | 概览检查行、画质检查行、ClientsPanel |

### 1.2 提案：五类语义 + 一个中性，别名全部废弃

| 语义 | 唯一类名 | 用于 | 废弃的别名 |
| --- | --- | --- | --- |
| 正常运行 / 成功 | `state-running` | 运行中、已同步、已完成、连接检查通过 | `success`、`ok` |
| 进行中 / 信息 | `state-starting`（或 `state-pending`） | 启动中、同步中、应用中、校验中 | `info`、`busy` |
| 需注意 / 待处理 | `state-warn` | 待重启、待核对、部分完成、存在风险 | `warning`、`warn` |
| 失败 / 危险 | `state-bad` | 保存失败、连接失败、不可达 | `danger`、`bad` |
| 中性 / 未开始 | `state-muted` | 未修改、未配置、未运行、已取消 | `neutral`、`muted` |

**关键决定要你确认**：

1. **保留 `state-*` 命名**（复用已有 CSS 与语义），还是改成 `data-tone` 属性？<br>建议**保留 `state-*`**：已有 6 条 CSS + 圆点伪元素 + 顶栏在用，改名要动 12 处消费点却零收益。
2. **`.tag.warning` / `.tag.success` 要不要补定义？**<br>现状是「声明了但没样式」，等于静默退化为中性。建议补，或统一改走 `state-*`。
3. `state-starting` 与 `state-pending` 现在共用同一套样式（蓝色）。是否合并成一个 `state-progress`？

## 2. 状态码表（评审项 B）

### 2.1 模型保存域：23 phase → 7 结论

后端 `runtime.rs` 的 `plan.phase` 实际有 **23 个值**（20 个 `.phase=` 赋值 + 3 个结构体字面量 `prepared`/`staging`/`pending_active`）：

| 结论级状态（提案 id） | 含义 | 归入的 phase | tone |
| --- | --- | --- | --- |
| `save_idle` | 没有进行中的保存 | （无 plan） | muted |
| `save_prepared` | 已冻结计划，尚未写入 | `prepared` | muted |
| `save_staging` | 正在准备草稿 / 暂存 | `staging` | starting |
| `save_applying` | **正在写入** | `applying`、`providers_written`、`order_written`、`visibility_written`、`hiding_none_selection`、`writing_credentials`、`writing_imported_authorizations`、`registering_new`、`new_registered`、`credentials_registered`、`history_providers`、`history_authorizations`、`history_registering`、`pending_active` | starting |
| `save_verified` | 写入完成并核实 | `committed`、`runtime_verified`、`credentials_verified` | running |
| `save_partial` | **部分核实通过，需核对** | `verified_partial` | warn |
| `save_rolling_back` | 正在回滚 | `compensating`、`compensating_direction` | warn |
| `save_rolled_back` | 已回滚 | `compensated` | muted |
| `save_failed` / `save_cancelled` / `save_unknown` | 失败 / 取消 / 结果未知 | （`SavePlan.error` + 超时态，非 phase） | bad / muted / warn |

注：14 个 `applying` 子阶段是否需要暴露给用户，取决于一个**未定问题**——见 §4 待裁决 1。

### 2.2 三个域的最终状态码（与已有枚举对齐）

| 域 | 状态码来源 | 值数 | 现状 |
| --- | --- | --- | --- |
| 运行时 | `RuntimeState`（已有） | 11 | ✅ 已统一，走 `lib/labels.ts` + `runtimeScenarios` |
| 连接 | `ConnectionState`（已有） | 7 | ✅ 已统一，走 `lib/labels.ts` + `webdavStates` |
| 通用操作 | `OperationState`（已有） | 8 | ⚠️ 有枚举有文案，但**无派生态**（无 tone、无动作），且**缺「部分完成」与「待确认」** |

| 模型客户端加载 | 无（`ModelClientState.status`） | 5 | ❌ 两处各译一份，3 个说法不同 |

### 2.3 `OperationState` 的缺口（这是真问题）

`OperationState` = `rolling_back / applying / backing_up / validating / failed / succeeded / cancelled / idle`。

缺两个原型明确要求的状态：

| 缺什么 | 原型怎么说 | 后果 |
| --- | --- | --- |
| **部分完成** | `index.html:3756` `OP_RESULTS.partial`「部分步骤未生效；已完成项与未完成项如下」 | 只能退化成「失败」或「成功」，用户不知道哪些生效了 |
| **待确认** | `index.html:3764` `OP_RESULTS.unconfirmed`「等待超时或核验未决；不假称成功或失败」 | 对应 `verified_partial` / 超时，现在被压成「保存待核对」红字 |

而 `数据与状态 §5.8` 已经把这两条写进契约（「部分完成、待重启生效」「等待超时、结果未知」）。**枚举没跟上文档。**

## 3. 落地形状（评审项 C）

若 A/B 通过，落地是这样的——**不新建框架，复用已有三件套**：

```
后端                             前端契约                      派生态                   渲染
plan.phase (23)  ──映射──▶  SaveState (7~10)  ──▶  saveScenarios      ──▶  <UiStatus state=... />
RuntimeState (11) ─────────▶  RuntimeState      ──▶  runtimeScenarios   ──▶  .state-pill   （已有）
ConnectionState(7)─────────▶  ConnectionState   ──▶  webdavStates       ──▶  .state-pill   （已有）
OperationState (8→10)──────▶  OperationState    ──▶  operationScenarios ──▶  .state-pill   （补）
```

**映射放在前端**（`lib/labels.ts` 同目录新增 `saveStates.ts`），理由：

- 后端 phase 是事务内部节奏，可能继续增删；映射到用户结论属展示语义，按 §36 归前端。
- 不改后端即可先统一界面，风险最小。
- 若将来后端也愿意产出结论级状态，这个映射表可整体下移，界面无感。

**渲染统一复用 `.state-pill` + `state-*` 六类**，模型页那个 `●` 文字圆点改成伪元素圆点（与顶栏一致）。

## 4.1 确认：统一后不会再有那两行（附实测）

用户问：「这样就不会像当前软件一样多出两行了吧？」——**是**，且不会丢功能。逐项核对：

| 当前这两行 | 提供什么 | 统一后的归宿 | 会不会丢 |
| --- | --- | --- | --- |
| `已写入 · 待重启 Codex` + `重启后重新检查` | 客户端加载态 | 并入状态框子标签（原型 `mp-policy-pending` 的位置），检查入口按原型收成 28px 图标键 | 不丢 |
| `上次保存尚未完成核对` + `查看原保存结果` | 上一次保存结果详情 | 「保存结果」弹窗仍可从**通知中心**打开 | 不丢（见下） |

### 「查看原保存结果」为什么可以删

已存在一条**不依赖该按钮**的入口链路：

| 环节 | 证据 |
| --- | --- |
| 保存结果事件 | `feedback.rs:122-140` `policy_terminal()` 发 `model-policy-save-succeeded` / `-failed`，带 `object_id` |
| 通知策略 | `event-registry.json` → `notification_policies.model_policy_failure`：`action = model_policy`，标题「渠道配置保存需要核对」 |
| 通知按钮文案 | `features/notifications/actions.ts`：`model_policy: '查看保存结果'` |
| 点击后行为 | `useAppController.ts:61-63`：写入 `policyNotificationTarget={planId:objectId}` → `routes.go('models')` |
| 打开弹窗 | `ChannelsView.vue:85-89`：watch 该 target → `policyResult(planId)` → `saveOpen=true` |

即：**「保存结果」弹窗本来就有一条从通知中心进入的路径**，该按钮是第二条入口。原型也正是这个分工（通知 `model.policy.save` 承接结果，页面只留状态）。

### 但有一处必须先补，否则删了会出问题

实测发现两个通知的 `action` 不一致：

| 通知策略 | action | 点开去哪 | 能否打开保存结果 |
| --- | --- | --- | --- |
| `model_policy_failure`（保存失败 / 待核对） | `model_policy` | 打开「保存结果」弹窗 | ✅ 能 |
| `model_policy_blocked`（**被门禁拦下**） | `models` | 只跳到模型页，**不打开弹窗** | ❌ 不能 |

被拦下时用户最需要看原因，而现在这条通知点进去只会落到列表页。它的 body 已经写了原因（`registry.rs:523-528` 会拼「本次确认没有写入：…」），所以**信息不缺，只是没有落到弹窗**。

因此实施方案里要加一条：**把 `model_policy_blocked` 的 action 也改成 `model_policy`**，或让 `models` 分支在带 `objectId` 时同样打开保存结果。否则删掉页面上那行按钮后，被拦下的用户会失去唯一的详情入口。

这一条属实现细节，不改语义，也不需要进原型。

### 视觉结果

| | 现在 | 统一后 |
| --- | --- | --- |
| 状态区行数 | 3 处（Tab 右侧 + 表格上方两行） | **1 处**（Tab 右侧状态框 + 子标签） |
| 垂直占用 | 表格起始 y=303 | 回到原型量级（原型 y=256） |
| 文字按钮 | 2 个（重启后重新检查、查看原保存结果） | 1 个 28px 图标键（重启后重新检查） |
