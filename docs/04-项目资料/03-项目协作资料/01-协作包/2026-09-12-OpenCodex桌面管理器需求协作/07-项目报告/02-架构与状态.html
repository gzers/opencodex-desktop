架构与状态

三条主线：前端只管画、后端独占外部访问、模块划分和能力域一一对应。状态上，一件容易踩的坑是把「在跑」「在同步」「在备份」压成一个状态机。

Constraints

几条不能破的约束

  • 单一真相源 + 投影：管理器维护统一事实，各客户端配置是投影，不是权威。
  • 只改目标节点：结构化读改写，保留未知字段与注释，不整文件重建。
  • 原子写：同目录临时文件写好后原子替换，替换后保留原文件权限。
  • 备份先行：任何可能覆盖数据的写入，前面必须先有一份可恢复的备份；备份失败就阻断。
  • 跨进程互斥：和官方 CLI、编辑器共享同一批配置文件，写入要拿跨进程文件锁，并比对内容摘要。
  • 凭据不出域：凭据不进日志、不进命令行参数、不进错误信息、不进未加密文件。
  • 后端独占外部访问：前端不直接触碰文件系统与网络。
Runtime

运行时与进程模型

  • 管理器进程：桌面应用本体，持有界面、后端逻辑和托管子进程。
  • 托管子进程：官方 ocx start / stop / restart 由它直接启动和持有，进程标识与退出码进入状态展示。
  • CLI 客户端：ocxd 不独立执行能力，而是连接运行中实例的本机 IPC 端点委托执行；实例没跑的时候不得绕过它直接改状态。
  • 重启语义：应用自更新会重启应用本体，但不会停掉托管中的 OpenCodex 代理；重启后重新接管并恢复状态展示。
  • 离线语义：代理离线时，依赖实时能力的功能（比如实时日志）明确标注不可用，本地历史日志和日志目录仍然可用。
State model

状态：三个维度，可以同时成立

最早文档只有一个「代理运行状态」，但原型里已经出现「正在同步」「正在备份」这类并行情况。压成一个状态机必然打架，所以拆成三个互相独立的维度。

运行状态 · 11 态

代理进程

未发现 / 正在探测 / 已发现未运行 / 启动中 / 待就绪 / 运行中 / 停止中 / 启动失败 / at-risk / 外部接管 / 不可达。

连接状态 · 7 态

外部依赖

未配置 / 未连接 / 连接中 / 同步中 / 已同步 / 冲突待处理 / 失败。

操作状态 · 8 态

单次动作

空闲 / 校验中 / 备份中 / 应用中 / 回滚中 / 已取消 / 成功 / 失败。

要能同时表达「运行中 + 同步中 + 备份中」。渲染规则：动作按状态渲染，不渲染没有解释的灰色禁用按钮，用一句状态说明说清为什么现在不能点。

环境前置门禁

安装发现之前先按 node → npm → ocx 顺序短路检查。前面一项没过就不查后面一项。四个状态：checking missing_node missing_npm missing_ocx。缺失时展示缺什么、当前状态和最短可复制命令；应用只做检测和引导，不代装。
