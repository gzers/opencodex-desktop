# A：基线与功能审计

入口：[实施计划](../IMP-OPENCODEX-DESKTOP-02.md)。本阶段不预判缺陷总量。

## 建立可追踪基线

1. 记录提交、分支、已有改动、操作系统、CPU 架构、工具链、依赖锁文件和启动方式；保留用户已有工作。
2. 确认正在测试的二进制对应当前源码，区分开发启动与历史安装包。记录实际构建路径。
3. 检查项目脚本与 CI，运行前端类型检查、测试、构建，以及 Rust 格式、Clippy、工作区测试。失败与跳过分别记录。
4. 识别测试是否使用真实文件系统、进程、IPC、钥匙串、网络或原生 WebView；统计分类用于发现空白，不设无意义的覆盖率指标。
5. 建立隔离测试数据根和假客户端目录。使用明确命名的测试凭据；清理只针对本轮创建的资源。

## 逐项审计

覆盖页面按钮、菜单、托盘、快捷操作、设置、CLI。为每项建立以下列：

| 字段 | 要求 |
|---|---|
| 能力及入口 | 用户能触发什么，相关界面位置 |
| 预期效果 | 文件、目录、进程、网络、布局或状态应怎样变化 |
| 执行链路 | 前端事件、命令、后端服务、真实资源、结果回读 |
| 已有验证 | 单元、模拟契约、真实集成、原生手测分别注明 |
| 复现与状态 | 已验证、失败、未验证、不适用；后者必须写原因 |
| 后续处理 | 缺陷编号、优先级、回归方法、证据索引 |

重点检查：只更新 UI 的动作；保存却不应用的设置；实际失败但提示成功；固定展示状态；旧结果掩盖新失败；重启丢失；多文件写入部分完成；取消后仍后台写入。

追踪实际调用，不能仅因文件名含 `mock` 就认定是假功能。对产品仅提供引导而没有自动执行的能力，核对文案与事实是否一致，不擅自扩展功能范围。

## 首批复现与优先级

- 缩放：观察当前打包应用修改前后的实际元素尺寸，并验证设置文件与重启值。
- 导入导出：检查声明范围和实际内容是否一致，异机凭据引用能否使用。
- WebDAV：检查“连接成功”与“同步完成”是否区分；双端能否得到相同配置。
- 进程与状态：用真实进程和健康检查核对 GUI 状态。

P0：数据丢失、破坏性误覆盖、敏感数据意外泄露。P1：核心能力不可用、假成功、无法恢复的一致性问题。P2：非阻断交互和展示问题。优先级不代表允许遗漏验收。

## 阶段交付

将基线回执、功能矩阵、初始缺陷和下一步写入关联的 `.adg/` 执行记录。P0 立即处理；其余按计划进入 B。外部条件缺失时写明受影响能力，继续能独立完成的审计。
