开工清单

22 个工作包，把 13 个能力域、27 条需求全部覆盖到，P0 / P1 / P2 和贯穿各阶段的工作都在里面。每个工作包都写了要做什么、产出什么、依赖什么、卡在哪里。

先说清这份清单的性质：它是派生的规划草案，用来对齐「开工要做什么」。正式的字段级契约由 IMP 冻结，任务拆分由治理流程产生。清单里的顺序表示先后依赖，不表示可以砍——范围原则仍然是「原型里出现的功能都要实现」。
Prerequisites

开工前必须先做完的三件事

这三件是治理动作，不是实施内容。跳过它们直接写代码，后面返工的概率很高。

第 1 步

定稿项目核心

产品定义、能力地图、系统架构、数据与状态、集成与安全边界这五份事实过一遍并确认。现在它们写的是「已确认的设计事实」，确认后才更新成「实际架构事实」。

第 2 步

创建 IMP，冻结 9 类契约

目录布局与数据根、状态协议、进程模型、发现/日志/升级、加密格式、扩展管理、WebDAV 同步、CLI 控制面、验收环境与 mock 数据。

第 3 步

拆实施任务

按下面的工作包拆分任务，每个任务带验收检查和证据保留要求。

P0

P0：运行管理主线

先把「发现 → 起得来 → 看得到 → 出问题有出路」这条线打通。这一段做完，产品就已经能日常用了。

WP-01

工程底座与桌面壳

P0支撑全部

目标：把能跑、能打包的空壳立起来，后面所有能力都往这个壳里加。

  • 初始化 Tauri v2 工程：Rust 后端 + Web 前端两个工作区，定目录结构与构建脚本
  • 约定 IPC 命令层：命名规则、请求 / 响应结构、错误模型与错误码、超时与取消
  • 把「前端不直接访问文件系统与网络」做成可检查的约定，而不是口头规则
  • 日志基础设施：分级、落盘位置、轮转、统一脱敏过滤器
  • 偏好与设置存储（manager state），确保不落明文凭据
  • macOS 上跑通开发与打包两条路径

WP-03

数据根与数据目录

P0AC-02REQ-02 ~ 04

目标：自有产物有地方放，已有的 OpenCodex 数据默认不动。

  • 数据根选择与检查：可写、空间、是否已有数据

  • 备份保留策略与完整性校验（备份不可定位时不得开始迁移）

WP-17

扩展写入引擎（Skills / MCP 共用）

P1AC-11REQ-26、27

目标：整个产品唯一允许写别人文件的地方，必须最稳。

  • 写入边界硬校验：只允许扩展配置；禁写 provider / 路由 / 模型映射与核心运行配置
  • 目标必须是普通文件；符号链接、FIFO、设备文件、越出预期根目录的路径一律拒绝
  • 备份 → 同目录临时文件 + 原子替换 → 保留原文件权限 → 重新校验
  • 跨进程文件锁 + 写入前内容摘要比对；单一状态锁串行化
  • 节点级写回：保留未知字段与注释；解析失败即拒绝，不做部分写回
  • 不改写同目录的凭据、认证等非目标文件；删除类操作进回收区
  • 检测到外部改写或客户端间不一致时进入待处理，不静默覆盖

几处需要留意的依赖

  • 备份能力是公共底座。WP-03 的备份与回滚会被 WP-09、WP-13、WP-14、WP-17、WP-19 一起用，所以要早做、做扎实。
  • 写入引擎要先于扩展管理。WP-17 是 Skills 和 MCP 的共同底座，先做引擎再做界面，避免两处各写一套。
  • WebDAV 排最后有原因。它同时依赖加密容器（WP-13）和写入与备份（WP-17），前面不稳，同步就会丢数据。
  • 安全阻塞项不排在最后。WP-20 和 WP-15 ~ WP-19 并行推进，因为 6 条阻塞风险就长在这些能力里。
  • 打包和签名要早准备。WP-22 支撑应用自更新，签名链路通常比预想的慢。
最后提醒一句：这份清单是为了让你看清工作量，不是授权开工。正式开工前要走完「开工前提」那三步；其中创建 IMP 和正式发布都属于需要单独确认的动作。
