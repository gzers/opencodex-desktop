# 通知自动收起进度条组件

2026-10-30，Asia/Shanghai。项目：OpenCodeX Desktop，桌面端。用户提出“所有通知底部有个消失动画进度条，先做一个组件”；本轮仅在组件专题制作可操作示例，尚未向全部业务通知或正式软件推广。

唯一活动入口为[总原型 / 组件与样式 / 通知与任务](原型/index.html#components?section=notifications)，本节“自动收起进度条”区域为#ctNotificationCountdown。界面继续引用原有材质、语义颜色、Toast/任务卡与铃铛，不建立第二个通知宿主。

## 可操作示例

| 入口 / 状态 | 行为 |
| --- | --- |
| 成功通知 / data-ct=notify-countdown-success | 右上既有Toast底部使用3px半透明光带，长度递减表示8秒可见停留时间，固定透明度，不明暗变化或横向流动，归零时收起。 |
| 错误通知 / data-ct=notify-countdown-error | 相同计时与中性半透明光带，取消左侧强调条；结果仍由原有标题与正文说明。收起只隐藏展示，铃铛待处理事项保留。 |
| 已完成任务 / data-ct=notify-countdown-task | 在原有完成任务卡底部使用同一组件；只挂组件示例，不给运行任务套自动消失计时。 |
| 指针悬停 / 键盘焦点 | 暂停计时及线条；所有停留条件结束后从剩余时长继续。页面不可见也暂停，避免回到页面时提示已消失。 |
| 重复播放 / 替换 / 手动收起 | 重复播放更新同一示例并重启展示计时；新通知替换正文即撤销旧倒计时；旧回调不得提前收起新通知。收起和删除语义分开。 |
| 减少动态 | 保留固定半透明渐变并按秒递减，仍使用相同8秒计时；三档材质不改变倒计时语义。 |
| 铃铛 / 历史 | 历史列表不显示倒计时，不自动删除。点击本示例通知可恢复原表面并重新计时。 |

底部线条只表示自动收起剩余时间，任务执行进度仍由任务自身表达。组件不显示每帧倒数文本，不使用持续live播报；保留对现有aria-describedby的关联，提供停留暂停说明。

## 组件与注册边界

- 组件登记ID：feedback.dismiss-countdown，原型资源notification-countdown.js / .css。组件只处理DOM、单调时钟和生命周期，不自行发布业务事件、不访问文件、网络或偏好。
- 示例事件：component.demo.countdown，先在既有maintenance-events目录登记，再由prototypeNotificationPublisher投到原Toast/任务卡/铃铛。variant仅接受success/error/task固定枚举；通知语义与读/解决/删除仍属于公共宿主。
- 当前消费者只有组件专题的这三个明确入口。文件导入/导出、WebDAV等原有业务通知不因本轮组件展示改变时效或自动装条。用户看过效果后，再确定统一推广与生产组件接入。
- 组件目录把本项标为“组件原型待评审 / 正式未实现”，不以示例动画完成冒充所有业务通知验收。关联同步通知规划仍沿[0.2.18问题清单S18-03](../06-问题记录/0.2.18-bugs.md)。

## 验证与待办

实际检查：组件时间/DOM9项、原有注册通知6项、事件目录31项通过。Chromium111项通过、页面异常0；WebKit110项功能与布局检查通过，但整页异常检查失败，记录两次ResizeObserver循环告警。改前原型同尺寸/效果检查也复现一次同类告警，未过滤错误或改动并行公共布局来报全绿。两种引擎均检查亮暗、1180×760/900×600、三档效果、悬停暂停/恢复和8秒实际收起，已人工查看成功、错误与任务卡底部细线。

首轮确定性测试误统计整个组件页的rAF回调，已改为只验证本倒计时持有的回调清理；首轮减少动态布局断言在550ms期待线条缩短，与按秒更新规则不符，改为1800ms观察，未更改产品计时。第一次改前对照把Logo子页面的index.html也误路由为主入口，已限定总原型目录，失效对照与有效对照分别保留。

检查脚本、实际结果、源文件摘要和失败过程见[本轮证据](../../../../.adg/evidence/0.2.18-postrelease/notification-countdown-component-20261030/validation.json)。未执行真实Windows通知或生产软件修改；未宣称整页WebKit无异常。下一步由用户在组件入口模拟三个示例，确认展示与暂停规则后再纳入全局实施。

## 用户视觉调整（2026-10-30）

用户要求通知去掉左侧强调条，底部进度不使用实色线，改为半透明、透明度变化的流动效果。总原型公共Toast去掉原来的左侧色条节点与样式；铃铛列表的未读圆点、任务结果图标及其他业务警示边界不在此次删除范围。

倒计时保持原3px高度和剩余长度，用中性文字色的透明渐变形成柔边进度；透明度以2秒周期柔和明暗，不使用红/绿实色填充。用户随后指出流动影响进度识别，已移除横向高光和位移动画，只让长度递减表示剩余时间。悬停、焦点及页面隐藏时，计时和透明度动画一起暂停，恢复后继续。减少动态偏好关闭明暗动画，保持原按秒递减。只改组件外观，未将倒计时推广到普通业务通知，所有示例仍使用已登记事件及现有公共宿主。

上一节为首版实际验证记录，此次视觉检查另列，不覆盖其原始源码与结果。

最终“无横向流动”版本：计时/DOM9项通过，Chromium与WebKit各183项通过、页面异常0，覆盖亮暗、宽窄、三档效果、减少动态、透明度实际变化、没有横向位移、悬停同时暂停和真实8秒收起；已目检成功通知和完成任务截图。光效首轮检查只取两个采样点，恰好分布在透明度谷值两侧，未捕获实际振幅；改用三个时点验证振幅，没有改变动画周期。前一流动候选的WebKit布局观察器告警作为已被用户否定的候选记录保留，不计入最终通过结果。[本次证据](../../../../.adg/evidence/0.2.18-postrelease/notification-countdown-opacity-20261030/validation.json)保存当前源文件与实际截图。

### 视觉复核记录：固定透明度（2026-10-30）

用户继续明确“不要明暗变化”。已移除透明度动画及其关键帧，底部进度保持固定半透明，只通过长度递减表达剩余时间；不闪烁、不流动，左侧强调条保持移除。8秒收起、悬停/焦点/隐藏页面暂停和减少动态按秒递减继续沿原组件。上一节为当时验证记录，不代表当前仍采用明暗效果。

此次仅改外观，未改计时逻辑。Chromium与WebKit分别核对浅色和深色：透明度在两个时点均固定为0.55、animation-name为none，剩余长度正常递减，左侧色条不存在；两引擎页面异常均为0。没有重复声明软件或全局业务通知已经采用。

同日视觉补充：用户要求左边不要渐变透明、右边保留。当前进度左侧以固定半透明起笔，前段保持相同透明度，右侧沿原渐变过渡至透明；没有闪烁、明暗或横向流动。仅修改渐变色标，不改变长度递减、8秒时长或暂停行为。Chromium与WebKit均核对浅色/深色的左右渐变色标、固定透明度和长度递减，页面异常0，已目检浅色通知截图。

### 已取消的对比版本：左端清晰，恢复明暗与流动（2026-10-30）

用户在左端取消透明渐变后，要求恢复闪动和流动看看。此轮恢复2秒柔和明暗和2.8秒横向光效，同时保留左端0%起笔为半透明、前段不渐隐、右端渐隐；不恢复左侧强调条。倒计时的长度、8秒收起及悬停/焦点暂停不变，减少动态仍关闭光效。本次是组件效果对比，尚未确定全局采用或修改软件；此前固定透明度段落保留为历史试用记录。

本次外观核对：Chromium和WebKit分别检查浅色/深色，左端非透明起笔及右端透明色标保持，透明度在三个时点有变化，横向光效启用、悬停后暂停，长度继续递减；两引擎页面异常0。已目检恢复后的浅色截图。

同日方向/速度调整：用户明确光效应从右往左、速度快一点。组件横向光效改为从+105%移动到−105%，周期从2.8秒缩短为1.6秒；左端不渐隐、右端渐隐和柔和明暗保留。倒计时长度仍按原8秒递减，光效速度不改变收起时间。Chromium与WebKit均核对浅色/深色的实际动画关键帧为+105%→−105%、周期1.6秒及8秒总时长，页面异常0。

用户试用后明确取消恢复闪动/流动的方案，认为效果差。已恢复固定半透明的进度条：左端不渐隐、右端保留渐隐，不闪动、不明暗变化、不横向流动，仅长度递减表示剩余时间。左侧强调条仍移除，8秒收起与悬停/焦点暂停不变；前述闪动/流动及速度调整仅保留为已取消的试用记录。仍仅组件示例，未推广软件。
