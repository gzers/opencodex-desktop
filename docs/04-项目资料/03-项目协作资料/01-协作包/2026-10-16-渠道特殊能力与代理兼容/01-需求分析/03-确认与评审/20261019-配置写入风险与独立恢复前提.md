## 核心风险判断

当前协助开发的 Codex 同时依赖待修改的配置时，配置错误可能使修复入口一并不可用。不能把“出错后由本对话中的 Agent 回滚”作为恢复保障；下一轮请求或应用启动失败时，Agent 可能无法继续执行工具。

| 风险 | 影响 | 单靠备份或解析不能证明的内容 |
|---|---|---|
| 配置语法、类型或字段组合错误 | Codex 加载失败，或相关能力未按预期启用 | 文件完整写入不代表内容可用 |
| 认证、地址或启动环境不匹配 | 应用能打开，但请求和后续修复对话不可用 | 解析成功、版本可读不代表认证和代理贯通 |
| 开发与被测实例共用配置或状态 | 测试影响日常客户端、会话或开发入口 | 设置一个环境变量不代表 Desktop 已隔离 |
| 多文件切换中断 | config、auth 与启动设置处于不同批次 | 逐文件原子替换不构成多文件原子事务 |
| 并发改写和错误自动回滚 | 覆盖其他客户端或用户后来保存的内容 | 持有旧备份不代表可以无条件恢复 |
| 状态、数据库或笔记发生变化 | 配置恢复后仍存在行为或数据差异 | 恢复配置不能撤销数据库迁移、笔记写入等副作用 |

Superba 的配置目录、说明文字和写入校验可以作为实现参考，不能代替本项目对失败恢复的验证。原子替换主要避免半写文件，仍可能完整写入一份无法使用的配置。

## 实施前提建议

以下作为后续方案必须回答的风险项和候选准入条件记录，具体实现待评审、开发与验证。

1. **保留可工作的开发入口。** 当前开发客户端使用已知可用配置；候选配置先进入独立测试目录和实例。验证前后检查日常配置内容与修改时间，发现越界立即停止该测试。
2. **验证真实隔离。** 为被测进程提供专用配置、认证、状态目录和必要的独立代理端口；核对 Desktop 实际消费的路径及进程环境、项目级配置、数据库和缓存。仅设置 `CODEX_HOME` 不作为通过依据。无法证明本机 Desktop 可隔离时，选择独立系统账号或虚拟机，具体方式待定。测试设置不得写入日常 Shell 启动文件或全局环境。
3. **恢复入口独立于 Codex。** 由外部管理器提供恢复能力，并保留终端可执行的本地恢复工具。恢复不要求模型请求、网络、Codex 启动成功，也不能先解析损坏的 Codex 配置才能找到备份。管理器自身无法打开时，仍有另一条经验证的恢复路径。当前未实现或演练这套专题恢复入口。
4. **按变更批次保存恢复材料。** 明确 config、必要认证文件及启动环境设置的实际变更范围；记录原文件是否存在、权限、摘要和恢复位置。运行时认证备份采用适当的本机凭据保护，不进入仓库、普通日志或协作资料。没有验证可读取、完整且可恢复的保护材料，就不进入正式切换。
5. **处理多文件中断与并发。** 切换前冻结并比对基准，保留独立事务记录；覆盖文件不存在、部分替换、进程崩溃及跨启动恢复。恢复前核对当前内容与本次事务的关系，发现后续外部修改时保留双方并报告冲突，不盲目覆盖。
6. **逐步扩大写入。** 先完成只读目录、版本识别和差异预览，再以少量字段验证受控写入。认证、地址、存储路径和上下文机制分别验证，避免一次覆盖整份教程配置。正式应用不以整个配置文件重建代替所属字段合并，未知字段与用户配置继续受保护。

以上均在外部管理层实现，保持不修改原版 OpenCodex 的边界。独立恢复工具的形式、存放位置、自动触发条件和多文件事务格式尚未冻结。

网络超时或渠道临时不可用不能一概触发自动回滚。只有与本次变更可明确关联、且满足并发保护的故障才可按未来确认的规则处理；触发和停止条件尚待设计。
