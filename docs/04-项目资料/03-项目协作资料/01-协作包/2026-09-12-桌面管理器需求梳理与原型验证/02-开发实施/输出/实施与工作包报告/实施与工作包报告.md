## 04 · 契约已经锁住了什么 {: #contracts }

IMP 不只是方向，已经把字段、参数和阈值定死。这里只挑影响开工顺序最大的部分：

| 契约域 | 已冻结的关键点 |
|---|---|
| 数据根 | 七个物理目录：`manager-state` / `opencodex-home` / `backups` / `logs` / `exports` / `cache` / `sync-state`；结构版本 `1` |
| 备份 | 每类最近 20 份、保留 30 天；备份清单含 SHA-256、字节数、文件数、可恢复标记 |
| 状态 | 内部与 `--json` 都用 `runtime` / `connection` / `operation` / `gate`；轮询 3 秒 / 15 秒，失败指数退避 |
| 进程 | 启动 20 秒、停止 10 秒；pending 判定 3 秒 ×10；取消不发 SIGKILL |
| 加密 | Argon2id：256 MiB、迭代 3、并行 2、盐 16 字节；AES-256-GCM：12 字节 nonce |
| 导入 | 明文 128 MiB、密文 512 MiB、数组 20,000 条；失败不部分写入 |
| 扩展 | 六客户端默认可写；用户可逐个关闭；未安装跳过且不落盘 |
| 写入 | 目标文件锁 3 秒；单一状态锁；SHA-256 比对；备份失败阻断 |
| 同步 | manifest 独立 AEAD；AAD 绑定格式、版本、设备名；旧快照进冲突 |
| CLI | 命令固定为 `ocxd`；`schema_version=1`；IPC socket 权限 `0600` |
| 审计 | 保留 90 天 / 5,000 条；只记参数键，不记值 |

## 05 · 数据字段与对象关系 {: #data-model }

这一章回答两个问题：实现时数据长什么样；对象之间怎么连。字段是精简版，完整定义仍以 `docs/02-项目核心/领域模型.md` 为权威，不影响阅读。

<div class="summary-box">
<strong>先记住整体链路：</strong><code>EnvironmentGate</code> 和 <code>Installation</code> 负责入口判断；<code>AgentProcess</code> / <code>RuntimeFacts</code> 看运行；<code>DataRoot</code> 是数据和备份的底座；<code>SyncEndpoint</code> / <code>SyncRun</code> / <code>Conflict</code> 处理同步；<code>ExtensionConfig</code> / <code>Skill</code> / <code>McpServer</code> / <code>McpServerProjection</code> / <code>ClientTarget</code> / <code>WriteTransaction</code> 处理扩展写入；<code>UpdateTarget</code> / <code>Notification</code> / <code>IpcEndpoint</code> 是外围通道。
</div>

<div class="card-grid">
<div class="card">
<h4>为什么要落到字段级</h4>
<p>防止不同人理解成不同版本。比如 <code>DataRoot.sections</code> 必须是七个 kebab-case 目录，<code>McpServerProjection.client_id</code> 必须落在六客户端枚举内，<code>SyncEndpoint.tls_policy</code> 固定 <code>verify_required</code>，这些都不能实现时临时改。</p>
</div>
<div class="card">
<h4>为什么对象关系要写</h4>
<p>很多对象不靠外键强约束，但生命周期必须绑住：备份失败要阻断写入；冲突覆盖必须留 <code>backup_ref</code>；同步和凭据只传 <code>ref_id</code>，不复制真实值；统一 MCP 定义要派生多个客户端投影。</p>
</div>
</div>

### 5.2 对象关系 {: #object-relations }

读法：<b>A → B 表示 A 引用或派生 B</b>。同一连线写清 1 : N；关系用引用或投影绑定，不是全量复制。这里不再画一张大关系图，避免把长页报告变成第二张架构图。

| 源 | 目标 | 基数 | 绑定字段 / 方式 | 实现时要守住的规则 |
|---|---|---|---|---|
| `DataRoot` | `BackupRecord` | 1 : N | 备份落点必须在其 `sections.backups` 内 | 备份失败阻断导入、同步覆盖、扩展写入、数据根迁移等破坏性动作 |
| `DataRoot` | `RuntimeFacts` | 1 : N（按时间事实） | `RuntimeFacts.data_root` | 展示生效数据根；管理器数据根与 `OPENCODEX_HOME` 分开处理 |
| `SyncEndpoint` | `CredentialRef` | N : 1 | `SyncEndpoint.credential_ref` → `CredentialRef.ref_id` | 只保存引用；界面、日志、`--json`、导出和同步都不得带真实凭据 |
| `SyncEndpoint` | `SyncRun` | 1 : N | `endpoint_id` / 内存与文件锁 | 单端点单次同步；连接 15 秒、单件 10 分钟、总时限 30 分钟 |
| `SyncRun` | `Conflict` | 1 : N | `scope=sync` + 冲突目标 | 旧快照、清单缺失、载荷乱序或哈希不一致不能直接应用 |
| `Conflict` | `BackupRecord` | N : 1 | `Conflict.backup_ref` → `BackupRecord.backup_id` | 被覆盖侧强制备份；无备份必须显式记录原因 |
| `ExtensionConfig` | `Skill` | 1 : N | `skills` 数组 | 统一配置是权威；反向导入只做合并，不覆盖其他客户端启用状态 |
| `ExtensionConfig` | `McpServer` | 1 : N | `servers` 数组 | 统一定义不携带单一客户端或单一启用开关 |
| `Skill` | `ClientTarget` | N : N（按派生落点） | `Skill.targets` + `ExtensionConfig.enablement` | 未安装跳过且不落盘；目标哈希不同进冲突 |
| `McpServer` | `McpServerProjection` | 1 : N | `McpServer.targets` | 统一定义派生逐客户端投影；同一定义可到多个客户端 |
| `McpServerProjection` | `ClientTarget` | N : 1 | `target_ref` → `ClientTarget` | 投影只在客户端落点里表达启用、形态和最近结果 |
| `WriteTransaction` | `BackupRecord` | N : 1 | `WriteTransaction.backup_ref` → `BackupRecord.backup_id` | 先备份再临时写入、原子替换、复验；备份失败阻断 |
| `WriteTransaction` | `ClientTarget` / 导入目标 | N : 1 | `target` / `scope` | 只覆盖受控目标；不删除目标文件里的其他节点 |
| `UpdateTarget` | `BackupRecord` | N : 1 | `backup_ref` → `BackupRecord.backup_id` | 本体升级和套壳自更新分开；签名失败即终止 |
| `Notification` | `RuntimeFacts` / `SyncRun` / `Conflict` / `WriteTransaction` / `UpdateTarget` | 0 : N | `action_ref` | 只存跳转引用；通知正文不携带 S3 级数据 |
| `IpcEndpoint` | CLI / GUI 调用 | 1 : N | `socket_path` + 请求 | 默认关闭；socket `0600`；关闭时移除并确认不可连接 |

<div class="callout callout-warn"><strong>不是关系的地方：</strong><code>McpServer</code> 不是“属于某个客户端”的记录；客户端归属在 <code>McpServerProjection</code>。<code>Conflict</code> 不是备份本身，它通过 <code>backup_ref</code> 找备份。<code>Notification</code> 不复制事件详情，只做通知与跳转引用。</div>

### 5.3 跨边界数据契约 {: #boundary-contracts }

领域实体之外，还有四类跨边界数据。它们不是 19 个领域实体里的独立业务对象，但字段同样已经冻结。

| 边界 | 关键字段 | 与领域对象的关系 |
|---|---|---|
| 加密导出容器 | 容器头：`magic="OCXDCONF"`、`format_version=1`、`kdf`、`aead`、`created_at`、`app_version`；KDF 用 Argon2id（256 MiB / 3 / 2 / 32B / 16B 盐），AEAD 用 AES-256-GCM（12B nonce）；载荷顶层只接受 `container` / `extension_config` / `sync_endpoints` / `preferences` | 导入后映射到 `ExtensionConfig`、`SyncEndpoint` 和偏好数据；引用 `CredentialRef.ref_id`，不带真实值 |
| 备份清单 | `schema_version=1`、`backup_id`、`action`、`target_path`、`stored_at`、`created_at`、`sha256`、`bytes`、`file_count`、`restorable`、`note` | 落盘清单对应 `BackupRecord`；字段同名同义 |
| 同步 manifest | 明文：`format="OCXDSYNC"`、`version=1`、`compat_version=1`、`snapshot_id`、`created_at`、`device_name`、`artifacts[]`；传输包：`manifest_magic="OCXDSYNCPKG"`、独立 AEAD、AAD 绑定格式 / 版本 / 设备名 / `schema_kind` | 生成 `SyncRun.snapshot_id`；`artifacts` 校验本地载荷；旧快照进 `Conflict` |
| CLI / IPC | `ocxd` 命令集；`--json` 顶层 `schema_version=1`、`command`、`ok`、`data`、`error`、`generated_at`；IPC 请求带 `request_id`、`command`、`args`、`confirm`、`contract_version` | 由 `IpcEndpoint` 承载；审计只记参数键，不记值 |

## 06 · 代码规划结构 {: #code-structure }

这一章是给实现者的阅读地图：先看分层，再看目录，最后看模块怎么接起来。目前只有规划，还没有代码；目录名是实现约定，不是本轮已创建的工程结构。

### 6.1 分层与调用规则 {: #layering }

代码按四层组织，外层只能调用相邻内层。这样做的好处是：界面只管状态展示，后端才碰外部资源，公共能力不会被业务模块重复实现。

| 层 | 职责 | 禁止 |
|---|---|---|
| UI / WebView 层 | 概览、面板、拓展、日志诊断、设置、托盘的界面状态与动作入口 | 不直接读写文件、网络、钥匙串 |
| 应用编排层 | Tauri command、命令参数校验、状态序列化、路由到后端模块 | 不绕过后端模块直接执行业务 |
| 后端模块层 | 13 个实现模块；模块只收命令、返回领域状态 | 模块之间不做循环调用 |
| 公共基建层 | 数据根、锁、备份、写入引擎、日志脱敏、错误、通知、加密、同步客户端 | 只提供能力，不记录业务结论 |

<div class="summary-box">
<strong>一条硬边界：</strong>前端只发命令和渲染结果；文件、网络、钥匙串都由 Rust 后端访问。<code>ocxd</code> 也只连运行中实例的 IPC，不变成第二个写入者。
</div>

模块不新增能力，只承接项目核心的 `MOD-01` ~ `MOD-13`。公共逻辑沉到基建层，避免重复实现。

前端按页面和状态切片组织，不按每个按钮拆文件。页面只渲染状态、触发命令，不解释业务细节。

### 6.6 错误、测试与依赖边界 {: #engineering-rules }

```text
AppError
  ├─ source        # 错误来源：ocx / fs / webdav / keychain / ipc / import / extension
  ├─ code          # AppErrorCode，对齐退出码 0 ~ 12
  ├─ message       # 用户可读摘要，最多 280 字符
  └─ hint          # 建议动作；可为空
```

| 规则 | 怎么做 |
|---|---|
| 统一错误出口 | 模块只返回 `Result<T, AppError>`；不散落 `anyhow` / `unwrap` |
| 脱敏在出口 | 日志、错误摘要、`--json`、通知统一走脱敏器 |
| 测试分层 | 单元测模块内逻辑；集成测命令 + fixture；验收测 AC-01 ~ AC-13 |
| 不用真实数据 | 测试走临时路径与 mock；不碰家目录真实配置 |
| 依赖隔离 | `process_runner`、`http_client`、`keychain` 抽成 trait，正式实现只放后端 |

<div class="callout callout-info"><strong>还缺一步：</strong>本节是实施规划。正式工程结构应在 <code>WP-01</code> 授权后初始化；如果落地时发现某个目录不合理，先回写本报告和 TASK，再改代码。</div>
