# 04-重启管理器后代理停止与版本归属

维护 ID：MNT-OPENCODEX-DESKTOP-20261004-01。补充日期：2026-10-04，Asia/Shanghai。受影响管理器 **0.1.0**；官方运行时 **2.69.0**。拟修复仍备注 **0.1.1**，0.1.2 未排期。

## 1. 已确认的现象与结论

用户在完全退出、重开管理器后报告 OpenCodex 也关闭，并进一步明确：**概览显示代理已停止，需要点“启动”**。这是代理运行中断，不只是内嵌面板窗口随管理器关闭。此前白屏恢复事实仍成立；新增反馈说明该恢复存在服务中断副作用。没有留存退出前后连续的健康探测、代理退出码或信号，所以准确退出机制仍待验证。

可拆为两个问题：退出时代理没有保持连续运行；重开管理器没有恢复之前的运行状态。前者有用户确认和托管方式的静态风险，具体信号/系统责任链未证实；后者的启动路径缺口可由源码确认。不能用“父进程退出必然杀掉子进程”概括，也不能说管理器明确执行了官方停止命令。

运行事实与时间线以 [RUN-OPENCODEX-DESKTOP-20261004-01](../../../../../../../03-开发实施/RUN-OPENCODEX-DESKTOP-20261004-01.md) 为准；本节不另外建立运行状态事实源。新增机器核对见 [生命周期观察](../../../../../../../../.adg/evidence/MNT-OPENCODEX-DESKTOP-20261004-01/lifecycle-observations.json) 与 [系统退出日志摘录](../../../../../../../../.adg/evidence/MNT-OPENCODEX-DESKTOP-20261004-01/lifecycle-launchd.log)。

## 2. 三项发现

| 编号 | 发现 | 已确认范围 | 尚未确认 |
|---|---|---|---|
| F-11 | 完全退出后的托管代理连续性缺口 | 用户确认代理已停止；运行中代理仍是桌面管理器的子树，启动路径未配置独立会话或后台服务 | 当次是否收到系统信号、由谁发出、具体退出码；独立托管方案是否解决 |
| F-12 | 重开后未恢复运行状态 | 管理器启动只读取偏好、采集状态与选择路由；没有恢复运行意图并重新启动的路径 | 是否以及哪些场景应自动恢复，需落实明确语义与真实验收 |
| F-13 | 关窗、退出与启动文案边界不清 | keep_proxy_on_close 只处理 CloseRequested；launch_main 只控制主窗口显示；“仅启动代理托管”可能让用户误认重开会启动代理 | 最终退出策略与用户可见文案，不能用文案当作已实现能力 |

### F-11：退出时为何会影响代理

仓库源码依据为 main@9ca7a9458d951ba313e8ea46c51c99cc14f8cd44。新增核对文件的摘要及其与 v0.1.0 的比较保存在生命周期观察中；安装包与提交的构建映射仍未证明。

- apps/desktop/tauri/src/lib.rs:366 的托盘 Quit 直接 app.exit(0)；ui/src/stores/app.ts:415 起退出入口调用 exit(0)。相关退出入口没有显式执行 ocx stop；最终 run 回调处理 macOS Reopen，没有代理连续性交接。
- tauri/src/infrastructure/process_runner.rs:240 起直接执行官方子命令；:254 明确 kill_on_drop(false)，标准输入输出均为空。这不是“Rust Child 析构自动杀服务”的证据。该启动路径未配置 setsid / 独立进程组，也未交给独立系统服务管理器。
- 本机官方 2.69.0 包的 bin/ocx.mjs:1063 起常规启动创建 Bun 子进程，未指定 detached；:1077 起转发 SIGINT、SIGTERM、SIGHUP。src/cli/index.ts:643–648 接收上述信号并进入正常关闭与清理。因此若启动器收到终止信号，代理会跟随关闭；**本次尚未取得实际信号记录**。
- 官方包另外存在 detached 启动与后台服务路径。例如 cli/index.ts 的 ensure 路径约 :786 起、ocx.mjs 更新恢复路径约 :460 起；它们不是管理器当前直接 ocx start 的同一入口，不能以其存在证明本机代理已独立托管。

恢复后观察为 desktop 51714 → Node 51882 → Bun 51884，代理启动晚于管理器约 42 秒，与用户说重开后手动点启动相符。PID 父子关系本身不证明退出时会被杀；POSIX 子进程可能被收养，系统应用退出收容、信号传播或其他异常仍需要现场证据。launchd 摘录只能确认旧应用服务退出并被移除，不能证明具体代理终止机制。管理器当时未留存子进程输出及退出原因，是取证缺口。

[稳定需求 AC-OPENCODEX-DESKTOP-09](../../../../../../../01-需求管理/需求/DMD-OPENCODEX-DESKTOP-MANAGER.md) 明确自身更新重启不停止托管代理。此次是人工恢复重启，不能伪造为更新失败复现；但相同生命周期可能影响自身更新重启，必须补专门验证，不能默认所有应用退出都应停止代理。

### F-12：为什么重开没有自动恢复

lib.rs:190 起 launch_main=false 只隐藏主窗；:245 起创建动作执行器，:254 起后台周期采集状态。ui/src/main.ts:21–35 与 ui/src/startup.ts 读取偏好和运行快照，再选概览或面板，没有代理 start 动作。preferences/mod.rs 中没有恢复前次运行的偏好或执行策略。

“随 Codex 启动 OpenCodex”走官方 codex-shim，与“启动管理器时恢复代理”是两个入口，不能混用。“打开主界面”“打开官方面板”也不是运行时 start。重开后观察到已停止而等待用户手动启动，符合当前实现；这解释恢复缺失，不能反推当次代理的终止原因。

候选方案应分别定义保持运行与恢复运行：优先让应保持的代理连续运行；需要恢复时记录可靠运行意图，重新探测健康与所有权，仅在规定场景恢复。启动前已停止、用户明确停止、外部代理仍运行、端口被其他应用占用、数据根变化等情形不能无条件 start。只自动 start 无法消除退出期间的请求中断。

### F-13：设置与退出语义

lib.rs:463–467 的 keep_proxy_on_close=true 只让窗口关闭变为隐藏，并阻止 CloseRequested；完全退出走不同路径。本机该偏好为 true，不能据此承诺托盘退出后仍连续。SettingsRoute.vue 中“关闭后仅启动代理托管”的启动说明实际只对应窗口可见性；“退出桌面壳”也没有交代服务是否受影响。

需要分别说明关窗隐藏、完全退出、重新加载主 UI、恢复重启和自身更新重启的结果，补真实行为测试。不可将 launch_main 改成自动启代理而沿用旧字段含义；不可把后台服务安装、系统自启动或官方配置修改作为未经范围确认的默认修复。

## 3. 版本判断与下一步

本机 Info.plist 的应用版本和构建版本均为 **0.1.0**。当前本地 v0.1.* 标签只发现 v0.1.0；这不是远端发布查询，但足以与本地安装身份和本维护的未实施状态交叉核对。**0.1.1 是之前用户要求的拟修复备注，尚无本任务实施、制品验收或发布。第二个故障不自动对应 0.1.2。**

建议 F-11～F-13 与白屏恢复一起作为 0.1.1 候选范围：恢复界面时不能引入未说明的服务中断。若后续 0.1.1 冻结、交付，或用户明确要求拆分版本，再把剩余工作排到 0.1.2；本次只记录“0.1.2 未排期”，不改软件版本号或制造发布事实。
