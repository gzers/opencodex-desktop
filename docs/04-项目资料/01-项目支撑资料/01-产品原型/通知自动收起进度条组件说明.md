# 通知自动收起进度条组件

2026-10-30，Asia/Shanghai。项目：OpenCodeX Desktop，桌面端。用户提出“所有通知底部有个消失动画进度条，先做一个组件”；本轮仅在组件专题制作可操作示例，尚未向全部业务通知或正式软件推广。

唯一活动入口为[总原型 / 组件与样式 / 通知与任务](原型/index.html#components?section=notifications)，本节“自动收起进度条”区域为#ctNotificationCountdown。界面继续引用原有材质、语义颜色、Toast/任务卡与铃铛，不建立第二个通知宿主。

## 可操作示例

| 入口 / 状态 | 行为 |
| --- | --- |
| 成功通知 / data-ct=notify-countdown-success | 右上既有Toast底部增加3px细线，从满到空表示8秒可见停留时间，归零时收起。 |
| 错误通知 / data-ct=notify-countdown-error | 相同计时，沿现有错误色；收起只隐藏展示，铃铛待处理事项保留。 |
| 已完成任务 / data-ct=notify-countdown-task | 在原有完成任务卡底部使用同一组件；只挂组件示例，不给运行任务套自动消失计时。 |
| 指针悬停 / 键盘焦点 | 暂停计时及线条；所有停留条件结束后从剩余时长继续。页面不可见也暂停，避免回到页面时提示已消失。 |
| 重复播放 / 替换 / 手动收起 | 重复播放更新同一示例并重启展示计时；新通知替换正文即撤销旧倒计时；旧回调不得提前收起新通知。收起和删除语义分开。 |
| 减少动态 | 线条按秒递减，仍使用相同8秒计时，避免持续运动；三档材质不改变倒计时语义。 |
| 铃铛 / 历史 | 历史列表不显示倒计时，不自动删除。点击本示例通知可恢复原表面并重新计时。 |

底部线条只表示自动收起剩余时间，任务执行进度仍由任务自身表达。组件不显示每帧倒数文本，不使用持续live播报；保留对现有aria-describedby的关联，提供停留暂停说明。

## 组件与注册边界

- 组件登记ID：feedback.dismiss-countdown，原型资源notification-countdown.js / .css。组件只处理DOM、单调时钟和生命周期，不自行发布业务事件、不访问文件、网络或偏好。
- 示例事件：component.demo.countdown，先在既有maintenance-events目录登记，再由prototypeNotificationPublisher投到原Toast/任务卡/铃铛。variant仅接受success/error/task固定枚举；通知语义与读/解决/删除仍属于公共宿主。
- 当前消费者只有组件专题的这三个明确入口。文件导入/导出、WebDAV等原有业务通知不因本轮组件展示改变时效或自动装条。用户看过效果后，再确定统一推广与生产组件接入。
- 组件目录把本项标为“组件原型待评审 / 正式未实现”，不以示例动画完成冒充所有业务通知验收。关联同步通知规划仍沿[0.2.18问题清单S18-03](../06-问题记录/0.2.18-bugs.md)。

## 验证与待办

实际检查：组件时间/DOM9项、原有注册通知6项、事件目录31项通过。Chromium111项通过、页面异常0；WebKit110项功能与布局检查通过，但整页异常检查失败，记录两次ResizeObserver循环告警。改前原型同尺寸/效果检查也复现一次同类告警，未过滤错误或改动并行公共布局来报全绿。两种引擎均检查亮暗、1180×760/900×600、三档效果、悬停暂停/恢复和8秒实际收起，已人工查看成功、错误与任务卡底部细线。

首轮确定性测试误统计整个组件页的rAF回调，已改为只验证本倒计时持有的回调清理；首轮减少动态布局断言在550ms期待线条缩短，与按秒更新规则不符，改为1800ms观察，未更改产品计时。第一次改前对照把Logo子页面的index.html也误路由为主入口，已限定总原型目录，失效对照与有效对照分别保留。

检查脚本、实际结果、源文件摘要和失败过程见[本轮证据](../../../../.adg/evidence/0.2.18-postrelease/notification-countdown-component-20261030/validation.json)。未执行真实Windows通知或生产软件修改；未宣称整页WebKit无异常。下一步由用户在组件入口模拟三个示例，确认展示与暂停规则后再纳入全局实施。
