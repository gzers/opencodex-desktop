把命令行操作收进一个窗口

What it is

这个项目是什么

一句话：把 OpenCodex 日常要敲的命令、要另开终端看的状态，收进一个 macOS 桌面应用，同时不改变 OpenCodex 自己的行为和权威。

产品身份

独立产品

仓库标识 opencodex-desktop，界面展示名 OpenCodeX-Desktop。与 OpenCodex 官方项目没有隶属、授权或背书关系。

技术选型

Tauri v2 + Rust

桌面壳用 Tauri v2，后端 Rust，前端是渲染在 WebView 里的 Web 界面。第一阶段以 macOS 优先，跨平台只做抽象预留，不算首期验收范围。

许可

MIT

本项目代码与素材用 MIT。官方素材（页面快照、界面截图、标识）不随仓库分发，只在本地保留。

为什么强调“不改变官方权威”：更新、provider、路由这些 OpenCodex 已经有官方通道的能力，本产品只做引导和展示，不自己再实现一套。
Problem

它解决什么问题

OpenCodex 的日常使用全靠命令行。麻烦的地方不在单条命令，而在于这些事散落在终端、配置文件和多个客户端之间。

现在

  • 启停要敲 ocx start / stop / restart
  • 状态和日志得另开一个终端看
  • 配置导出、跨机同步没有图形入口
  • Skills 和 MCP 要手工改好几份客户端配置
  • 出问题只能自己翻日志、翻环境

装了它之后

  • 一个窗口里点启停，直接看到健康、端口、PID
  • 日志和诊断中心并排看，敏感值自动打码
  • 配置导成加密容器，走 WebDAV 同步，覆盖前先备份
  • Skills / MCP 统一管一次，再分发到六个客户端
  • 出问题给原因和建议动作，不甩一个红点
Scope

做哪些、明确不做哪些

先说清边界，后面才不会返工。范围原则只有一句：原型里出现的功能都要实现，P0 / P1 / P2 只表示先做后做，不表示可以不做。

做

  • 发现并校验本机已有的 OpenCodex 安装（npm 形态）
  • 托管官方 ocx start / stop / restart 子进程，展示健康、端口、进程标识、最近错误
  • 日志只读脱敏、运行环境诊断、内嵌官方 Web 面板
  • 加密的配置导出 / 导入，以及经 WebDAV 的加密同步
  • Skills 与 MCP 统一管理，并分发到多个客户端
  • 两条独立更新通道：OpenCodex 本体升级引导、应用自身更新
  • 托盘、macOS 原生菜单，以及默认关闭的可选 CLI 控制面

不做

  • 不重写 OpenCodex 核心，不绕过官方 API
  • 不管 npm（安装、卸载、依赖解析）
  • 不替代官方 ocx update 的更新事务
  • 不安装或管理 launchd，不接管 codex-shim
  • 不写入 provider、路由、模型映射等核心运行配置
  • 不自动覆盖外部 provider 托管的配置，只检测、解释、引导官方 restore
  • 不明文迁移或同步凭据
唯一的例外：扩展配置可以写。具体是 Skills 目录同步和各客户端的 MCP 服务器节点，除此之外的一切 OpenCodex 配置仍然不可写。这也是安全评审里被反复盯住的边界。

Architecture

架构：前端只管画，后端独占外部访问

三层结构。前端不直接碰文件系统和网络，所有外部交互都收在 Rust 后端里，模块划分和能力域一一对应，方便从能力追到实现。

前端界面层概览 / 面板 / 拓展 / 日志 / 设置 / 托盘
→
管理器后端Rust · 全部业务逻辑
→
外部依赖ocx CLI / 官方面板 / 客户端配置 / WebDAV / 更新通道

几条硬约束

  • 单一真相源 + 投影：管理器维护统一事实，各客户端配置是投影，不是权威。
  • 原子写：同目录临时文件写好后原子替换，替换后保留原文件权限。
  • 备份先行：任何可能覆盖数据的写入，前面必须先有一份能恢复的备份。
  • 跨进程互斥：和官方 CLI、编辑器共享同一批配置文件，写入要拿跨进程文件锁并比对内容摘要。
  • 凭据不出域：凭据不进日志、不进命令行参数、不进错误信息、不进未加密文件。
  • 进程模型：应用自更新会重启应用本体，但不会停掉正在托管的 OpenCodex 代理，重启后重新接管。
State model

状态：三个维度，可以同时成立

最早文档只有一个“代理运行状态”，但原型里已经出现“正在同步”“正在备份”这类并行情况。压成单一状态机必然打架，所以拆成三个互相独立的维度：

运行状态 · 11 态

代理进程

未发现 / 正在探测 / 已发现未运行 / 启动中 / 待就绪 / 运行中 / 停止中 / 启动失败 / at-risk / 外部接管 / 不可达。

连接状态 · 7 态

外部依赖

未配置 / 未连接 / 连接中 / 同步中 / 已同步 / 冲突待处理 / 失败。

操作状态 · 8 态

单次动作

空闲 / 校验中 / 备份中 / 应用中 / 回滚中 / 已取消 / 成功 / 失败。

能同时表达「运行中 + 同步中 + 备份中」。渲染规则：动作按状态渲染，不渲染没有解释的灰色禁用按钮，用一句状态说明说清为什么不能点。
Flows

10 张关键流程图

挑的是有分支、有失败、有回滚的地方。图上所有连线只有横竖两个方向、单条直线段，不穿节点，方便直接读。

01 首次发现与前置门禁

node → npm → ocx 短路检查，缺什么给什么命令。

02 正常启停

未运行 → 启动中 → 待就绪 → 运行中；失败、停止、重启各自成支。

03 状态采集数据流

官方状态源 → 后端映射 → 三维状态 → 前端渲染。

04 受控写入

校验 → 备份 → 原子替换 → 重新校验 → 成功或回滚。

05 数据目录切换

引用优先、迁移可选；检查不过就阻断，迁移失败自动回滚。

06 Restore 引导

看风险 → 备份 → 用户确认 → 走官方 restore → 刷新状态。

07 导入配置

口令、完整性、版本三重校验；失败一律拒绝，不做部分写入。

08 WebDAV 同步

客户端加密 → 清单比对 → 有冲突先入待处理，不静默覆盖。

09 应用自身更新

下载 → 签名校验 → 安装 → 重启接管；失败保留上一版本。

10 官方升级引导

升级前必须备份成功，再引导官方 ocx update。

Data & safety

数据与安全边界

这个产品大半的复杂度都在这里：它要改别人机器上的配置文件，还要搬运凭据。原则是能不动就不动，非要动就先备份、可回滚、留证据。

数据根分区

分区放什么
manager state桌面壳设置、数据根元信息、界面偏好
opencodex home可选承载 OPENCODEX_HOME
backups升级、导入、同步覆盖前的备份
logs桌面壳操作日志与旋转后的日志
exports加密配置导出容器（按凭据文件处理，权限 0600）
cache可丢弃缓存
sync stateWebDAV 冲突记录、远端索引摘要、同步历史摘要

数据分级

S0 公开 / S1 内部

应用版本、官方项目信息；安装路径、版本、运行状态、端口、进程标识、数据根路径。

S2 敏感 / S3 凭据

日志正文、备份内容、Skills 文件内容、MCP 配置结构；API key、token、WebDAV 账号口令、加密口令、MCP 环境变量值。S3 不得进仓库、Markdown、日志、命令行参数或未加密文件。

掩码在取值之前完成，不是“先明文取回来，再在界面上打码”。env、args、headers 一律按潜在敏感值处理。

扩展配置落在哪

六家客户端的 MCP 节点位置、容器结构和文件格式都不一样，所以必须一家一个适配器，不能假设有统一 schema。

客户端MCP 配置落点格式
Codex$CODEX_HOME/config.tomlTOML
Claude Code~/.claude.json；项目级 .mcp.jsonJSON
Gemini CLI~/.gemini/settings.jsonJSON
Grok CLI~/.grok/user-settings.jsonJSON（数组）
OpenCode~/.config/opencode/opencode.json[c]JSON / JSONC
Hermes Agent~/.hermes/config.yamlYAML

WebDAV 的信任假设

  • 远端一律视为不可信，上传前在客户端加密。
  • 证书校验失败默认拒绝，并且不提供「忽略证书」选项。
  • 哈希只用来发现传输损坏和回放，真实性由认证加密负责，不能拿哈希当防恶意远端的措施。
  • 和官方 ocx connect 的 remote hub 是并列能力：不自建 hub，也不替代官方 hub，只同步用户自己指定的端点。

Prototype

原型长什么样

原型是为了定界面结构和状态分支，用的全是 mock 数据：不调用真实 ocx，不读真实配置，也不会真的启停或备份。官方面板那一屏是官方 GUI 的源码级快照，用来做视觉对照。

原型按 1180 × 760 的 macOS 应用窗口表达，最小 900 × 600。界面里不出现 P0 / P1 / P2，只用功能名和「规划中 / 可用」。
