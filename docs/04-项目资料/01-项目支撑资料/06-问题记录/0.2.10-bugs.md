## WP-68：已确认重启后仍被「已有保存计划待核对」挡住（死锁）

**优先级**：P0（客户端核对流程完全无法完成）
**位置**：模型 → 渠道模型 → 状态框 → 核对 Codex 客户端加载 → 我已重启，重新检查
**用户原话**：「为什么我已经确认重启了，还是『已有保存计划待核对，请先核对原计划或撤回其未完成写入』？」
**状态**：已定位（2026-10-26）

### 现象

用户已按提示重启 Codex、点「我已重启，重新检查」，弹窗里出现红字：

> 已有保存计划待核对，请先核对原计划或撤回其未完成写入

同时状态框显示「保存结果待核对 · 上次保存待重启」。此时弹窗内只有「稍后」「我已重启，重新检查」两个按钮——**没有「核对原计划」也没有「撤回」**，用户被卡死，无路可走。

### 根因：两个计划互相挡路，而只有一个能被看到

`client_state::check()` 的第一行（`client_state.rs:152-153`）：

```rust
let _guard = runtime::execution_lock(root)?;
runtime::reject_incomplete(root)?;      // ← 先扫全库，任何未完计划都直接报错
let plan = target(root)?.ok_or_else(...)?;  // ← 之后才判断「我这次要核对谁」
```

`reject_incomplete()`（`runtime.rs:519-530`）遍历**所有** plan，只要有一个 phase 不在 `prepared / committed / compensated` 里就整体报错。

而死锁是这样形成的：

| 步 | 发生了什么 |
| --- | --- |
| 1 | 某次保存进入 `verified_partial`（写入后核对发现部分不符），计划留在磁盘上等核对 |
| 2 | 用户按提示重启客户端，点「重新检查」 |
| 3 | `check()` 先执行 `reject_incomplete()`，扫到那个 `verified_partial` 计划 → 报「已有保存计划待核对」 |
| 4 | 用户想「核对该计划」，但**页面上没有入口**——`latest()` 只返回最新一个计划；若该计划不是最新（或已被后续保存覆盖），前端根本拿不到它 |
| 5 | 用户想「撤回」，同样需要先打开该计划才能看到「撤回本次未完成写入」按钮 |

**即：报错要求用户处理一个界面无法访问的对象。**

### 为什么「确认重启」这一步一定失败

这条错误与重启无关。`reject_incomplete` 检查的是**磁盘上的计划状态**，不是运行目录是否已加载；用户重启一百次，只要那个 `verified_partial` 计划还在，`check()` 就在第一步被拒。

### 三处设计缺口

| # | 缺口 | 证据 |
| --- | --- | --- |
| 1 | `check()` 的拒绝顺序错：先全库拒绝，后判断目标。应当先定位本次目标，只拒绝**与目标冲突**的计划 | `client_state.rs:152-156` |
| 2 | 前端只能看到「最新一个」计划：`latest()` 过滤后只返回 max(createdAt)，其余未完成计划成为不可达对象 | `runtime.rs:435-449` + `ChannelsView.vue:94` |
| 3 | 错误信息把「处理入口」写进文案（「请先核对原计划或撤回」），但没有对应的可达入口 | `runtime.rs:528` |

### 修法（未实施，待确认）

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A** | `check()` 改为「先定位 target，再只校验该 target 自身是否可核对」；其它未完计划不阻塞客户端核对（它们与运行目录是否加载无关） | 最小改动，直接解死锁。需确认：不阻塞是否会漏掉真正的写入冲突 |
| **B** | `latest()` 之外增加「未完成计划列表」接口，页面提供核对 / 撤回入口 | 改动大，但让错误信息变得可执行 |
| **C** | A + B 都做：先解死锁（A），再补入口（B） | 彻底，工作量最大 |

倾向 **A 先行**（它是 P0 死锁），B 作为可用性补强。

### 边界

- 未复现到具体的 `verified_partial` 生成路径（需要用户机器上的 plan 文件确认 phase 与 created_at）。
- 未验证：该残留计划是否与「上次保存待重启」是同一个对象（状态框同时显示两者，可能是两个计划）。
- 本轮只做诊断，未改代码。

## WP-68 更正（2026-10-26，第二轮核实）

上一轮补充里我写「页面没有任何通往原计划的路径」，**这是错的**。原因是我把通知 JSON 的字段名读成了 `object_id`，实际序列化出去的是 `objectId`，值一直都在。更正如下。

### 一、不是全新设备问题

| 项 | 结论 |
| --- | --- |
| 全新安装会不会一出现 | **不会**。`model-save-plans/` 为空时 `reject_incomplete()` 遍历 0 个计划直接通过 |
| 触发条件 | 必须先发生一次「写入后核对发现部分不符」，把计划留在 `verified_partial` |
| 与版本的关系 | `verified_partial` 的产生逻辑是早期就有的；**0.2.10 只是拿掉了页面内的保存结果入口**，让已有缺陷从「有两处入口」变成「只剩通知一处」 |

### 二、用户机器上的确切数据（已核对）

| 项 | 值 |
| --- | --- |
| plan | `9697b33c-724e-44d7-bd36-1199f38d6305` |
| phase | `verified_partial` |
| error | `provider_write` |
| createdAt | 2026-10-25T08:04:19Z |
| 期望写入 | 74 个模型 slug；顺序以 `FeiMao/gpt-5.5` 开头 |
| 凭据变更 | 0 项（不涉及 Key 改写） |
| 同目录其它计划 | `committed` ×3、`compensated` ×2、`prepared` ×3 —— 都在白名单内，不挡路 |

### 三、通知链路其实是完整的（上一轮误判）

`notifications.json` 里这条仍在，且字段齐全：

```json
{ "notification_id": "model-policy-save-failed:9697b33c-…",
  "title": "渠道配置保存需要核对",
  "action_ref": "model_policy",
  "event_identity": { "object_id": "9697b33c-724e-44d7-bd36-1199f38d6305", … },
  "resolved": false, "read": false, "deleted": false }
```

链路核对：

| 环节 | 证据 |
| --- | --- |
| 通知策略 | `event-registry.json` → `model_policy_failure.action = model_policy` |
| 按钮文案 | `features/notifications/actions.ts` → `model_policy: '查看保存结果'` |
| 点击行为 | `useAppController.ts:61-63` → `policyNotificationTarget = objectId` → `routes.go('models')` |
| 打开弹窗 | `ChannelsView.vue:99` → `policyResult(planId)` → `saveOpen = true` |

即：**点铃铛里那条通知就能打开保存结果**，弹窗内有「核对原计划」与「撤回本次未完成写入」。

### 四、真正的问题重新定义

不是「没有入口」，而是**入口在通知里，而客户端核对弹窗被拒时没有告诉用户去通知中心**。那条红字写「请先核对原计划或撤回」，但没写「在哪核对」。

### 五、三种解法的代价（用户可选）

| 做法 | 结果 | 代价 |
| --- | --- | --- |
| **点通知 → 核对/撤回** | 正常解决，保留全部 7 条历史 | 无 |
| `rm` 单个 plan 文件 | 也能解 | 丢这条计划与其恢复基线 |
| 删整个 `manager-state/` | 也能解 | 丢 7 条计划 + 保存历史 + 偏好 |

三种都不影响渠道模型配置（在 `opencodex-home/`，1.2G，含官方 `config.json`）。

### 六、修正后的修复清单（待实施）

| # | 内容 | 优先级 | 性质 |
| --- | --- | --- | --- |
| a | `check()` 改为先定位 target，只校验与目标冲突的计划 | **P0** | 后端死锁根因 |
| b | 客户端核对弹窗的错误里给可达出口：加「打开保存结果」按钮（有残留计划时出现） | **P0** | 让错误信息不再把人堵住 |
| c | 无入口时文案改成可执行说法 | P1 | 文案 |
| d | 0.2.10 删掉的页面内入口是否部分恢复（只留 28px 图标键，不占一行） | P1 | 密度 vs 可达性 |

### 七、方法教训

- 用 `python json` 读文件时，字段名以**实际序列化结果**为准（`objectId` 而非 `object_id`），不要用 Rust 侧的结构体字段名去猜。
- 「确认某入口不存在」必须同时查：模板里的入口、程序里置状态的地方、以及该状态的数据是否具备（本例 `event_identity.object_id` 有值）。
