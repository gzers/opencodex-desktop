## WP-89：Windows 的 OpenCodex 安装向导拒绝自身默认安装路径

### 用户现象与影响

设置 → 安装配置 → “安装 OpenCodex”的第一步中，默认安装位置带有 Windows 扩展路径前缀，例如下方形式；界面提示“安装位置必须是当前平台的完整绝对路径，且不能包含 . 或 ..”，“下一步”置灰。

~~~text
\\?\D:\Software\Develop\OpenCodeX Desktop\data\runtime\opencodex
~~~

完整[用户截图](../../../../.adg/evidence/0.2.16-issues/windows-default-install-path/user-screenshot.png)与[只读复现结果](../../../../.adg/evidence/0.2.16-issues/windows-default-install-path/analysis.json)已保留。截图是**软件内部的 OpenCodex 托管运行环境安装向导**，不能据此判定 Desktop 的 MSI/NSIS 安装目录本身错误。

影响为默认安装流程被第一步拦住；“恢复默认”仍取同一来源，可能再次产生同样的无效界面状态。首次安装、重装沿用历史前缀及离线安装都共用这一入口，均需回归。截图中的目录含空格不是本次词法拒绝的原因。

### 已确认原因

1. [SettingsRoute.vue](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/ui/src/routes/SettingsRoute.vue#L829) 将后端 managedPrefix 原样填入安装框；“恢复默认”取 defaultPrefix。第一步只要 installPrefixIssue 非空就禁用下一步，尚未调用安装命令。
2. [runtime source DTO](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/tauri/src/commands/runtime.rs#L134) 将已登记前缀或数据根下 runtime/opencodex 直接转成字符串。数据根启动链使用 Windows 原生 canonicalize，可能产生合法的扩展盘符或扩展 UNC 路径。
3. [installPath.ts](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/ui/src/features/runtime/installPath.ts#L6) 只识别普通盘符与普通 UNC；把扩展前缀中的问号视为不允许的 UNC 根，返回无效路径。同一解析器也让“数据根内/外”判断返回未知。
4. [既有测试](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/ui/tests/settings-install-path.test.ts#L69) 明确将扩展盘符路径放入“应禁用”用例，固化了错误口径。并非仅缺少一个界面提示。

实际加载发布源码中的路径函数，得到以下词法结果；没有调用安装、写用户配置或操作 Windows 文件系统：

| 输入形式 | 当前路径校验 | 当前能否进入下一步 |
| --- | --- | --- |
| 普通 D 盘绝对路径，包含空格 | 通过 | 是 |
| 同目录的扩展盘符形式 | 返回无效绝对路径 | 否 |
| 普通 UNC 共享目录 | 通过 | 是 |
| 同目录的扩展 UNC 形式 | 返回无效绝对路径 | 否 |

默认落点“数据根/runtime/opencodex”这一产品约定本身没有被证据推翻。已确认的是**自动返回的 Windows 路径表示与前端识别规则不一致**；移除前缀后词法通过，不等于证明真实安装、权限或 npm 命令均能成功。

### 修复建议与关联检查（待实施）

- [ ] 统一已知 Windows 盘符、UNC 及其扩展形式的路径身份；展示、默认预填、恢复默认、目录选择、输入校验和数据根包含关系使用一致规则。规范化后应指向原目录，不悄悄变更用户选择或已有安装登记位置。
- [ ] 显示采用可读的普通路径时，保留实际路径语义与长路径边界；不能对任意设备路径做字符串删前缀。设备命名空间、GLOBALROOT 等未支持形态继续明确拒绝。
- [ ] 后端使用实际文件系统校验绝对路径、权限、链接/重解析点及系统目录。现有 runtime/paths.rs 的 Windows 系统目录检查以字符串比较为主，扩展形式的身份等价也须同步复核；不能只放开前端而造成保护规则漏判。此项为源码风险与待验要求，未声称已在 Windows 上证明绕过。
- [ ] 首次默认安装仍落在当前数据根的 runtime/opencodex；重装沿最近有效安装记录，“恢复默认”取数据根默认值。不得以本次兼容修复把所有位置改为固定盘符或重新规划数据根。
- [ ] 纠正将合法扩展路径一律拒绝的旧测试；覆盖默认值和真实后端 DTO，而不只手工构造普通路径。保留相对路径、盘符/共享根、控制字符、遍历、跨共享及保护目录等原有拒绝要求。
- [ ] 保持原型安装向导的布局、按钮和四步流程，只修默认值及校验口径；不增加额外确认、核对状态或新的通知样式。

### 修复后必做验收

1. Windows 新安装在非系统盘、含空格/中文的数据根打开向导，自动默认值无需改字即可进入下一步；目录选择与恢复默认同样成立。
2. 使用实际 Windows 原生 canonicalize/DTO 返回的扩展盘符路径，并覆盖普通/扩展 UNC 的解析与身份等价；网络共享实际安装是否受支持按真实文件系统结果说明，不由词法通过推导。
3. 数据根内/外判断准确，兄弟目录、不同共享不误认；保护目录及其扩展等价形式不因规范化而放行，权限与链接检查保留。
4. 在隔离原生安装器环境完成一次真正的 OpenCodex 托管安装：核对最终落点、登记记录、可执行入口与版本读回；覆盖重装、恢复默认及离线共用入口。Desktop 安装/首屏通过不能替代本步骤。
5. 安装失败或权限不足保留用户选值并如实报错；macOS 的默认路径和保护规则保持原行为。没有 Windows 实测和真实安装回执前不标记修复完成。

### 证据与当前边界

本轮完成截图登记、发布源码链路核对、四种路径的只读词法复现和旧测试口径审查。确认了第一步的 UI 阻断原因；未在用户 Windows 上调用安装命令，未验证该目录实际权限，未修改软件、原型或用户配置，未指定下一修复版本。后续实施时将本问题纳入对应版本文档主线、开发、真实安装测试与发布范围。

## WP-90：托管安装的目标归属、写前校验与落位后回滚不完整

**P1，共用生产库三种隔离场景已复现，Windows 原生待验。** 应补现有安装事务的边界，不要求清空旧配置或增加保存计划。

1. **非受管非空目录被整体替换。** runtime/paths.rs 的 validate_install_target 检查绝对路径、链接、保护目录、目录类型和可写性，没有核实已有内容归属；atomic_replace_prefix 对已有目录改名，新目录落位后递归删除旧目录。夹具中目标只有非受管 old-sentinel、没有托管清单，安装仍成功，原文件消失。误选已有目录可造成数据丢失。
2. **入口写失败，旧包已经删除。** [install.rs:1334](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/tauri/src/modules/runtime/install.rs#L1334) 先替换包体并删除旧目录，再写 runtime/bin 稳定入口和激活凭证。夹具把入口父目录设为普通文件，安装报 filesystem，但旧 sentinel 消失、新包存在、启动器不存在，与“失败时不改现有前缀”注释冲突。另补先通过生产安装器建立有效托管包及 manifest、再制造入口异常的重装夹具，得到相同的旧包内容丢失结果。
3. **拒绝目标前已有副作用。** [install.rs:1292](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/tauri/src/modules/runtime/install.rs#L1292) 先创建父目录，后校验目标。夹具经受管范围中的链接指向隔离外部目录，最终返回 symlink_component，但外部 new-parent 已创建。Windows 系统目录/别名拒绝也要验证“先拒绝、后写入”，不能只检查错误码。

- [ ] 锁定目标实际身份；非空非受管目录拒绝整体覆盖。已有托管目录以有效 manifest、包身份与登记判断，不因可写就视为本软件包体。
- [ ] 保留旧包、旧入口、manifest/激活证据及来源记录，直至落位、入口版本读回和登记均成功；失败恢复先前状态，不吞恢复失败。
- [ ] 创建目录、写探针、临时区前校验完整目标及祖先；拒绝不留下新目录。保留原型现有确认，不让额外泛化确认替代软件判断归属。
- [ ] Windows 隔离覆盖普通/管理员、非系统盘、非受管非空目录、入口异常/锁定/ACL、激活凭证失败、回滚再次失败及拒绝路径零副作用；macOS 同源问题一起回归。

## WP-91：安装版本探针忽略非零退出码

**P1，真实 Node 进程与共用生产探针已复现。** [RealVersionProbe](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/tauri/src/modules/runtime/install.rs#L674) 得到任何退出状态都结束等待，随后只从 stdout 提取版本，不检查退出是否成功。

夹具输出 2.77.0 后 exit 7，真实退出码 7，探针仍返回 Some(2.77.0)，可能误判失败入口可运行。它与 OfficialCliVersionSource 是不同实现，后者 Windows 非零退出测试通过不能替代本项。

- [ ] 安装成功须真实零退出、可解析版本且符合请求；非零/超时/不完整输出不发布成功，保留旧包和输入。
- [ ] 复核有界输出和进程收口：目前先等退出再读 stdout，还需测试大输出、派生进程持有管道，不能让 read_to_end 在超时之后无限等待。此为关联风险，未声称本轮已复现全部管道场景。
- [ ] 两平台用真实生产探针覆盖零/非零、版本不符、无版本、超时、大输出/派生进程及旧包保留，不仅使用固定成功探针。

## WP-92：Windows 工具发现的版本管理器布局覆盖不足

**P2，兼容风险，不作为已复现 Windows 故障。** [候选实现](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/tauri/src/infrastructure/discovery_paths.rs#L46) 已支持 Known Folders、NVM_SYMLINK/NODE_HOME/NVM_HOME、nodejs/npm 固定目录和 npmrc prefix；Volta/fnm/pnpm 则主要拼接 AppData 一级目录，未完整表达 VOLTA_HOME、FNM_DIR、版本子目录/激活链接布局。

- [ ] 实际 Windows 覆盖官方 Node、NVM、Volta 默认/自定义 HOME、fnm、pnpm、自定义 npm prefix、重开后的新环境。候选存在与 node/npm/ocx 组合可运行分别判断。
- [ ] 沿受控声明和验证目录，不执行 shell profile、扫全盘或盲信任 PATH；缺失沿原显式选择/引导说明。
- [ ] 与 WP-89 共用身份规则，但只读发现和安装写入边界分开，不把写路径系统目录/链接禁区套到正常 Node 发现。

## WP-93：正式安装包文档入口依赖构建机路径

**P2，源码/公共打包契约确认，Windows 点击待验。** [project_document](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/tauri/src/commands/workspace.rs#L203) 用编译时 CARGO_MANIFEST_DIR 祖先拼仓库 LICENSE 和 docs 下第三方声明，指向构建机；tauri 配置未将两份材料作为资源。用户安装后缺少源码目录，关于页“查看 MIT 许可/第三方声明”会进入文档不可用分支。

公共 macOS 发布归档也没有许可资源，证明共用打包契约有问题；没有声称本轮已枚举 Windows 每一项安装文件，见[资源分析](../../../../.adg/evidence/0.2.16-issues/windows-full-audit-20261028/packaged-documents-analysis.json)。

- [ ] 将真实许可/声明纳入正式资源或使用批准的稳定来源；按运行资源解析，不依赖工作区、构建机绝对路径或用户拥有 docs 分支。
- [ ] 实际 NSIS/MSI/macOS 包在无源码环境点击验证，反馈沿既有样式，不新增文档中心。

## WP-94：Windows CLI 能力说明与实现不一致

**P2，描述不一致已确认，不代表公开 CLI 应立即启用。** [设置](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/ui/src/routes/SettingsRoute.vue#L1183)和[后端守卫](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/tauri/src/commands/preferences.rs#L48)禁用 Windows CLI 并称“本机 IPC 未实现”，但 ipc/endpoint.rs 和 ocxd.rs 已有 Windows named-pipe 服务/客户端、隔离身份和连接测试。

- [ ] 统一“传输已实现、公开 CLI 仍未开放”的产品边界、文案和文档，不继续称底层完全未实现。
- [ ] 保留未验能力禁用；若后续支持 CLI，另验公开命令、注册/注销、用户身份、普通/管理员令牌和权限，不因找到代码直接去掉守卫。
- [ ] 清理“当前正式目标只有 macOS”等失效平台注释；停止/取消契约保留，不顺带增加强杀或产品状态。

## WP-95：Windows 全链验收与发布门禁补齐

**P1，确认的覆盖缺口。** 0.2.16 已通过结论在原范围内保留，不能扩大为所有 Windows 场景通过：

- 安装主测试模块仅 [cfg(all(test, unix))](https://github.com/gzers/opencodex-desktop/blob/v0.2.16/apps/desktop/tauri/src/modules/runtime/install.rs#L1812)。Windows 有真实启动器/npm 参数/版本/状态/Doctor/锁测试，未等价覆盖完整安装/回滚事务。
- 安装器脚本对 NSIS 显式 /D、MSI 显式 INSTALLDIR，没有使用默认目录，也未在软件内完成真实 OpenCodex 安装。
- 最新 startup 报告 mode=any、applicationElevated=true；管理员通过不代表普通用户无需提权可用。历史专题普通权限报告不能替代本版本默认链路。
- 六档主题质量与 CSS 缩放不是原生 DPI/Win10/11 材质全部通过；安装器报告明确不包含真实升级/OTA。
