## WP-40：渠道表操作列被挤出可视区

**优先级**：P1
**位置**：模型 → 渠道模型 → 渠道列表「操作」列
**用户原话**：“渠道列太宽，导致操作列超出软件宽度了。”
**状态**：仅分析，未实施

### 现象

行尾的操作按钮溢出到软件右边缘之外，最后一颗「置顶」被截断；表格本身没有可用的横向滚动，用户无从看到被裁掉的部分。

### 实测（隔离页 1:1 拷贝 tokens.css / base.css 与组件 scoped 样式）

| 项 | 实测值 |
| --- | --- |
| 操作列声明宽度 | 200px（内容盒 184px，两侧各 8px 内距） |
| 操作按钮自然宽度 | **299px** |
| 被裁掉的部分 | **107px** |
| 各列实际宽度 | 36 / 296（弹性）/ 190 / 76 / 76 / 200 |
| 表格宽度 | 800px（min-width）；容器 758px 时横向溢出 107px |

### 根因：列宽照原型，按钮比原型多两个

原型 `model-config.js` 的渠道行操作区只有 5 个控件：编辑 / 复制 / 删除（sm）+ ↑↓（14–18px 的 mini 对）。行本身 `draggable="true"`，**没有独立的拖动把手按钮，也没有「置顶」按钮**。原型 `--mp-provider-columns` 里操作列就是 200px，正好等于这 5 个控件的自然宽度（实测 184px，含内距刚刚好）。

实现侧 `ChannelsView.vue` 在同一列里放了 **7 个 `size="sm"` 按钮**：↕（拖动把手）、编辑、复制、删除、↑、↓、置顶。全部是 28px 高、10px 横向内距的 sm 规格，累计 299px；200px 的列装不下，而 `ui-row-actions` 的 `flex-wrap: nowrap` 又强制单行，于是溢出单元格。

**为什么看不到滚动条**：`table-layout: fixed` 下单元格内容溢出是「可见溢出」，不会把表格撑宽，所以 `overflow-x: auto` 的容器没有可滚动内容，用户只能看到被页面右边缘裁掉的结果。

### 备选改法（同一隔离页实测）

| 方案 | 操作列内容 | 自然宽度 | 200px 列是否装得下 |
| --- | --- | --- | --- |
| A 完全照原型 | 编辑 / 复制 / 删除（sm）+ ↑↓（mini 对） | **184px** | 刚好装下 |
| B 原型 + 置顶 | A + 置顶（mini） | 205px | 差 13px |
| C 原型 + 置顶 + 拖动把手 | B + ↕（mini） | 226px | 差 34px |
| D 加宽操作列到 280px | 现状按钮 mini 化后 | 264px | 需改列宽，渠道列被压到 138–188px |

结论：**A 是唯一能在 200px 列里严丝合缝的方案**，也正是原型口径。若要保留「置顶」与「拖动把手」，必须按 D 把操作列加宽到 280px，代价是渠道列被压缩、长渠道名开始换行。

### 建议

按既有决策「完全按原型，不扩散」取 A：移除行内独立的拖动把手按钮与「置顶」按钮（拖动改由行本身承载，原型即如此），↑↓ 收成 mini 对。这样 200px 列不再溢出，也不需要改列宽。

若「置顶」确有必要，应先在原型补出位置与规格，再按 D 加宽——不在实现侧单方面加按钮。

### 待确认

1. 「置顶」是否保留？保留则需改原型并把操作列加宽到 280px。
2. 行内「↕」拖动把手是否保留？原型是整行可拖，没有独立把手。
3. 若选 A，↑↓ 的 mini 规格是否按原型 18px 高、5px 圆角。

### 未验

未在应用内点击验证裁剪边界（隔离页已复现同样像素），未做 Windows 原生核对。

## WP-41：服务节点下拉里「当前节点」与「未检测」未垂直对齐

**优先级**：P2
**位置**：模型 → 渠道模型 → 服务节点列的下拉触发器
**用户原话**：“当前节点的下拉‘当前节点’和未检测不垂直方向对齐。”
**状态**：仅分析，未实施

### 实测（取文字实际渲染盒，不是元素盒）

| 对齐方式 | 名称文字盒 | 状态文字盒 | 基线差 | 中心差 |
| --- | --- | --- | --- | --- |
| 现状 `align-items: center` | 高 14px（12px 字） | 高 13px（11px 字） | **-0.4px** | 0 |
| 改 `align-items: baseline` | 高 14px | 高 13px | **0** | 0 |
| 统一 11px + center | 高 13px | 高 13px | **0** | 0 |

### 根因

`.node-current-label` 用 `align-items: center`。两段文字字号不同（名称继承 `.select-trigger` 的 `--text-label` 12px，状态用 `--text-caption` 11px），行盒高度 14.4px 与 13.2px 不同；居中让两个**盒**的中心对齐，但**文字基线**差了 0.4px，视觉上就是小字略高、大字略低。

原型 `.mp-node-picker-trigger` 把触发器整体设为 `font-size: var(--text-caption)`，名称与状态同一字号，因此没有这个偏差。

### 建议

两处一起改，既修偏差又与原型一致：

- `.node-current-label` 改为 `align-items: baseline`（混合字号时按基线对齐，最稳）。
- 触发器内名称字号统一为 `--text-caption`（对齐原型）。若认为 11px 偏小，至少保留 baseline 对齐。

实测两种改法都能把基线差降到 0。

### 待确认

1. 节点名是否接受 11px（原型口径）？若不接受，只改 baseline 也可消除偏差。

### 未验

未在应用内放大截图复核（隔离页已量化基线差），未做 Windows 原生与 200% 缩放核对。
