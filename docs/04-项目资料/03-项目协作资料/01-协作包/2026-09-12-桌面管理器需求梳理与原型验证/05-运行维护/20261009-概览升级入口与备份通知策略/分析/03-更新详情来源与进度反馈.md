# 更新详情来源与进度反馈（0.1.10）

2026-10-10；依据用户对检查结果、两类详情与设置更新流程的批注。属于概览升级入口的设计深化，不新增版本或生产已完成声明。原型布局及交互见 [DESIGN](../原型/DESIGN.md)，核对记录见 [QA](../原型/原型QA.md)。

## 界面与共享流程

检查结果改为较宽弹窗、管理器与面板上下排列。每个对象展示当前版本、候选版本、检查状态、来源与简短内容摘要，分别进入详情。详情采用版本摘要、更新内容、影响与备份选项、底部操作的顺序；标题与底部操作固定，更新内容有独立滚动区，正文过长时可滚动，避免按钮被顶出窗口。

概览和设置使用同一个对象记录、详情组件和更新事务。点击检查只查询，不开始安装。无更新不显示虚构候选；失败显示当前版本及重试动作。原型按现有令牌扩大至 min(90%, 780px)、最高 88% 容器高度；这是评审尺寸，生产需按实际窗口核验浅深主题、标准 / 紧凑与三档画质的可读性、键盘滚动、焦点和小窗口布局。

更新内容分别有加载中、可阅读、发布者未提供、加载失败四态。说明失败不抹掉成功的版本检查结果，不自动转为安装失败；提供独立“重试说明”。缺失时明确说明，并保留已核实的发布网页出口；没有经过核实的链接就隐藏对应入口。详情备份选项仍默认勾选管理器偏好备份，不扩大成面板完整配置备份。

## 如何取得真实更新内容

只读基线 main@de6862d4：管理器 commands/update.rs 的检查返回仅记录候选版本；modules/update/mod.rs 的 UpdateStatus 没有更新说明或网页字段。install_update 的 download_and_install 两个回调目前均为空闭包。这里确认的是这些代码路径的字段与回调缺口，不代表其他安装路径都没有进度。实现应增加投影及后端事件，原型不能替代此工作。

| 对象 | 候选版本事实源 | 说明获取建议 | 网页入口 |
|---|---|---|---|
| 桌面管理器 | 同一通道的 updater 元数据及真实版本比对 | 优先保留匹配版本的 updater 说明；缺失时按候选对应的 GitHub Release 查询 body | 使用匹配 Release 返回的 html_url，不用 latest 链接代替具体版本详情 |
| OpenCodex 面板 | 固定官方包 @bitkyc08/opencodex 的精确版本及完整性记录 | 从该版本的官方发布说明 / CHANGELOG 取得；官方仓库与版本映射必须经维护配置核实 | 使用核实后的版本发布 URL；缺失时只提供官方包页面 / 发布列表，不声称是该版本详情 |

管理器建议发布阶段继续以 main 的 CHANGELOG.md 为用户可见事实源，从同一版本条目生成 Release 正文和 updater 说明，避免两份人工文案漂移。现有真实发布列表为 https://github.com/gzers/opencodex-desktop/releases；按 tag 查询需要匹配候选、通道与非草稿身份，beta 标签不得直接套 stable 标签命名。

npm version / dist.integrity 只能证明版本与包摘要，不能凭它生成更新说明；npm 包页面与通用 README 也不自动等于精确版本 CHANGELOG。实施时先核实 repository / homepage 和官方发布路径；无法建立版本映射时显示“发布者尚未提供本版本更新说明”，不编造说明或猜测版本网页地址。

后端归一化对象至少包含 target、channel、currentVersion、candidateVersion、notesState、notes（纯文本或受限 Markdown）、notesSource、releaseUrl（可空）、publishedAt（可空）、fetchedAt。查询使用当前网络代理与通道策略，设置超时、体积上限、缓存和重试；按对象 / 通道 / 版本缓存，旧 generation、通道切换或对象变更后丢弃迟到结果。说明查询不触发安装，不自行频繁重试。

远端正文仅作数据，先转义或安全渲染受限 Markdown，禁止直接插入远端 HTML、脚本、iframe、远端图片与内嵌样式。URL 仅接受核实来源的 HTTPS 地址；无可用网页时不得拼出虚构链接。下载来源、完整性与签名校验沿原门禁，说明与网页不可替代安装校验。

原型不联网：管理器与面板的正文均为固定排版 fixture，面板“功能改进”等内容不构成官方 2.51.0 事实。右侧工具明确说明 fixture 范围。页面链接分别为管理器官方发布列表、npm 官方包页面参考，未核实精确候选网页，不能冒充 0.1.10 / 2.51.0 的真实更新详情。生产精确链接和内容获取仍待实现与验收。

## 更新过程与反馈

阶段顺序：检查 → 确认（可选偏好备份）→ 准备 / 备份 → 下载 → 完整性或签名校验 → 应用 / 安装 → 面板版本与入口核验，或管理器待重启 → 重启后版本回读。每阶段展示名称、状态和必要影响；失败指出失败阶段、保留状态及重试出口。

- 下载有真实总字节时展示 downloaded / total 算出的百分比，仅表示下载阶段；下载 100% 不能等同于整体更新完成。未知总量、准备、校验、应用采用不确定进度，不用计时器伪造百分比。超时给可读的等待 / 错误状态，不自动假报完成。
- 概览有紧凑反馈和“查看进度”；设置有相同阶段与进度；详情确认后进入进度窗口。关闭窗口只隐藏视图，事务继续，重新打开读同一 operationId 的最新状态。完成不得抢占用户后来打开的其他弹窗。
- 后端事件按 operationId、target、candidateVersion、channel 与序列号关联。单事务互斥，旧回调及倒退进度拒绝；结果以真实校验和版本回读为准。已有完成 / 失败 / 取消事件沿统一注册表投递，进度每次 tick 不生成一条通知。
- 生产取消动作由后端阶段能力明确提供。原型演示准备 / 下载 / 校验可取消，写入阶段取消禁用；这不是对实际 Tauri 或 npm 事务可取消性的承诺。实际写入 / 安装中不得强制停止造成半安装，撤销与回滚边界需实现验证。
- 管理器安装就绪仍显示旧运行版本和“等待重启”，投递已注册的 update.restart.required；重启后回读确认才显示新版本并发 update.complete、解除待重启提醒。原型“重启并完成更新”只在内存模拟回读，不执行重启。
- 高档展示等待动画与进度过渡；中 / 低档保留静态进度、阶段文字与百分比，不重新绑定系统减少动态设置。动画仅辅助反馈，操作可用性与文本状态不能依赖动画。

## 实施与验收门禁

代码归 main / feature 分支实施，本文只引用真实提交和证据。先明确更新说明 DTO、受控来源、精确网页映射及进度 / 取消能力，再接共享 UI。Windows / macOS 验收概览和设置两入口的加载、缺失、说明独立失败、长正文内部滚动、网页链接、下载已知 / 未知总量、签名失败、应用失败、关闭重开、切页、取消及迟到结果。还需核验管理器重启前后版本、面板更新目标与入口，保留现有备份 / 签名 / 安装隔离门禁。

本轮原型状态与 Node VM 测试不构成浏览器实屏或生产更新验收；不得以动画演示关闭发布门禁。
