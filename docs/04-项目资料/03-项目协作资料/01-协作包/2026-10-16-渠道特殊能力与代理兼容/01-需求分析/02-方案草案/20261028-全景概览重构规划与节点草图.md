## 1. 本轮需求与旧稿处置

用户反馈上一版效果不好：概览应将上半部分与连接关系融合，让可视化占满概览；节点带信息、更新、同步及相关操作。客户端不止 Codex，在右上角“概览设置”中选择当前机器确实存在的客户端，发现方式参考官方面板。连接关系按此前架构和实际链路表达，当前视觉与 Superba 差距较大。

本轮进一步要求：“你先规划记录，然后给我模拟画一个节点大概怎么样，不画原型。”因此本次仅文档与静态图。旧 #connection-map 保留为首轮历史演示；14 项检查仅证明该轮技术接线，不代表设计获接受。不继续在旧卡片框内局部美化，不将旧稿接入正式概览。

## 2. 整体构图方向

方向名：融合节点。概览正文作为同一画面，左侧本机客户端，中间 OpenCodex，右侧上游渠道；Desktop 管理器位于管理侧支。保留外壳与标题栏，右上角增加“概览设置”。采用自动布局，首轮不增加自由拖线或保存任意节点坐标。

现有动态 Logo 直接成为 OpenCodex 运行节点：图形、连线锚点、运行状态、版本和操作属于同一对象；取消上方独立 Logo 与下方小代理节点的重复。背景光由它驱动并铺到整个概览，文字和线不再套大型玻璃面板。节点以品牌图标、短标签和两三行信息构成，操作与详情浮层才使用小面积玻璃材质。

借鉴 Superba 的节点比例、路径节奏、旁路、状态标记与节点动作，不只复制路径文字。“占满概览”指完整工作区成为可视化阅读与操作空间，不是无限放大图标或堆装饰。数量增加时按客户端组、渠道组折叠，选中再展开相关支路；900×600 优先展示主路径与分组数量，保持字号。

## 3. 节点信息与动作归属

| 节点 | 常驻信息 | 选中／聚焦后的操作 |
| --- | --- | --- |
| Desktop 管理器 | 本应用版本、可用更新、管理连接状态 | 检查更新、更新详情、管理偏好 |
| OpenCodex | 动态 Logo、运行状态、已知版本、端口、更新提示 | 打开面板、重启；更多中放停止、日志、连接详情；未运行时提供启动 |
| 客户端实例／分组 | 图标、名称、可核实版本、运行与接入状态 | 已实现的打开、接入配置、路径详情；不补造第三方统一升级能力 |
| 渠道／服务节点 | 渠道、节点、可用状态、所选或实际采用模型 | 查看渠道、检测服务节点、公共模型选择器；沿既有保存流程 |
| 配置同步 | 文件同步／WebDAV 各自状态与最近结果 | 打开同步、查看差异／恢复结果；归 Desktop 管理关系，不串进推理请求路径 |
| Desktop 能力适配（可选后台能力） | 仅实际启用时显示实例、状态和用途 | 归属 Desktop，展开实际路径时显示；无部署不占位，不成为所有渠道必经 |

常态保留名称、状态、版本及更新／异常小标记。选中、悬停或键盘聚焦显示常用动作，完整信息放小浮层，避免长期铺满画布。节点动作随真实状态变化，动画不宣布操作成功；更新复用既有更新中心，第三方升级取决于自身已支持机制。同步默认排除和选择语义不随视觉迁移改变。

## 4. 概览设置与本机客户端

“概览设置”只编辑展示偏好：显示哪些客户端、信息简略／详细、备用渠道显隐、管理／同步关系显隐、自动布局与恢复默认。主题、全局特效和渲染器继续使用唯一公共设置。隐藏节点不等于停用客户端、修改路由或改变同步范围。

不写死 Codex App／CLI；读取官方面板客户端目录与接入事实，同时区分：本机存在（可执行文件、应用或 IDE 扩展）、有效配置接入、最近请求观察。默认显示本机确认存在且已接入的客户端；其他已安装客户端可手动选择，未接入时不伪造连接线。仅残留目录／配置的结果单独说明，不自动进入“本机已安装”清单。

品牌可以分组，实际路由不同的 App／CLI／profile 保留实例身份。暂未运行、已停用与未安装分别表达；同品牌不能合并不同来源观察。

源码边界：Desktop 的 features/extensions/clients.ts 当前由 Skills／MCP 路径投影推导 installed；OpenCodex 2.84.0 部分 native 状态将 installed 固定为 true，文件客户端也有基于目录存在的廉价检测。这些都不能单独证明应用安装。复用它们的接入事实并独立补齐安装证据；已有 cursor-detect 等专项检测按实际范围复用，不建立与面板脱节的品牌清单。

## 5. 按真实链路表达

- 普通请求：客户端 → 原版 OpenCodex → 已选渠道／服务节点。
- 实际启用出站增强时：客户端 → 原版 OpenCodex → Desktop 能力适配 → 原版已选渠道；原版负责选路，不引入第二套路由器。
- 直连或其他网关按客户端有效配置另画，不强行经过 OpenCodex。
- Desktop 的启停、状态、配置、更新和同步归管理关系；制模助手实际发模型请求时才作为独立请求来源。
- 模型是渠道／请求属性，不增加网络跳数；策略服务、存储和 UI 不作为推理必经节点。只有真实 owning 实例连接成立时才展示其执行关联。

配置指向、待客户端重启、最近请求、活跃请求和过期记录分别表达；选中具体请求再展开其尝试／回退。HTTP／WebSocket 及协议按入口／出口分别取证，未知不写固定值；探测延迟、首字延迟、总耗时不混用。

架构依据：[执行架构与扩展边界](20261027-对话策略执行架构与OpenCodex扩展边界.md)、[Superba 连接源码核对](20261028-Superba连接关系源码核对与原型计划.md)。本次规划不改变原版完整性、公开接口限制和未接通能力。

### 5.1 Desktop 归属与多渠道聚合补充

2026-10-28 后续讨论明确：出站适配属于 Desktop 产品的后台能力，界面管理它，但具体实现可以是后台模块或由 Desktop 托管的独立进程，形态尚未确定，不能依赖窗口保持打开。产品归属与请求经过的运行组件分别表达；不把整个 Desktop 界面画成每个请求必经代理，也不把适配节点当作外部第三方产品。

OpenCodex 继续聚合全部已配置渠道，负责选路、认证和既有故障切换。Krill 只是目前研究上下文特殊能力的一项渠道，不代表所有上游；适配也不限定为 Krill 专用，其他渠道只有在明确配置和能力核实后才沿对应支路处理。适配接收已选目标，不擅自将其他渠道请求改送 Krill。

同一客户端实例的上下文策略与渠道兼容性需要同时成立，不随每次选路临时改全局配置。涉及上下文状态的续聊／回退不能只凭同名模型认定兼容。当前出站 Hook 缺少完整渠道与任务身份，可靠匹配及相关上下文能力仍有接入缺口；这是现有方案限制，不因将适配归属 Desktop 就视为解决。

## 8. 多渠道展示收敛与按需展开

2026-10-28 用户进一步担心列举所有渠道会过多、过杂，随后要求“思路记录下来”。以下记录为当前候选交互方向；本次只回写资料，不制作新图或修改原型。具体数量、排序及固定偏好仍待布局评审，版本与开发时机未定。

概览展示当前关注的关系，完整渠道清单继续放模型页，不将所有已配置渠道和所有客户端画成交叉线。整页可视化通过节点信息、留白和相关操作构成完整画面，不靠堆满渠道填充空间。

| 情况／动作 | 展示规则 |
| --- | --- |
| 默认客户端 | 展示用户勾选且本机存在性已确认的客户端；沿第 4 节区分安装、接入与请求观察 |
| 默认渠道 | 优先展示近期请求涉及的渠道，以约 3 个为首轮密度候选；其余收为“其他渠道 · N”，不视为已冻结上限 |
| 选中客户端 | 突出可确认属于它的配置／请求路径，其他关系弱化；不能归属的记录不强行连到该客户端 |
| 选中具体请求 | 仅展开该请求实际经过的目标、Desktop 能力适配及尝试／回退；不串联不同请求的渠道 |
| 没有请求记录 | 根据已保存有效配置展示可确认的关系，标明“尚未观察请求”；有多个路由候选时不能擅自指定唯一实际渠道 |
| 点击“其他渠道 · N” | 打开可搜索清单，选择某渠道后临时展开；数量仅统计当前收起的渠道，分组不是额外网络节点 |
| 概览设置 | 可固定常用渠道、调整可见范围；固定渠道同样标明它是配置关系还是已有请求观察，不暗示正在使用 |

搜索、临时展开和固定常用的关系要保留阅读上下文；数量超过当前空间时折叠其他非关注项，不无限追加节点或缩小全部字号。是否保留“显示全部”的独立动作，以及固定项与最近项的优先级，在整页静态构图时比较，不在本轮补造硬规则。

Desktop 能力适配按实际路径展开：某个请求确认经过该组件时显示；仅配置计划但未接入时只表达配置／待接入关系，不伪装实际流量。普通渠道沿原通路，不给每个渠道统一增加适配一跳。管理、配置同步和模型请求各自保持原有关系语义。

上述收起、隐藏、搜索、固定均只改变概览可视性，不停用渠道或客户端，不改变 OpenCodex 聚合、模型选择、回退顺序或同步范围。显示偏好与运行配置分别保存；其持久化方式尚未在本轮实施。

后续评审补充覆盖：少量／大量渠道、多个客户端共享渠道、零请求记录、无法关联来源、特殊能力与普通路径并存、折叠数量、搜索临时展开、固定项超出空间、选中请求回退，以及最小窗口下阅读与返回位置。当前仅记录思路，不将这些场景标为已实现或已验收。
