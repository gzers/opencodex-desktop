## WP-28：查看草稿入口多余

**优先级**：P2
**位置**：模型配置 → 渠道模型 → 顶部操作行（预览选择器 / 状态 / 查看草稿 / 还原修改 / 保存）
**用户原话**：“查看草稿也是多余的吧，先记录。”
**状态**：待修复

### 现象

顶部操作行第四个按钮“查看草稿”打开 `PolicyDraftDialog`，展示草稿相对最近保存的差异、按渠道分组的变更条目，并提供“处理”跳转与“保存”。

### 判定为多余的理由

1. **信息重复**：左侧紧邻的状态框（“未保存修改 / 未修改 / 待核对”）已经回答“有没有改动”，而改动明细在保存流程里本来就有——`prepareSave()` 打开的“确认保存渠道配置”对话框逐条列出范围、目录变化、协议分组与运行字段差异。为了看差异要点两次弹窗，第二次才可提交。
2. **原型自身口径不一致**：原型 `model-config.js` 第 442 行的注释写明“从左到右：预览选择器 → 状态 → 还原修改 → 保存”，四件套里没有“查看草稿”；但同文件仍保留 `draftDialog()` 与 `view-draft` 动作，属于旧入口未清理。本轮以该注释描述的最终形态为准。
3. **入口含义含糊**：“草稿”在本页已是工作区常态（编辑即入草稿、自动暂存），再单列一个“查看草稿”会让人以为草稿是另一份独立副本；实际它就是当前列表内容。
4. **动作重叠**：对话框里的“保存”与顶部“保存”是同一动作，两条路径各自带着 `can-save` 判定，容易出现一处可点、一处禁用的错觉。

### 拟定改法

- 渠道模型列表移除“查看草稿”，顶部回到四件套：预览选择器 / 状态 / 还原修改 / 保存。
- 差异查看能力合并进保存确认对话框（已有 `savePlan.runtimeChanges` 与范围明细），必要时在该对话框补“草稿相对已保存”的完整分组视图，避免能力净减少。
- 渠道详情侧栏的“查看草稿”同步移除；`ChannelEditor` 的 `draft` 事件与 `PolicyDraftDialog` 组件一并清理，或保留组件仅供保存确认复用（实施时决定，需同步组件登记表）。
- 原型侧删除 `draftDialog()`、`view-draft` 分支与对应按钮，使原型与注释口径一致。

### 待确认

- 是否保留一个只读、不可保存的差异查看入口？若保留，应放在状态框点击处（点“未保存修改”看明细），而不是并列一个按钮。
- `PolicyDraftDialog` 若被移除，组件登记中对应条目与消费者需要同步更新，避免清单指向不存在的实现。

### 验证口径

- 顶部只剩四个控件；无“查看草稿”文本与对应 `data-*` 钩子。
- 保存确认对话框仍能回答“改了哪些渠道、哪些字段、目录条数如何变化”。
- 原型与实现按钮集合一致，注释描述与界面一致。

## WP-29：默认渠道只是界面移除，后端仍强制校验

**优先级**：P1（阻塞保存）
**位置**：模型配置 → 渠道模型 → 保存
**用户原话**：“保存还提示默认渠道至少一个模型，说明你只是界面上取消。但是并没有真正意义上没有这个功能。本身没有要求这个。”
**状态**：已修复（未发布）

### 现象

0.2.3 只删掉了列表上的选择器，保存仍报“默认渠道须启用且至少选择一个模型”。

### 根因

`defaultChannelId` 在后端是官方 `defaultProvider` 的写入开关，且有三处把它当强制项：

1. `channel_actions::default_provider()`：渠道未启用或 `selection: none` 时直接报错，且报错文案就是用户看到的那句。
2. 同函数末尾：官方 `defaultProvider` 指向被删除渠道时，要求“先选替代默认渠道”。
3. `runtime.rs` 保存前：官方默认渠道被停用时报“不能在未选择替代默认渠道时停用当前默认渠道”。

本机实测：草稿 `model-config-draft.json` 的 `defaultChannelId` 指向 `openai`，而该渠道 `selection: none`、`discovered: 0`，于是每次保存都被这条校验拦住——不是提示文案问题，是保存被永久卡死。

### 改法

- `default_provider()` 改为只在“用户显式指定且渠道可用”时改写官方 `defaultProvider`；引用失效或被停用一律忽略，不阻断。
- 删除上述三处硬校验；官方 `defaultProvider` 指向被停用或被删渠道时交回官方自行回落。
- 分范围保存不再复制 `defaultChannelId`；历史恢复不再把它当冲突项；导入导出不再携带、不再写入、不再据此拒绝接收。
- 前端差异清单与共享范围说明去掉“默认渠道”；删除渠道时清掉残留值。
- 字段本身保留在 schema 里，只为能读旧数据，不再参与任何保存判定。

### 验证

- 后端 `cargo test --lib` 958 项通过（4 项忽略），新增 `stale_default_channel_does_not_block_saving`。
- 前端 149 文件 740 项通过，新增 `default-channel-retired` 两项：残留值不进差异清单、共享项说明不含该项。
- `cargo fmt --check`、`vue-tsc`、`vite build` 通过。

### 待办

本机旧草稿仍带着该残留值；新版本保存时不再复制它，但存量文件未主动改写。是否需要在升级时清理存量 `model-config-draft.json` 的该字段，待确认（清理属改写用户本机状态，需单独授权）。

## WP-30：已装 OpenCodex 却提示“未发现 npm 全局安装”

**优先级**：P2
**位置**：设置 → 安装配置 → 运行环境与安装发现
**用户原话**：“这里提示没有发现 npm 但是我都装上 opencodex 了。是不是有问题。”
**状态**：已修复（未发布）

### 现象

同一页下方“OpenCodex 运行来源”已明确显示托管安装、路径与版本 2.84.0，上方“运行环境与安装发现”却写：可执行文件未发现、安装形态未发现 npm 全局安装、版本 —、Codex 运行时 —。

### 根因

`SettingsRoute.installRows` 只读 `app.environment.ocx`，也就是“npm 全局安装探测”这一项；没有看 `app.runtimeSource`。本机 OpenCodex 由托管安装提供（数据根内 runtime/bin/ocx），npm 全局里确实没有，于是整块按“未发现”渲染。

同类问题还有一处：Codex 运行时那行把版本写死成 `0.154.0-alpha.6.2`，与实际观测无关，属于用常量冒充事实。

### 改法

- 可执行文件、安装形态、版本、Codex 运行时改为“npm 全局 或 运行来源”二者取一；可用性判定为 `report.ocx.found || fromSource`。
- 安装形态按来源类型显示：npm 全局安装则写 `npm 全局 · @bitkyc08/opencodex`，否则写 `运行来源 · 托管安装 / 用户指定 / 自动发现`。
- Codex 运行时改为读状态快照的 `facts.runtime_label`，读不到写“未读取”。

### 验证

- 前端 150 文件 742 项通过；新增 `install-discovery-source` 两项断言（参考运行来源、版本优先取来源解析值）。
- 未做应用内实屏：本机运行中的为已发布 0.2.3，需装含本修复的构建后确认该区块显示托管安装路径与 2.84.0。

### 备注

这条与概览的环境门禁是两处独立渲染：门禁早已按“运行来源可用”判定通过（`runtimeProvidesOcx`），只有安装发现这块漏改，因此出现“上面报未发现、下面显示已安装”的自相矛盾。

### 追加（2026-10-22）：Windows 与非默认 prefix

用户补充：“这个要考虑 windows，也是要考虑不是只有全局默认路径。”

复核发现原实现范围确实过窄：

- 非 Windows 只查 `~/.local/bin` 一个目录；Homebrew、nvm、Volta、pnpm、`npm config set prefix` 自定义前缀全部漏掉。
- Windows 只查 `.local/bin`、`.nvmd/bin`、`AppData/Roaming/npm`、`AppData/Local/Programs/nodejs` 与 Program Files；Volta、fnm、pnpm、自定义 prefix 未覆盖。
- 安装形态一栏固定写“npm 全局 · @bitkyc08/opencodex”，等于假定所有安装都在 npm 默认前缀下。

改法：

- 非 Windows 候选扩为：`~/.local/bin`、`~/.npm-global/bin`、`~/.volta/bin`、`~/Library/pnpm`、`~/.local/share/pnpm`、`~/.bun/bin`、`~/.nvm/versions/node/*/bin`（最多 16 个，新版本优先）、`~/.npmrc` 的 `prefix`、Homebrew（`/opt/homebrew/bin`）与 `/usr/local/bin`。
- Windows 补 `LOCALAPPDATA`/`APPDATA` 下的 `Volta/bin`、`fnm`、`pnpm`、`npm`，以及 `~/.npmrc` 的 `prefix`。
- 读取 `~/.npmrc` 只接受绝对路径，忽略注释与相对值；仍不读 PATH、不执行任何探测命令，符合该模块原有约束。
- 安装形态按实际路径判断：npm 全局（含 `node_modules/@bitkyc08/opencodex/`）/ Volta / fnm / pnpm / Homebrew·系统前缀 / 独立可执行文件·非默认前缀。

验证：后端 961 项通过，新增 4 项测试（非默认 prefix 与 Volta 可发现、npmrc 边界、nvm 顺序与上限）；前端 742 项通过；`cargo fmt --check` 通过。未做 Windows 真机与 macOS 实屏验证。

## WP-31：文件保护口令应为非必填，允许无口令携带凭据

**优先级**：P1（涉及凭据保护边界，需确认后才能改）
**位置**：同步 → 文件同步 → 其他凭据与同步选项
**用户原话**：“文件保护口令（含凭据，必需）是不对，应该非必填。改成：文件保护口令，如果没有填口令也可以携带凭据的。”
**状态**：已登记，未实施（需先确认安全边界）

### 现状

0.2.2/0.2.3 我按“含凭据时口令必需”改过文案，但后端本来就是这样强制的，因此这一条不是文案写错，而是功能行为与用户预期相反。当前拦截点有六处：

1. `file_objects::seal_scope()`：`include_keys && 口令空` 直接报“携带渠道Key时须设置独立文件保护口令”。
2. `portable_file::seal()`：`secret_objects > 0` 且无口令时报 `passphrase_required`。
3. `portable_file::open()`：明文载荷却声明 `secretObjects > 0` 时报 `portable_protection`（“携带凭据的配置文件必须受保护”）。
4. `file_objects::remote_objects()`：`secret_objects > 0 && !protected` 视为清单不一致。
5. `file_objects` 导入路径（约 926 行）：同样拒绝“有凭据但未受保护”。
6. 前端 `ModelTransfer.vue`：`requiresPassword` 把“选了渠道Key / 扩展凭据 / WebDAV 密码”都算成必须填口令，导出按钮据此禁用。

### 这条要求意味着什么

允许“无口令携带凭据”＝配置文件里出现明文 API Key 与 WebDAV 密码。该文件：

- 落在本机导出目录（默认 `exports/`），任何能读取该目录的进程或用户都能拿到全部渠道 Key；
- 若通过 WebDAV 或聊天工具传出，等同于直接发送密钥；
- 与现有“受保护部分须独立口令加密”的界面说明、以及 0.2.0 起的安全边界文档冲突。

所以我不能把它当成纯 UI 文案直接改掉，需要你确认这是有意放宽。

### 拟定改法（待确认后执行）

- 容器层：`seal()` / `open()` 允许 `secret_objects > 0` 且无口令，改为写 `encrypted: false` + `secretsIncluded: true` 两个显式标记，导出与导入两侧都据此提示“此文件含明文凭据”。
- 业务层：`seal_scope()` 与 `remote_objects()` 去掉“有凭据必须受保护”的强制判定，改为返回状态而非报错。
- 界面：口令标签改为“文件保护口令（可选）”，占位符写“留空则凭据以明文写入文件”；勾选携带凭据后在按钮上方常驻一行红色警示，说明该文件可直接被读取。
- 导入：读取到含明文凭据的文件时，确认页显著提示来源与风险，采用仍需显式确认。
- 文档：同步与备份契约、CHANGELOG 的安全边界段落同步改写，不能只在代码里放宽。

### 待确认

1. 是否确认允许明文携带凭据（含渠道 API Key 与 WebDAV 密码）？
2. 若允许，是否仍保留“WebDAV 上传”场景的强制口令？（本地文件导出可放宽，网络传输建议保留）
3. 是否需要“仅本次免密、下次默认回填必填”这种折中？

### 用户决策（2026-10-22）

1. 允许明文携带凭据（含渠道 API Key 与 WebDAV 密码）不加密，由用户自行决定承担；因此“导入时必须输入口令”也一并取消。
2. WebDAV 不保留强制口令。
3. 不做“仅本次免密、下次回填必填”的折中。

### 已实施

**容器层** `modules/sync/portable_file.rs`

- `seal()`：`None | Some("")` 一律写明文载荷；不再因 `secretObjects > 0` 报错。
- `open()`：明文载荷即使声明 `secretObjects > 0` 也照常读出，`protected: false` 如实返回。
- 明文模式没有口令参与 AAD，因此 manifest 字段不可认证；可依赖的是文档摘要，载荷被改仍会因摘要不符被拒。

**业务层** `modules/model_config/file_objects.rs`

- 删除 `seal_scope()` 的“携带渠道Key须设置独立口令”。
- 删除 `remote_objects()` 与导入路径的“有凭据必须受保护”。
- 删除裸文档与资源读取分支的同类拒绝。
- 远端重建只在 `remote_protected || local_protected` 时才要原口令。

**界面** `features/sync/ModelTransfer.vue`

- 口令标签统一为“文件保护口令（可选）”/“配置同步保护口令（可选）”。
- 向导选中凭据但未填口令时，占位符写“留空则凭据以明文写入文件”，并在凭据清单下方常驻“未填口令，这些内容会以明文写入文件”。
- 导出按钮不再把未填口令当阻断条件。
- 导入对话框：不填口令也能继续，按钮文案按是否填口令切换“直接读取并比较”/“解密并比较”。

### 验证

- 后端 `cargo test --lib` 961 项通过（4 项忽略）。
- 前端 151 文件 746 项通过；新增 `passphrase-optional` 四项断言。
- `cargo fmt --check`、`vue-tsc`、`vite build` 通过。

### 遗留风险（用户已知并接受）

- 未加密的导出文件包含明文渠道 Key 与 WebDAV 密码，任何能读取该文件的进程或用户都可直接使用；
- 经 WebDAV 或聊天工具转发时等同于直接发送密钥；
- 明文文件可被篡改后重新计算摘要，缺少口令即没有完整性认证（仅能发现意外损坏）。
