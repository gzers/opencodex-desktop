# 数据与状态

> 字段级配套：分区里的条目实体见 `领域模型.md`；加密容器的头字段见 `契约字段.md`；凭据分级见 `集成与安全边界.md`。

## 1. 数据根

用户可选择一个自定义数据根，管理器按用途划分产物。`OPENCODEX_HOME` 可以选择放在数据根内，也可以由用户指定为独立路径。

### 1.1 分区

| 分区键 | 用途 | 内容 | 可丢弃 | 需备份 |
|---|---|---|---|---|
| `manager state` | 桌面壳设置、数据根元信息、UI 偏好 | 设置项、数据根元信息 | 否 | 是 |
| `opencodex home` | 可选承载 `OPENCODEX_HOME` | OpenCodex 自身数据 | 否 | 是 |
| `runtime` | 管理器托管的 OpenCodex 运行时（私有 npm 前缀与入口） | `runtime/opencodex/`（私有 `package.json` + `package-lock.json` + `node_modules`）、`runtime/bin/ocx` 入口、`.runtime-manifest.json` | 否（可重装，但离线时不可恢复） | 否（包体不备份，只备份状态与锁文件） |
| `backups` | 升级、导入、同步覆盖等动作前的备份 | 备份对象 | 否 | 否（本身即备份） |
| `logs` | 桌面壳操作日志与旋转后的本地日志 | 日志文件 | 否 | 否 |
| `exports` | 加密配置导出容器 | 加密容器 | 否 | 否 |
| `cache` | 可丢弃缓存 | 探测结果、缩略图等 | 是 | 否 |
| `sync state` | WebDAV 冲突记录、远端索引摘要、同步历史摘要 | 索引摘要与冲突记录 | 否 | 否 |

- 分区键是稳定标识，实现与文档引用分区时用分区键；物理目录名见 IMP `FZ-01`。

**托管的 OpenCodex 运行时**（2026-09-25 补冻结，IMP `FZ-47` ~ `FZ-51`）：

| 项 | 冻结 |
|---|---|
| 前缀 | `runtime/opencodex/`——等价私有 npm 项目（`package.json` + `package-lock.json` + `node_modules/`）；**可由用户显式改为其它目录**，但必须过路径校验（绝对路径、非符号链接、可写、**不在系统保护目录内**） |
| 入口 | `runtime/bin/ocx` 是**稳定入口**，运行来源指向它，不指向 `node_modules/.bin` |
| 落地事实 | 前缀内 `.runtime-manifest.json`：包名 / 版本 / tarball 摘要 / 安装时间 / npm 路径 / 是否带脚本 / 来源（registry / offline） |
| 来源与历史 | `<数据根>/manager-state/runtime.json`：来源四态 + 优先级 + 安装 / 卸载历史（≤50 条，只在终态写） |
| 原子性 | 临时区安装 → 校验 → **原子替换**；失败清理临时区，**不改现有前缀与运行来源** |
| 卸载 | 一级只删本记录登记的 `target` 与 `entry`（前置校验 + 备份 + 重算来源）；二级只引导官方 `ocx uninstall`，本产品不删文件 |
| 代理 | 只作用于本次安装；不写系统代理与全局 npm 配置、**不落盘**；含凭据时改写临时 `--userconfig`（`0600`，用完即删），凭据不进命令行参数 |

> 字段级定义见 `领域模型.md` §18 / §19 与 `契约字段.md` §6。

### 1.2 路径解析

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | 用户在设置中显式指定的数据根 | 唯一权威来源；切换走 §1.3 |
| — | 初始化时机 | 首次启动建立默认数据根；设置只提供「重建管理器索引 / 缓存」，不提供一键重建全数据根 |
| 2 | 默认位置（`~/` 下的应用数据目录） | 首次启动时建立 |
| — | `OPENCODEX_HOME` | **独立解析**：可在数据根内，也可为独立路径；界面不得与数据根混用 |

### 1.3 切换语义

切换分成两条流程：**A. 管理器数据根切换**只影响 `manager state`、`backups`、`logs`、`exports`、`cache`、`sync state` 这些管理器自有分区；**B. `OPENCODEX_HOME` 切换**只处理 OpenCodex 自身数据目录。两者界面必须分开展示，不得混成一条「目录切换」。

#### A. 管理器数据根切换

```text
选择数据根 → 检查（可写、空间、已有管理器数据） → 引用 或 迁移管理器分区
→ 备份 manager state 与待迁移分区 → 停止代理 → 执行迁移 → 校验 → 更新数据根配置 → 恢复代理
→ 成功 / 回滚
```

| 步骤 | 停止 OpenCodex | 备份 | 迁移 | 改 `OPENCODEX_HOME` | 重启接管 |
|---|---|---|---|---|---|
| 引用已有数据根 | 按并发写入风险确认 | 是 | 否 | 否 | 引用变更生效 |
| 迁移管理器分区 | 是 | 是 | 是 | 否 | 是 |

- **引用优先**：默认引用已有位置，不搬动数据。
- **迁移可选**：仅在显式选择时移动管理器自有分区；迁移前强制备份，失败自动回滚并保留原数据根。
- 该流程不改写、不移动 `OPENCODEX_HOME`；若 `OPENCODEX_HOME` 位于旧数据根内，只显示影响提示，实际处理走 B 流程。

#### B. `OPENCODEX_HOME` 引用 / 迁移

```text
选择 OPENCODEX_HOME → 检查（可写、空间、已有 OpenCodex 数据） → 引用 或 迁移
→ 运行前备份 → 停止 OpenCodex → 执行引用或迁移 → 校验 → 更新环境引用与启动注入 → 重启接管
→ 成功 / 回滚
```

| 步骤 | 停止 OpenCodex | 备份 | 迁移 | 改环境引用 | 重启接管 |
|---|---|---|---|---|---|
| 引用已有 `OPENCODEX_HOME` | 是 | 是（配置与关键状态） | 否 | 是 | 是 |
| 迁移 `OPENCODEX_HOME` | 是 | 是 | 是 | 是 | 是 |

- `OPENCODEX_HOME` 是 OpenCodex 自身数据目录，不是管理器分区；切换前必须先停止 OpenCodex，避免迁移期间产生新的写入。
- **引用优先**：默认引用已有位置，不搬动 OpenCodex 数据。
- **迁移可选**：仅在显式选择时移动；迁移前强制备份，失败自动回滚并保留原 `OPENCODEX_HOME`。
- 管理器数据根可继续保留在原位置，两个路径的切换互不隐含。

通用检查项字段（检查阶段即阻断，不进入下一步）：

| 检查项 | 判定 | 失败行为 |
|---|---|---|
| 可写 | 目标目录当前用户可创建与写入 | 阻断并说明原因 |
| 空间 | 迁移所需空间可得 | 阻断并说明原因 |
| 已有数据 | 是否已是有效数据根或有效 `OPENCODEX_HOME` | 是则默认走「引用」 |
| 结构版本 | 已有数据的结构版本可比对 | 异常即阻断 |

失败、取消、回滚分支：

| 分支 | 触发 | 结果 |
|---|---|---|
| 失败 | 目录不可写 / 空间不足 / 迁移中断 / 校验失败 | 回滚到原路径；备份可定位可恢复 |
| 取消 | 确认阶段取消 | 保持原路径，不写入任何变更 |

## 2. 状态模型

**2026-09-28 已确认方向（DMD Revision 12，REQ-31 / AC-15）**：用户界面采用一条运行主线，操作归入节点支线，错误沿原流程收口；权威语义见 §2.7、§5.8。下列三维枚举保留为现有接口兼容基线，不再作为并列铺陈全部状态的产品设计。**现行原型已按本条收敛并验证（见 IMP-04 §19.31）；本文确认目标语义，不表示源码已完成重构或字段迁移。**

现有状态按三个**互相独立、可同时成立**的维度建模，仍须保留“代理在跑且同时同步”等真实事实，不能为减少显示而丢弃。

三维之外另有一组**环境前置门禁状态**，属发现阶段的门禁，不是第四个维度。

### 2.1 运行状态（`runtime`）

代理进程观测。

| 取值 | 含义 | 可用动作 |
|---|---|---|
| `not_found` | 未发现安装 | 无 |
| `loading` | 正在探测安装与状态 | 无（瞬时进度，不写说明句） |
| `stopped` | 已发现但未运行 | 启动 OpenCodex |
| `starting` | 正在启动 | 无（瞬时进度，不写说明句） |
| `pending` | 端口可达但未通过就绪检查 | 无（瞬时进度，不写说明句） |
| `running` | 运行且就绪 | 打开面板、停止、重启、查看日志 |
| `stopping` | 正在停止 | 无（瞬时进度，不写说明句） |
| `starting_failed` | 启动失败 | 重试启动、查看日志 |
| `at_risk` | 官方状态报告 startup at-risk，且代理未在运行 | 启动 OpenCodex、查看建议 |
| `external_takeover` | 外部 provider 接管配置 | 查看建议 |
| `unreachable` | 进程或端口不可达 | 查看日志 |

> 2026-10-02 修订（用户确认，IMP-07）：**「刷新状态」是全局能力**（概览顶栏右上角图标，IMP-06 落地），
> 不再挂在任何状态的动作里，也不再进「更多」折叠——否则会出现「更多里只有刷新」的空壳菜单。
> 本表据此删除各状态的「刷新状态」动作；`at_risk` 仍保留「启动 OpenCodex」（2026-09-21 修订：风险只提醒不阻断）。

> 界面文案：`starting_failed` 下启动按钮文案为「重试启动」；十个状态各有一条说明句，但**不再出现在概览状态卡**里，
> 而是按性质分流展示（见下条 2026-09-25 修订）。
>
> 2026-09-21 修订：**风险只提醒，不阻断动作**。`at_risk` 由「代理未运行 + 官方 startup at-risk」折叠而来，
> 启动代理正是恢复手段，因此允许启动；只排除契约明确禁止的 `external_takeover`（不代改被接管的配置）。
> **备份状态不参与风险判定**——备份是破坏性写入前的动作门槛（见 §`失败即阻断`），不是风险等级的一部分。

> 2026-09-24 修订（用户决策）：**托盘不承载风险结论**。托盘菜单项会被长文案撑宽，且托盘只是进程控制入口，
> 因此「存在风险」这一结论与它的状态说明句**不再写进托盘**（头部与 tooltip 都只放「运行标签 · 地址」）；
> 托盘里 `at_risk` 如实显示为**「未运行」**（这一层能确认的进程事实）。状态说明句（启动保护、重启安全、
> 自启服务、版本偏差等）仍由官方运行事实生成，但只在**应用内**展示——通知中心 / Toast / 日志；
> 需要展开细节时用托盘的动作入口（运行 Doctor / 打开诊断中心 / 打开主界面）进应用看。

> 2026-09-28 替代 2026-09-25 三档分流规则：概览采用简略摘要与按需详情（`UI规范.md` §19）；不再按运行枚举机械地产生持久通知或稳定态 Toast。是否触达由操作结果和问题生命周期决定（§5.8）。已有原型与测试中的旧断言属于待调整项，不证明新规则已实现。

### 2.2 连接状态（`connection`）

外部依赖（当前为 WebDAV）的连接与同步状态。

| 取值 | 含义 | 标签 | 动作区 |
|---|---|---|---|
| `unconfigured` | 未配置端点 | 未配置 | 配置 WebDAV（单颗整行） |
| `disconnected` | 已配置未连接 | 未连接 | 立即同步 / 测试连接 |
| `connecting` | 正在连接 | — | 取消 / 测试连接 |
| `syncing` | 正在同步 | 同步中 | 取消同步 / 测试连接 |
| `synced` | 已同步 | 已同步 | 立即同步 / 测试连接 |
| `conflict` | 冲突待处理 | 冲突待处理 | 处理冲突 / 立即同步 |
| `failed` | 连接或同步失败 | 连接失败 | 重试连接 / 立即同步 |

- 「未配置」**不整卡置灰**：主体说明未配置，动作区只留一颗「配置 WebDAV」直达设置，右上角更多菜单恒可用。
- 目标语义：连接测试通过只证明可连接，不证明内容已同步；存在未处理冲突时不得宣称全部同步完成。上表枚举仍为兼容基线，连接事实与同步过程/结果的拆分待实施。

### 2.3 操作状态（`operation`）

单次动作的执行阶段。

| 取值 | 含义 | 备注 |
|---|---|---|
| `idle` | 空闲 | 默认值 |
| `validating` | 校验中 | 含前置校验与内容比对 |
| `backing_up` | 备份中 | 失败即阻断，不进入下一步 |
| `applying` | 应用中 | 写入或迁移的实际执行 |
| `rolling_back` | 回滚中 | 失败路径 |
| `cancelled` | 已取消 | 必须收到终止确认；是否存在已完成步骤或副作用另由结果证明 |
| `succeeded` | 成功 | — |
| `failed` | 失败 | 需带失败原因 |

### 2.4 环境前置门禁状态

按 `node` → `npm` → `ocx` 顺序**短路检查**，前一项未通过时不继续。

| 取值 | 含义 |
|---|---|
| `checking` | 检查中 |
| `missing_node` | 缺 Node.js，阻塞后续检查 |
| `missing_npm` | 缺 npm，阻塞后续检查 |
| `missing_ocx` | 缺 `ocx`，阻塞后续检查 |

全部通过后不常驻大门禁卡；摘要与详情遵循 `UI规范.md` §19。缺失态先展示实际阻断项与处理入口，命令和检查明细按需展开；环境依赖由用户安装，OpenCodex 本体可走已授权的托管安装支线。自动发现候选为空不能否定已经解析并核验可用的运行来源。

### 2.5 并存与优先级

- 三个维度**必须能同时表达**，例如「`running` + `syncing` + `backing_up`」。
- 运行、连接事实和操作过程互不覆盖；目标展示按 §2.7 的主线与支线组织，操作状态归具体操作实例。
- 三维字段在代码与 `--json` 输出中统一为 `runtime` / `connection` / `operation` / `gate`。

### 2.6 渲染规则

- 动作按同源能力渲染，不渲染无解释的禁用按钮；必要的阻断原因在所属入口简述，详情按 `UI规范.md` §19 展开。
- 阶段编号（P0 / P1 / P2）**不出现在应用界面**；界面只用功能名与状态（「规划中 / 可用」）。
- 敏感值永远掩码。

### 2.7 主线、支线与状态收敛（2026-09-28，已确认方向，原型已收敛、代码待实施）

**目的**：让用户清楚当前事实、当前操作和下一步；减少重复状态、重复入口与重复报错，不削减已有功能或必要的核验差异。

| 稳定主线节点 | 事实依据 | 节点支线 |
|---|---|---|
| 待接入 | 没有已核验可用的运行入口，且没有相反的有效运行观测 | 检查环境、安装、离线导入、指定来源 |
| 未运行 | 已接入可用入口，且观测确认代理未运行 | 启动、更换来源、处理阻断项、卸载 |
| 运行中 | 有有效的进程运行观测 | 打开面板、停止、重启、处理运行问题 |

- 以上为产品主线候选标签与语义，**不直接替换现有 `RuntimeState` 或 CLI 枚举**；最终字段和映射由实施契约另行冻结。
- 未获可靠事实时显示“正在确认”；旧观测过期时保留“上次观测”并标记未更新。采集失败、入口消失、进程退出分别判断；仍有运行进程时不能因入口被移除而抹去运行事实。
- `starting` / `pending` / `stopping` 归当前操作进度；`starting_failed` 归操作结果；启动保护、所有权、服务可达性归问题或动作约束，不与稳定主线抢占同一状态槽。
- 进程运行不等于健康就绪、端口可用或页面已加载；面板入口由相应能力核验决定。官方 `at-risk`、`protection=none` 或“曾经启动过”均不能单独证明故障；未知字段不得当作 `false`。
- 同步、扩展、迁移、偏好、更新、诊断有各自支线，不改写运行主线。环境依赖按当前动作判定，不用安装依赖缺失推翻真实运行事实。
- 支线采用共同流程语义：**待确认 → 执行 → 核验 → 结果**；短操作不强制展示全部步骤。备份、下载、回滚等仅作为有证据的内部步骤。
- 结果必须区分成功、部分完成、失败、已取消，以及结果待确认；“等待重启生效”保留为明确后续条件。IPC 正常返回不等于业务成功，超时不等于失败，请求取消不等于已取消。
- 每个事实域一个权威来源，每次操作一个执行记录；页面只保留输入、筛选、分页、展开等视图状态。忙碌、按钮状态、完成文案从所属事实/操作派生，不另存多份布尔结论。
- 动作能力与限制原因同源供概览、设置、托盘和原生菜单消费；后端执行前再次校验。按资源冲突控制并发，不以一个全局 busy 锁住所有独立支线。
- 事实新鲜度、事件次序和失效重采由统一刷新规则保证，见 `系统架构.md` §6.1；具体跨边界字段见 `契约字段.md` §5.1 的待冻结要求。

> 2026-09-29 补记（概览状态形象）：概览的 Logo 三结构动画是本节投影的**另一种视觉表达**，不是新状态机、也不是第二状态源。生产接入见 `apps/desktop/ui/src/features/runtime/motion/projection.ts`：`projectMotion(runtimeState, fresh, problem)` 把既有运行主线、刷新新鲜度与持续问题投影为形象状态；主线标签仍取自本节，形象不替代 `runtimeState`。缺省按「新鲜」处理，仅在明确判定旧响应/超阈值时才显示「过期」，不伪造过期。界面与验证见 `UI规范.md` §25。

## 3. 持久化与备份

| 对象 | 落点（分区键） | 约束 |
|---|---|---|
| 应用设置与偏好 | `manager state` | 不含真实凭据明文 |
| 操作与运行日志 | `logs` | 只读、脱敏、可轮转 |
| 升级 / 导入 / 覆盖前备份 | `backups` | 必须可定位、可校验、可恢复 |
| 托管安装 / 卸载记录与运行来源 | `manager state` | `runtime.json`：来源类型、路径、版本、安装与卸载历史；不含凭据 |
| 托管安装的包体 | `runtime` | 只由管理器安装/卸载；不写系统目录与全局 npm 前缀 |

> 2026-09-25 修订：**安装过程的进度是瞬态的，不进持久化**——进度（百分比、联网命令行明细、离线段）按操作任务实时推送，
> 只有**终态**（`succeeded` / `failed` / `rolled_back` + 版本 + 落地路径）写入 `runtime.json` 历史；
> **联网代理不落盘**（只作为本次安装的 `--proxy` 参数，不写系统代理与全局 npm 配置，见 `集成与安全边界.md`）。
> 界面表现见 `UI规范.md` §18.2。
| 配置导出文件 | `exports` | 未加密配置 + SHA-256 完整性校验（2026-09-20 起）；按凭据文件处理，Unix 权限 `0600` |
| 同步索引与冲突记录 | `sync state` | 记录远端清单摘要与冲突，用于变更检测 |
| 可丢弃缓存 | `cache` | 可随时清空 |

备份的最小信息字段见 `契约字段.md` 的备份清单。

### 3.1 备份规则

| 规则 | 要求 | 来源 |
|---|---|---|
| 备份先行 | 任何可能覆盖数据的写入前必须生成备份 | `ARC-04` |
| 失败即阻断 | 备份失败时阻断后续破坏性动作 | `AC-06` `AC-08` `AC-11` |
| 可定位可校验可恢复 | 备份必须能被找到、校验、还原 | `REQ-16` |
| 删除可恢复 | 删除类操作进回收区，保留恢复窗口 | `REQ-27` |
| 恢复窗口 | 回收区保留 30 天；上限 1,000 项 / 5 GB | ✅ `FZ-05` |
| 日志轮转 | 单文件 5 MB、5 份、保留 30 天；日志总上限 125 MB | ✅ `FZ-15` |
| 保留策略 | 每类最近 20 份与 30 天内记录 | ✅ `FZ-04` |

## 5. 反馈与通知状态

本节定义**操作任务的进度与真实终态**、**通知的读/处理/删除/过期维度**、**收起状态**以及**持久化与恢复规则**。实体字段见 `领域模型.md` §16，触达渠道与去重、排队、关闭、超时、清理规则见 IMP `FZ-43`。本节不复制完整实体字段表与视觉尺寸。

### 5.1 反馈渠道与职责

六类反馈是**职责与展示渠道**，不是六种实体类型；同一事件只允许一个主展示渠道。

| 渠道 | 职责 | 是否持久化为 `Notification` | 是否计入未读 |
|---|---|---|---|
| 操作反馈（Toast） | 用户刚刚发起的短操作结果 | 否 | 否 |
| 操作任务（任务卡） | 持续时间不确定、等待后端终态的操作 | 否 | 否 |
| 操作性通知 | 需要后续知悉或处理的事件 | 是 | 是（未读且未解决） |
| 日志型记录 | 技术、审计与排障事实 | 否 | 否 |
| 阻断式确认（Modal） | 高风险、不可逆或会覆盖数据的决策 | 否 | 否 |
| 页面内状态 | 当前页面或区域持续存在的状态 | 否 | 否 |

### 5.2 操作进度与真实终态

- 操作任务沿用 §2.7 的支线语义；§2.3 的 `validating / backing_up / applying / rolling_back` 是兼容阶段，归属具体操作，不是覆盖所有任务的全局开关。
- **界面等待超时与后台任务失败分开**：等待超时显示结果待确认，不写成失败；仅在确实继续观察时说明“仍在后台观察”。各域以自身执行与核验事实收口，启停由官方运行观测确认，不能用运行快照代替同步或配置写入的结果。
- **启动事实分层**：指令发出、子进程创建、进程运行、`ready` 通过、官方页面加载是不同事实；界面只能展示**已收到**的阶段证据，**不得靠固定延迟伪造成功**。
- **重复轮询不产生重复提醒**；同一操作终态只触达一次。
- 隐藏卡片、停止观察、请求取消、已取消必须分别定义：隐藏卡片只收起展示，不停止后台任务；请求取消要等待确定结果；已取消表示已确认终止，已执行步骤及副作用另行如实报告。

### 5.3 通知三维度

`read`、`resolved`、`deleted` 是**互相独立**的维度，不是「读了就解决」的线性状态链。

| 维度 | 含义 | 变更条件 | 关闭详情 / 收起浮层是否影响 |
|---|---|---|---|
| `read` | 用户是否已知悉 | 打开详情、批量「全部已读」 | 否 |
| `resolved` | 用户是否已处理完成 | 用户显式「标记已解决」，或对应风险/冲突获得真实终态处置 | 否 |
| `deleted` | 是否软删除 | 用户单条删除、批量清理（默认只清已解决） | 否 |

- **已读 ≠ 已解决**；`read=true` 不得自动置 `resolved`。
- 用户点击「已解决」记录的是**用户确认**，不得解释为服务实际恢复。
- 未读计数只统计**存活且未读且未解决**的通知；已解决不再计入未读，角标颜色语义（未读点、铃铛角标）单独保留。

### 5.4 过期与清理

- **过期与清理资格不等于删除**：获得资格只是允许被清理，实际删除仍需按策略或用户动作。
- **未解决风险、进行中任务、需要用户决策的事项不得静默过期清除**；这类通知 `expires_at = null`。
- 可过期的低优先级信息才允许设置 `expires_at`。
- 通知中心的「清理通知」默认只清理已解决通知；存在未处理通知时必须改文案并二次确认。
- 通知保留期与日志保留策略独立：日志按 `FZ-15` 轮转与保留，通知按实体保留期清理。

### 5.5 去重、排队与触达

- **去重键**：同一 `dedupe_key` 在存活期内只保留一条，重复事件只更新该条而不新增。
- **排队**：同一操作的进行态任务只允许一个活动实例，重复触发复用或拒绝；通知按 `level` 与 `created_at` 排序呈现。
- **主展示渠道默认唯一**：一个事件默认选一个主展示渠道；日志可同时记录，但不得反复叠加 Toast / 卡片 / Modal。

### 5.6 收起状态

- 通知中心面板、Toast、任务卡支持「收起到铃铛」：图标在通知表面右上角，收起时向铃铛收拢并触发铃铛脉冲。
- **收起不等于已读、已解决、删除或取消任务**；未读角标保留，后台任务继续。
- 收起状态是**视图状态**，不进入实体字段；重新打开后应按原状态呈现。
- 收起动效按 `UI规范.md` §26 用户档位统一处理，不读取系统 `prefers-reduced-motion`；收起不改变实体状态。

### 5.7 持久化与恢复

| 对象 | 落点（分区键） | 恢复规则 |
|---|---|---|
| 通知实体 | `manager state` | 重启后按 `read` / `resolved` / `deleted` 原样恢复；未解决通知不因重启丢失 |
| 操作任务观察 | `manager state` | 重启后重新接管可恢复的观察；已发起的系统调用以官方状态采集为准，不臆测终态 |
| 日志型记录 | `logs` | 只读、脱敏、按 `FZ-15` 轮转；不随通知删除 |
| 同步索引与冲突记录 | `sync state` | 冲突记录保留至解决；被覆盖侧必有备份 |

- 通知中心与「诊断中心 → 通知历史」是**同一实体的投影**；任一处改动同步，不维护第二份数据。
- 正式运行不得用演示种子冒充真实通知；测试夹具与场景切换器只在开发 / 测试环境存在。

### 5.8 错误与结果沿流程收口（2026-09-28，已确认方向、待实施）

| 情形 | 主承载位置与处理 |
|---|---|
| 输入不合法、缺少操作前提 | 当前字段或支线入口；指出具体条件 |
| 用户取消 | 原流程结束，不作为故障告警 |
| 操作失败 | 原流程结果：失败步骤、影响、重试或详情入口 |
| 等待超时、结果未知 | 原流程显示“结果待确认”，继续核验或允许显式重查，不假称失败/成功 |
| 部分完成、待重启生效 | 原流程列出已完成项、未完成项、生效条件 |
| 持续影响使用的问题 | 全局一条待处理摘要，回到原流程；恢复后解除当前待处理状态，保留历史 |
| 界面自身异常 | 恢复弹窗，见 `UI规范.md` §24 |
| 技术详情 | 展开详情与脱敏诊断日志 |

- 同一操作/问题只生成一份原因、结果和恢复建议，Toast、任务卡、通知引用同一事实；当前流程已展示时不重复弹多种提示。离开页面后的必要通知承接原记录。
- 未安装、主动卸载、正常停止、未启用非必需保护不自动升级为故障。风险依据应是明确缺陷或用户所需能力失效，不能只按一个枚举匹配。
- 报错至少可定位所属操作、失败步骤、稳定原因、实际影响和下一步；技术信息与用户说明分开。结构化原因不能只嵌入英文 message 再由前端正则猜测。
- 只有确认未写入或已成功回滚，才能声称“未修改／已保留原配置”；回滚失败、部分写入、待确认结果必须如实说明。
- 问题出现、变化、解除独立于运行主线迁移；进程一直运行时出现的新问题也必须更新。已读、已解决、删除仍按 §5.3 独立处理。
