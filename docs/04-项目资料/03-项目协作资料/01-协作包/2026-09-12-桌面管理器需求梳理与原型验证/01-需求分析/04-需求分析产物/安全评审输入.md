# 安全评审输入

## 1. 定位与范围

- 本文件是 **Gate C 安全门**的评审输入，不含实现细节、不连接真实凭据、不写入真实配置。
- 覆盖四个待评审域：**P1 扩展管理（Skills / MCP）**、P1 配置迁移、P2 WebDAV、P1（可选）CLI 控制面。
- **四域材料均已齐备**：扩展管理（§3 ~ §11、§15）、配置迁移 / WebDAV / CLI 控制面（§12）；评审结论见 §16。
- 本文件只描述**控制与边界**，具体参数（保留份数、恢复窗口、客户端清单）在 IMP 冻结。

## 4. 允许写入的客户端清单与判定依据

### 4.1 判定依据（四条同时满足才允许写入）

1. **范围合法**：写入目标属于扩展配置节点，不涉及 provider、路由、模型映射与核心运行配置。
2. **可解析可回写**：配置文件格式可稳定解析；写回时能保留未知字段，不做整体重写。
3. **可备份可回滚**：能定位原文件、生成可恢复备份，并支持原子替换。
4. **不制造写者竞争**：官方拥有写入权的核心运行配置一律不写；MCP 扩展节点允许受控共享写入，但必须锁、摘要比对、备份、原子替换并处理冲突。

### 4.2 清单（2026-09-14 已按各项目开源源码核实）

> 核实方式：读取各客户端官方仓库源码与随仓文档（分支快照：Codex / Gemini / Claude / Hermes / Grok 为 `main`，OpenCode 为 `dev`）。核实对象是**落点、格式与键形状**，不读取任何真实配置与凭据。

| 客户端 | 配置落点 | 格式 | MCP 键与形状 | 判定 | 状态 |
|---|---|---|---|---|---|
| Codex | `$CODEX_HOME/config.toml`（默认 `~/.codex/config.toml`） | TOML | `[mcp_servers]` 表，值为 `McpServerConfig`；`command` + `args`；**内联 `bearer_token` 被官方拒绝**，要求改用 `bearer_token_env_var` | 通过 | 已核实 |
| Claude Code | 用户级 `~/.claude.json`；项目级 `<project>/.mcp.json`；Claude Desktop `claude_desktop_config.json` | JSON | `mcpServers` 映射；另有 `disabledMcpServers` / `enabledMcpServers` 数组 | 通过（须并发写保护，见 F-1） | 已核实 |
| Gemini CLI | 用户级 `~/.gemini/settings.json`；工作区 `<project>/.gemini/settings.json` | JSON | 顶层 `mcpServers`（服务器定义）+ 顶层 `mcp`（全局规则） | 通过（官方 CLI 亦写此节点，见 F-1） | 已核实 |
| Grok CLI | 用户级 `~/.grok/user-settings.json`；项目级 `<project>/.grok/settings.json` | JSON | `mcp.servers`，且为**数组**而非映射 | 通过 | 已核实 |

### 4.3 核实发现

**F-1（重要）：六个客户端全部存在官方写入者，MCP 节点是共享节点。**

- 官方 writer 举例：`claude mcp add / add-json / remove`、`gemini mcp add`、`opencode mcp`、Grok 的 `saveUserSettings`、Hermes 后端 `_replace_mcp_servers`、Codex 的 `mcp_edit`。
- 佐证：Claude Code 的 CHANGELOG 记录过「并发会话静默回退彼此的 `~/.claude.json` 改动」的缺陷；OpenCode 在同目录使用 `Flock`（文件锁）；Gemini 的 `mcp add` 走 `settings.setValue` 做目标键合并而非整文件重写。
- 结论：判定依据 #4「不制造写者竞争」**不能靠"独占"满足**，只能靠"受控共享写入"。因此写入必须同时具备：**文件锁 + 写入前内容摘要比对 + 备份 + 原子替换 + 显式确认**，并在检测到外部写入时进入冲突待处理（对应 §9）。

**F-2：MCP 配置形状在各客户端之间不统一。** 键名（`mcp_servers` / `mcpServers` / `mcp.servers`）、容器类型（映射 / 数组）、命令形态（`command`+`args` 与 `command` 数组）、环境变量键名（`env` / `environment`）、格式（TOML / JSON / JSONC / YAML）都不同。

- 结论：**IMP 必须按客户端定义适配器**，不得假定统一 schema；"节点级写回"必须是**每客户端独立实现**，且只改目标节点、保留未知字段。

**F-3：凭据处理已有官方先例可对齐。** Codex 明确拒绝 `mcp_servers` 中的内联 `bearer_token`，要求使用 `bearer_token_env_var`。

- 结论：本产品的掩码策略采用同一原则——**只允许写入环境变量引用，不写入内联凭据值**（与 DMD §10 一致）。

**F-4（定位相关，非阻塞）：官方项目自身也在建设扩展编辑能力。** Codex 仓库已有 `mcp_edit.rs`、`plugin_edit.rs`、`marketplace_edit.rs`；Claude Code 有插件市场与 `mcp-integration` 技能；Hermes 桌面端有 MCP 页签与 Skills 页签。

- 结论：本产品的扩展管理将在"官方也会做"的区间内竞争。这不改变已确认的范围，但**建议在 IMP 明确"我们只做跨客户端统一视图与受控写入，不复制官方编辑器"**，避免与官方能力重复建设（见 `风险与开放问题.md` R-15）。

## 5. MCP 配置节点范围

- **允许写入**：各客户端的 **MCP 服务器节点**（键名与形状按客户端不同，见 §4.2：`mcp_servers` / `mcpServers` / `mcp.servers`）及其标准字段（名称、命令与参数、环境变量及其他标准键）。
- **禁止写入**：provider、路由、模型映射，以及任何 OpenCodex 核心运行配置。
- **写回策略**：只改目标节点；保留未知字段与格式（在格式允许时保留注释）；解析失败即拒绝写入，不做"尽力而为"的部分写回。
- **删除策略**：删除节点前先备份；删除内容进入回收区，可从备份恢复。
- **单一真相源 + 投影**：本项目维护统一的扩展配置（含 per-app 启用矩阵），各客户端 live 文件是**投影**；逐客户端适配器负责转换（采纳 cc-switch 做法，见 §15.6）。
- **非目标文件不可触碰**：只写 MCP 节点所在文件，且只改该节点；不得改写同目录的凭据、认证等非目标文件（如 Codex 的 `auth.json`）。
- **路径安全**：写入前校验目标路径与源存储不重叠、不互为别名，并拒绝符号链接逃逸（对应 T-E6）。

## 6. MCP `command` / `args` / `env` 的执行边界与确认模型

- **定义**：这三个字段是**待执行指令的数据**，不是本产品的立即执行动作。本产品不代用户运行 MCP 命令。
- **展示边界**：新增、编辑、导入含 `command` 的 MCP 时，必须展示**将要写入的完整命令行与参数**，以及环境变量**键名**（值掩码）。
- **确认模型**：写入前需用户**显式确认**该命令行与参数；从外部 JSON 导入时同样确认，不因"只是导入"而跳过。
- **风险提示**：绝对路径、shell 元字符、下载执行类模式（如管道执行远程脚本）标记为高风险并额外提示。
- **禁止行为**：静默写入、静默执行、把 `command` 当普通文本字段处理（DMD §8 / §10）。

## 7. 环境变量与凭据掩码策略

- 默认掩码：值以固定长度掩码显示，**不通过长度泄漏真实值长度**。
- 唯一例外：用户主动进入编辑或校验时，按字段短暂显示；离开即恢复掩码。
- 服务端约束：掩码必须在**取值之前**完成，不得"先明文取回再在 UI 掩码"。
- 禁止落点：日志、错误信息、命令行参数、导出摘要、通知正文。
- 文件权限：涉及凭据的配置文件在 Unix 上固定 `0600`（新文件与替换后的文件都生效），并保留原文件权限位（采纳 cc-switch 的 `atomic_write_private`，见 §15.3）。

## 8. 写入事务：备份 / 原子替换 / 回滚 / 恢复窗口

```text
读取原文件（含未知字段）
→ 备份到数据根 backups/extension/
→ 生成新内容（只改目标节点）
→ 写入同目录临时文件
→ flush + fsync
→ 原子 rename 覆盖
→ 重新解析校验
→ 记录写入清单（目标、时间、备份位置、内容摘要）
```

| 失败点 | 处理 |
|---|---|
| 备份失败 | **阻断写入**，不进入下一步 |
| 临时写入 / rename 失败 | 保留原文件，删除临时文件，报原因 |
| 校验失败 | 从备份**回滚** |
| 回滚失败 | 进入人工恢复指引，保留备份路径与原因 |
| 用户取消 | 不产生任何写入 |

- **删除恢复窗口**：删除（卸载 Skills、删除 MCP）移入回收区而非直接抹除，默认保留策略与窗口留 IMP 冻结。
- 备份必须**可定位、可校验、可恢复**（DMD §10）。
- **临时文件约定**：同目录 `<文件名>.tmp.<pid>.<时间戳>.<计数>`，以 `create_new` 创建防碰撞，写入并 flush 后 rename 替换；替换后保留原文件权限位（采纳 cc-switch，见 §15.3）。
- **写入串行化**：扩展配置写入（MCP 与 Skills）由**单一状态锁**串行化，避免并发动作互相覆盖（采纳 cc-switch `skill_state_lock`，见 §15.4）。
- **未安装客户端不落盘**：目标客户端未安装（其目录与配置文件都不存在）时，**跳过写入与删除，且不创建任何文件或目录**（采纳 cc-switch `should_sync_*`，见 §15.3）。

## 9. 多客户端与外部改写的冲突检测

写入前读取当前内容，与**上次写入清单的内容摘要**比对（摘要统一采用 **SHA-256 内容哈希**，与 Skills 的更新检测共用同一手段；采纳 cc-switch，见 §15.4）：

| 情形 | 判定 | 处理 |
|---|---|---|
| 内容与上次写入一致 | 无冲突 | 直接写入 |
| 内容被外部应用改写 | 冲突 | 提示冲突，保留外部版本，让用户选择；**不静默覆盖** |
| 本产品上次写入未完成 | 半完成 | 提示恢复，先回滚再重写 |
| 客户端之间配置不一致 | 不一致 | 标记差异并提示，逐客户端确认 |

## 12. 其余三域评审材料

### 12.1 P1 配置迁移（导出 / 导入）

#### 数据流

```text
导出：全量配置 → 内存 → 口令派生密钥（Argon2id）→ AES-256-GCM 加密 → exports/ 容器文件
导入：容器 → 格式/版本/完整性校验 → 口令派生 → 解密到内存 → 结构校验
     → 备份当前配置到 backups/ → 写入（临时区 + 原子替换）→ 校验 → 成功 / 回滚
```

#### 本域数据分类

| 数据 | 级别 | 落点 / 流向 |
|---|---|---|
| 全量配置内容（含凭据） | S3 | 仅以加密容器形态落盘；解密仅存在于内存 |
| 用户口令 | S3 | 仅内存；**不得进入命令行参数、日志或配置文件** |
| 派生密钥 | S3 | 仅内存，用完即弃 |
| 加密容器 | S2 | 数据根 `exports/` |
| 导入前备份 | S2/S3 | 数据根 `backups/`，权限收紧 |

#### 威胁清单

| ID | 威胁 | 场景 | 控制 |
|---|---|---|---|
| T-M1 | 口令被暴力破解 | 弱口令 + 弱 KDF 参数 | Argon2id 强参数（IMP 冻结）；口令强度提示；不在 UI 回显口令 |
| T-M2 | 容器被篡改 / 截断 | 位翻转、半截文件 | AES-256-GCM 认证加密，解密或校验失败即拒绝，不部分导入 |
| T-M3 | 版本不兼容 | 新容器被旧版本解析 | 容器头写入格式版本与 KDF 参数；不兼容即拒绝并说明支持范围 |
| T-M4 | 容器内容带副作用 | 伪造结构、路径逃逸、超大条目 | 结构白名单校验；拒绝未知字段与越界路径；条目数与大小上限 |
| T-M5 | 部分写入 | 写入中断 | 临时区 + 原子替换；失败回滚 |
| T-M6 | 备份失败仍继续 | 备份目录不可写 | **备份失败即阻断**，不进入写入 |
| T-M7 | 凭据明文泄漏 | 口令进日志/参数、内容进错误信息 | 口令只经内存/stdin；掩码；错误信息不含敏感值 |
| T-M8 | 导出文件离线破解 | 容器被他人获取 | 依赖口令强度；明确提示"容器可离线尝试破解"，建议强口令与安全存放 |
| T-M9 | 回滚失败 | 目标文件不可写 | 进入人工恢复指引，保留备份路径与失败原因 |

#### 恢复路径

1. 导入前备份必须可定位、可校验、可恢复。
2. 校验失败 → 中断，不写入。
3. 写入失败 → 自动回滚到备份。
4. 回滚失败 → 展示备份路径 + 人工恢复步骤。
5. 用户取消 → 无任何副作用。

#### 参考实现对照（cc-switch）

cc-switch 的导入是**加固过的**，值得采纳其思路：

| 做法 | 说明 | 我们的对应 |
|---|---|---|
| 导入内容不得拥有任意执行能力 | SQLite 导入时使用 **pragma 白名单**（仅 `foreign_keys`、`user_version`）并挂 **authorizer** 钩子限制可执行操作 | 对应 T-M4：容器内容只做**数据**，不做指令；结构白名单 |
| 先落地临时区、校验后再生效 | 导入先写临时库 → 校验 schema → 再迁移应用 | 对应 T-M5：临时区 + 原子替换 |
| 备份用数据库自身备份 API | 用 SQLite backup API 而非文件拷贝，且 `lock_backup_file_operations` 串行化 | 对应 REQ-03：备份需一致性，不能裸拷贝 |
| 周期性备份 | `periodic_backup_if_needed` + `backup_database_file` | 可纳入 backups 保留策略（IMP） |

> 差异：cc-switch 的导出是**明文 SQL**，我们要求**口令保护的加密容器**（DMD AC-06，已确认需求），此处比参考基线更严。

#### 待冻结契约

容器格式与版本、KDF 参数、结构白名单与拒绝策略、备份命名与保留、回滚语义、口令输入方式。

### 12.2 P2 WebDAV 同步

#### 数据流

```text
上传：本地载荷 → 客户端加密 → 上传载荷 → 上传 manifest（最后）
下载：取 manifest → 校验格式/协议版本 → 逐件下载并校验（大小 + SHA-256）→ 解密 → 应用
```

#### 本域数据分类

| 数据 | 级别 | 落点 / 流向 |
|---|---|---|
| WebDAV 端点、账号 | S2 | 管理器设置；不进日志 |
| WebDAV 口令、同步加密口令 | S3 | 权限收紧存放；默认掩码；不进仓库/日志 |
| 同步载荷（含配置与凭据） | S3 | **本地加密后**才上传 |
| manifest | S2 | 远端；含结构元数据与各件哈希，不含明文内容 |
| 同步索引摘要 | S2 | 数据根 `sync state/`（上次同步的 manifest 哈希/ETag） |
| 覆盖前备份 | S2/S3 | 数据根 `backups/` |

#### 控制措施（采纳 cc-switch 的 manifest 协议）

| 机制 | cc-switch 做法 | 我们采纳 |
|---|---|---|
| manifest 结构 | `format` / `version`（协议号） / `dbCompatVersion` / `snapshotId` / `createdAt` / `deviceName` / `artifacts{name: {size, hash}}` | 采纳同一结构，字段名在 IMP 冻结 |
| 上传顺序 | **载荷先、manifest 后**（best-effort 一致性，避免 manifest 指向不存在的载荷） | 采纳 |
| 下载校验 | 逐件按 manifest 校验后才应用 | 采纳 |
| 版本兼容 | 校验格式串与协议版本，不符即拒绝并给出可读原因 | 采纳 |
| 远端变更检测 | 记录上次同步的 manifest 哈希 + ETag，比对识别远端变化 | 采纳（对应冲突检测） |
| 同步互斥 | `sync_mutex` + `run_with_sync_lock` 串行化 | 采纳（对应"单端点单次同步"） |
| 大小上限 | `MAX_MANIFEST_BYTES` / `MAX_SYNC_ARTIFACT_BYTES` | 采纳 |
| 解压防护 | ZIP 条目数上限 + 逐条读取校验 | 采纳（防压缩炸弹与路径穿越） |

#### 威胁清单

| ID | 威胁 | 场景 | 控制 |
|---|---|---|---|
| T-W1 | 明文外泄 | 上传未加密载荷 | **客户端加密后再上传**（AC-07） |
| T-W2 | 端点冒充 / 中间人 | 指向恶意 WebDAV | TLS 校验；明确提示端点可信性；凭据只在 TLS 下发送 |
| T-W3 | 远端被篡改 | 载荷被替换 | 逐件哈希校验；校验失败拒绝应用 |
| T-W4 | manifest 回放 / 降级 | 用旧 manifest 覆盖新数据 | 协议版本与兼容版本校验；比对上次同步哈希；不一致进入冲突待处理 |
| T-W5 | 冲突静默覆盖 | 本地与远端都被改 | 冲突先入 `conflict`，覆盖前对被覆盖侧备份 |
| T-W6 | 网络中断 | 半同步 | 载荷后 manifest 的顺序保证"半同步不被当作有效快照" |
| T-W7 | 凭据泄漏 | 口令进日志或错误信息 | 掩码；错误信息脱敏 |
| T-W8 | 超大对象 / 压缩炸弹 | 恶意远端 | 大小上限 + 条目数上限 + 逐条校验 |

#### 恢复路径

1. 覆盖前备份必须可恢复。
2. 校验失败 → 不应用远端内容，保持本地不变。
3. 冲突 → 用户选择后执行，保留被覆盖侧备份。
4. 同步中断 → 状态回到可重试，索引摘要不推进。
5. 凭据失效 → 明确提示重新配置，不清空本地数据。

> **关键差异（不跟随参考基线）**：cc-switch 的 WebDAV/S3 同步**未做客户端加密**（直接上传数据库 SQL 与 skills zip，S3 侧仅用 SigV4 鉴权）。我们的 `AC-07` 明确要求"上传前必须客户端加密"，此处**更严，保留**。

#### 待冻结契约

manifest 字段与协议版本、加密算法与密钥来源、载荷切分与命名、冲突判定粒度、备份保留、时限与重试。

### 12.3 P1（可选）CLI 控制面

#### 数据流

```text
ocxd 命令 → 本机 IPC（受限 socket）→ 运行中实例校验调用方 → 执行管理器自有域操作 → 返回文本 / --json
```

#### 本域数据分类

| 数据 | 级别 | 落点 / 流向 |
|---|---|---|
| 命令与参数 | S1/S2 | 本机进程；不得含明文凭据 |
| `--json` 输出 | S1/S2 | 仅管理器自有域状态；敏感值掩码 |
| IPC socket | S1 | 本机；权限收紧 |
| 实例在线状态与并发锁 | S1 | 管理器运行时 |

#### 威胁清单

| ID | 威胁 | 场景 | 控制 |
|---|---|---|---|
| T-C1 | 非本机可调用 | socket 暴露到网络 | 仅本机 socket（Unix domain / 回环且鉴权）；不监听外部地址 |
| T-C2 | 权限过宽 | 其他用户可连接 | socket 与目录权限收紧（同类比 0600），仅允许当前用户 |
| T-C3 | 调用方伪造 | 冒充合法调用方 | 调用方校验（对端用户 / 令牌），不只依赖路径 |
| T-C4 | 绕过实例直接写状态 | 实例未运行仍能改状态 | 变更类命令**必须实例在线**；未运行时只读降级或报错 |
| T-C5 | 破坏性操作无确认 | 脚本误删/误覆盖 | 破坏性命令必须带确认标志，语义与 GUI 一致 |
| T-C6 | 机读输出泄漏 | `--json` 输出含凭据 | 输出层统一掩码；禁止输出 S3 级数据 |
| T-C7 | 关闭后残留入口 | 关掉开关仍可调用 | 关闭即移除端点并校验不可用 |

#### 恢复路径

1. 实例未运行 → 只读降级说明 / 变更类报错，不产生副作用。
2. 缺少确认标志 → 拒绝并说明。
3. 命令执行失败 → 返回非零退出码与原因（退出码语义 IMP 冻结）。
4. 端点异常 → 可重新启用重建端点。

#### 参考实现对照

cc-switch 没有 CLI，但有 **deeplink（`ccswitch://`）**这一"外部可触发面"，其做法是**任何外部触发都先弹确认框**（`McpConfirmation` / `SkillConfirmation`），再执行写入。

- 采纳点：**外部触发面必须经用户确认**，与 T-C5 一致；外部输入只当数据、不当指令（与 T-M4 同源原则）。
- 差异：我们的 CLI 是给脚本/AI 用的机读面，需要额外的**调用方校验**与**机读输出脱敏**，cc-switch 无对应实现。

#### 待冻结契约

命令集与子命令、`--json` 契约、退出码、确认标志语义、socket 路径与权限、调用方校验方式、PATH 注册落点、并发锁归属。

## 15. 参考实现分析：cc-switch

### 15.1 为什么参考它

`farion1231/cc-switch` 是同类产品：**Tauri + Rust（`src-tauri`）**、面向同一批客户端（Claude Code、Codex、OpenCode、OpenClaw、Grok Build、Hermes Agent），且已经把 MCP 与 Skills 做成了可用产品。它的取舍可作为本项目的**参考实现**，用于验证我们的边界设计并降低自创风险。

> 定位差异：cc-switch 只做**配置管理与分发**，不托管客户端进程；本产品额外承担 **OpenCodex 运行管理**（启停、状态、日志、面板）。因此 cc-switch 的做法可直接借鉴其配置侧，运行侧仍由本项目自有设计承担。

### 15.2 核心架构：SSOT + 投影 + 逐客户端适配器

| 机制 | cc-switch 做法 | 对我们的意义 |
|---|---|---|
| 单一真相源 | 自己的数据库存统一 MCP/Skills 定义（`MultiAppConfig` / `McpConfig`），含 `enabled` 标志与 `apps: { claude, codex, gemini, grokbuild, opencode, hermes }` 启用矩阵 | 对应我们 §5 的"节点级写回"：应升级为**统一扩展配置 + 逐客户端投影**，而不是"直接编辑别人家文件" |
| 逐客户端适配器 | `src-tauri/src/mcp/<client>.rs`，每个客户端一套四件套：`import_from_*` / `sync_enabled_to_*` / `sync_single_server_to_*` / `remove_server_from_*` | 直接验证并落地 F-2（每家 schema 不同 → 必须独立适配器） |
| 写回策略 | 单条读写：读现有 → 改一条 → 写回；不整文件重建 | 对应我们 §9 的冲突检测与 §5 的节点级写回 |
| 平台包装 | Windows 下把 `npx` / `npm` 包装为 `cmd /c`；识别 WSL 路径 | 我们 P0 限 macOS，可作为后续预留 |

### 15.3 MCP 的关键做法

| 主题 | cc-switch 做法 | 我们的对应条款 |
|---|---|---|
| 原子写 | `config::atomic_write()`：同目录临时文件（`.tmp.<pid>.<ts>.<counter>`，`create_new` 防碰撞）→ 写入 + flush → 保留原文件权限 → rename（Windows 用 `ReplaceFileW`） | §8 写入事务（采纳，并补齐"保留原文件权限"） |
| 凭据文件权限 | 另有 `atomic_write_private()`，Unix 下新文件与替换文件固定 `0600` | 我们 §7/§10：**采纳**，凭据相关配置一律 0600 |
| TOML 保注释 | Codex 走 `toml_edit::DocumentMut`，只改 `mcp_servers` 节点，**尽量保留未改区域的注释、空白与顺序**；并明确**不触碰 `auth.json`** | §5 节点级写回（采纳；补"保留注释与顺序"为硬要求） |
| 客户端未安装 | `should_sync_*()`：目录与文件都不存在时**跳过写入/删除，不创建任何文件或目录** | **新增条款**：我们不创建未安装客户端的配置文件 |
| 导入容错 | 逐项校验，单项失败跳过并收集错误继续，不整体失败；已存在的服务器只"启用该 app"，不覆盖其他字段 | 与我们 §9 一致；补"已存在条目只改启用位"的语义 |
| 命令校验 | `validate_command_in_path(cmd)` 检查 stdio 命令是否在 PATH | 作为我们 §6 风险提示的**辅助信号**（不替代显式确认） |
| 与官方 CLI 共存 | 未引入文件锁；依赖原子写 + 单条改写降低破坏面 | 我们**更严**：F-1 已要求文件锁 + 摘要比对 + 冲突待处理 |

### 15.4 Skills 的关键做法

| 主题 | cc-switch 做法 | 我们的对应条款 |
|---|---|---|
| SSOT 源存储 | 默认 `~/.cc-switch/skills/`，可切换到 `~/.agents/skills/`（社区 agent 约定目录），切换时**平滑迁移不丢状态** | §8 需补"Skills 源存储位置可切换"与迁移语义 |
| 分发方式 | `SyncMethod`：**优先 symlink，失败回退 copy**；设置中可切换 | **新增条款**：Skills 分发支持软链接/复制两种方式 |
| 安装位置 | Claude `~/.claude/skills/`、Codex `~/.codex/skills/`、Gemini `~/.gemini/skills/`、OpenCode `~/.config/opencode/skills/`、Hermes `~/.hermes/skills/` | 补齐我们未覆盖的 Skills 落点清单（此前只核实了 MCP） |
| 可恢复删除 | 卸载前**自动备份到 `skill-backups/`**，再从各应用目录 + SSOT + 数据库移除；提供"从备份恢复"与"删除备份"（需确认） | §8 回收区 + 恢复窗口（采纳其具体形态） |
| 更新/变更检测 | 用 **SHA-256 内容哈希**比对本地与远端，支持单项/批量更新 | §9 摘要比对（采纳同一手段：内容哈希） |
| 路径安全 | `ensure_distinct_skill_roots` / `paths_alias` / `paths_overlap`：校验 SSOT 与各应用目录不重叠、不互为别名，并处理 dangling symlink | 直接对应用户威胁 **T-E6 路径逃逸**（采纳为强制校验） |
| 并发控制 | `skill_state_lock()`（`RwLock`）串行化 skill 状态变更 | 对应 F-1 的并发写入控制（采纳；MCP 侧同样需要） |
| symlink 读取上限 | 对 symlink 目标设读取上限（4 KiB），防指向超大文件 | 防御性细节，纳入实现约束 |
| 生态互操作 | 解析 `~/.agents/.skill-lock.json` 读取社区锁文件；集成 skills.sh 公共注册表 | 可选：作为后续"仓库管理"来源之一 |

### 15.5 差距与保留意见

cc-switch 未覆盖、我们需要**保持更严**的部分：

1. **MCP 执行边界确认**：cc-switch 只做命令 PATH 校验，未见"写入前展示完整命令行并要求显式确认"的机制。我们 §6 的要求保留。
2. **凭据最小化**：我们采用"只写环境变量引用、不写内联凭据值"（F-3，与 Codex 官方拒绝内联 `bearer_token` 一致），比 cc-switch 更严。
3. **多写入者并发**：cc-switch 依赖原子写而未引入锁；鉴于 Claude Code 自身曾出现"并发会话静默回退彼此 `~/.claude.json`"的缺陷（F-1），我们保留文件锁 + 摘要比对 + 冲突待处理。
4. **运行侧能力**：进程托管、状态观测、日志、官方面板属本项目独有，cc-switch 无可借鉴。

> 这四条**不因采纳 cc-switch 而放宽**：第 1、2 条是 DMD `AC-11` / §10 已确认的需求条款（MCP 执行边界确认、环境变量掩码），不是设计偏好；第 3 条是对 F-1 的应对；第 4 条是本项目独有范围。cc-switch 参考的是**实现机制**，不改动已确认的安全需求。

### 16.2 阻塞项（必须整改）

| ID | 问题 | 风险 | 要求 |
|---|---|---|---|
| B-1 | 目标配置文件**非普通文件**（符号链接指向他处、FIFO、设备文件）时未定义行为 | 越界写入或永久阻塞。Claude Code 曾因项目 `.mcp.json` 是 FIFO / 设备文件符号链接导致 `claude mcp add/remove` 挂起或耗尽内存 | 写入前校验目标为**普通文件**；解析后路径必须落在预期根内；否则拒绝写入并报可读原因 |
| B-2 | `args` / `headers` 未与 `env` 同等纳入敏感值处理 | 凭据经命令行参数泄漏（如 `--api-key=...`、`Authorization` 头） | 将 `args`、`headers` 一并视为潜在敏感：默认掩码、禁止进入日志/错误信息/通知；仅结构化展示 |
| B-3 | 并发保护只写了"状态锁"，未区分进程内与跨进程 | 官方 CLI / 编辑器是**进程外**写入者，进程内锁无效 | 冻结为**文件锁（跨进程）** + 内容摘要比对；进程内锁仅作补充 |
| B-4 | WebDAV 的哈希校验只保证**完整性**，不保证**真实性** | 恶意远端可同时替换载荷与 manifest 中的哈希，校验依然通过 | 明确信任模型：**远端视为不可信**；真实性由客户端加密（AEAD，密钥仅本地持有）或签名覆盖；哈希只用于传输损坏与回放检测 |
| B-5 | TLS 证书校验失败时的行为未定义 | 出现"忽略证书"开关会导致凭据与载荷暴露 | 证书校验失败**默认拒绝**；**不提供**"忽略证书"选项；错误信息可读但不含凭据 |
