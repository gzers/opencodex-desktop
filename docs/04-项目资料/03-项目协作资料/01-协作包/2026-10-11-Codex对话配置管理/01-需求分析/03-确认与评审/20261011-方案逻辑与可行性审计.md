# 方案逻辑与可行性审计

日期：2026-10-11。对象：本独立协作包的《Codex 对话配置与实时生效方案》。版本、开发时机仍待定。

## 1. 结论

整体方向可行，已有原生能力比原草案写得更充分；主要缺口是**配置如何到达实际执行进程**，以及如何证明目标项目 / 对话采用了配置。仅增加 Desktop 配置页和内存 overlay，不能完成全部目标。

本次完成源码审阅和隔离的原生 app-server 验证，8 项检查通过。项目列表、稳定 ID、对话改名和同实例后续轮次模型 / effort 热更新已获得运行证据。搜索 sidecar、标题辅助调用路由和子 Agent 配置以 OpenCodex 源码为证据，尚未做真实搜索、自动生成标题或子 Agent 推理验证。

本次侧重逻辑修正，不增加审批流程。后续应先验证一个真实执行接入闭环，再决定产品范围；无需等待所有候选字段验证完才继续讨论。

## 3. 关键逻辑缺口与修正

### F1：配置执行接入缺失（优先解决）

原草案要求 Desktop 在每次请求 / 创建子 Agent 前合并配置，但现有 Desktop 主要管理 OpenCodex 进程、页面及官方 shim。外部 Codex App / CLI 的请求不会因为 Desktop 保存了策略而自动经过该合并逻辑。

实测进一步确认：第二个 app-server 使用同一个临时 CODEX_HOME，可以 thread/read 第一个实例的对话；但对该对话调用 thread/settings/update 返回 -32600、thread not found，第一个实例的后续请求模型不变。**读到持久化记录不代表拥有运行中线程的控制权。** 在第二个实例 resume 同一对话也不能当作“连接第一个实例”的证明。

修正：区分配置管理、对象发现、执行适配三个部分。代理负责的搜索 / 路由策略应在 OpenCodex 请求路径读取作用域配置；原生模型、角色、并发、标题事件等能力需接入实际拥有该 thread 的 Codex 执行端。Desktop 只是管理端时，不能承诺拥有每个请求和 spawn 事件。

### F2：用全局管理接口模拟局部配置会串项目（优先解决）

原 overlay 第 4 步允许“调用管理接口更新下一次执行默认值”，与“不改全局配置”及多项目并发目标冲突。项目 A 写搜索模型 A，项目 B 紧接着写模型 B，A 的实际请求就可能使用 B；事后恢复旧值也不能消除并发窗口。

OpenCodex 的 sidecar、shadow-call、injection-model 管理接口操作共享配置，没有本方案所需的 project/thread 参数。

修正：全局设置可以复用现有接口；局部设置需要请求级配置副本 / 策略快照，不能反复 PUT 全局接口模拟。若当前没有对应执行适配器，局部策略可保存，但显示“尚未接入执行”，不显示“已应用”。

### F3：一次性覆盖与恢复继承的语义不成立（已实测）

该 Codex 版本的 turn/start.model、effort 会作用于本轮及后续轮次。thread/settings/update.model = null 也不会恢复全局默认。测试先把全局模型改为 mini，已加载对话仍使用原模型；传 null 后依旧如此，显式传入重新解析的 mini 才改变实际请求。

修正：每个字段区分“缺省 / 继承”“关闭 false”“显式空列表”和“原生字段允许的 null”。列表按整体替换；不要用真假值合并。撤销覆盖、切换项目或临时请求结束后，应重新解析有效值并应用；直接省略旧参数会留下原生会话中的旧值。

一次性覆盖只有在控制下一轮开始的接入点存在时才能可靠实现；按 thread 顺序执行更新，避免临时值的恢复覆盖用户刚保存的新设置。serviceTierForTurn 是原生明确的一次性字段，不能把它的语义推广给 model / effort。

### F4：项目身份、父子继承和离线编辑还未闭合

当前原生协议已有 project/list、project/create/update，thread 带 projectId、parentThreadId、sessionId；不必先用 cwd 自造一套项目 ID。thread/list 不传 projectId 表示全部，null 表示未分配项目；归档需要单独查询。实测归档不会让 ID / 项目绑定失效。

OpenCodex 能读取 thread/session 请求头，但这不等于每种标题 helper、搜索和 child 请求都带有可直接使用的项目 ID。子 Agent 若只按自己的 thread ID 查策略，会丢掉父对话覆盖；共享 session ID 也不能当成唯一 thread ID。

修正：对象键带上宿主 / Codex 数据源身份，再保存原生 projectId、threadId。发现层维护原生父子关系索引；child 在创建边界继承父执行快照。身份无法确认时只应用可确认的全局策略，并显示局部策略未匹配，不能根据提示词中的路径猜项目。

项目改名、归档不要求重新绑定；确认删除 / 跨数据源迁移才处理失效。列表暂时失败时，允许继续编辑、保存已有绑定的策略，状态为“发现信息待刷新”；移除原草案每次保存前强制查存在、离线就禁存的要求。

### F5：搜索“模型可配置”不等于全部搜索都被接管

2.78.0 已有 webSearchSidecar：backend、model、reasoning 等字段，支持 OpenAI、Anthropic、xAI、Gemini、Exa。无需再把独立搜索模型写成完全未知能力。

但 planWebSearch 在 passthrough 路径直接返回；上游原生 hosted search 并不使用此 sidecar。候选模型受 backend 和认证方式限制，不能任意选择普通渠道模型；Exa 是搜索服务，不应要求选择 LLM 模型和推理档位。/alpha/search 另有调用路径，不能混成同一种搜索。

现有配置没有通用搜索 fallback 数组。“跟随回答模型”也只在该模型满足所选搜索 backend 条件时成立。管理 GET 的 webSearch 没有回显 reasoning，不能以此断言未保存，也不能把缺失值回写为默认值。

修正：先显示实际执行路径和该路径可用字段。全局 sidecar 设置可复用；项目 / thread sidecar 覆盖、统一回退链属于新增执行能力。热更新按下一次搜索 plan 构建生效，不能承诺当前 sidecar 循环中下一次工具调用一定读取新配置。启停 sidecar 还涉及原生搜索配置注入，应与仅改 model 分开说明。

### F6：标题模型路由与完整自动命名策略混为一谈

shadowCallIntercept 已能重定向 Codex 的辅助调用模型，但它按 sourceModels 匹配，覆盖标题、提交信息等 helper，并排除 spawned child；不是专门的“仅标题”路由。它不负责触发首轮完成事件、模板或手工标题保护。

原生 thread/name/set 已实测可回写标题，但请求只有 threadId / name，没有 expectedVersion 或标题 CAS。先读标题再写不能提供原子手工锁保护。若 Codex 原生命名和 Desktop 自建命名同时运行，还会竞争覆盖。

修正：区分“复用原生命名，仅调整辅助模型”与“自建命名任务”。后者需要明确事件来源和单一命名执行者；任务携带策略 / 标题修订号，过期结果丢弃。缺少原生 CAS 时，外部手工改名竞争只能尽力检测，不能承诺绝不覆盖；默认首轮一次，不把每轮重命名作为已确认能力。失败保留原标题且不阻塞主对话。

### F7：子 Agent 的推荐、默认、强制限制和读取时机被混用

subagentModels 是最多 5 个推荐模型的 roster，不是强制默认或完整模型集合；injectionModel / effort 默认是指导提示。syncCodexSubagentDefaults 开启后由配置注入路径处理原生默认值；管理接口保存该标志不等于已有会话已加载它。

已有全局 / 按模型的子 Agent fallback，但不是搜索 fallback。角色管理接口依赖 LazyCodex / omo，只修改已有角色的 model / effort；这一限制不能反推出 Codex 原生完全不支持新建角色。独立子 Agent Fast、角色工具白名单和通用新建角色尚无本次运行证据。

V1 / V2 也不一致：max_depth 是 V1 路径；effort-policy 在 config.multiAgentMode = v1 时跳过 caps。不能给本机 V1 配置统一标上“effort 上限强制生效”。代理 cap / fallback 在后续请求读取，不能同时承诺整个子 Agent 生命周期模型永远固定。

修正：每项注明提示、原生默认或代理强制执行，并记录读取边界。并发要说明是父线程树的数量还是管理器跨项目预算，不能把原生 max_threads 当成全应用调度器；调低上限不取消已运行任务。角色 / 指令 / 权限原则上在创建时装载；已运行 child 的后续 HTTP 请求若受 live cap / fallback 影响，单独展示，不能隐藏在“已启动不变”之下。

### F8：“实时生效”的时间单位和状态反馈不统一

一个用户 turn 可以包含多次模型 HTTP 请求、搜索循环及多个子 Agent。原方案同时写“当前请求冻结”“新 child 总用最新配置”和“child 全生命周期固定”，在长 turn 期间保存配置时无法同时成立。

建议：新增作用域策略以父 turn 开始时的策略修订为快照，期间新建 child 继承该快照；保存影响下一父 turn。若实际接入只能看见 HTTP 请求，就明确标成“下一模型请求生效”，不宣称 turn 级冻结。已有 live 全局 cap 等原生行为单列，不能仅靠 Desktop 文档改变。

界面用“已保存 / 执行端可用 / 已观察到采用”区分三件事，并提示具体生效边界。记录策略修订、命中作用域、执行路径、最终模型和简要回退原因即可，不需要完整提示词日志或每次保存新增审批。

## 4. 最小验证结果

| 检查 | 观察结果 |
|---|---|
| 原生项目与分页 | 创建 2 个项目，limit=1 分页完整；改名后 ID 不变 |
| 对话项目与标题 | 本地一轮完成后可改名并读回；projectId 与 null 筛选区分正确 |
| 后续轮次热更新 | 同一个进程、同一 thread：settings/update 后实际发出 mini / high |
| turn/start 的持续性 | 显式模型 / effort 在下一轮省略参数时继续沿用 |
| 配置写入与已加载会话 | config/read 能读到新默认；新 thread 采用；旧 thread 保留原值 |
| 恢复继承 | null 未恢复；重新解析并显式设置后实际请求恢复新默认 |
| 第二实例控制边界 | 能 read 同一对话，settings/update 返回 thread not found；原实例保持原模型 |
| 归档与删除区别 | 归档对话从非归档列表消失，归档列表仍有相同项目绑定 |

8 个本地 Responses 请求，8 项检查通过。该结果不覆盖真实上游、已安装 App 的私有连接、搜索 sidecar、子 Agent spawn、跨平台或旧版 Codex。

## 5. 建议的下一条可行性验证

优先确定连接**实际执行端**的方式，再做两个项目并发、同一搜索类别配置不同模型的端到端验证；观察最终模型和父子作用域来源。若暂时接不到执行端，可先形成全局原生设置管理与项目 / 对话策略编辑，但要把“配置已保存”和“局部执行已接通”分开。

已有管理 API 可以由 Desktop 调用；作用域路由若没有官方扩展点，需要在 OpenCodex 请求路径补能力并明确兼容 / 交付方式，不能默认只改本仓 UI 就够。子 Agent 继续交给 Codex 原生调度，不需要为本方案先建立 Skill 调度器。

这些是后续讨论及验证建议，不构成版本或开工承诺。
