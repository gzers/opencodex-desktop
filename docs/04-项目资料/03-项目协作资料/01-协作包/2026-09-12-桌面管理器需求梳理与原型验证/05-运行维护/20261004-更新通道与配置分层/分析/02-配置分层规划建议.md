## 1. 设计结论与现状修正

已确认采用 **“随版本固化的默认配置 + 单文件分域用户偏好 + 既有机器配置 + 独立运行状态 + 凭据引用”**。分层解决来源、权限与可迁移性；分域解决业务归属。两者是不同维度，不应把所有东西塞进一个可任意覆盖的大 JSON，也不必把每个设置域都拆成文件。

| 编号 | 本次核对结果 | 设计影响 |
|---|---|---|
| C-01 | 当前 `Preferences` 为 **30 字段**；Rust 持久化结构、Rust DTO/转换、TS DTO、设置页默认值分别手写 | 统一类型契约与默认值；清理需要兼容保留的退役字段，不能只按页面搬家 |
| C-02 | 保存调用 `validate()`，读取只反序列化；默认值与枚举/数值约束又在 UI 重复 | 读、写、导入、同步全部通过同一套校验；UI 使用后端返回的有效配置 |
| C-03 | `stable-24h / beta-6h / manual` 同时编码通道与频率；静态扫描未发现 6h/24h 自动检查调度 | 拆字段并补消费链路；改变 JSON 结构本身不会让更新通道或调度生效 |
| C-04 | updater 端点同时出现在 Rust 与 Tauri 配置；Rust `endpoint()` 仅被测试调用，生产检查/安装读取 Tauri 静态配置 | 检查与安装共用按通道解析的策略；同通道镜像列表不可混入另一通道 |
| C-05 | registry URL **不在偏好中，也未显式传给 npm**；npm/node 请求路径与来源在独立安装/运行链路中 | 问题是默认策略分散、实际来源不可见；不能写成“这些参数已混入 preferences.json” |
| C-06 | `serde(default)` 已支持旧文件缺少新增字段；真正缺少的是显式版本、语义迁移、未来版本保护 | 不能把所有旧文件判成损坏；迁移重点是改名、类型改变、退役字段和降级读取 |
| C-07 | theme 在 localStorage；部分旧偏好仅保存、不参与决策；导出容器只接受扁平原始值 | 同步/迁移范围、有效字段与兼容适配必须一起规划 |

## 2. 五类数据与可信边界

| 层 | 应放内容 | 谁能改 / 如何生效 | 导出与同步 |
|---|---|---|---|
| 随版本固化的默认配置 | 偏好初始值、更新通道地址、平台发现候选、运行超时/轮询/保留默认、产品链接、客户端描述表 | 仓库评审、构建校验后随应用发布；打包后只读 | 不随用户配置传输 |
| 用户偏好 | 外观、窗口行为、通知、备份选择、导出范围、冷同步、更新通道与自动检查选择 | 用户通过类型化接口保存；注明立即、下次动作或重启生效 | 只传输明确允许迁移的字段 |
| 本机/部署配置 | 数据根、OPENCODEX_HOME、可执行路径、安装前缀、代理、registry/更新镜像覆盖、WebDAV 端点 | 保留现有独立存储；覆盖有字段白名单与路径/URL校验 | 不进入普通偏好同步；既有容器中的脱敏端点迁移继续走专门章节与本机重新认证 |
| 运行状态 | 当前/可用版本、上次检查、端口、安装历史、同步接受状态、错误与缓存 | 业务执行器写入；UI 只读投影 | 不作为配置覆盖，也不随偏好同步 |
| 凭据 | WebDAV 密码、token 等；JSON 仅保存引用 | 沿用 Keychain；日志与有效配置视图脱敏 | 不导出真实值，不复制另一台机器的有效引用 |

另有**受信任构建与协议契约**：updater 公钥、包身份、Tauri CSP/capabilities、TLS 要求、协议版本/魔数、备份 SHA-256、导入上限等。这些可以集中成构建常量或受版本管理的清单，但不能因为“放进文件”就允许用户覆盖。私有签名密钥属于发布环境秘密，不进入上述默认配置。

机器配置与运行状态先在类型和消费接口上区分。`runtime.json` 当前同时保存来源选择与安装事实，`data-root.json` 同时保存结构元数据与运行定位；第一阶段保留其存储格式，不能在一次“配置整理”里直接拆文件、搬数据根。

## 3. 文件与模块规划

以下为**拟新增路径**，尚未创建；代码产物将来只在 main 或其特性分支实现。

```text
apps/desktop/config/
  preferences.defaults.json   # 唯一偏好初始值，不含机器路径/凭据
  runtime.defaults.json       # 通道端点、发现候选、超时/轮询/保留默认
  product.json                # 第二阶段：包身份、产品链接（构建只读）
  clients.json                # 第二阶段：已支持客户端的描述（构建只读）

<现有数据根>/manager-state/preferences.json  # 一个版本化文件，内部按域组织
<现有位置>/manager-state/data-root.json     # 保持现有结构元数据与定位兼容
<现有数据根>/manager-state/runtime.json                   # 保持现有来源登记与历史兼容
<现有数据根>/manager-state/sync-endpoints.json
<现有数据根>/manager-state/extension-config.json
<启动定位根>/manager-state/runtime-overrides.json # 仅在确需镜像/registry覆盖时增加
```

`启动定位根` 指目前 Tauri `app_data_dir()` 引导使用的位置。覆盖文件位置必须先能被启动器定位，不能要求读取被它自己定位的数据根才能找到它。第一阶段不引入新 bootstrap 文件；后续若拆 `data-root.json`，另行设计迁移。

默认配置在构建阶段校验并嵌入应用，运行期不从工作目录寻找可被替换的同名文件。`runtime.defaults.json` 中按 `updates / discovery / process / status / sync / install / retention / diagnostics / ui / extensions` 分组；补查新增命令窗口、首屏/面板/生命周期提示与桥接、日志读取默认、扩展初始选择，见硬编码清单H-23～H-29。仅开放经评审允许覆盖的字段。协议、安全上限即使集中也不参加普通覆盖。

建议在 Rust 提供 `ConfigService` 与类型化 `EffectivePreferences / UpdatePolicy / DiscoveryPolicy / RetentionPolicy`。调用方拿已解析、已校验的类型，不自行拼默认值或读取 JSON。产品链接/客户端清单作为目录接口返回前端；描述表不能绕过代码中的 writer 能力与路径保护。

Rust 类型是字段契约来源，JSON 是默认值来源；构建检查 JSON 满足 Rust 模型。TS DTO 从同一契约生成，磁盘 snake_case 与 IPC camelCase 的转换由统一边界负责。前端偏好初始化、恢复默认、设置页回显均取后端结果；若需首屏缓存，仅作缓存，加载失败不得把缓存写回覆盖真实偏好。首屏等待预算与前端桥接节奏来自同一`runtime.defaults.json`构建生成的只读TS子集，挂载前即可导入，避免“等后端配置才能确定等待后端配置的期限”；不另手写一份生产数字，也不包含机器路径或凭据。

## 5. 解析、保存与生效规则

不是每一层都能覆盖所有字段。逐字段指定来源：

- 用户偏好：版本默认 → 经迁移和校验的偏好。用户显式选择优先；缺失新增字段才取默认。
- registry/代理/发现路径/镜像：版本策略 → 经白名单校验的本机配置 → 本次操作明确允许的参数。机器绝对路径必须由本机检查；不增加任意环境变量覆盖或不受控 PATH 扫描。
- 运行状态和凭据：不参与覆盖。端口、已安装版本不能被 preferences.json 声称或修改。
- 公钥/协议/安全约束：固定可信来源。`allow_scripts` 仍是本次安装的授权，不变成永久默认放行配置。

缺失文件可取默认；文件存在但损坏、字段非法或版本过新时显式失败并保留原件，不能静默以默认覆盖。读取与所有写入来源使用同一类型校验。未知字段在旧格式适配器中有明确保留/拒绝策略，新格式普通保存不接受任意键；新版本文件不得被旧应用“忽略未知字段后再写回”。

建议保存请求带 `expected_revision`，按域提交类型化变更，锁内验证并原子写入，避免两个窗口用各自的整份旧快照互相覆盖。首次可保留旧 IPC 包装适配器，但它也必须进入同一保存服务。

保存结果返回持久化版本、有效值与生效时机。即时值更新共享投影；重启项标注待重启；下次动作项只影响新事务。运行期应用失败时明确报告“已保存，尚未应用”或回滚已保存值，不能用泛化成功通知掩盖不一致。GUI、托盘与 CLI 读取同一有效配置。

有效配置诊断至少给出来源层、当前值、默认值和生效状态；URL 中凭据、token与实际密码不可显示。恢复默认按域重置用户选择，不重置本机路径、凭据或运行历史；退役兼容数据按迁移规则处理。

## 6. 四条需要同时修正的消费链路

### 6.1 桌面更新

`updates.desktop.channel = stable|beta`，`auto_check = true|false`，`check_interval_seconds` 为正整数且限制允许档位；**不再把 manual 作为间隔值**。关闭自动检查后通道仍有效，手动检查仍可执行。

检查与安装共用 `resolve_update_policy()`；端点按所选通道取同通道镜像列表。安装绑定用户已检查/确认的版本、通道与策略修订，变更通道后作废旧候选，防止再次检查时换成别的更新。消除“保存偏好 + 单独改内存通道”两个事务，状态里的 channel 仅为有效配置投影。

自动调度应由后台生命周期承载，主窗口关闭仍按产品策略运行；避免多个窗口重复检查。上次尝试/成功、可用版本、失败退避存为状态，不覆盖用户选择。网络失败不把通道切回 stable。真实端点、公钥与签名制品仍需独立发布工作完成。

### 6.2 OpenCodex 查询与安装

桌面 stable/beta 与官方 npm latest/preview 是两个不同对象，不能隐式映射。官方卡片若选择新增远端查询，应为它单独解析 tag、registry、proxy 和超时，并与 pack/install 共享同一来源策略。先把 tag 解析成确定版本，再安装该版本与完整性信息，避免查询到一个版本却执行浮动 latest。

当前 npm 调用未显式传 registry。第一阶段保留现有 npm 配置来源并如实显示“继承 npm 配置”；若要采用内置默认 registry URL，需在评审中确定地址及 `.npmrc` 的继承优先级，再将同一显式 registry 传给查询、pack 与 install。不能只给卡片换源而安装继续走另一来源。

### 6.3 生命周期超时

现在领域/编排 start=20秒，实际进程 runner 将 start/restart 都取30秒。必须先解释启动子进程等待、代理就绪观察、整个动作窗口是否为不同阶段，再给策略命名。若应同义则消除重复；若不同则显式分别定义并验证组合上限。首阶段统一来源并保持已冻结约束，不能擅自选一个更大的超时作为新行为。前端另有stop=15秒、start/restart=35秒的提示窗口，提示后额外观察180秒；属于`ui.lifecycle`，不能替换后端执行窗口，超时也不代表真实进程失败。面板子视图8秒加载提示、首屏两类1500ms等待分别命名；改变策略须核对实际生效时机。

### 6.4 备份与清理

当前保留是**最近 N 份或30天内记录的并集**：仅当同时“数量超出 N”且“已过30天”才删除，不能改成硬上限 N。将数量与天数表达为 `RetentionPolicy`，天数先取版本固化值30，是否开放用户修改另行裁决。

导入与同步当前总会先备份存在的目标；这是事务保护，不能仅因三个历史布尔字段被分组就关闭。SHA-256 是当前清单契约；不开放没有实现的算法选择。日志 UI 保留与 IPC 审计保留分别解析，不能用一个普通偏好缩短全部审计记录。最近日志200行归`diagnostics.logs`，同样与清理保留、文件轮转分开。扩展默认方法symlink与默认客户端启用归`extensions`初始策略；用户选择继续保存在extension-config.json，默认更新不能重新启用已关闭客户端，也不触发分发写入。

## 7. 迁移、导入导出与同步兼容

1. **识别格式**：先读 JSON 值和 schema，再经旧字段映射迁移到最新类型，最后校验。明确区分缺文件、缺新增字段、非法值、未知未来版本。
2. **旧更新值**：`stable-24h` → stable/true/86400；`beta-6h` → beta/true/21600；`manual` → stable/false/86400。旧文件没有保存“关闭前的通道”，无法恢复所谓“保持通道”；stable 是旧实现的确定行为，86400仅作将来重新开启的默认。自动检查的真实实现另有产品裁决，不能把旧字段有频率等同于曾经执行过调度。
3. **回退**：先生成迁移预览与原文件备份，再在同一目标锁下原子写入0600；失败保留原件和旧格式，不静默重置。记录 schema与默认配置版本，升级/降级兼容范围明确。本次不执行真实迁移；随版本发布的常规格式转换可自动完成，数据根搬迁等独立操作不归入通用转换。
4. **容器不是原始文件复制**：现有 `PreferenceValue` 仅 Boolean/Integer/Text，导出代码逐顶层字段转换。第一阶段内部类型分域、磁盘仍扁平，可继续原容器；若磁盘改成嵌套，必须同步添加扁平兼容投影。当前30字段可保留旧导出适配器，但新增 theme、通道/频率自由组合无法无损装入原枚举，必须声明兼容导出丢失范围，或为新偏好章节增加明确版本并保留旧 reader。不能在原格式版本下偷偷改变含义。
5. **同步需要版本协商**：当前上传原始 preferences.json；接收只验 JSON 和完整性，不验偏好模型。分层后使用可迁移偏好投影，并在应用前迁移/语义校验；远端版本不支持时保留双方，不覆盖本机。混用旧新客户端必须协商能力或隔离同步版本，不允许旧应用忽略新字段再上传造成静默丢失。
6. **移植范围**：默认配置、mirror/registry覆盖、机器路径、密钥和运行状态不进入普通偏好投影。同步端点仅沿用专门的脱敏迁移章节，本机重新认证；扩展配置仍由已有模块校验，不并入 preferences.json。
7. **主题边界**：后端迁移无法直接读取 webview localStorage；由受控 UI 一次性提交历史主题，再通过同一保存服务写入。新值已存在时不能被缓存反向覆盖。

8. **后续版本自动转换**：应用版本与配置schema独立；统一迁移服务执行已发布步骤，支持跳版本、当前版本不重复写盘、迁移前备份、中断恢复与未来版本保护。启动读取、CLI、导入和同步共用校验/转换；常规格式转换无需每次弹窗，含义不明确或高风险动作走专门流程，详见 [通用自动配置迁移机制](05-通用自动配置迁移机制.md)。

1. **构建/启动先选环境身份**：日常发布保持现有标识和配置位置。开发与集成测试使用独立沙箱身份/安装产物（标识例如 `com.gzers.opencodex.desktop.sandbox`，为拟议值），在初始化目录、实例锁、读取定位文件及配置迁移之前确定。沙箱根选择失败即停止，不能回退到日常目录。该身份属于构建与启动策略，不能依赖尚未读取的 `preferences.json`。
2. **隔离全部可写目标**：启动定位根、管理器状态、偏好、运行配置、业务数据根、OPENCODEX_HOME、迁移原件/记录、日志、缓存、WebView存储及IPC均在沙箱中；Keychain使用测试专用服务/账户或测试替身。机器配置中复制来的绝对路径、客户端分发目标、安装前缀和现有进程连接不能沿用日常环境；对实际可能写出的外部目标逐项采用测试替身或沙箱路径。拒绝符号链接/路径别名等逃逸到日常目标的写入。
3. **迁移测试用独立副本**：自动化用历史fixture与每次运行的临时根。真实配置样本仅在明确需要时只读获取，生成脱敏、无真实凭据引用的字节副本；不能使用硬链接/符号链接共享原件。转换、故障注入及恢复只作用于副本，新schema不写回日常文件。
4. **同步与后台动作单独隔离**：配置转换测试默认用本地替身，不启用真实同步、CLI注册、客户端分发、更新安装或代理写入。需测试这些链路时显式使用测试端点/远端独立命名空间、沙箱运行时与本机测试目标；不能上传到日常同步空间，也不能用共享远端让旧客户端拿到新schema。清理只允许处理本次沙箱。
5. **配置环境与更新通道独立**：`updates.desktop.channel=beta` 只选择更新来源，不自动创建测试数据目录。日常安装选择beta属于原地升级，仍读写自己的配置；开发验证必须用沙箱启动方式。README须写清两者差别，并按已交付入口给出实际操作方法。
6. **验收“日常目录未变”**：隔离测试覆盖缺省启动、配置保存、旧schema转换、中断恢复、重复启动、CLI及同步路由；在受控的模拟日常根放置哨兵文件，验证文件内容/时间、目录条目和写入目标没有改变，错误环境不能回退或连入日常实例。日常版与沙箱版分别修改后结果互不覆盖。先通过该验收，再开展完整应用配置迁移冒烟；不在用户真实环境做破坏性验证。

日常版正式升级时，自动转换会按设计在其自身配置目录中备份并升级格式，这是预期的升级行为；测试通过后才随发布启用。转换后的文件能否被旧版读取取决于兼容表，不能承诺启动旧版即可自动还原。旧二进制没有未来版本保护的问题仍按[自动迁移机制§8](05-通用自动配置迁移机制.md#8-降级与恢复)处理。
