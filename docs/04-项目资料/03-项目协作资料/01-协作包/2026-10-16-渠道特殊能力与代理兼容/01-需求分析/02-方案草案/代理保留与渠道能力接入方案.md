## 项目边界

本项目只做外部管理层，保持原版 OpenCodex 的源码、安装包、认证及会话逻辑完整。集成使用原版公开 CLI/API 和允许的客户端配置入口；不维护补丁、fork 或定制包，不私改核心配置、生成目录或私有内存状态。现行[集成与安全边界](../../../../../../02-项目核心/集成与安全边界.md)继续适用。

前序提出的核心修改方向已撤回。前置网关及完整 Krill 会话绕开 OpenCodex 的方案只是历史备选，未被采用；当前方向是让原版继续选择渠道，再由外层处理发往已选渠道的请求。

## 当前链路与职责

```mermaid
flowchart LR
    C[Codex 桌面客户端] --> O[原版 OpenCodex]
    O -->|已选能力渠道的请求| E[出站适配层]
    E --> K[Krill 等已配置渠道]
    O --> A[其余现有渠道]
```

回程仍沿原链路返回。出站层不解析或改写响应内容，原样流式转发状态、必要头与响应流，并正确处理取消和连接结束；这不取消原版 OpenCodex 自己的响应处理。具体进程或模块形态及公开接入方式未选定。

| 层 | 责任 |
|---|---|
| Codex 客户端 / 实际引擎 | 读取当前生效的上下文策略和速度配置，使用已识别的模型能力 |
| 原版 OpenCodex | 保留现有渠道选择、模型路由及已支持的请求处理，不扩展内部实现 |
| 出站适配层 | 根据明确的渠道配置处理地址、请求头和参数，发往已选渠道；不再次动态挑选渠道或探索模式 |
| Desktop 管理器 | 在渠道管理承载配置，进行静态组合校验，区分保存与应用状态，管理允许的生效流程 |
| Krill / 其他渠道 | 提供实际支持的协议与速度档；接入结果形成固定能力规则 |

出站位置能否通过原版公开配置接入、是否保留必要请求与回程协议，均需一次性验证。渠道凭据和核心运行配置继续走原版公开入口；外层如需独立凭据，应明确归属，不通过私读上游密钥文件取得。

## 渠道管理中的选项

上下文策略采用单选，速度档独立设置；只展示渠道明确支持的能力，具体字段 schema 与默认值尚未冻结。

| 上下文策略 | `async_compaction` | `context_management` | `token_budget.enabled` |
|---|---|---|---|
| 常规压缩 | 关闭 | 关闭 | 关闭 |
| 后台压缩 | 开启 | 关闭 | 关闭 |
| 新版 history/notes | 关闭 | 开启 | 开启 |

新版上下文管理配合 `use_history_notes_extension = true`。互斥依据是用户提供的 Krill 说明，配置表不代表所有引擎版本或当前链路均已验证支持。需处理布尔 / 配置表写法、profile 及覆盖层下的有效值。

速度档为 Standard / Fast / Ultrafast。优先复用原版公开入口，必要的出站参数按明确渠道策略处理，不从被删除的字段猜测客户端选择。需要区分“渠道固定档位”和“跟随客户端档位”；具体优先级待细化，不能把原版目录开关开启当作上游已按档执行。

配置落点补充：客户端顶层速度选择可按 default / fast / ultrafast 映射，Fast 对应请求 priority；具体保留和覆盖以已验证规则为准。远程协议的显式设置仅对确实支持该入口的自定义 provider 开放，不能将 Superba 的渠道 Native / Unsupported 声明当作内置 openai 的本地 / 远程开关。压缩协议偏好、后台执行与代理实际摘要 / 原生处理分别表达；PAT / API Key 和实际消费者版本列为前置条件。详见上述来源记录，默认值与完整组合尚未冻结。

## 配置应用流程

1. 在渠道管理选择上下文策略与速度档。
2. 保存并静态校验互斥、渠道支持和配置作用域，显示待重启 Codex。
3. 通过允许的入口应用配置并重启 Codex，再核对当前有效配置。
4. 运行按固定渠道规则执行；异常明确报告，不自动试探其他机制或静默改策略。

保存值、当前应用值和实际能力验证结果分别表达。重启后可以确认应用了哪套配置，不能仅凭重启宣称 Krill 链路已通过。保存后、重启前不将新策略展示为已生效；客户端与出站规则如何保持一致应在实现前明确。

渠道偏好与客户端开关作用域不同。同一 Codex 实例不能被假定为随每次路由自动切换上下文策略；模式来源、并行渠道兼容范围、不兼容故障切换与重启时机仍为待细化项。此前渠道管理的重启流程可复用，但不推定所有原版渠道配置都必须靠客户端重启生效。

## 固定配置与验证边界

| 已知事实 | 当前处理 | 仍需确认 |
|---|---|---|
| 渠道和所选模式由配置确定 | 运行时不猜测意图，不自动探测或轮流尝试模式 | 一次性接入验证后才能把能力标为可用 |
| Ultrafast 决策函数可按策略保留档位 | 优先验证原版公开能力及明确的出站档位规则 | 最终序列化、客户端目录、上游执行与日志差异 |
| 压缩触发可能已被原版转成摘要 | 不在出站层反向发明原生状态 | 实际出口是否仍保留所需协议，以及回程能否继续处理 |
| history/notes 可能在内部被拒绝或未被声明 | 不把固定配置当作能生成未到达出口的请求 | 端点到达、能力声明、认证、服务身份与续聊 |

上述验证用于明确支持范围，不是运行时探索机制。不满足条件的能力保留为上游依赖或另行提出方案，不修改核心，也不自动转向前置分流。
