## A. 功能性缺陷（阻断，已修）

### A-1 导出报「实际渠道含当前适配器未知字段，请升级适配后再导出」

| 项 | 内容 |
| --- | --- |
| 现象 | 同步页点「导出配置」直接报错，导出无法进行 |
| 触发渠道 | 只有 `FeiMao-CNM` |
| 根因 | 该渠道对象里有一个 `name` 字段（值等于渠道 id） |
| 为什么会有 | 官方 `POST /api/providers` 会把请求体里的 `name` **回写进 provider 对象**；当场是用它做真实写入测试时被持久化的 |
| 为什么我们的代码会拒绝 | `provider_fields.rs` 的白名单 `PUBLIC`/PRIVATE`/`RUNTIME` 都不含 `name`，落入「未知字段」分支 → `public_from_raw` 返回错误 → 整个导出失败 |
| 关键事实 | **官方 `OcxProviderConfig` 类型（144 个字段）没有 `name`**，但官方 `ocx config validate` 对该配置返回 `ok`，且官方自己会写它 |

**判定**：这是我们的白名单比官方更严导致的**过度阻断**，属于软件缺陷。用户配置没有错。

**修法**：新增 `ECHO` 分类（`&["name"]`）——「官方容忍、仅作身份回显」的字段。
- 不再让它触发「未知字段」错误；
- 但仍**不进入**写入载荷（`selected` 只保留 PUBLIC 字段），因此不会成为写入权威；
- 真正的未知字段（例如 `futureSecretBlock`）**仍然拒绝**，安全边界不变。

**验证**：新增单测 `tolerated_echo_field_does_not_block_export_and_never_becomes_write_authority`，断言「不报错 + 不出现在输出 + 未知字段仍拒绝」，已通过。

## B. 界面与原型不一致（待修）

### B-1 导出确认页与原型不一致（外部与内部都要比对）

| 差异 | 原型 | 软件现状 |
| --- | --- | --- |
| 右侧区域 | 原型右侧是**凭据与保护选项**（渠道 API Key 可单独分享、扩展凭据、全局采用与渠道组顺序、文件保护口令） | 软件做成「其他凭据」列表 + 口令输入，但**位置与分组不同**，且缺少原型里「接收方自行填 Key」的说明层级 |
| 内部结构 | 原型：导出目录 → 生成位置树 → 文件保护 → 携带凭据 → 管理器配置 → 扩展资源 | 软件顺序被打散，部分说明文字缺失 |
| 密钥填写 | 原型要求**在窗口内填写与确认** | 软件把口令输入挤在右栏底部，未按原型分组 |

**需要逐项比对原型 `model-config.js` 中导出确认的 HTML 结构后重排。**

### B-2 渠道模型顶部操作按钮状态与原型不一致

| 差异 | 原型 | 软件现状 |
| --- | --- | --- |
| 分组 | 单行「状态 → 还原修改 → 保存」，三者等高 | 状态与按钮分成多块，高度不齐 |
| 状态位置 | 状态框在按钮组左侧同一行 | 状态另起一行 |

原型源码：`channelPolicyStates` 注释明确写「从左到右：状态 → 还原修改 → 保存……状态框和保存按钮等高」。

### B-3 渠道详情头部状态显示多行且复杂

| 差异 | 原型 | 软件现状 |
| --- | --- | --- |
| 结构 | `.mp-channel-state` = 开关 + 「启用/停用」单行，`white-space:nowrap` | 软件渲染成多行，混入节点/模型计数 |
| 触发 | 原型 `model-config.js:387-388` | — |

### B-4 模型模版 Agent 配置：按钮下方不应外露已选模型

| 差异 | 原型 | 软件现状 |
| --- | --- | --- |
| 形态 | 只有一个「Agent 配置」按钮 | 按钮下方额外显示一行「GZGG-NewApi / gxlq-local-deepseek-flash · 高 · 快速能力待核对」 |
| 按钮顺序 | 原型固定顺序 | 软件顺序不同 |

原型：`model-config.js:425` —— `'<div class="mp-actions">'+button('Agent 配置','settings')+'</div>'`，**没有伴随文字**。

### B-5 保存预览：改名 + 顺序必须严格按定义顺序

用户要求（同时改原型）：

| 要求 | 说明 |
| --- | --- |
| 改名 | 「保存 · 选择器预览」→「**保存预览**」 |
| 顺序 | 渠道与型号必须**完全按已定义的顺序**排列，不能用其他自定义顺序渲染 |

**这条需要同时改原型与软件**，且属于规格变更（写进 UI 规范），不是单纯修 bug。

## D. 后续修复顺序建议

| 序 | 项 | 理由 |
| --- | --- | --- |
| 1 | A-1（已修） | 阻断性：不修则导出完全不可用 |
| 2 | B-5 原型改动 | 先定规格，避免软件改完再返工 |
| 3 | B-2 / B-3 | 同一区域（渠道头部与顶部操作），一起改一次回归 |
| 4 | B-4 | 单点，改动小 |
| 5 | B-1 | 结构性重排，工作量最大，放最后单独验证 |

每项都要有「原型写法 → 软件现状 → 修后断言」三段证据，不接受只改视觉不给断言。
