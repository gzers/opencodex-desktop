# 需求基线

## 1. 定位与口径

- 本文件把 `DMD-OPENCODEX-DESKTOP-MANAGER` revision 2 拆成可追踪的需求条目。
- 本文件是**派生分析**，不是事实源；稳定需求仍以 DMD 为唯一权威。
- 可能改变范围的内容只进入 `风险与开放问题.md`，不直接当作事实写入 DMD。
- 编号稳定，不随排序变化；条目状态变化只在“状态”列体现。

### 1.1 状态口径

| 状态 | 含义 |
|---|---|
| `confirmed` | 已由用户确认，并已回写或可直接回写 DMD；可进入验收设计。 |
| `derived` | 从 DMD、原型或现状观察推导，方向明确但尚未逐条回写 DMD。 |
| `open` | 存在未冻结的分支、契约或范围问题；完成前阻塞对应 AC 的验收。 |
| `blocked` | 依赖外部决策或安全评审，当前不得进入实现。 |

### 1.2 范围口径

| 范围 | 含义 |
|---|---|
| P0 | 本期原型与验收范围。 |
| P1 | 一阶段增强，原型已表达，实施前需安全评审。 |
| P2 | 二阶段能力，原型已表达，不阻塞 P0。 |
| P1（可选） | 默认关闭、需用户显式启用的能力。 |
| 候选 | 原型已探索，但范围归属未决；**未确认前不得视为本期已承诺范围**。2026-09-14 后无条目使用该档（扩展管理已定案纳入 P1）。 |

> **范围原则（2026-09-14 确认）**：**本次原型中的全部功能都必须实现**，`P0` / `P1` / `P2` 只表示实现与交付顺序及前置依赖，不表示取舍。因此本表不存在"不做"的条目；下表所有 `P0` ~ `P2` 与「可选」条目均为范围内需求。

## 4. 状态维度拆分（覆盖审计 §二·6）

审计发现原型状态数量已超过文档描述，且混成一个状态机。基线明确拆成三个维度，彼此可同时存在：

| 维度 | 取值 | 说明 |
|---|---|---|
| 运行状态 | `not_found` / `loading` / `stopped` / `starting` / `pending` / `running` / `stopping` / `starting_failed` / `at_risk` / `external_takeover` / `unreachable` | 代理进程观测。 |

> 枚举以 `docs/02-项目核心/数据与状态.md` 为准：**运行 11 / 连接 7 / 操作 8**，另有 4 个环境前置门禁态。改动枚举先改项目核心，再回来同步本表。
| 连接状态（7 态） | `unconfigured` / `disconnected` / `connecting` / `syncing` / `synced` / `conflict` / `failed` | 外部依赖连接与同步。 |
| 操作状态 | `idle` / `validating` / `backing_up` / `applying` / `rolling_back` / `cancelled` / `succeeded` / `failed` | 单次动作执行阶段。 |

- 三个维度必须能同时表达，例如「`running` + `syncing` + `backing_up`」。
- 状态渲染规则仍按 `state-and-flows.md` 的动作按状态渲染执行，不做无解释的禁用按钮。
- 字段命名与 UI 映射留 IMP 冻结。
