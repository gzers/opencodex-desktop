## WP-74：用「自己没读到的清单」否定「文件里存在的模型」——整套「核对」该删掉

**优先级**：P0（保存被自己的校验卡死，功能用不起来）
**位置**：模型 → 渠道模型 → 保存前（「调整本次保存范围」与保存预览）
**用户原话**：「为什么还有核对什么的，我觉得就不应该，或者换句话说，现在你的思路就是不对，我觉得就是直接读取那个模型配置文件作为当前渠道模型数据，然后修改保存就是直接修改文件，这样能理解吗？你的过度设计太影响使用，导致用不起来。」
**状态**：已定位（2026-10-26），**本轮先记录，未改代码**

### 一、现象

保存前的「调整本次保存范围」弹窗顶部出现红字：

> 所选模型未在当前发现清单中核对

并且弹窗里 **26 个渠道全部标为「修改」**，但用户并没有改过任何渠道。

### 二、根因：三层数据不同步，最后用最不可靠的那层做断言

实盘取证（用户本机 `manager-state/model-policy.json` vs `opencodex-home/config.json`）：

| 渠道 | config.json `models` | config.json `selectedModels` | manager `discovered` |
| --- | --- | --- | --- |
| **A6api** | **116** | **35** | **0 ← 空的** |
| FeiMao | 7 | 0 | 7 |
| FeiMao-Claude | 10 | 3 | 10 |
| GZGG-NewApi | 29 | 16 | 29 |
| 其余 22 个 | 与 config 一致 | — | 与 config 一致 |

**26 个渠道里只有 A6api 一个的 `discovered` 是空的**，而 config.json 里它有 116 个模型、35 个已选。红字就是它。

触发点在 `runtime.rs:1085`（`compile_materials`）：

```rust
if row.enabled && row.selected {
    let slugs = if source.is_some() { ... }
    } else if channel.discovered.iter().any(|m| m.id == row.model_id) { ... }
    } else {
        return Err(invalid("model_unverified", "所选模型未在当前发现清单中核对"));
    };
}
```

即：**只有当模型同时出现在 manager 自己的 `discovered` 里才放行**。A6api 的 `discovered` 是空数组，所以它 35 个已选模型全部触发这条错误，**保存直接中止**。

### 三、为什么这条校验从根上就不该存在

**用户的反驳决定了这一点，我承认之前想错了：**

> 「你怎么知道是不是写错了呢？其实你判断不了吧，因为模型有可能有些站点就是这样命名。」

我上一轮提了两个折中方案（不在清单里的标灰 / 手动输入 ID 时弹确认），**两个都建立在「我能判断哪个 ID 是错的」这个前提上，而这个前提不成立**：

| 现实情况 | 我的清单能否判断 |
| --- | --- |
| `claude-opus-5` vs `claude-opus-5-20251001` | 不能——两种都是合法命名 |
| 站点随时新增模型 | 不能——我没刷新不等于它不存在 |
| 站点用完全自定义名称 | 不能 |
| 上游临时下线某模型但用户想留着选择 | 不能——这正是 `retainModels` 的用途 |

**我唯一能确认的只有「我的清单里没有」，而这 ≠「它不存在」。** 把自己的信息缺失当成用户配置有问题，是错的。

### 四、决定性证据：文件本身从来是自洽的

对用户 config.json 全量检查 `selectedModels ⊆ models`：

```
selectedModels 里有 config.json models 之外的：
count: 0
```

**26 个渠道，零个例外。** 也就是说：用户从来没有选过「不存在的模型」。

那句红字 100% 是管理器自己 `discovered` 为空造成的误报。校验没有抓到任何真实问题，只制造了阻塞。

### 五、附带发现的第二个缺陷：26 个渠道全标「修改」

`ChannelsView.vue:54` 的 `changedTargets`：

```ts
return ids.flatMap(id => {
  const before = saved.find(c => c.id === id), after = draft.find(c => c.id === id)
  return JSON.stringify(before) === JSON.stringify(after) ? [] : [{ id, ..., kind: '修改' }]
})
```

而「有没有未保存修改」用的是 `canonicalPolicy`（`policyEquality.ts`，会跳过 `sourceReadId` / `importedConfig` 这两个本机记账字段、并排序键名）。

**同一份草稿，两处判据不同**：

| 判据 | 结果 |
| --- | --- |
| `channelDirty`（canonicalPolicy） | 未修改 |
| `changedTargets`（原始 JSON.stringify） | **26 个全部「修改」** |

读取现有渠道时会给每个渠道写 `sourceReadId`，所以每个渠道的原始 JSON 都与快照不同 → 全部误判为「修改」。

### 六、用户给出的正确模型（本版本的长期事实）

> 「就是直接读取那个模型配置文件作为当前渠道模型数据，然后修改保存就是直接修改文件。」

拆成三条可执行原则：

| # | 原则 | 含义 |
| --- | --- | --- |
| 1 | **唯一事实源是 config.json** | 打开页面 = 读它；显示的渠道/模型/选择 = 文件里有什么就是什么 |
| 2 | **修改即改内存，保存即写回文件** | 中间没有「发现清单」「核对」「基准比对」这些层 |
| 3 | **不做「我猜你可能错了」的判断** | 判断不了的事不做拦截、不标灰、不弹确认 |

### 七、要删的（本轮范围）

| 对象 | 说明 |
| --- | --- |
| `model_unverified` 拦截 | `runtime.rs:1085` 那条 `return Err`，用 `discovered` 否定用户选择 |
| `discovered` 作为权威 | 改为直接来自 config.json 的 `models`；不再依赖「上次获取模型清单」的残留 |
| `changedTargets` 的原始 JSON 比较 | 改用 `canonicalPolicy`，与 `channelDirty` 同一判据 |

**保留**（拦的是我自己的编码错误，不是用户配置）：

- `model_identity_collision`：两条不同来源算出同一个 slug，是我的 bug，必须拦。
- `model_identity`（官方模型缺少路由身份）：官方数据形状异常。
- `known` / `source_rows`：仍用于生成路由 slug（`provider/model`），**只是不再用来拒绝用户的选择**。
