## WP-89跟进：安装路径可推进，但可读展示仍未收口

状态：显示遗漏已在修复分支 `0ca7689b` 完成原生验证；历史 npm_failed/退出码1的具体根因仍未确认，详见文末。以下保留修复前取证：用户反馈发生于0.2.17发布后，但截图没有关于页版本号，不把截图当作精确安装版本证明。

### 本次事实

- 安装向导第一步仍直接显示Windows扩展路径前缀，并混用Windows反斜杠和runtime/opencodex中的正斜杠。
- 截图中“下一步”呈可用样式，旧的红色路径校验错误没有出现。这支持“第一步词法阻断已改变”，不支持“用户机器完整安装已成功”或“点击下一步后仍失败”。
- 用户最初提出的是默认路径问题。上一轮已修合法路径被误判和后端安装身份，但漏了原清单要求的显示、默认预填、恢复默认一致；不能继续以“全部解决”概括。

### 发布源码原因

以v0.2.17/d7c7978f0核对：

1. apps/desktop/tauri/src/commands/runtime.rs:156～160将managed/default prefix直接to_string_lossy输出；数据根canonicalize保留Windows扩展路径形式。
2. apps/desktop/tauri/src/modules/runtime/mod.rs:32的相对路径常量为runtime/opencodex；与原生Windows根拼接后可在字符串层产生混用分隔符。
3. apps/desktop/ui/src/routes/SettingsRoute.vue:829～842的默认预填、恢复默认没有可读显示转换；目录选择同样直接使用原始返回值。
4. 后端runtime/paths.rs只在安装准入时规范存储路径，不会反向修正输入框。
5. test/smoke/windows-install-ui.mjs:14/18要求输入框等于原始DTO；只检查可推进，没有检查可读显示。这是验收遗漏，原绿灯不能覆盖该需求。

### 后续修复边界

- 默认预填、恢复默认、目录选择统一采用保持原目录身份的可读Windows路径展示，常规本地目录统一反斜杠；不能直接对任意设备命名空间删前缀。
- 保持实际保存/安装目标、历史自定义位置、长路径与UNC语义；不为显示修复搬移数据根或要求用户清空配置。
- 单独检查“显示正确”与“原生安装成功”，覆盖后端真实返回值、常规/扩展盘符及UNC、受保护/设备/点段拒绝。修正把原样显示作为正确条件的测试。
- 用户已补充实际安装失败提示；其具体根因仍需原始npm输出，不能将路径展示遗漏直接外推成npm失败原因。

用户明确给出的Windows路径格式：

### WP95跟进：真实npm错误详情被最终提示丢弃

已从v0.2.17发布源码确认的错误信息缺陷：

1. runtime/install.rs的SystemNpmRunner对pack/install均收集脱敏后的末尾输出，并用npm_reason写入NpmFailed.detail。
2. InstallError::message匹配NpmFailed时忽略detail，仅返回退出码；转换为AppError再序列化后，原npm错误没有出现在最终失败提示中。
3. pack和install共用NpmFailed；最终一律叫“npm安装”，不能由该文案分辨下载打包还是安装阶段。
4. 界面又原样展示AppError中的内部英文分类串，既不可操作，也使用户无法根据摘要判断原因。执行中联网向导的输出区会显示进度行；补充截图与源码复核确认，失败后该区被隐藏，不能让用户继续从该区取得npm错误。内存仅保留最后400行，重新安装会清空前次输出。

此项并入WP95安装失败可诊断性，不声称已证明npm失败是路径、网络、权限或Node版本造成；退出码1仅说明npm命令失败。后续修复应保留脱敏原因、实际命令阶段及可追溯日志位置，沿现有错误/通知样式，不新增另一套界面。

待补证据：本次失败前的npm error/ERR错误段及所报npm日志路径；联网/离线与所选官方版本在原输出可见时一并核对。本次仅分析/记录，软件未修复、未发布下一版本。

### WP95补充：失败隐藏输出并误显示离线步骤（2026-10-28）

用户提供第4步失败截图：泛化npm_failed/退出码1、三项全未完成的“校验离线包／展开到私有前缀并链接bin／校验并切换运行来源”，没有npm输出区。“允许安装脚本并重试”置灰；此错误并非scripts_required，不能以授权脚本作为解决出口。

已核对真实源码并运行现有presentation模块：phaseShowsCommandLine在installing返回true，在failed返回false；offlineSteps(failed)返回三项pending。SettingsRoute.vue的showInstallCommandLine要求联网来源且处于downloading/installing，模板v-else无条件显示offlineStepList，导致联网失败也呈现离线列表。因此截图上的“离线包”不能证明用户选了离线安装，也不能据此断言是离线缓存缺失。

当前确认两处串联的信息缺陷：后端最终提示/历史丢弃NpmFailed.detail；前端失败阶段隐藏现存输出并切到错误来源步骤，且全pending丢失到达阶段。用户无法从该画面提供被要求的npm错误详情，上一轮“请从窗口取日志”的指导需纠正。

具体npm失败根因仍未取得原始stderr，不能断言是路径/网络/权限。命令创建SystemNpmRunner时明确设置缓存到当前数据根/cache/npm，原npm调试日志通常位于其_logs目录。按用户默认数据根对应D盘Software目录，可检查data/cache/npm/_logs的最新npm日志；不使用日常用户默认npm缓存位置猜测此次记录。

后续修复同归WP95：失败/完成时仍保留本次已脱敏输出或沿现有样式提供可访问的错误详情；步骤按真实安装来源和最后到达阶段展示，不能在联网失败时兜底成离线列表。需覆盖registry/offline × success/failure与关键阶段失败的UI回归。路径可读显示仍归WP89；本次只有分析记录，无软件开发或新发布。

### WP95取证补充：退出码1日志筛选无匹配

用户按给定只读PowerShell脚本筛选后返回“未找到退出码为1的日志”。这只证明所给目录下当前文件没有匹配该行格式，不证明npm未启动、日志从未生成或具体根因属于路径/网络/Node版本。

源码进一步核对：SystemNpmRunner在Windows启动npm可执行入口（通常为npm.cmd）；若OS启动失败则映射filesystem，本次npm_failed/exit1表示已启动的调用进程返回1，仍可能发生在包装入口/命令解释器阶段，不一定到达npm内部生成日志阶段。元数据查询的current_dir是用户HOME，pack/install在私有临时目录；成功view并不等于相同工作目录/参数下的安装调用成功。其他缓存位置、日志保留/轮换及输出格式也未实测，不能从无匹配排除。

当前根因继续未知；已确认的缺陷仍是错误detail被丢弃、失败输出隐藏及来源步骤误显示。后续修复应保留脱敏stdout/stderr，并关联实际命令阶段、可执行入口、工作目录和本次日志位置，再以用户Node22.20.0/npm10.9.3及自定义Node目录环境复现。不要继续要求用户按同一条件翻不存在的日志、循环重装或先清空配置/升级Node/删除缓存来试错。[负面筛选结果及源检查](../../../../.adg/evidence/0.2.17-issues/install-failure-presentation/no-matching-failure-log.json)。

## Windows 原生接手修复与验证（2026-10-28）

代码基线为远端最新 main `65581b589c8b210049e96022ce58603350450426`，修复分支 `feature/0.2.17-windows-install-diagnostics`，提交 `0ca7689b85ce4eeb01aa0a212a86920dd490b3a4`。治理事实和证据仅写 `docs/governance-main`。本轮沿 WP89/WP95 补漏，没有新增发布、修改历史 tag 或替换日常安装。

### 原始故障与本轮实测必须分开

- 本机已安装 EXE 的启动日志证明版本 0.2.17、提交 `d7c7978f043278baae8f2fc8c2119315a4660f12`。来源记录的两次历史失败发生于北京时间 2026-10-28 16:44:36、17:18:37，均只有退出码 1；它们的原始 stdout/stderr 已无法从历史记录回取，具体根因仍未确认。
- 原有 `08_36_25_876Z` npm 日志确实只是成功的 `npm view`，已保留原文件。直接读取原应用进程的允许环境字段和工作目录，没有读取任意凭据环境；该进程的临时目录为 `C:\Users\15119\AppData\Local\Temp\2`。
- 本机实际发现的是 NVMD `npm.exe`，不是最初怀疑的 `npm.cmd`；实测 Node 22.12.0 / npm 10.9.0，与先前用户贴出的 22.20.0 / 10.9.3 是不同环境事实。按当前真实入口、完整参数、受控环境和含空格目录执行 pack/install 均成功；补齐原进程 TEMP 与无窗口标志后 pack 仍成功。
- 独立对照确认扩展格式 `\\?\C:\...\npm.cmd` 会使命令解释器直接退出 1，OEM 936 stderr 为“系统找不到指定的路径。”；普通入口成功。此项是已实证的批处理边界缺陷，不能用来冒认上述两次 NVMD npm.exe 历史失败的根因。

所有当前命令的程序、argv、工作目录、受控环境、stdout/stderr 和退出码均已归档。没有据此要求清空配置、移走合法空格、删除原 npm 缓存或升级用户 Node。

### 已确认原因与修改

1. WP89 显示遗漏：默认预填、恢复默认和目录选择之前直接使用后端内部路径。现统一转换为同一普通 Windows 目录身份的可读形式，统一反斜杠，保留合法空格。设备、异常目录段和可能需要扩展语义的长路径不盲目删前缀；不改变数据根或历史自定义位置。
2. WP95 错误详情丢失：`InstallError::message` 忽略 `NpmFailed.detail`；现把真实 npm 阶段、脱敏原因及命令日志位置带入错误、历史和 IPC。前端只去除内部英文错误封套，稳定原因码继续用于安装脚本授权判断。
3. Windows 输出丢失：原 `BufRead::lines()` 遇非 UTF-8 行即退出。现按字节读行，优先 UTF-8，Windows 原生错误按系统 OEM 解码，并保留后续行；读取失败也有明确记录。实际命令日志按 stdout/stderr 标记，记录退出码，输出先脱敏；界面进度本身仍只在内存。
4. 命令入口：仅在 npm 外部命令边界使用 `dunce::simplified` 安全简化入口及受控 PATH，不修改存储身份；覆盖规范化扩展 `.cmd` 的真实执行回归。
5. 失败展示：联网输出持续保留到核验、失败和完成，不再用离线步骤作兜底。离线按最后实际到达阶段保留已完成/失败/待处理步骤，并沿既有详情样式访问本次输出。完整命令日志保存在数据根 `logs/runtime-install/`，不再依赖向导最多 400 行或 npm 自身是否已生成调试日志。
6. 恢复入口：原“完成”按钮可在来源刷新结束前关闭向导，立即重开会撞上安装中的保护。现等待实际安装和来源刷新全部完成后才启用，未扩大安装脚本授权条件。

向导步骤、按钮、命令输出区、详情与错误样式沿现行原型；未新增第二套通知或配置重置流程。
