# 通用自动配置迁移机制

维护 ID：MNT-OPENCODEX-DESKTOP-20261004-02。分析日期：2026-10-04。承接用户提出的“后续版本发布后，配置文件转换作为通用自动功能”。用户于2026-10-04随配置规划确认本机制，并要求后续README说明。**方案已确认，尚未实施；本次不执行真实配置转换，0.1.2范围未冻结。**

## 1. 设计结论

可以建立通用的 `ConfigMigrationService`，随应用发布，在新版本首次读取旧配置时自动转换。之后每个版本只需登记新增格式的转换规则、兼容范围和测试样例，复用识别、锁、备份、校验、提交、恢复与诊断机制。

“通用自动”是引擎自动执行已发布、已验证的规则。字段改名、枚举拆分和语义变化仍须由开发者明确描述；引擎不能猜测任意新旧JSON之间的含义。转换规则嵌入应用，不运行从网络或用户配置下载的脚本。

常规、无损、保留选择的格式转换默认自动执行，无需每次弹窗。涉及信息丢失、新的产品选择、数据根搬迁、外部程序写入、密钥替换或重加密时，返回需要专门处理的结果，不把它伪装成普通格式转换。本次用户确认的是能力规划，当前没有运行迁移。

## 3. 三种版本分别管理

| 版本 | 含义 | 变更原则 |
|---|---|---|
| 应用版本 | 例如0.1.2、0.2.0 | 软件发布，不要求配置随之升级 |
| 配置schema版本 | 某一类文档的字段、类型与语义契约 | 只在格式/语义变化时提升；每类文档独立登记 |
| 默认配置版本 | 随应用嵌入的默认策略版本 | 可与schema独立变更；用户显式选择不被新默认覆盖 |

`preferences / runtime-overrides / sync-endpoints`等按文档种类登记版本与适配器；没有改变格式的文档不强制加字段或重写。`data-root`保持自己的结构版本与定位兼容流程；运行缓存如可重建，由其模块声明，不能通用地当作偏好重置。

无schema文件仅在匹配已支持的旧文档形状后识别为legacy v0。已声明schema的文件若版本不是合法整数、类型错误或太新，显式拒绝。迁移链按已发布版本执行，如`vN → vN+1 → … → 当前`；支持跳过应用版本升级。上一份方案的schema=2仍为拟议编号，不在这里凭空定义v1历史格式。

每一步使用对应版本的旧模型/校验和历史默认规则，最后才转换成当前类型；不能先用新结构反序列化而丢掉旧字段。新增字段补值由步骤指定。旧文件保存了整份默认值时，通常无法区分用户主动选择与当年默认，首次转换保留原有有效值，不擅自采用新默认重置。

## 4. 通用引擎与专用规则的边界

建议在Rust新增独立配置迁移模块（拟议位置`modules/config_migration/`），由ConfigService使用。每种文档登记：`document_kind / current_schema / minimum_supported_schema / legacy_detector / migration_steps / validators / writable_path_policy`。

每个步骤具有稳定ID、from/to版本、适用条件、转换函数、输入/输出校验与变更说明。转换函数只处理内存数据，不访问网络、执行npm、操作Keychain或自行写文件。确需主题历史等外部输入时，由专门适配器显式提供，不能藏在通用函数里。

统一的执行结果至少包含：`Current / Migrated / NeedsInput / UnsupportedFuture / Invalid / Failed`，以及受影响文档、旧新schema、步骤ID和脱敏错误。`prepare`返回候选数据与变更计划，`commit`在锁内执行备份和持久化。当前schema且校验成功时直接读取，不重写文件、不重复生成备份。

普通保存、恢复默认、CLI读写、启动读取、导入和同步都经过统一版本识别与语义校验；各自现有授权、目标保护和业务事务仍由调用方承担。

## 5. 何时自动触发

| 入口 | 流程 |
|---|---|
| 新版本首次启动 | 沿现有方式定位数据根 → 读取bootstrap兼容信息 → 检查未完成迁移 → 转换该版本需要的配置 → 发布有效配置 → 启动依赖它的后台服务 |
| 后续启动 | 当前schema只校验读取；无变化不写盘 |
| 首次通过CLI访问 | 复用同一服务和锁，避免GUI未开时旧配置绕过转换 |
| 导入旧容器 | 先完成容器认证/解密/解析与章节适配 → 内存转换和预览 → 经既有导入确认/目标备份事务提交 |
| 同步接收旧配置 | 先验完整性、来源版本与能力 → 转换允许同步的投影 → 依既有冲突决策应用；转换成功不等于自动同意远端覆盖 |
| 主题旧localStorage | 后端无法自行读取；UI提供一次性历史值。缺输入时标记该步骤待处理，不用默认theme提前落盘而盖掉旧选择 |

启动时，读取偏好的自动清理、同步、更新调度等必须等待所依赖的迁移完成。失败时保留修复界面/诊断入口，禁止相关写入和后台动作；若本机定位损坏则不能继续猜测数据根。可独立的模块是否继续运行由依赖关系决定，不统统以默认值代替失败配置。

## 6. 持久化、备份与中断恢复

普通单文件迁移按以下顺序执行：

1. 获取目标跨进程锁，在锁内读取原始字节、版本与摘要；检查所有写入口是否遵守同一锁。保存请求的revision检查也在此完成。
2. 在内存跑完整迁移链并逐步校验，得到确定候选。非法数据、步骤缺失、过新版本或需要用户裁决时，在改写原文件前停止。
3. 为实际要变更的文件持久化原件备份、摘要和prepared记录；任何备份/记录失败都不替换目标。备份为原始字节，使用原配置同级保护，Unix0600及平台目录/权限策略，不记录密码内容到日志。
4. 通过同目录临时文件及原子替换提交；需要文件和目录持久化的行为按平台核验。schema只有随成功提交才更新，不能先写“已迁移”标记。
5. 核验已提交内容并登记committed，然后向消费者发布新配置。配置提交与后台业务应用是两个状态；应用失败不静默切换默认值或盲目回滚已经生效的文件。
6. 重启发现prepared但无committed时，核对目标摘要：等于旧摘要则可重新准备/提交，等于候选摘要则补完成记录；两者都不等则视为外部变更，保留文件和证据，停止自动恢复。不得只凭日志阶段覆盖目标。

建议迁移原件和记录置于`<数据根>/manager-state/config-migrations/<document_kind>/<transaction_id>/`，在既有backup之前可独立工作。恢复所需原件不纳入“最近N份/30天”的普通业务备份清理，未完成事务不能清理；已完成备份按独立恢复窗口管理，窗口值实施时定稿。bootstrap自身的备份必须放在无需读取其候选内容也能定位的原位置。

原子替换只保护一个文件。首阶段优先独立转换，文件之间没有依赖就各自提交；若新格式要求多个文件必须同时改变，须新增明确的事务清单、固定锁顺序和启动恢复屏障，不能连续调用rename后声称整体原子。本次不会顺带拆runtime/data-root或搬迁数据目录。

## 7. 默认值与用户选择

- 配置中的显式值优先保留；字段改名和结构分组只改变表达方式。
- 缺失字段才按对应转换步骤补值；已有合法false、0等值不能被当作缺失。
- 含义变化、删除旧能力或新增决策必须有明确步骤，退役数据依分层方案进入兼容区，不能重新激活。
- 未知字段由各版本契约决定保留或拒绝，不任意丢弃后保存。无效值报错并保留原件，不把损坏当首次安装。
- 变更默认策略本身不强制迁移用户文件。若未来存储“继承默认/明确覆盖”，需要显式契约；历史扁平文件不能推断这种区别。

当前旧更新值到三字段的映射、30字段去向以及主题来源仍以[配置分层规划§4/§7](02-配置分层规划建议.md#7-迁移导入导出与同步兼容)为准。容器外层格式版本、偏好章节schema与同步能力版本分别处理，单机转换不能替代跨客户端版本协商。

## 8. 降级与恢复

新迁移器不自动把新配置转回旧结构。遇到比当前应用支持的schema更高的文件，未来加入此机制的所有读写入口须返回UnsupportedFuture，禁止保存、同步上传、启动清理等产生改写；用户可改用兼容新版，或显式恢复与目标版本匹配的迁移前备份。恢复会放弃迁移后的更改，必须让用户知情。

已经发布、没有未来版本检查的旧二进制无法被新JSON“教会”保护自己。因此需明确最早兼容/可降级版本，并让后续安装/更新入口拦截不支持的降级；用户直接运行旧二进制仍不能依靠新引擎保障。应先引入版本检查，再发布依赖它的新存储布局，保留恢复用旧字节与发行说明。

备份恢复、目录迁移、密钥轮换和不可逆转换仍走各自受控流程；不纳入默认无提示的格式升级。

## 9. 每次发布的交付规则与验收

开发者改变配置格式时，提交新契约、迁移步骤、兼容表、历史fixture和说明；没有格式变化就不增加迁移步骤。构建检查每个声明支持的旧schema到当前schema均有完整路径，避免一个中间版本漏登记导致跳版本失败。

| 验收场景 | 预期 |
|---|---|
| 当前schema重复启动 | 内容与mtime不变，无新备份 |
| 无schema旧文件、缺字段 | 识别已知legacy格式，保留已有选择，按步骤补值 |
| 跨多个应用版本升级 | 从每个支持的旧schema执行完整链，结果与规则一致 |
| 配置损坏、非法枚举/版本、未来schema | 原字节不变，明确错误，不静默重置 |
| GUI/CLI/同步并发 | 使用同一锁/revision，不丢另一方写入 |
| 备份失败、写盘失败、提交前后崩溃 | 原件或完整候选可识别恢复，不出现半文件或重复副作用 |
| 更改默认值 | 已保存用户值保持；继承规则仅作用于明确缺失/继承项 |
| 旧容器、新旧同步客户端、降级 | 版本边界明确，不能让旧writer悄悄覆盖新字段 |
| macOS/Windows持久化 | 核验权限、替换及崩溃恢复，不以Unix测试替代Windows行为 |
| localStorage主题、退役字段、固定备份保护 | 正确衔接来源和既有语义，不因迁移恢复旧开关 |
| 测试与日常环境隔离 | 沙箱独立启动定位/存储/凭据/IPC/同步目标；迁移副本与中断恢复不改动模拟日常根，错误环境不回退 |

## 10. 与现有阶段的关系

建议把通用迁移服务列为独立候选U-09。A/B阶段可以先补版本识别与未来版本拒绝、搭建纯转换注册接口，同时保持扁平存储；C阶段首次改变磁盘布局时，自动迁移链、容器适配与同步兼容必须同时交付。后续版本复用引擎和验收门禁，不再为每次发布另写一次性修复脚本。

这是一项通用产品能力，可跨后续版本持续使用；是否完整纳入0.1.2、最早支持的schema/应用范围及备份恢复窗口仍在候选记录评审，不能把设计登记当作已实现。

配置格式自动转换交付时，须同步更新根 `README.md` 与 `README.en.md`，解释触发时机、备份/恢复、失败与未来版本保护、降级范围，并与容器导入导出区分。此要求已登记为U-10，验收内容见[分层规划§9](02-配置分层规划建议.md#9-readme-配置说明交付要求已确认)。


## 11. 自动转换的测试隔离

当前完整应用没有自动区分开发/测试数据根，不能在日常用户目录验证新schema。转换服务的测试使用独立fixture/临时根，集成冒烟须先完成[配置规划§10的沙箱要求](02-配置分层规划建议.md#10-配置测试隔离与正式升级)。只备份同一日常目录并不能阻止测试影响正在使用的配置。

沙箱中迁移的是测试副本；日常安装正式升级才按发布规则迁移其配置。beta更新通道与沙箱身份独立，选择beta不是隔离保证。后续README说明须包含这一边界。
