## S22-POST-01：保存时间未知与首次同步边界

### 发现证据

[用户原始截图](../../../../.adg/evidence/0.2.22/post-release-20261106/reported-sync-save-time/windows-sync-unknown-save-time.png)，字节摘要及静态复核见[证据记录](../../../../.adg/evidence/0.2.22/post-release-20261106/reported-sync-save-time/reported-evidence.json)。截图未展示实际软件版本/构建；按本轮发布后反馈登记0.2.22，不把截图当作已证明安装了该精确包。

### 已核对的触发规则

当前发行v0.2.22的sync_state.rs::compare_content不以“是否同步过”、上次同步记录或设备安装时间判断方向。顺序为：

| 所选内容状态 | 当前行为 |
| --- | --- |
| 云端无快照，本机有内容 | 上传，不因缺少历史同步记录被阻止。 |
| 本机所选内容确实为空，云端有所选内容 | 下载，先于保存时间判断。 |
| 所选内容完全相同 | 无需更新，不要求凭保存时间区分先后。 |
| 两端所选内容均非空且不同，两端时间可靠 | 按可靠内容保存时间选择上传/下载；同刻异内容另行阻止。 |
| 两端所选内容均非空且不同，任一侧时间不可靠 | 无法判定，禁止本次更新；本截图为两侧都未知的表现。 |

因此：不是仅历史版本会出现，也不是所有从未同步过的设备都会出现。新装设备若已带默认项、扫描已有客户端配置、导入对象或其它所选内容，只要这些内容缺少与当前摘要匹配的可靠保存凭据，也可能触发；“新安装软件”不等于“本机所选内容为空”。已经同步过的设备，若随后外部编辑/范围变化等使凭据不再覆盖当前所选内容，也可能触发。

file_objects.rs::object_fact要求所选原子全部具有匹配且可信的保存时间；任一未覆盖对象可使汇总时间变成“—”。content_versions.rs::observe对缺失/摘要不符的凭据给unknown；读取、升级、打包、同步操作时间不认证业务保存时间，无变化保存也不会补时间。因此不能建议单纯反复同步、重新安装或点一次无变化保存来保证消除本提示，也不能把第一次上传时间当作可靠内容时间。

### 尚待确认与后续边界

截图与静态代码尚不能确定该Windows设备的所选对象、是否含默认偏好/扫描存量/扩展资源、两端快照及具体缺失凭据。不能据此宣称已复现用户现场或确定是旧包兼容问题。

### 2026-11-06 用户确认：name对应实际渠道

用户明确：“name本身就应该对到实际渠道上”。作为S22-POST-02修复合同采用：name是用户面对的统一渠道名称，不能仅作为管理器布局别名；用户保存改名时，应同步落实到实际OpenCodex渠道配置及相关运行引用，经过读回、服务重载与目录刷新后，使Codex采用相应的新渠道名称。不能只显示“名称保存成功”而实际仍沿用旧渠道身份。稳定管理UUID继续负责对象关联，不作为用户需要维护的第二个名字，也不重新引入运行标识必填字段。

必须覆盖已存在name=Krill、实际provider键=Krill-1的状态：明确保存时应识别并处理该不一致，不能以输入文字未变跳过。普通可用名称Krill的结果应为实际providers.Krill及Codex的Krill/模型标识，相关引用通过既有事务更新；不靠直接修改生成目录或整文件字符串替换。名称唯一性继续校验。中文、空格或保留词名称仍需兼容合法内部键，并保证名称与实际渠道有明确映射及Codex可见效果；不能把所有名称机械写作不合法provider键，也不能将内部键出现在选择器当作名称生效。此类显示映射的技术方案仍待验证，不以本合同宣称已实现。

### 2026-11-06 名称与旧运行标识字段专项验证

用户判断：原先独立的标识字段可能才决定Codex的实际渠道名，当前改名仅改变显示层，应联动修改实际配置。已验证该判断的关键字段语义，但不能概括为0.2.22所有改名都不写实际配置。

| 字段 | 用途 | 单独修改能否改变普通自定义渠道的Codex模型前缀 |
| --- | --- | --- |
| 管理器channel.id | 稳定管理身份，关联草稿、采用和本机状态。 | 否，不能把它当作渠道名改。 |
| 管理器channel.label / OpenCodex providers[key].name | 显示名称；管理器读取时会优先采用已有布局label。 | 否，普通路由模型名称不是只读这个name。 |
| channel.connection.providerId / OpenCodex config.json的providers对象键 | 真实运行路由身份；旧“运行渠道标识”对应此层。 | 是，本例模型slug由该键与模型ID生成。 |

从已采用维护归档2.97.0-post021.ownerquery.2验证SHA256后提取实际slug-codec.ts与catalog/derive-entry.ts函数，以TypeScript转译执行：provider键Krill-1而name=Krill时仍得到Krill-1/gpt-6.1-sol；provider键改为Krill后得到Krill/gpt-6.1-sol。这里核对普通自定义渠道，不外推原生保留渠道、专门别名或模型显示覆写。实际业务源是当前OpenCodex HOME的config.json；其生成目录再供Codex使用，不应只手改Codex缓存目录或把Codex原生配置的某个name字段当作全部事实源。

当前管理器renameChannelLabel已对新的Krill-1→Krill同时分配providerId=Krill；后端provider_renames/apply_renames会移动实际providers键、改已存在的name并迁移默认渠道、型号选择/禁用和发现引用，保存事务还处理所属凭据与当前选择。真实临时目录保存/读回测试通过，因此正常新改名的迁移机制已存在。

确认的条件缺口：已有布局label=Krill、providerId=Krill-1时，再输入Krill会在channelRename.ts:15直接返回；即使先改临时名称再改回Krill，:18会恢复saved.providerId=Krill-1。后端看到providerId没变也跳过迁移；仅看管理器名字“已保存”不能证明真实运行身份改变。此路径用实际前端模块已复现，尚未读取用户现场来确认是否就是本次原因。

建议后续修复按用户的“名称联动实际配置”目标处理：在明确保存当前渠道时核对最终名称与实际运行身份，补齐这种已有显示名/运行键分离的路径，不能只依赖输入文字发生变化；继续通过既有事务迁移真实键和受影响引用，读回后再完成服务重载/目录刷新及客户端生效验证。无需重新暴露运行标识输入框，不通过全文件字符串替换或直接写生成目录修复。中文/空格/保留词名称当前会分配channel-内部键，这类合法名称不能用简单providerId必须等于label判断；若要求这类名称在Codex也逐字一致，需要另核对显示映射方案，不能以普通Krill用例通过替代。

### 2026-11-06 较早方案：发布确认读文件、后续写入仍用ETag（已由下节替代）

用户建议“回读不好做，可以再查文件确认就好了”。技术核对表明方向可行，但“查文件”需要核对当前生效指向和本次载荷内容，不能仅凭目录中存在某个文件、名称/大小/mtime相同就宣称同步成功。当前上传本身已GET并逐字节核对配置载荷，之后才条件发布config-v1-latest.json；报错处confirm_publication又复用pointer_for，而pointer_for在解析有效指针后强制要求强ETag，导致“已经读取到匹配的最新文件内容但缺强ETag”也无法确认。此为代码上确定的耦合，不证明现场读回失败一定由ETag导致。
