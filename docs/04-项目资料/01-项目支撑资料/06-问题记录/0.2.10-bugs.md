## WP-68：已确认重启后仍被「已有保存计划待核对」挡住（死锁）

**优先级**：P0（客户端核对流程完全无法完成）
**位置**：模型 → 渠道模型 → 状态框 → 核对 Codex 客户端加载 → 我已重启，重新检查
**用户原话**：「为什么我已经确认重启了，还是『已有保存计划待核对，请先核对原计划或撤回其未完成写入』？」
**状态**：已定位（2026-10-26）

### 现象

用户已按提示重启 Codex、点「我已重启，重新检查」，弹窗里出现红字：

> 已有保存计划待核对，请先核对原计划或撤回其未完成写入

同时状态框显示「保存结果待核对 · 上次保存待重启」。此时弹窗内只有「稍后」「我已重启，重新检查」两个按钮——**没有「核对原计划」也没有「撤回」**，用户被卡死，无路可走。

### 根因：两个计划互相挡路，而只有一个能被看到

`client_state::check()` 的第一行（`client_state.rs:152-153`）：

```rust
let _guard = runtime::execution_lock(root)?;
runtime::reject_incomplete(root)?;      // ← 先扫全库，任何未完计划都直接报错
let plan = target(root)?.ok_or_else(...)?;  // ← 之后才判断「我这次要核对谁」
```

`reject_incomplete()`（`runtime.rs:519-530`）遍历**所有** plan，只要有一个 phase 不在 `prepared / committed / compensated` 里就整体报错。

而死锁是这样形成的：

| 步 | 发生了什么 |
| --- | --- |
| 1 | 某次保存进入 `verified_partial`（写入后核对发现部分不符），计划留在磁盘上等核对 |
| 2 | 用户按提示重启客户端，点「重新检查」 |
| 3 | `check()` 先执行 `reject_incomplete()`，扫到那个 `verified_partial` 计划 → 报「已有保存计划待核对」 |
| 4 | 用户想「核对该计划」，但**页面上没有入口**——`latest()` 只返回最新一个计划；若该计划不是最新（或已被后续保存覆盖），前端根本拿不到它 |
| 5 | 用户想「撤回」，同样需要先打开该计划才能看到「撤回本次未完成写入」按钮 |

**即：报错要求用户处理一个界面无法访问的对象。**

### 为什么「确认重启」这一步一定失败

这条错误与重启无关。`reject_incomplete` 检查的是**磁盘上的计划状态**，不是运行目录是否已加载；用户重启一百次，只要那个 `verified_partial` 计划还在，`check()` 就在第一步被拒。

### 三处设计缺口

| # | 缺口 | 证据 |
| --- | --- | --- |
| 1 | `check()` 的拒绝顺序错：先全库拒绝，后判断目标。应当先定位本次目标，只拒绝**与目标冲突**的计划 | `client_state.rs:152-156` |
| 2 | 前端只能看到「最新一个」计划：`latest()` 过滤后只返回 max(createdAt)，其余未完成计划成为不可达对象 | `runtime.rs:435-449` + `ChannelsView.vue:94` |
| 3 | 错误信息把「处理入口」写进文案（「请先核对原计划或撤回」），但没有对应的可达入口 | `runtime.rs:528` |

### 修法（未实施，待确认）

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A** | `check()` 改为「先定位 target，再只校验该 target 自身是否可核对」；其它未完计划不阻塞客户端核对（它们与运行目录是否加载无关） | 最小改动，直接解死锁。需确认：不阻塞是否会漏掉真正的写入冲突 |
| **B** | `latest()` 之外增加「未完成计划列表」接口，页面提供核对 / 撤回入口 | 改动大，但让错误信息变得可执行 |
| **C** | A + B 都做：先解死锁（A），再补入口（B） | 彻底，工作量最大 |

倾向 **A 先行**（它是 P0 死锁），B 作为可用性补强。

### 边界

- 未复现到具体的 `verified_partial` 生成路径（需要用户机器上的 plan 文件确认 phase 与 created_at）。
- 未验证：该残留计划是否与「上次保存待重启」是同一个对象（状态框同时显示两者，可能是两个计划）。
- 本轮只做诊断，未改代码。

## WP-68 补充（2026-10-26）：这是 0.2.10 引入的回归，不是历史残留

用户提出「这是不是历史版本问题，清空配置文件重开就行」。核对后结论：**清空能解，但把一个本可修的死锁变成了用户自己承担的代价**，而且死锁有一半是我在 0.2.10 引入的。

### 用户机器上的实际数据

`~/Library/Application Support/com.gzers.opencodex.desktop/manager-state/model-save-plans/` 共 7 个计划：

| plan | phase | 创建时间 | 是否挡路 |
| --- | --- | --- | --- |
| `9697b33c…` | **`verified_partial`** | 2026-10-25 08:04 | ⛔ **就是它** |
| `622a2015…` | `committed` | 10-24 | 否 |
| `c7f0c889…` | `committed` | 10-23 | 否 |
| `d7bdabc5…` | `committed` | 10-23 | 否 |
| `738286fb…` / `ce151db2…` | `compensated` | 10-23 | 否 |
| `49aa8dc5…` / `62a4491b…` / `bb9b5bca…` | `prepared` | 10-23 | 否 |

只有 `9697b33c` 一条 `verified_partial`（error=`provider_write`）在挡路；其余按 `reject_incomplete` 的白名单都合法。

### 两个独立缺口，而第二个是 0.2.10 引入的

| # | 缺口 | 引入版本 | 说明 |
| --- | --- | --- | --- |
| 1（后端） | `check()` 先`sweep`全库、后定位目标，导致「处理不了的计划挡住能处理的」 | 早期 | `client_state.rs:152-156` |
| 2（前端） | **「保存结果」弹窗失去页面入口** | **0.2.10** | 0.2.9 有「查看原保存结果」按钮；我按提案 §4.1 删掉后，只剩通知能进 |

缺口 2 是我的判断失误：当时核实过「通知中心能打开保存结果」，但没核实**没有通知时**还能不能进。实际只有 `policyNotificationTarget` 一处会置 `saveOpen=true`（`ChannelsView.vue:99`），而它只由通知点击触发。于是：

- 状态框显示「保存结果待核对」→ 用户想知道哪里核对 → 点开客户端核对弹窗 → 报「请先核对原计划」→ **但页面上没有任何通往原计划的路径**。
- 这正是 WP-68 描述的「要求用户处理一个界面无法访问的对象」，0.2.10 把可达性也一并拿掉了。

### 清空配置文件行不行

| 项 | 结论 |
| --- | --- |
| 能解开死锁吗 | **能**。删掉 `model-save-plans/9697b33c…json` 即可；或删整个 `manager-state/` 目录。 |
| 会不会丢渠道模型配置 | **不会**。真正的配置在 `opencodex-home/`（官方 `config.toml` 等），`manager-state/` 是管理器自己的状态（计划、历史、偏好）。 |
| 代价 | 丢失 7 条保存历史与恢复基线（含两次 `compensated` 的补偿记录），但当前运行配置不受影响。 |
| 是否该由用户承担 | **不该**。一条 `verified_partial` 让整个客户端核对不可用，且无 UI 出口，这是产品缺陷。 |

**最小操作**（若只想立刻解）：删除单个文件

```
rm "~/Library/Application Support/com.gzers.opencodex.desktop/manager-state/model-save-plans/9697b33c-724e-44d7-bd36-1199f38d6305.json"
```

不要删 `opencodex-home/`（1.2G，是官方运行配置与模型清单）。
