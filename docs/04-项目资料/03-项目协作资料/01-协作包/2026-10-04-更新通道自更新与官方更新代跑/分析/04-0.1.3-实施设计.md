# 0.1.3 实施设计（U-01～U-04、C）

维护 ID：MNT-OPENCODEX-DESKTOP-20261004-03。登记日：2026-10-04。承接 [0.1.3-范围与待裁决](02-0.1.3-范围与待裁决.md)；网络代理（U-05/U-05b）设计见 [03](03-网络代理配置与更新通道快捷跳转.md)。本文件给 U-01～U-04 与 C 阶段的具体实施设计，不预写执行结果。

## 1. U-01 桌面自更新真实端点

- 现状：`config/runtime.defaults.json` 的 `updates.desktop.channels.stable/beta` 与 `tauri.conf.json` 的 `endpoints` 都是 `https://updates.example.invalid/...` 占位。
- 目标：改用本仓库 GitHub Releases 的更新清单地址。
  - stable：`https://github.com/gzers/opencodex-desktop/releases/latest/download/latest.json`
  - beta：发布到固定 `beta` tag 的 release，`https://github.com/gzers/opencodex-desktop/releases/download/beta/latest.json`
- `tauri.conf.json` 的 `endpoints` 与 `runtime.defaults.json` 保持单一来源：命令层已从通道解析取端点，配置里不再留两份假地址。
- 依赖：U-02 未完成前，真实端点尚无 `latest.json` 可拉取；U-01 只保证端点结构正确，端到端生效以 U-02 完成为准。

## 2. U-02 签名公钥与 CI 签名制品（发布安全操作，动手前单独确认）

- 生成：`tauri signer generate` 得到公私钥对。
- 公钥：写入 `tauri.conf.json` 的 `pubkey`（编译期常量，不可运行时配置），替换占位串。
- 私钥：写入 GitHub Actions secret `TAURI_SIGNING_PRIVATE_KEY`（配套 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 如设置口令）；不进仓库、不进日志。
- 制品：`tauri.conf.json` 打开 `bundle.createUpdaterArtifacts`；`release.yml` 注入私钥，产出各平台 `.sig` 与 `latest.json` 并随 Release 上传。
- 安全边界：TLS 与签名校验不可关闭；私钥泄露只能换新密钥并随新版本重新分发公钥。
- **单独确认**：生成私钥、写入 CI secret、打开签名产物均需用户单独授权后执行。

## 3. U-03 官方版本卡片只读远端查询

- 现状：`official_project_facts` 只执行本地 `ocx --version`，无远端比较。
- 目标：新增只读远端查询命令（建议 `official_remote_latest`）：
  - 执行 `npm view @bitkyc08/opencodex@latest version` 与 `dist.integrity`（或在可用时读 registry JSON），带超时（沿用 `network_defaults` 超时）与失败不改写本地状态。
  - 与本地/运行版本（`runtime.json` 的 `resolved_version`）比较，返回 `{ local, remote, has_update, integrity }`。
  - 查询（只读）与安装（写）分开；查询不产生副作用，界面显示「有可用更新 / 已是最新」。
- 前端：官方版本卡片新增「远端最新」行与状态；失败时如实标注不可用，不显示假结果。
- 代理：远端查询走统一出站代理（U-05）。

## 4. U-04 复用 install_runtime 代跑官方更新

- 复用：命令层新增「应用官方更新」动作，调用现有 `install_runtime`（`InstallSource::Registry { version, proxy }`，`prefix` = 当前登记前缀）。
- 绑定确定版本：先由 U-03 解析出的确定版本（非浮动 `latest`）作为安装版本；查询与安装共用同一来源策略。
- 安全路径沿用：`npm install --prefix <前缀>`（不落全局）、`.runtime-manifest.json`、离线包、代理、`allow_scripts` 确认、取消、重启提示。
- 不代理官方更新器去改托管前缀；不写全局 npm 前缀。
- 二次确认：安装属写操作，需界面显式确认；完成后按现状提示是否重启托管代理。

## 5. C 阶段配置存储 schema 迁移

- 现状：0.1.2 已建 `config_migration` 引擎（识别/迁移链/未来版本拒绝/备份与原子提交/中断恢复/启动自动迁移），但磁盘仍是扁平偏好文件。
- 目标：偏好磁盘结构升级为分域（appearance / backup / updates / maintenance / extensions / legacy…），schema 版本提升；同步适配容器与同步投影。
- 兼容：
  - 旧扁平文件按 legacy v0 识别，迁移链转换为新结构，保留原件备份。
  - 容器导出：新结构需要新的章节版本；旧枚举无法无损表达的新字段（通道/频率自由组合、theme）声明兼容导出范围。
  - 同步：接收端按 schema 校验并迁移，过新载荷不写入；混合版本客户端显式拒绝。
- 测试：以 0.1.2 的沙箱身份跑，副本迁移；受控「模拟日常根」哨兵在整轮后内容与 mtime 不变。
- 范围提示：C 阶段改动面大，实施分步提交，先引擎与磁盘结构，再容器/同步投影。
