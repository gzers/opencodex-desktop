## WP-40：渠道表操作列被挤出可视区

**优先级**：P1
**位置**：模型 → 渠道模型 → 渠道列表「操作」列
**用户原话**：“渠道列太宽，导致操作列超出软件宽度了。”
**状态**：已按原型定案，未实施

### 实测（生产样式隔离页：1:1 拷贝 tokens.css / base.css 与组件 scoped 样式）

| 项 | 实测值 |
| --- | --- |
| 操作列声明宽度 | 200px |
| 该列可用宽度 | 184px（td 两侧各 8px 内距） |
| 按钮组自然宽度 | **299px** |
| 被裁掉 | **107px** |
| 各列实际宽度 | 36 / 296（弹性）/ 190 / 76 / 76 / 200 |
| 容器 758px 时的横向溢出 | 107px |

### 原型怎么做的（源码核对 + 隔离页实测）

**1. 布局是 grid，不是 table**

`--mp-provider-columns: 36px minmax(130px,1fr) 190px 76px 76px 200px`，行 `display:grid`、`gap:12px`、`padding:14px 4px`。操作列是 grid 子项，**自身没有内距**，200px 全部给内容。

**2. 操作区只有 4 个 flex 子项**（`.mp-provider-actions{gap:6px;flex-wrap:nowrap}`）

| 子项 | 规格 | 宽度 |
| --- | --- | --- |
| 编辑 | `.btn` 默认 md：34px 高 / 13px 字 / 12px 内距 | 52px |
| 复制 | 同上 | 52px |
| 删除 | 同上 + danger | 52px |
| `.mp-mini-pair` | **竖排** ↑↓，每个 22×14px | 22px |

合计 52 + 52 + 52 + 22 + 3×6（gap）= **196px**。

**3. ↑↓ 是竖排**：`.mp-mini-pair{display:grid;gap:1px}`，两个 mini 只占 22px 宽。这是它能塞进 200px 的真正原因；并排摆放会各占 ~46px。

**4. 拖动把手在选择格，不在操作列**：行首 36px 的格子里是「复选框 + `⠿`（`.mp-grip`）」，整行 `draggable="true"`。操作列没有独立 ↕ 按钮。

**5. 没有「置顶」**：原型全仓搜索“置顶”为 0 次，排序只有 ↑ 上移 / ↓ 下移。

### 我们为什么溢出

同一列放了 7 颗 sm 按钮：↕ 把手、编辑、复制、删除、↑、↓、置顶，累计 299px；td 又有 8px 横向内距，200px 只剩 184px；`ui-row-actions` 的 `flex-wrap:nowrap` 强制单行，于是溢出单元格。

为什么没有横向滚动条：`table-layout:fixed` 下单元格内容溢出属于可见溢出，不会撑宽表格，`overflow-x:auto` 的容器没有可滚内容，用户只能看到被窗口右边缘切掉的结果。

### 决策（按原型）

1. 操作列只保留 **编辑 / 复制 / 删除（md）+ ↑↓（竖排 mini 对）**。
2. **移除「置顶」**：原型没有该入口。
3. **移除行内独立的 ↕ 把手**：拖动改由整行承载；⠿ 移到选择格，与复选框并排。
4. 按钮回到 **md** 规格，不再用 sm 缩水（原型就是 md）。
5. 操作列宽保持 **200px**；该列 td/th 不再吃 8px 横向内距（原型 grid 子项本无内距），把 200px 全部给按钮组。

### 实现映射（待开发）

| 位置 | 改动 |
| --- | --- |
| `ChannelsView.vue` colgroup | 保持 36 / auto / 190 / 76 / 76 / 200 |
| 操作列样式 | `.channel-table td:last-child, .channel-table th:last-child{padding-inline:0}` |
| 操作区 | 三个 `UiButton`（默认 md）+ 一个 22px 竖排容器装 ↑↓ |
| ↑↓ 容器 | `display:grid;gap:1px;width:22px`；按钮 `22×14、圆角 5px、字号 --text-caption` |
| 选择格 | 复选框 + ⠿ 文本并排，行保持 `draggable` |
| 删除 | 「置顶」按钮与 `reorderChannel` 调用移除；`move()` 保留 |

### 余量核算

200 − 196 = **4px 余量**（td padding-inline:0）。若保留 4px 左内距则余量归零，不采用。

### 边界

「置顶」若确有需要，须先在原型补出位置与规格，再按加宽列宽的方式处理；不在实现侧单方面加回。

### 未验

未在应用内实屏核对裁剪边界（隔离页已复现同样像素）；未验 200% 缩放与 Windows 原生。

## WP-41：服务节点下拉里「当前节点」与「未检测」未垂直对齐

**优先级**：P2
**位置**：模型 → 渠道模型 → 服务节点列的下拉触发器
**用户原话**：“当前节点的下拉‘当前节点’和未检测不垂直方向对齐。”
**状态**：已按原型定案，未实施

### 实测（取文字实际渲染盒，不是元素盒）

| 对齐方式 | 名称文字盒 | 状态文字盒 | 基线差 |
| --- | --- | --- | --- |
| 现状 `align-items:center` | 14.4px 行盒（12px 字） | 13.2px 行盒（11px 字） | **-0.4px** |
| `align-items:baseline` | 14.4px | 13.2px | **0** |
| 两段统一 11px + center | 13.2px | 13.2px | **0** |

### 原型怎么做的

`.mp-node-picker-trigger{font-size:var(--text-caption);height:32px;padding:5px 8px;gap:7px;display:flex;align-items:center}` —— 字号设在**整只按钮**上，名称（`.mp-node-picker-value`）与状态（`.mp-node-picker-current-speed`）同属 11px，行盒等高，center 即等同于基线对齐。

结构是 `value(flex:1, 省略号) + speed(flex:none) + ▾` 三段 flex 子项。

我们这边名称继承 `.select-trigger` 的 `--text-label`（12px），状态是 `--text-caption`（11px），字号不同才产生 0.4px 基线差。

### 决策（按原型）

1. 触发器内统一 **11px**（照原型），名称与状态同号。
2. `.node-current-label` 用 `align-items:baseline`：即使日后某处字号再分叉，也按基线对齐而非盒中心。

### 实现映射（待开发）

| 位置 | 改动 |
| --- | --- |
| `ChannelNodeSelect.vue` `.select-trigger` | 追加 `font-size:var(--text-caption)` |
| `.node-current-label` | `align-items:center` → `baseline` |

### 未验

未在应用内放大截图复核（隔离页已量化基线差）；未验 Windows 原生与 200% 缩放。

## WP-42：读取现有渠道后持续提示未保存——基准与规则序列化需分开处理

**优先级**：P1
**关联**：WP-21（0.2.2 的等价比较修复不完整）
**用户原话**：“我直接读取现有渠道以后，还是有未保存修改的说法为什么？”
**状态**：已确认两类原因，未修复；真实“保存 → 再读取”尚未执行

### 已核实的原因

1. **本机存在草稿，但管理器尚无已提交策略文件。** 已核对当前数据根记录：`manager-state/model-config-draft.json` 有 25 个渠道，`manager-state/model-policy.json` 不存在。后端 `store.rs::load_unlocked()` 在此情况下以空 `Policy::default()` 为已保存基准。前端 `store.ts` 将草稿与这个基准比较，必然显示差异。官方已有渠道配置，并不等于管理器已经保存了同一份策略。这类首次导入差异不能一概当作误报。
2. **旧等价比较漏掉“省略”和“显式继承”的等价关系。** `upstream.ts::mergeUpstream()` 用 `emptyRules()` 重建发现清单，会为 5 个可选规则写入 `{mode:'inherit'}`。后端 `schema.rs::ModelRules` 对这 5 个字段使用 `skip_serializing_if = is_inherit`，读取/保存返回时会省略它们。字段缺省的语义也是继承，但 `policyEquality.ts` 仅忽略读取回执与对象键顺序，仍把缺字段与显式继承判为不同。

5 个字段为 `pinnedEffort / effortMap / noReasoning / reasoningAuthoritative / fastWire`。用本机已有的最新公开读取快照与现有草稿做**内存重算**，228 个型号都发生“省略 → 继承”，合计 1,140 处字段表示差异；型号成员和顺序均未改变。再次合并同一快照是稳定的，但“按后端规则省略继承字段 → 再合并同一快照”的模拟仍会被判 dirty。

因此，不能再断言“保存一次后就一定不会出现”。本轮模拟证明序列化表示仍会重新制造差异；未为验证而实际保存用户配置。核查时的数量与截图不是同一时点，不把内存重算数量当作截图中 98/100 的复现结果。

### 修复方向

- 在明确的 `ModelRules` 对象范围内，将上述可选规则“缺字段 / 继承”按同一语义比较；不能全局删除所有规则字段，也不能忽略显式 `custom(false)`、`custom(null)`、强制档位或映射，它们有真实含义。
- 区分首次导入、上游目录资料刷新、用户编辑与真正未提交策略，不把“读取”本身等同为修改，也不通过读取后自动写官方配置消除提示。
- 已有用户草稿必须保留。不得简单重置 `channelClean` 来掩盖启停、名称、节点、采用与顺序的真实变化。

### 验收条件

- 已有等价基准时“读取 → 不编辑 → 再读取”不新增修改；隔离环境中“保存 → 后端序列化返回 → 再读取”同样不误报。
- 覆盖 5 个可选规则在发现清单、渠道默认、单模型覆盖与族覆盖中的表示差异；显式自定义值、启停和顺序仍能触发修改提示。
- 无管理器基准但官方已有渠道的首次导入，准确解释当前状态，保留真实待提交差异。

## WP-43：详情中已启用的模型在预览中无法对应，展示与激活计数口径不一致

**优先级**：P1
**用户原话**：“我在渠道模型启用的模型，实际在预览选择器选不上。”
**状态**：展示与交互缺陷已定位；未证实官方运行配置丢失启用状态

### 代码事实

- 后端 `compiler.rs::project()` 返回全部规则投影行，单独带 `enabled`（渠道启用）、`selected`（型号公开/启用）及 `discovered`；`known_active_models` 按三者同时为真计数。
- `SelectorPreviewDialog.vue::groups` 只过滤停用渠道，不依据行的 `selected/discovered` 区分模型状态，导致上方激活数与下方全部型号标签范围不同。截图的“98 个激活 / 229 个基础模型”有这一来源，不能将 229 直接理解为 229 个都已启用。
- 型号标签渲染为 `span`，渠道名为 `h3`，都没有点击事件。现有实现无法在预览里“选中/启停”；不是按钮点击成功后又把启用状态丢掉。
- 标签的颜色目前由 `rules.fast` 控制，表示 Fast 支持能力，没有表达型号启停状态。
- 草稿与已保存来源不同也可能导致观察不同；列表直接点击还存在 WP-45 的事件误传。

### 处理与验收

- 预览、详情开关及激活统计读取同一当前草稿；明确区分全部候选、已启用与缺失待核对项。
- 型号启停颜色由型号状态决定；Fast 能力单独说明，不能用其代替启用状态。
- 预览中启停能力按 WP-44 补齐。新增验证应断言具体 `channelId + modelId` 与 `selected` 的一致性，不只比较总数。
- 当前证据只支持界面口径及交互缺失，未做真实客户端加载与官方运行目录比对。

## WP-44：预览选择器增加渠道和模型的快速启停（本轮新需求）

**优先级**：P1
**关联**：WP-43、WP-45
**用户原话**：“应该可以在预览选择器实现快速选择就启用停用……点击渠道就停用，渠道名称置灰，模型全看不到了，再点击就启用，有颜色效果区分。模型点击可启用停用。”
**状态**：用户意图已确认，待原型表达后实施

### 目标行为

1. 点击渠道名切换渠道启停。停用时名称置灰并保留可点击入口，组内型号全部隐藏；再次点击恢复渠道启用并重新显示型号。停用不清空型号白名单、原规则与组内顺序。
2. 启用渠道下，点击型号标签切换此型号启停。停用型号仍以置灰标签保留，以便再次点击启用；不能像停用渠道的整组型号一样消失。
3. 启用/停用有清楚的颜色与文字/可访问状态区别，交互使用按钮或等价可键盘操作的控件；不能仅靠颜色区分，也不能用 Fast 支持色混淆启停色。
4. 修改进入**同一渠道草稿**，与渠道列表开关、详情开关和激活数即时联动。关闭预览保留本轮草稿，页面统一“还原修改 / 保存”继续承担撤回与提交；点击预览标签不直接调用官方配置保存。
5. 快速减少或增加公开项仍遵循既有 all / whitelist / none 语义。渠道恢复启用应恢复原选择；型号从 all 切为精确范围时保留其余已启用型号，不丢失顺序。
6. 官方管理/只读渠道仍尊重既有可编辑范围；不能借预览绕过权限。超预算时给出可理解提示，仍可继续停用项来缩减范围。

### 与历史约定的关系

0.2.3 曾将误接公共模型选择器的预览改回只读，当时的原型也是只读。本次用户明确要求增加**草稿配置启停**，应以新输入更新原型与实现，不能继续用历史“只读”限制否定本轮需求。

公共“执行模型选择器”仍是选择执行模型的用途，只列非隐藏型号；本需求只扩展配置页的预览编辑入口，不因此把隐藏型号重新放进执行模型选择器。

### 原型与验收

- 在唯一主原型 `index.html#models` 的 `model-config.js::preview()` 表达渠道开/关、模型开/关、空组、预算变化以及关闭重开后的草稿保持。
- 覆盖“渠道关闭 → 所有模型隐藏且名称可再次点击 → 渠道开启恢复原白名单”“单模型停用后仍可点击恢复”“预览与详情两边交叉修改保持一致”。
- 原型旧注释和测试中的“预览不改变配置”须按草稿编辑语义更新；不得只加视觉按钮而不连草稿。

## WP-45：预览来源显示 PointerEvent；新交互下收敛为当前草稿

**优先级**：P1（参数误传）
**用户原话**：“这个预览来源是什么不知道还有没用，没用的话 原型也不要这个了。”
**补充确认**：“预览固定当前草稿那就可以不要这个了，固定值的话其实就可以不展示了。”
**状态**：事件误传已确认；来源入口按本轮草稿启停需求登记收敛

### 原因与用途

- 列表按钮使用 `@click="showPreview"`，而函数签名为 `showPreview(source: 'draft' | 'saved' = previewSource.value)`。Vue 将点击的 `PointerEvent` 作为实参传入；默认参数仅在实参是 undefined 时生效，类型注解也不做运行时拦截。
- 函数将事件写入 `previewSource`。公共下拉找不到匹配选项，就回退显示传入值，得到截图中的 `[object PointerEvent]`。详情侧通过无参 `emit('preview')` 打开，则走了另一条无事件参数的路径。
- “来源”原本有真实用途：查看当前草稿与管理器最近提交的策略。已保存策略也不等于客户端已加载的实际运行目录，不能混称为当前生效配置。

### 本轮收敛方向

## WP-50：节点检测/测速实机不可用，读取渠道的认证未接入探测链

**优先级**：P1
**用户原话**：“我发现测速功能不可用。”
**状态**：认证链缺口已定位；实机失败码与最终成因待验证

### 已核实链路

检测已有完整入口：`NodePicker.measure → useNodeMeasurements.measure → model_node_measure → measurements::measure → discovery::readonly`。它读取**模型清单接口的请求耗时**及模型数量，并非推理速度，也不是凭空生成的模拟延迟。

探测请求仅传协议、节点地址、私网许可、临时 apiKey 和管理器 credentialRef；**没有传渠道身份/sourceReadId，也没有从官方渠道认证 owner 解析现有认证的分支**。读取官方渠道时 `mergeUpstream()` 对新导入渠道设置 `credentialRef:null`，仅保留公开来源回执；详情页的 `apiKey` 初始为空，页面也没有把连接弹窗里的输入直接绑定到它。

对用户所示 Input-1 的本机草稿仅核查非敏感标志：authMode=key、有公开读取回执、无管理器凭据引用、一个节点、活动节点 ID 与已有节点匹配。此状态下检测会在没有其他凭据来源时构造无认证清单请求；如果服务要求 Key，就可能返回认证失败。页面的“认证：未配置”也只看管理器 credentialRef，不能证明官方 Key 不存在。

后端使用独立 `reqwest` 客户端并 `no_proxy()`，协议适配会构造模型清单路径；网络、代理需求、DNS、接口路径、清单结构与私网许可也都可能影响结果。**尚未对真实 Input-1 发检测请求，不能将“可能 401”写成实际返回 401。** 渠道停用状态本身不在探测请求中，不应要求先启用才允许检测。

### 修复与验收方向

- 从已确认的渠道身份和认证 owner 取得该目标节点可用的认证；只允许把凭据用于其已确认绑定的地址/协议，修改节点后不能直接把旧 Key 发到任意新地址。无需让用户为每次测速重填 Key。
- 同时修正认证状态投影，区分“官方已有认证 / 管理器本机引用 / 暂无认证 / 读取失败”，避免误导。
- 展示逐节点等待、检测中、耗时/数量或明确失败原因，支持停止与重试；缺凭据时就地说明，地址/协议/认证变化后忽略旧结果。失败不清空模型或自动切节点。
- 同一节点的列表下拉与详情检测应共用一致的目标和结果口径，不能一处可用另一处无认证。
- 回归包含已有官方 Key、管理器引用、无需认证、需要代理、路径/协议差异、私网限制、超时、部分失败与停止。真实服务与两个原生平台仍需授权范围内验证，不用本地 mock 通过冒充实机恢复。

### 本轮验证

前端节点相关与行缓冲的 4 个既有测试文件共 15 项通过。后端 `measurements::tests` 两项通过，使用临时 Key 和本地回环测试服务，覆盖只请求清单、不持久化临时凭据和取消；没有读取真实 Key、没有向用户服务发请求。它们未覆盖“导入渠道后复用官方认证”这一缺口。

## WP-56：导出按“日期 / 单次备份包”组织，便于完整拷贝一份

**优先级**：P2
**用户原话**：“关于导出结构的问题，我发现你的维度有点出入，其实我更希望是日期/备份包格式，现在变成了模块/日期，这种不方便拷贝单份。”

导出以**日期与单次备份包**为组织维度；同一次导出的所选模块内容归入同一个包，模块分组放到包内。用户复制一份包即可带走该次所选内容，不需要跨多个模块目录寻找同一次的文件并手工拼装。

导出目录/
└── 2026-10-23/

    │   └── 本包清单与必要校验信息

        └── 另一次导出的内容…

## WP-57：拖拽或操作时误框选文字，操作与文本选择缺少明确边界

**优先级**：P2（公共交互）
**用户原话**：“拖拽或者操作经常会有框选文字的迷惑误操作。分析怎么回事？”；分析后用户要求“记录”。
**状态**：源码问题已分析并登记，未实施；原生鼠标事件过程尚未复现
**关联**：WP-46 拖拽失效 / 闪屏、WP-40 / WP-47 按原型调整列表及拖拽入口

### 已确认的源码事实

- 软件 `ChannelsView.vue` 和 `ChannelModelTable.vue` 只有“↕”按钮声明 `draggable`，行本身只接收 dragover / drop。从名称或手柄外的文字起拖，并不会调用排序的 dragstart 处理；浏览器仍可能执行默认选字。
- 公共样式及相关操作组件没有统一的 `user-select / -webkit-user-select` 防误选规则，也没有区分拖拽与文本选择的 selectstart / 起手状态处理。dragover / drop 上的 preventDefault 只处理拖放接收阶段，不处理此前的按下和选字。
- 渠道列表搜索 / 忙碌 / 保存中会禁止排序；模型列表筛选 / 忙碌 / 校验 / 未确认编辑时同样禁止排序。现有逻辑主要禁用手柄及拒绝排序，没有覆盖操作区域的文本选择行为。
- `.btn:disabled` 还设置 `pointer-events:none`，命中可能落到容器；是否放大了实机误选需验证。不能仅凭缺少 CSS 声明认定每一种原生按钮内部文字都可选，实际仍受 WebView 默认样式和命中位置影响。
- 当前原型让符合条件的整行可拖，并排除输入 / 按钮 / 下拉起拖，与软件命中范围不同；原型相关样式也没有完整的防误选规则，因此仍需核验原型和软件两端，而非直接复制拖拽事件即判定修复。

这些事实支持“拖拽没有接管时落回网页默认选字”的原因判断；尚未证明用户每次误选都由同一条事件路径触发，也不能把它与 WP-46 的排序后闪屏视为同一个已证实根因。

### 整改方向与保留边界

- 公共按钮 / 图标操作、导航、拖拽手柄及明确的操作区域统一防误选，兼顾 macOS WebKit；相关状态由公共组件 / 样式承担，避免每页各写一套。
- 拖拽命中范围按确认原型统一；输入框、按钮、下拉等交互控件排除行拖拽。禁止排序时不产生拖动已开始的假反馈，也不能通过防误选绕过现有筛选和未确认编辑保护。
- 实际进入拖动时抑制该次手势的文字选择；结束、取消、窗口失焦、组件卸载时清理临时状态。不能全局拦截所有 mousedown / pointerdown，导致原生 HTML 拖拽、控件焦点或键盘操作失效。
- 输入框、文本域、可编辑内容，以及需复制的日志 / 错误信息 / 配置文本保持选择和复制能力；若对容器设禁选，须明确处理这些子区域。不得全局禁止选字或在普通点击时无条件清空用户已有选择。

## WP-64 规格校正（2026-10-24，依据官方 2.84.0）

原 §29.1 写“目录 display_name 必须能对应所属渠道与原始模型”，实现时若按“渠道名/原始模型ID”直接写入会与官方冲突。实测与源码确认如下：

- 官方 2.84.0 src/config/provider-validation.ts 的 modelDisplayNamesConfigError 明文要求 must not contain slash，长度上限 128；管理器自己也有一致校验。
- 官方 Codex 目录的 display_name 由 src/codex/catalog/derive-entry.ts::routedDisplayName 生成，返回 providerId/模型ID 形式的 slug；人类渠道名写进 config.toml 的 provider name（inject/config-toml.ts）。
- 本机真实数据印证：FeiMao-CNM 的 modelDisplayNames 是 DeepSeek V4 Flash 这类友好名，且 name 与运行标识相同。这正是用户抱怨“友好名称覆盖渠道标识”的现场。

结论：管理器内部与预览仍用“渠道名/原始模型ID”；客户端目录展示名交给官方按 providerId/模型ID 生成，管理器只负责不写 modelDisplayNames 并在保存时清除历史条目。§29.1 已据此改写。把渠道名硬塞进 display_name 既过不了官方校验，也会破坏官方路由展示口径，属错误规格，不予实现。

已实施：投影、执行目录读回、正式写入三处统一；保存读回定向测试通过（写入清名、读回名称与顺序一致、不回流）。仍未验：真实官方保存 → 客户端目录读回 → 重启加载。

### A6 补缺：新通知的 toast 一半此前缺失（2026-10-24）

- `features/notifications/store.ts` 的 `notifications-changed` 监听只调用 `load()` 重拉列表；全前端没有“新通知到达即提示”的通道（123 处 `showToast` 均为操作反馈）。
- 结果：保存被拦下时通知中心会有记录，但用户当场看不到任何提示，容易以为点击没生效。

修复：新增 `announce()`，在事件流里先记录已有 ID，重拉后仅对“此前不存在且未读未解决”的条目调用一次 `showToast`；读取失败直接返回，不把查询错误伪装成业务通知；同一条不会重复提示。

回归：`notification-center.test.ts` 新增 1 项覆盖三点——首次提示、同条不重复、后端失败不提示。前端 758 项通过。

仍未验：真实环境下 toast 与通知中心同时在桌面端出现（需要真实保存并把模型页切走）。

### §38.3.1 长按规格的两处遗漏（2026-10-24）

对照 §38.3.1 逐条核查，实现缺两条：

| 规格要求 | 原实现 | 修复 |
| --- | --- | --- |
| 滚动开始也要清理计时器 | 只在 pointerup / pointercancel / pointerleave 清理；列表一滑，计时器仍在跑，滑动手势会被误判成“长按看说明” | 在 `.selector-preview-order` 上挂 `@scroll.passive`，滚动即清计时并收起说明 |
| 点击空白处收起 | 只支持移出与再次长按 | 弹窗内容层监听 click；命中标题行以外即收起，点击标题行本身仍走上停用 / 恢复 |

回归：`selector-preview-dialog` 新增 2 项——滚动取消长按且不影响后续正常点击、点击空白处收起。该文件 12 项通过，前端 760 项通过。

仍未验：真机触屏上的 500ms 手感与滑动误触（需触摸屏设备）。

### §38.2 原生渠道只读未完全生效（2026-10-24）

原生 / 官方渠道在预览里应当是只读的：标题已是静态 `h3`，但**型号标签仍可点击并发出启停**，且 title 写着「点击停用 / 点击启用」，等于鼓励用户去改一个改不动的渠道。

回归：`selector-preview-dialog` 新增 1 项——原生渠道无按钮标题、所有型号标签 disabled、点击不发 `toggle-model`；该文件 13 项、前端 761 项通过；`audit:preview` 27 项仍全过。
