# Superba 远程笔记调用链核对

2026-11-10。用户要求转向Superba源码查明远程笔记的实际做法。核对当日默认分支HEAD：3ecc0db00f0b536ee070d6cb1c56e01566b3115a（提交日期2026-11-05）。本轮读取固定源码与测试，没有安装、启动Superba、修改日常配置或新增模型请求。

## 结论

**Superba有笔记相关配置及局部兼容处理，但读取调用链未发现它自建完整的远程笔记服务。** 路由模式会在本地回答thread_hint，返回空提示；模型真正调用的历史／笔记接口仍交上游处理。这是比先前“只写配置”更具体的差异，但不能据此认定它能解决Krill历史列表和笔记列表的404。

## 配置与执行链路

| 环节 | Superba实际实现 | 对当前疑问的意义 |
|---|---|---|
| 新Krill配置预设 | krill_recommended从PAT_RECOMMENDED_KEYS生成可编辑设置，包含context_management=true、token_budget.enabled=true、use_history_notes_extension=true | 解释群友为何看到Superba默认开启；是预设，不是渠道支持的运行证明 |
| 设置写入 | render按该profile实际管理的设置写入；不再管理的推荐键恢复基准 | 不是每次切PAT都无条件强制开启，用户可以修改profile设置 |
| PAT认证 | auth.json写personal_access_token与OPENAI_API_KEY，另配内置openai入口及认证环境 | 与本项目已有原生PAT补验前提一致，未找到额外笔记专用认证形状 |
| 路由侧提示 | POST /backend-api/codex/alpha/notes/v2/thread_hint由local_backend回答200，内容为{"text":""} | 只回答空提示，不读出或保存远程笔记；可避免这一条后台提示404 |
| 真实笔记／历史调用 | 其他/alpha下的请求作为upstream流量；相对路径拼接到所选member的base URL后转发 | 没有看到把已知v2列表／读写改到另一套笔记服务的路由 |
| 上游404 | proxy普通4xx不触发故障切换，保持上游错误 | 不能把本地thread_hint成功等同于上游列表／读写可用 |
| 线路和Key探测 | 探测whoami、accounts/check、模型目录；可另测Responses及compact | 没有覆盖笔记创建、读取、续聊；“所有检查通过”不能推广到远程笔记完整可用 |

## 两种容易混淆的功能

1. 路由器cipher模块会处理跨Provider不可读的加密历史／笔记工具输出，例如在上游明确拒绝后移除不能读取的密文或补说明。这是请求兼容，不是解密远程笔记或实现笔记服务。[cipher说明](https://github.com/krill-lab/superba/blob/3ecc0db00f0b536ee070d6cb1c56e01566b3115a/crates/superba-router/src/cipher/mod.rs#L1)。
2. compaction_proxy为部分目标生成摘要并封装自己的加密压缩项。这是合成上下文压缩，与history/notes工具的远程读写分别判断。[合成压缩说明](https://github.com/krill-lab/superba/blob/3ecc0db00f0b536ee070d6cb1c56e01566b3115a/crates/superba-router/src/compaction_proxy/README.md#L1)。

当前源码也已有本地TLS／PAT路由兼容设施，不能直接套用早期“所有路由只能API Key”的笼统描述；这仍不改变笔记工具要由上游提供的事实。

## 与已有404的对照

本项目原生PAT补验已分别观察到thread_hint、list_windows和list_files_by_prefix的404。按Superba源码：走其路由可在本地消除thread_hint这一条提示错误；另外两个真实工具列表仍会转发，不会因为这项本地兼容自动恢复。

因此下一步若要专项运行Superba，应把“本地空提示成功”和“上游真实列表／读写成功”分开检查，不能只看界面无报错或一次普通对话完成。当前源码没有提供可直接替代那两个404的新接口，尚无据此扩大真实模型调用的必要。本轮结论为源码分析，不是Superba已安装运行或真实渠道验收。
